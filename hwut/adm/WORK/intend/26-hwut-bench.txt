A TEST APPLICATION DRIVES A BOARD TODAY THE WAY IT DRIVES ANYTHING: it
prints, hwut compares. What it lacks is not a face of hwut but the small
things every such application re-solves alone: reaching the target over a
link, loading and activating an image through the vendor's tool, telling a
corrupt line from a UUT's answer, and keeping all of it out of the picture.

THE AUTHOR'S EXAMPLE (2026-10-25): an FPGA is flashed via USB-Blaster; a
tiny send/receive stimulator/report agent is installed on the device; the
test communicates with it and prints the results; the test carries a label
such as 'max10-connected'. Read off that example, what is wanted:

    0 presence      jtagconfig: cable and device            -> a probe
    1 provision   quartus_pgm -o pv;uut_agent.sof   -> a loader, verifying
    2 connect     the kit's UART                    -> a link
    3 reset       the UUT in a defined state        -> an agent register
    4 stimulate   set / apply / report, per vector  -> the agent, a protocol
    5 picture     one line per vector, fixed width  -> the writer's prints
    6 end           <hwut-end>                              -> HwutRunner

DONE CHANGES THIS: a writer imports the modules that fit his board, writes
the five lines of a session and prints rows; the agent is proven on every
host under iverilog before it ever meets a board; nothing a link does
(retransmission, discarded noise, timing, identity) reaches a GOOD file
except as '##' lines; and hwut learns nothing of it beyond one block of
configuration.

WHAT IT IS NOT

- Not a hub daemon, not a bench description interpreted by hwut, not an
  adapter catalogue, not reservations and locks of hwut's own: the writers'
  elaboration of 2026-10-25, struck. One owner per board is 'collision'
  (R-32); a board's presence is a label (intend 25).
- Not one test switched between benches: a hardware test is written for
  its target; the simulation test is its own application that may share
  code with it. '--variant' benches: struck 2026-10-25.
- Not a framework: a library. The sequence of a session stands in the test
  application, top to bottom, and is thereby documented.
- hwut 2.0 reads configurations. It learns nothing from a running
  application: the interview is the migration path (R-44), nothing else.
  Struck 2026-10-26: a 'BENCH:' info line, a plan-time probe, an exclusion
  derived from a shared bench, values handed over in the environment.

THE SHAPE

    HOST                                         TARGET
    test application ─ create_hub ─▶ hwut_remote ══ link ══▶ agent ─ UUT
                                     support/remote/host/   target/<impl>/
                                     link, line, session,
                                     entry, <loader>, capture
    Makefile ── flash ──▶ hwut_remote.<loader> ── vendor tool ──▶ image

    the test:        the board's configuration, serial ... loader ...
                     (o-35; where it stands: o-37)
    hwut-root.conf:  platform = [ { name = "local", provides = [ "max10" ] } ]
                                                         where it is attached
    A bubble specifies 'max10'; the platform that provides it runs the
    bubble (o-26). The test opens its hub and knows nothing of the
    platform (intend/42, ruling 1); a board it cannot reach, it reports
    by exit 77 (o-36). The picture and the names stand in the spec,
    section 1.

What the code decides: the tool chain, the board and its configuration --
device path, cable, baud. What a platform definition decides: where a
board is attached ('provides'). What hwut decides: nothing; it runs a
board's bubble where its name is provided, and takes exit 77 as 'the
infrastructure is absent'.

ONE LAW, ONE PLACE: the protocol is one page (PROTOCOL.txt), the agent's
registers one page (MAP.txt), both in support/remote/; the agent
implementations and the host modules implement them and nothing else.

______________________________________________________________________________

WHY A REGISTER MAP (o-10, 2026-10-26)

The surveyed systems are not distinguished by their verbs -- 'g'/'m',
'SET_MTA'/'UPLOAD', 'shift:' are interchangeable -- but by how they answer
five questions beneath the verbs: who proves the target is the one just
loaded; what a receiver does with a byte it did not expect; how a late
reply is told from the next one; who owns the clock; who may hold the
board. A control-and-status register map answers the first with a register
(image id) and leaves the agent's parser with no semantics at all:
identity, reset, apply, capabilities, timeout, a FIFO, a load window are
addresses. Every later feature is an address, never a verb.

______________________________________________________________________________

WHY THE PROTOCOL IS WHAT IT IS -- the review's rules, each with a precedent

    a CRC, width by length   Maxino & Koopman: a CRC, never XOR or a
                             sum; an 8-bit CRC keeps HD=4 only to 14
                             data bytes
    a token in every reply   GDB's documented hole: a late reply reads
                             as the next one; CMSIS-DAP, esptool echo
    idempotent read-back     Lampson, Candea & Fox, XCP SYNCH: a
                             protocol whose state can be re-read never
                             needs a retransmission counter
    bounded, counted discard RFC 1662: "silently discard" still counts;
                             Twister's RunID: the first valid frame
                             carries an identity, or a stale agent passes
    the target owns time     dSPACE, XCP DAQ: the agent waits on the
                             UUT, bounded; the host never sleeps (R&S:
                             a fixed pause is a defect)
    out of band, existing    labgrid, LAVA, Twister: load through the
      tools                  vendor tool, consume its exit status,
                             verify, then activate
