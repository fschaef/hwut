VUT-ORCHESTRATOR-SCHEDULER -- RATIONALE
============================================================================
Settled. Read-only. S-N handles; the plan's rulings cited as P-N,
exploration's as R-N. S-1 and S-2 stood first in the plan's RATIONALE
as P-13 and P-14 and moved here with the component.

----------------------------------------------------------------------------
S-1  THE SCHEDULER'S SEAM
----------------------------------------------------------------------------
PROBLEM   The scheduler must execute a plan without becoming a
          runner: running is test_run's (P-1).
DECISION  'I_Dispatcher' -- run_script, run_build, open_session,
          close_session, run_test -- every member a coroutine,
          every failure a VALUE, never an exception. The scheduler
          reads the plan, asks CPlanState who may start, starts
          what fits, and awaits the FIRST ending. The state
          machine (state.py) holds no clock and runs nothing.
COST      Two units where one loop would do; a dispatcher must be
          written per world (test_run's, and a test's own).
GRAVEYARD The scheduler calling test_run directly (no plan could
          then be executed without processes, and no trace could
          be blessed). Exceptions as failures (a failure that
          unwinds the loop cannot be a node state).

----------------------------------------------------------------------------
S-2  A TERMINAL STATE SATISFIES AN ORDERING LINK
----------------------------------------------------------------------------
PROBLEM   What an ordering link does when its source never runs,
          or runs and fails.
DECISION  ANY terminal state satisfies it: ENDED_GOOD, ENDED_BAD,
          UNSUPPORTED, MISDEP. The link is ordering, not success
          (R-33), and a node that will never run must not hold its
          dependants for ever.
COST      A dependant runs after a broken dependency -- stated,
          and the author who wants otherwise has no key for it
          yet.
GRAVEYARD Verdict-carrying ordering links (R-33 says otherwise).
          Waiting on a node that can never end (deadlock as a
          policy).

----------------------------------------------------------------------------
S-3  READINESS IS ASKED ANEW BEFORE EVERY START
----------------------------------------------------------------------------
PROBLEM   Starting one member of an exclusion set withdraws
          admission from the others; a snapshot of 'ready()' taken
          before the start no longer states the truth, and
          starting from it is refused by the state machine.
DECISION  The dispatch loop asks 'ready()' before EVERY start and
          takes the first name. The snapshot defect was found by
          the suite before blessing; the refusal at the door is
          what surfaced it.
COST      One readiness computation per start instead of one per
          wave.
GRAVEYARD Starting a whole snapshot (the defect). Filtering the
          snapshot inside the loop (re-states the readiness rules
          in a second place).

----------------------------------------------------------------------------
S-4  THE BOUND IS A BUDGET, AND IT MAY BE SHARED
----------------------------------------------------------------------------
PROBLEM   'worker_max_n' was a private integer of one Scheduler; the
          tree scheduler's host-global bound (run/RATIONALE O-12)
          needed the count to stand ACROSS schedulers.
DECISION  'CBudget' (budget.py): 'take_f()' now or nothing, 'take()'
          when free, 'give()', 'changed()' a future resolved on the
          next give. The dispatch loop takes a slot before each start
          and awaits its own tasks OR a 'changed()' of the budget, so a
          slot given back elsewhere wakes it. Frame scripts take a
          slot. 'Scheduler(worker_max_n=)' accepts a number (a private
          budget) or a CBudget (shared); every existing GOOD stands.
COST      One future created and cancelled per wait.
GRAVEYARD asyncio.Semaphore around the work task (the 'started'
          notification moves after the previous holder's 'ended';
          bounded-run traces would change).

----------------------------------------------------------------------------
S-5  A CASE STARTS WHERE ITS DISK HAS ROOM FOR IT              (2026-10-19)
----------------------------------------------------------------------------
PROBLEM   Reported (DEFECTS-hwut-78e11f7, D-24): disk caps without a
          key, and sibling cases killed when one case wrote 150 MB.
          MEASURED: the procsitter summed the WHOLE test directory
          against every case's 'max_disk_mb' (now the case's own: procsitter
          MANUAL 4), and
          nothing looked at the disk before a start.
DECISION  RULED (Frank-Rene, 2026-10-19): "both caps, but the
          orchestrator should have also a limit that her doesn't even
          start a process if the free space is less than max(2 * limit,
          expected limit due to TMP file data entries)" -- "the
          orchestrator shall keep the limits in mind, and possibly
          delay. that disk safety limits shall be per disk not per
          directory."
          'CDiskGuard' (disk_guard.py), ONE per process ('HOST_DISK_
          GUARD'): reservations per disk ('st_dev'). The dispatcher asks
          it before a test and before a session (held to the session's
          close): need = max(2 x the case's 'disk_mb', the 'peak_disk_mb'
          this machine last observed for the case); granted where
          'free - reserved >= floor + need'; WAITS where something is
          reserved on that disk; refused, 'disk-short' with its numbers,
          where nothing is. The floor is the root's 'free_disk_min_mb',
          one for every disk (exploration R-99).
          'expected' was left open ("no preference"): the last observed
          peak was taken because the observation database already holds
          it, per machine.
COST      The floor is added to the need, which the ruling does not
          spell: a case that starts with exactly 'need' free would push
          its disk under the floor at its cap. Pessimistic: what a
          running case already wrote is counted in 'free' and in its
          reservation. A waiting case holds its budget slot. Peaks
          observed before procsitter's D-24 measured the whole directory
          and overstate, until the case runs once.
GRAVEYARD Waiting forever where nothing is reserved (nothing would ever
          make room). A gate in the scheduler (it knows no caps; the
          dispatcher does).
