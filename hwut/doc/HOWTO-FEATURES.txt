==============================================================================
HOWTO-FEATURES -- say what a tree does, and see which test runs prove it
==============================================================================

A FEATURE is one thing a piece of software does, said in one sentence. A
TEST RUN is one test application run with one choice; its verdict stands
in 'GOOD/book.csv'. A test run is LINKED to the features it proves. From
the links and the verdicts every feature has a state, on two axes:

    IMPLEMENTED    runs of its own or children,       ok        every one passes
                   no child OPEN                      fail      one fails
                                                      untested  none fails, one
                                                                never ran
    OPEN           neither, or a child OPEN           untested
    RETIRED        no longer claimed (section 6)      no verdict

A feature FOLDS ITS OWN RUNS AND ITS CHILDREN'S: its verdict is the worst
below it -- fail, then untested, then ok. The axes are independent: OPEN
says nothing proves the claim, and that is no failure.

ONE ID PER FEATURE, AND THREE FILES beside 'hwut-root.conf', each with one
job (spec 43):

    hwut-feature-forest.csv        WHERE a feature stands: its parent
    hwut-feature-doc.dat           WHAT it is: its sentence, its documents,
                                   whom it concerns; the retired
    hwut-feature-external-map.csv  what SOMEBODY ELSE calls it

and the test headers, which LINK by the id. Nothing encodes a directory:
a directory that moves changes no file.

    gateway/
      hwut-root.conf
      hwut-feature-forest.csv        gateway : forwarding, buses ...
      hwut-feature-doc.dat           [[forward]] A CAN frame is ...
      hwut-feature-external-map.csv  keep-order ; REQ-4711
      router/TEST/test-route.sh      features = ["forward"]
                  test-restart.sh
      can/TEST/test-frame.sh         features = ["decode"]

The example is a CAN-MOST gateway; every excerpt is the output of that tree.

1  FEATURES AND LINKS
______________________________________________________________________________

A FEATURE ID is a word of '[A-Za-z0-9_-]' -- the author picks it, an
intuitive shorthand: 'forward', 'keep-order'. Case counts. There is no
path in it, no dot, no colon: the place of a feature is the forest's, its
sentence the doc file's. One namespace for the tree.

A test run LINKS to features in its '@hwut { }' block -- for the whole
test, or per choice, where the choice's list replaces the test's:

    # @hwut {
    #     title    = "Routing"
    #     features = ["forward"]
    #     choices {
    #         single { }
    #         burst  { features = ["forward", "keep-order"] }
    #     }
    # }

A link names a feature id, from any directory: the feature need not be
written down near the test. A conf's application links the same way
('apps { delivery.json { ... features = ["..."] } }'). A run that links
nothing, in a TEST directory whose other runs link, is NONSENSE? -- no
failure, a question ('hwut.help' asks it, section 11).


2  THE FOREST AND THE DOC FILE
______________________________________________________________________________

'hwut.features.init' begins them: an empty forest and an empty doc file,
each opening with comments that say how it is written. Then the author
writes them.

THE FOREST, one line per feature that has children:

    gateway    : forwarding, buses
    forwarding : forward, keep-order, drop-unknown
    buses      : decode

An id that stands as no child is a ROOT ('gateway'); roots are not
declared, they are what is left -- several roots make a forest. Every id
stands ONCE as a child: a second parent is a FAULT, and so is a circle.
Whitespace and '#' comments are free.

THE DOC FILE, one block per feature, headed by its id:

    [[forwarding]]
    documents: router/README.txt
    Frames reach their destination.

    [[forward]]
    A CAN frame is forwarded to its MOST address.

The first prose line is the TITLE, the rest the DOC. 'documents:' names
where more is said -- paths from the doc file's directory, ',' between,
'#<anchor>' may follow, or URLs. A feature with children may have runs of
its own; one without children and without runs is OPEN.

A feature in a forest line needs no block -- a child may lean on its
parent's sentence. A documented feature in NO forest line is UNPLACED: it
stands, the report lists it apart, and 'register' notes it (section 5).

ONE FOREST FOR THE TREE: a bubble below (an inner 'hwut-root.conf')
without a forest of its own belongs to the forest above, and is judged
there whichever directory a face is called in. A bubble WITH its own
forest begins its own features -- the showcase does, a tree meant to be
copied, root and all -- and is not walked from above.

'hwut.features.tree' prints the forest:

    $ hwut.features.tree -e
    gateway  A CAN-MOST gateway.
      forwarding  Frames reach their destination.
        forward  A CAN frame is forwarded to its MOST address.
        keep-order  Frames of one sender leave in the order they came.  = REQ-4711
        drop-unknown  A frame with no route is dropped and counted.
      buses
        decode  A CAN frame is decoded.

'<id>' prints its subtree only; '--list' one id per line, to paste into
'f/<id>' or the report.


3  THE REPORT
______________________________________________________________________________

    $ hwut.report.features
    AGGREGATE gateway -- A CAN-MOST gateway. 3 implemented, 1 open; 3 ok, 0 fail, 1 untested
        state      OPEN untested
        audience   integrator
        AGGREGATE gateway/forwarding -- Frames reach their destination. 2 implemented, 1 open; 2 ok, 0 fail, 1 untested
            state      OPEN untested
            audience   integrator
            see        router/README.txt
            [IMPLEMENTED ok]   forward -- A CAN frame is forwarded to its MOST address.
                audience    integrator
                [PASS] router/TEST/test-route.sh [single]
                [PASS] router/TEST/test-route.sh [burst]
            [IMPLEMENTED ok]   keep-order -- Frames of one sender leave in the order they came.
                audience    integrator
                names       REQ-4711
                [PASS] router/TEST/test-route.sh [burst]
            [OPEN untested]    drop-unknown -- A frame with no route is dropped and counted.
                audience    integrator
        AGGREGATE gateway/buses    1 implemented, 0 open; 1 ok, 0 fail, 0 untested
            state      IMPLEMENTED ok
            audience   integrator
            [IMPLEMENTED ok]   decode -- A CAN frame is decoded.
                audience    integrator
                [PASS] can/TEST/test-frame.sh

    OUTSIDE THE RELATION
        NONSENSE? test run, links to no feature => hwut.help
            router/TEST/test-restart.sh

A feature with children is an AGGREGATE line, its tree path, its counts
(those of the features below it with no children) and its state. UNPLACED
and RETIRED follow the forest. OUTSIDE THE RELATION names a link to an id
that stands nowhere ('did you mean' where one is near), a link to a
retired feature, NONSENSE?, a document that does not stand, and what the
files disagree on (section 5).

THE WHOLE TREE IS READ, whichever directory the face is called in
('--directory=<path>' says only where from): a feature has no directory.
Every path is written from where the face was called.

A BARE ID CUTS THE PAGE -- its subtree, the features above it as headers,
counted over what is kept; several ids are a union:

    $ hwut.report.features forwarding

An id that stands nowhere, or a retired one, is refused by name. '-F', '-e'
and '-k' are gone (section 7).


4  AUDIENCES, AND THE OUTSIDE'S NAMES
______________________________________________________________________________

AUDIENCES are documentation, nothing else: no face selects by one, no
verdict depends on one. The doc file declares them, and a heading assigns
them:

    [[CUSTOMERS]]
    integrator: the engineer who builds the gateway into a car

    [[gateway to integrator]]
    [[keep-order not integrator]]

'to' adds the audiences to the feature AND EVERYTHING BELOW IT in the
forest; 'not' takes inherited ones off. An audience not declared is a
FAULT, with 'did you mean'. A set of runs is a label (section 7).

THE OUTSIDE'S NAMES: a customer, a ticket system, a standard has its own
name for one of our promises. 'hwut-feature-external-map.csv' says so,
one pair per line:

    keep-order ; REQ-4711

Our id must stand in the forest; their name is a free string, never
checked. The file starts absent, and its first line is written the day
somebody outside is told a name of their own. Because the outside's name
lives here, OUR id may change (section 6).


5  KEEPING THE FILES IN ORDER
______________________________________________________________________________

'hwut.features.register' names what the files and the links disagree
about -- one NOTE each, never a fault, and it adds nothing:

    NOTE  'spare' is documented and stands in no forest line => hwut.features.tree
    NOTE  the root 'gateway' stands in no block of the doc file => '[[gateway]]'
    NOTE  'decod' is linked by bus/TEST/test-bus.sh and stands in no forest line and no doc block -- did you mean 'decode'?
    NOTE  'gone' is linked by bus/TEST/test-bus.sh and is a retired feature
    NOTE  'old/TEST/hwut-features.conf' is a file of the past, read by nothing => ...

A tree that agrees says 'nothing disagrees'. 'hwut.sanitize.propose
--relations' gives the same notes. What a file states that cannot be read
-- a second parent, a circle, an id twice in the doc file, a retired id in
a forest line, a map line naming an id the forest does not hold -- is a
FAULT, and no face of the features runs until it is mended.


6  RENAMING, AND RETIRING
______________________________________________________________________________

OUR ID IS OURS: what the outside holds stands in the map. A rename follows
every reference in one step:

    $ hwut.features.rename keep-order keeporder
    renamed  keep-order -> keeporder
        hwut-feature-forest.csv
        hwut-feature-doc.dat
        hwut-feature-external-map.csv
        link renamed in router/TEST/test-route.sh

-- both sides of the forest's lines, the doc heading (its audiences kept),
the map's left column, every 'features = [...]' of the headers and confs.
An id that stands already, or is no id, is refused; nothing is written.

A claim no longer made is RETIRED:

    $ hwut.features.retire drop-unknown

Its block takes the heading '[[drop-unknown:retired]]' -- the claim kept as
it was -- and its id leaves every forest line. It has no verdict and counts
nowhere; 'f/drop-unknown' refuses it, and a test still linking it is named.
A feature with children is refused (retire them first), and so is one the
map names: the outside was told it. REVIVAL is by hand: ':retired' struck,
the id back in a forest line.


7  CHOOSING RUNS BY FEATURE: THE LABEL 'f/<id>'
______________________________________________________________________________

A feature reaches the runs as a LABEL (intend/three-worlds): 'f/<id>' names
the runs linked to that feature AND to every feature below it, in every
face that takes '-l':

    $ hwut.report.list -l f/forwarding
    ./router/TEST/test-route.sh burst
    ./router/TEST/test-route.sh single
    $ hwut.run -l "f/gateway AND NOT slow"

'f/' is LIVE: the links decide at the time of use. It combines as every
label does -- AND, OR, NOT, brackets -- and may stand in a derived label of
'hwut-root.labels':

    [derived]
    focus = f/forwarding AND NOT slow

A frozen copy is a label of its own: 'hwut.labels.create forwarding_today
-l f/forwarding' stores the runs as they are linked now.

'-l' STANDS ALONE: beside a target, '--dir', '--fail' or any other word of a
wish it is refused, and so the runs of a feature that failed are a label
and an expression ('hwut.labels.create failing --fail', then
'-l "f/gateway AND failing"'). Refused by name: an id that stands nowhere,
a retired one, a word that is no id -- a misspelt word that silently
selected nothing would let an author believe the set is empty:

    $ hwut.report.list -l f/keep-ordr
    REFUSED: 'f/keep-ordr' names no feature: 'keep-ordr' stands in no line of 'hwut-feature-forest.csv' and no block of the doc file => hwut.features.tree --list -- did you mean 'keep-order'?

A feature with no run yet is legal: the selection is empty. Without a
forest every feature label is refused => hwut.features.init. '-F', '-e'
and '-k' are gone from every face: the runs of a feature are 'f/<id>'.


8  THE TABLE
______________________________________________________________________________

'hwut.report.features --matrix' prints the links as a table, one per TEST
directory whose runs link a feature, in place of the tree. A row is a test
run, a column a feature linked there (#1 .. in the order it is first
linked), a cell the run's verdict where it links; a column is named with
the feature's state -- 'stands nowhere' or 'retired' where it has none.

    $ hwut.report.features --matrix
    can/TEST       #1
    test-frame.sh  PASS
      #1 decode  IMPLEMENTED ok

    router/TEST             #1    #2
    test-restart.sh         .     .     <- NONSENSE?
    test-route.sh [single]  PASS  .
    test-route.sh [burst]   PASS  PASS
      #1 forward     IMPLEMENTED ok
      #2 keep-order  IMPLEMENTED ok

An empty row is a test run that proves nothing stated ('<- NONSENSE?'). A
feature nobody proves has no column: the tree shows it OPEN. 'OUTSIDE THE
RELATION' follows the tables as it follows the tree.


9  THE CODE A FEATURE'S RUNS REACHED
______________________________________________________________________________

'hwut.cov.run' measures which lines each test run executes and writes a
coverage output directory ('hwut.coverage/' by default). With such an
output, 'hwut.report.features --code' adds to each feature that has a
linked test run the lines those runs executed:

    [IMPLEMENTED ok]   router.keep-order -- Frames leave in the order they arrived.
        [PASS] TEST/test-route.sh [burst]
        code only    queue.c: 41..58
        code shared  112 line(s) in 3 file(s)

    code only     lines executed by this feature's test runs and by NO
                  other measured test run; per source file
    code shared   lines executed by this feature's test runs and by
                  others; a count
    code   <n> of <m> linked run(s) not measured
                  linked test runs the coverage output does not hold

The coverage output is the one '--cov-dir=<dir>' names; else the nearest
'hwut.coverage/' from the directory upward. Where none is found the
first line is a NOTE and the page stands without code.

The lines say where the runs WENT. Which lines are 'only' depends on
what else the coverage run measured: measured alone, a test run owns
every line it touches. Source files standing in a TEST directory are
left out. '--matrix' prints no code.


10  THE FEATURE DOCUMENT
______________________________________________________________________________

'hwut.report.features --html=<file>' writes the report as one
self-contained HTML page; '--ods=<file>' as an OpenDocument spreadsheet.
Both hold four tabs:

    Matrix     a row per feature: id, brief (its title), state, and
               the test runs that implement it, with their verdicts
    Tree       the forest, roots first; each feature with children with
               its title, state and counts
    Features   a row per feature: id, title, doc, the feature above it,
               state, the outside's names, audiences, documents
    Tests      a row per test application: file, title, doc, test runs
               with their verdicts, features

    an id in 'Matrix'            leads to its row in 'Features'
    a test run in 'Matrix'       leads to its test's row in 'Tests'
    a feature in 'Tree'          leads to its row in 'Features'
    a document of a feature      opens from its row in 'Features'

The tree is interactive. On the page: 'Expand all', 'Collapse all', a box
per state to show only the IMPLEMENTED ok, IMPLEMENTED fail, IMPLEMENTED
untested or OPEN untested leaves, and a word filter. In the spreadsheet the levels are row groups, folded and
unfolded at the sheet's margin.

    $ hwut.report.features --html=features.html
    'features.html' written -- 4 feature(s), 3 test(s)

The 'Tests' tab shows what a test says of itself: its 'title', and its
'doc' -- a text of as many lines as it takes, written in the test's block
between three double quotes:

    # @hwut {
    #     title    = "Routing"
    #     doc      = """
    #         Sends CAN frames through the router and prints where each
    #         one leaves.
    #
    #         'burst' sends two in a row: their order must hold.
    #         """
    #     features = ["forward"]
    # }

The text is taken as written; the indentation common to its lines is
removed. Only TEST directories that state features are in the document.
The same tree yields the same file, byte for byte.

THE WAY TO THE CODE. After a coverage run the document can say where each
feature's test runs went, and lead there:

    $ hwut.cov.run
    $ hwut.cov.conv.to_html -o covpages
    $ hwut.report.features --html=doc/features.html --cov-html=covpages

The 'Features' tab then carries, per feature, the sources and lines only
its runs executed (section 9); each source is a link to its coverage page,
at the first of those lines:

    calc/calc.py: 5..7    ->    ../covpages/calc/calc.py.html#L5

The link is relative to where the document stands: the document and the
directory of pages travel together. '--code' alone gives the column
without links.


11  ONE BRANCH, MANY OWNERS: PROTOTYPES
______________________________________________________________________________

The gateway has two ports, and each does the same: receive, send, and
handle the errors of its bus. Written out, the forest says it twice, and
every new word has to be added in two places. A PROTOTYPE says it once:

    gateway   : can-port, most-port
    can-port  : +port
    most-port : +port
    +port     : receive, send, +errors
    +errors   : bus-off, overrun

A line headed '+<name>' declares a prototype; its right side holds its
MEMBERS and, written with '+', other prototypes it aggregates. '+port' in
an owner's line AGGREGATES it: the owner HAS what the prototype holds. The
forest expands each aggregation into an INSTANCE named '<owner>+<id>':

    $ hwut.features.tree
    gateway  The gateway forwards what reaches it.
      can-port
        can-port+port  What every port does.
          can-port+receive  A frame is received.
          can-port+send  What every port does.
          can-port+errors  What every port does.
            can-port+bus-off  What every port does.
            can-port+overrun  What every port does.
      most-port
        most-port+port  What every port does.
          most-port+receive  A MOST frame is received, in its slot.
          ...
    (prototypes)
      +port  What every port does.
        receive  A frame is received.
        send
        +errors
          bus-off
          overrun

An instance is a feature like any other: a test links it, it folds its
runs and its children's, it is selected and reported. A prototype and a
member are no feature -- the stuff instances are made of: a link to
'receive' stands outside ("a member of a prototype -- link
'<owner>+<id>'"), and so does one to '+port'.

THE DOC FILE documents a member once for every instance, '[[receive]]',
and a prototype, '[[+port]]'. An instance's own block wins for that one:
'[[most-port+receive]]'. What has no block takes the one of the
prototype it stands in, or of a prototype around that. Audiences fold
down the instances as down any branch.

THE LABEL takes a glob, in any position: 'f/*+receive' is every port's
receiving, 'f/can-port+*' everything the CAN port has, 'f/*' every
feature. A glob that matches nothing is refused by name, as an id that
stands nowhere is. 'f/+port' is refused: a prototype names no instance.

RULES the forest holds a prototype to, each a FAULT with file and line:
it is declared once and aggregated with '+'; a member stands in one
prototype, and its id is no feature's; no circle among prototypes; an
owner reaches a prototype once. 'register' NOTEs a prototype nobody
aggregates and a member that nothing documents.

RENAMING a member or a prototype renames every instance and every link to
one, in one step; renaming the owner carries its instances. RETIRING a
member takes it out of its prototype's line and retires its block -- in
every instance at once. A prototype, an instance, a prototype's last
member are not retired: strike the '+<prototype>' from the owner's line.


12  WHAT hwut.run DOES WITH ALL THIS
______________________________________________________________________________

Nothing that changes a verdict. A test runs and is judged whether or not
its links name a feature that stands. Where runs below the run's
directory link an id that stands nowhere, or a retired one, its last line
says how many => hwut.features.register; 'hwut.help' says more. The
relation is read by 'hwut.report.features', 'hwut.help', 'hwut.sanitize',
the label 'f/<id>' and the 'hwut.features.*' faces.


13  REFERENCE
______________________________________________________________________________

    hwut.features.init                    an empty forest and doc file
    hwut.features.register                names what disagrees
    hwut.features.tree [<id>] [--list] [-e]
    hwut.features.rename <old id> <new id>
    hwut.features.retire <id>             a feature without children
    hwut.report.features [<id>]... [--matrix] [--code] [--cov-dir=<dir>]
                         [--html=<file>] [--ods=<file>] [--cov-html=<dir>]
                         [--directory=<path>]
    hwut.help                             explains 'NONSENSE?' and the
                                          links to no feature
    hwut.sanitize.propose --relations [-o <file>]
    <any face with a wish> -l f/<id>      the runs of a feature (a label)
                           -l 'f/*+<id>'  a glob: every instance of a member

    hwut-feature-forest.csv        <id> : <child-id>, <child-id>, ...
                                   <id> : +<prototype>, ...
                                   +<prototype> : <member>, +<prototype>
    hwut-feature-doc.dat           [[CUSTOMERS]]
                                   <audience>: <who that is>
                                   [[<id>]] | [[+<prototype>]]
                                            | [[<owner>+<id>]]
                                            | [[<id> to <audience>, ...]]
                                            | [[<id> not <audience>, ...]]
                                            | [[<id>:retired]]
                                   documents: <path>, ...
                                   <title>
                                   <doc>
    hwut-feature-external-map.csv  <our id> ; <their name>
    '@hwut { }' block              features = ["<id>", ...]
                                   doc      = """<text>"""

'hwut-features.conf' in a TEST directory, 'hwut-root-features.conf' and
'hwut-feature-map.conf' are the vocabulary of an earlier HWUT: nothing
reads them, 'register' names them. 'hwut.features.move' and
'hwut.features.key.*' are gone with them -- no file holds a directory, and
keys are left out. Every face answers '--help' with its full text. The
complete statement is 'adm/WORK/spec/43-feature-id-space.txt'; the
prototypes are 'adm/WORK/intend/44-feature-prototypes.txt'.
