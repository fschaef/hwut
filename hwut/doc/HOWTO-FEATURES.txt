==============================================================================
HOWTO-FEATURES -- say what a tree does, and see which test runs prove it
==============================================================================

A FEATURE is one thing a piece of software does, said in one sentence. A
TEST RUN is one test application run with one choice; its verdict stands
in 'GOOD/book.csv'. A test run is LINKED to the features it proves. From
the links and the verdicts every feature has a state, on two axes:

    IMPLEMENTED    one linked test run or more        ok        every one passes
                                                      fail      one fails
                                                      untested  none fails, one
                                                                never ran
    OPEN           no linked test run                 untested
    RETIRED        no longer claimed (section 6)      no verdict

The axes are independent: OPEN says nothing proves the claim, and that is
no failure. An aggregate is OPEN where a claim below it is; its verdict is
the worst below it -- fail, then untested, then ok.

TWO kinds of file carry it. Each TEST directory DEFINES its features in its
'hwut-features.conf'. ONE file at the top, 'hwut-root-features.conf' beside
'hwut-root.conf', REGISTERS them: it gives each the id the world knows it
by, and groups them the way a reader thinks of them -- which need not be
the way the directories are laid out.

    gateway/
      hwut-root.conf
      hwut-root-features.conf          ids, the tree of features, the retired
      router/TEST/hwut-features.conf   the router's features
                  test-route.sh        features = ["forward"]
                  test-restart.sh
      can/TEST/hwut-features.conf      the CAN side's features
               test-frame.sh           features = ["decode"]

The example is a CAN-MOST gateway; every excerpt is the output of that tree.

1  FEATURES AND LINKS
______________________________________________________________________________

The feature file of a TEST directory lists its features under 'childs'.
The KEY of a feature is its name; it is what a test writes to link to it.
'router/TEST/hwut-features.conf':

    features {
        childs {
            forward      { title = "A CAN frame is forwarded to its MOST address."
                           keys  = ["latency"] }
            keep-order   { title = "Frames leave in the order they arrived." }
            drop-unknown { title = "A frame without a route is dropped and counted." }
        }
    }

    key           the feature's name, unique in the file: letters, digits,
                  '_' and '-', no dot. Digits may lead ('007').
    title         one sentence: what the software does.
    doc           what more there is to say, optional: as many lines as it
                  takes, between three double quotes.
    documents     where more is said of the feature, optional: a list of
                  paths from this file's directory ('#<anchor>' may
                  follow), or URLs --
                      documents = ["../README.txt", "../spec.txt#3"]
                  The report prints each as 'see <path>' under the
                  feature and names one that does not stand; the feature
                  document makes each a link.
    keys          categories the feature belongs to (section 4), optional.

A test links to features by name, in its block. 'router/TEST/test-route.sh':

    # @hwut {
    #     title    = "Routing"
    #     features = ["forward"]
    #     choices {
    #         single { }
    #         burst  { features = ["forward", "keep-order"] }
    #     }
    # }

'features' at the root of the block holds for every choice. 'features' in
a choice REPLACES the root's list for that choice; '[]' links the choice
to nothing. A name is looked up in the feature file of the test's own
TEST directory only.

A FEATURE OF ANOTHER DIRECTORY is linked by its INTERNAL ID, '<directory
id>:<name>' -- what the report's 'internal' line and the leaf line of the
central file show. An end-to-end test at the top, say, proving a sentence
of 'router':

    #     features = ["Qm9xB_2a:forward"]

The run is listed under that leaf beside router's own. The external id
('router.forward') is the name for the world and no link: a test writing
it is said under OUTSIDE THE RELATION, with the internal id to write. An
internal id survives a move of its directory; where it does change -- a
rename, a repoint, a fold, a test carrying a feature away -- every link by
it is rewritten in that step, each file named.


2  THE CENTRAL FILE
______________________________________________________________________________

'hwut.features.init' writes it, once, at the top of the tree. Its header
says in comments what follows here. As written by 'init' every feature
stands unplaced; the author then groups the lines. 'gateway/
hwut-root-features.conf':

    features {
        directory_map {
            "Zk3aT-7c" = "can"
            "Qm9xB_2a" = "router"
        }
        tree {
            gateway {
                title = "CAN-MOST gateway"
                doc   = "Carries frames between a CAN bus and a MOST ring."
                childs {
                    forwarding {
                        title = "Frames reach their destination."
                        keys  = ["routing"]
                        childs {
                            "router.forward"      = "Qm9xB_2a:forward"
                            "router.keep-order"   = "Qm9xB_2a:keep-order"
                            "router.drop-unknown" = "Qm9xB_2a:drop-unknown"
                        }
                    }
                    buses {
                        title  = "Both buses are served."
                        childs { "can.decode" = "Zk3aT-7c:decode" }
                    }
                }
            }
        }
        retired {
        }
    }

    directory_map   a generated id for each directory whose TEST directory
                    defines features -> where it stands, below the top.
                    Never edit an id. A directory that moves changes ONE
                    line.
    tree            AGGREGATES group LEAVES. An aggregate is a block:
                    title, doc, documents, keys, childs. A leaf is one
                    line:
                        "<external id>" = "<directory id>:<feature name>"
                    A leaf stands under ONE aggregate, or at the top of
                    'tree', unplaced; keys say the other categories
                    (section 4).
    retired         what is no longer claimed, kept as it was (section 6).

THE EXTERNAL ID, left of a leaf line, is what customers, documents and
tickets refer to. The INTERNAL id, right of it, is where the feature is
defined: the directory's id and the feature's name. External ids and
aggregate keys form ONE namespace: each stands once. An id is a word of
letters, digits, '_' and '-' -- words joined by '.' for an external id;
any script, in NFC. The tree is the author's to reshape at will: no id
depends on it.

    $ hwut.features.tree
    gateway  CAN-MOST gateway
      forwarding  Frames reach their destination.
        forward  (router)  A CAN frame is forwarded to its MOST address.
        keep-order  (router)  Frames leave in the order they arrived.
        drop-unknown  (router)  A frame without a route is dropped and counted.
      buses  Both buses are served.
        decode  (can)  A CAN frame is decoded into its signals.

'-e' adds the external ids, '-b' prints the aggregates only, '--list' one
tree path per leaf -- lines '-F' takes as they stand (section 7):

    $ hwut.features.tree --list
    gateway/forwarding/router.forward
    gateway/forwarding/router.keep-order
    gateway/forwarding/router.drop-unknown
    gateway/buses/can.decode


3  THE REPORT
______________________________________________________________________________

'hwut.report.features' prints the tree of the central file below the
current directory ('--directory=<path>' names another). It runs nothing;
it reads the texts and the verdicts.

    $ hwut.report.features
    AGGREGATE gateway -- CAN-MOST gateway      3 implemented, 1 open; 3 ok, 0 fail, 1 untested
        state      OPEN untested
        doc        Carries frames between a CAN bus and a MOST ring.
        AGGREGATE gateway/forwarding -- Frames reach their destination. 2 implemented, 1 open; 2 ok, 0 fail, 1 untested
            state      OPEN untested
            keys       routing
            [IMPLEMENTED ok]   router.forward -- A CAN frame is forwarded to its MOST address.
                internal    Qm9xB_2a:forward  (router)
                keys        latency, routing
                [PASS] router/TEST/test-route.sh [single]
                [PASS] router/TEST/test-route.sh [burst]
            [IMPLEMENTED ok]   router.keep-order -- Frames leave in the order they arrived.
                internal    Qm9xB_2a:keep-order  (router)
                keys        routing
                [PASS] router/TEST/test-route.sh [burst]
            [OPEN untested]    router.drop-unknown -- A frame without a route is dropped and counted.
                internal    Qm9xB_2a:drop-unknown  (router)
                keys        routing
        AGGREGATE gateway/buses -- Both buses are served. 1 implemented, 0 open; 1 ok, 0 fail, 0 untested
            state      IMPLEMENTED ok
            [IMPLEMENTED ok]   can.decode -- A CAN frame is decoded into its signals.
                internal    Zk3aT-7c:decode  (can)
                [PASS] can/TEST/test-frame.sh

    OUTSIDE THE RELATION
        NONSENSE? test run, links to no feature => hwut.help
            router/TEST/test-restart.sh

A leaf is addressed by its external id. An aggregate folds what stands
below it: IMPLEMENTED where everything below is, the verdict ok where
every verdict below is; an aggregate with nothing below is OPEN. Its
counts are the sum of its leaves. Leaves in no aggregate follow under
UNPLACED, the retired under RETIRED. Asked below the top, only the leaves
whose directory stands below, under the aggregates that hold them.

'OUTSIDE THE RELATION' names what the tree says too little or too much
of:

    what is named                               what it means
    ---------------------------------------------------------------------
    test run, names a feature its TEST          a misspelt name, or a
    directory does not define                   feature not yet written
    test run, names an external id -- no        link the internal id named
    link; link the internal id                  behind '=>'
    test run, links by internal id what does    an id in no 'directory_map'
    not resolve                                 line, a name its directory
                                                does not define, a retired
                                                leaf
    NONSENSE? test run, links to no feature     a test run that proves
                                                nothing its directory
                                                claims. NO FAILURE: its
                                                verdict stands. 'hwut.help'
                                                says what to do with it.
    claim, names a document that does not       'documents' of a feature
    stand
    statement, not read                         a file with a fault; the
                                                position and the fault
    feature, defined and not registered         section 5
    central file and tree, not as they          section 5
    should stand

The exit status is 0 whatever is listed; 3 where no TEST directory stands
below; 2 where no central file stands at the top (=> hwut.features.init)
or it states a fault.

Feature files are not mandatory. A TEST directory without one is named
nowhere, and its tests are nobody's nonsense.


4  KEYS
______________________________________________________________________________

The tree says WHERE a feature belongs. A KEY says WHAT KIND it is: a
category that cuts across the tree -- 'latency', 'safety', 'slow'.

    keys = ["routing"]            on an aggregate: applies to it and to
                                  everything below it
    keys = ["latency"]            on a feature (its TEST file): applies to it
    keys = [...] at the top of    applies to every feature of the file
    a TEST file

Keys travel DOWNWARD only. In the report a leaf lists its EFFECTIVE keys --
its own, those of its TEST file and those of every aggregate above it:

    router.forward    keys   latency, routing

    hwut.features.key.add <id> <key>       on a leaf (written into its TEST
                                           file) or an aggregate
    hwut.features.key.remove <id> <key>    the key it states itself
    hwut.features.key.remove --all <key>   the key off every claim

Keys are not labels. A label (hwut.run -l) marks a set of test runs and is
ephemeral; a key is a durable category of features.


5  KEEPING THE CENTRAL FILE IN ORDER
______________________________________________________________________________

The DIRECTORIES and the TEST files are the fact; the central file is held
against them. A feature written today has no line yet. 'hwut.run' ends
with one line where that is so -- its verdicts are untouched:

    2 feature(s) not registered => hwut.features.register

'hwut.features.register [dir]' adds what is new below the current
directory (or the one named): an id for a new directory, a line for each
new feature, unplaced under a first external id -- move the line into an
aggregate. It names every other disagreement, and where it is CERTAIN of
the remedy, the line that heals it. After 'mv can bus/can' and the
feature 'keep-order' renamed 'in-order':

    $ hwut.features.register
    NOT AS IT SHOULD STAND -- read, then heal by hand or by the lines after '=>':
        dir-gone   Zk3aT-7c   'can' stands no more
                       => redirect Zk3aT-7c bus/can  # from can
        leaf-gone  router.keep-order   Qm9xB_2a:keep-order is defined no more
                       => repoint router.keep-order Qm9xB_2a:in-order  # from Qm9xB_2a:keep-order

'hwut.sanitize' does such lines one at a time, or a file of them:

    $ hwut.sanitize.propose --relations -o heal.txt
    $ hwut.sanitize.apply heal.txt
     redirect Zk3aT-7c bus/can ............................................ [DONE]
          Zk3aT-7c now stands for bus/can
     repoint router.keep-order Qm9xB_2a:in-order .......................... [DONE]
          router.keep-order now binds Qm9xB_2a:in-order
    Done 2/2

    register <dir>                  the id and the lines <dir> lacks
    redirect <id> <path>            a directory moved: its ONE line follows;
                                    every external id below stays valid
    repoint <external> <internal>   a feature renamed or moved: the
                                    external id is bound to what it became
    fold <id> <first id>            one path under two ids (two branches
                                    merged): the later goes

A PAIRING IS PROPOSED ONLY WHERE IT IS CERTAIN: a directory by the names
of its features (the best match both ways, at least half); a feature as
the ONLY one gone and the ONLY one new of its directory, or by its name
elsewhere. Where it cannot tell, it says 'unpaired' with the candidates
and does nothing -- so move ONE directory, then register. A new name in a
directory whose gone feature it cannot pair is HELD: no line is written for
it until the gone one is repointed or retired, and each side names the
other. It never retires (section 6). Every command judges again before it
acts.

The faces that change the tree keep the central file themselves:

    hwut.features.move <dir> <new>  moves the directory and its line (and
                                    every line below it)
    hwut.features.rename <external> <new name>
                                    renames a feature: its definition, the
                                    links of its TEST directory's tests,
                                    the leaf's internal id; the external id
                                    stays
    hwut.move <test> <dir>          carries the features the test links to
                                    into the target's TEST file, and takes
                                    them out of the source's; the leaf
                                    follows to the target's directory id
                                    (one is registered where none stands),
                                    and every link by its old internal id
                                    follows. A feature a test that stays
                                    still links is not copied: the moved
                                    test links it by internal id.
    hwut.rename                     adapts nothing: the link stands in the
                                    test's block.
    hwut.remove                     names the features left without a
                                    linked test run.


6  IDS THAT STAY, AND RETIRING
______________________________________________________________________________

A customer who refers to 'router.keep-order' still means the same feature
after the directory moved and the feature was renamed: the external id
stays; only the right side of its line changed. When what a customer holds
must change, edit the left side -- there, and nowhere else. A rename
REPLACES the old id; there is no alias.

A feature that is no longer claimed is RETIRED, never deleted:

    $ hwut.features.retire router.drop-unknown
    retired  router.drop-unknown  (Qm9xB_2a:drop-unknown)
        definition taken out of router/TEST/hwut-features.conf

Its line and its definition move into 'retired', as they were. An
aggregate retires with everything below it. A retired id is never given
again: register refuses to bind it, and a name defined again under a
retired internal id is named. Revival is by hand: the block back into the
tree, the definition back into its TEST file.

The file holds the CURRENT state only. Who retired what, and when, is
version control's: keep 'hwut-root-features.conf' under it, and never
delete it -- 'register' will not make a new one where features stand.


7  CHOOSING RUNS BY FEATURE AND KEY
______________________________________________________________________________

Every face that takes a wish (hwut.run, hwut.report.list, hwut.accept ...)
takes three more words:

    -F, --feature <id-glob>     the runs linked to the leaves a tree path
                                names
    -e, --feature-ext <id>      the runs linked to the leaf of an external id
    -k, --keys <expr>           the runs linked to leaves with these keys

    $ hwut.report.list -F gateway/forwarding
    ./router/TEST/test-route.sh burst
    ./router/TEST/test-route.sh single
    $ hwut.report.list -e router.keep-order
    ./router/TEST/test-route.sh burst
    $ hwut.report.list -k latency
    ./router/TEST/test-route.sh burst
    ./router/TEST/test-route.sh single

'-F' globs over TREE PATHS -- the aggregate keys from the top, '/' between,
the external id last; an unplaced leaf is its external id alone:

    *        any part of one level
    **       any number of levels, none included
    {a,b}    alternatives
    a word   '**/word': an aggregate or a leaf anywhere
    X:name   an internal id ('Qm9xB_2a:*' every leaf of a directory)

An aggregate brings its subtree. '-e' takes an external id whole, '*' any
characters. Several '-F' and '-e' are ONE union; '-k' narrows it; all
narrow the rest of the wish like '--dir' does: '-F gateway/forwarding
--fail' is the failing runs of forwarding.

'-k' takes the expression of '-l' -- AND, OR, NOT, brackets, ',' for OR --
over a leaf's EFFECTIVE keys (section 4).

A run linked to no feature is wanted by none of them. Refused by name: an
external id that names no leaf, a retired id, and a key no leaf carries --
a misspelt word that silently selected nothing would let an author believe
the set is empty:

    $ hwut.report.list -e router.gone
    REFUSED: '--feature-ext router.gone' names no feature: no line of 'hwut-root-features.conf' has that external id => hwut.features.tree -e

A '-F' glob that matches nothing is legal: the selection is empty. Without
a central file every feature word is refused => hwut.features.init.


8  THE TABLE
______________________________________________________________________________

'hwut.report.features --matrix' prints the links as a table, one per TEST
directory that carries a feature file, in place of the tree. A row is a
test run, a column a feature (#1 .. by position), a cell the run's verdict
where it links; a column is named with its leaf's state.

    $ hwut.report.features --matrix --directory=router
    TEST                    #1    #2    #3
    test-restart.sh         .     .     .     <- NONSENSE?
    test-route.sh [single]  PASS  .     .
    test-route.sh [burst]   PASS  PASS  .
                                        ^     no test run
      #1 forward       IMPLEMENTED ok
      #2 keep-order    IMPLEMENTED ok
      #3 drop-unknown  OPEN untested

    an empty row      a test run that proves nothing stated
                      ('<- NONSENSE?'; '<- no feature defined' where it
                      names only features the directory does not define)
    an empty column   a feature no test run proves ('^ ... no test run')
    'not registered'  in place of a state: no line names the feature

'OUTSIDE THE RELATION' follows the tables as it follows the tree.


9  THE CODE A FEATURE'S RUNS REACHED
______________________________________________________________________________

'hwut.cov.run' measures which lines each test run executes and writes a
coverage output directory ('hwut.coverage/' by default). With such an
output, 'hwut.report.features --code' adds to each feature that has a
linked test run the lines those runs executed:

    [IMPLEMENTED ok]   router.keep-order -- Frames leave in the order they arrived.
        [PASS] TEST/test-route.sh [burst]
        code only    queue.c: 41..58
        code shared  112 line(s) in 3 file(s)

    code only     lines executed by this feature's test runs and by NO
                  other measured test run; per source file
    code shared   lines executed by this feature's test runs and by
                  others; a count
    code   <n> of <m> linked run(s) not measured
                  linked test runs the coverage output does not hold

The coverage output is the one '--cov-dir=<dir>' names; else the nearest
'hwut.coverage/' from the directory upward. Where none is found the
first line is a NOTE and the page stands without code.

The lines say where the runs WENT. Which lines are 'only' depends on
what else the coverage run measured: measured alone, a test run owns
every line it touches. Source files standing in a TEST directory are
left out. '--matrix' prints no code.


10  THE FEATURE DOCUMENT
______________________________________________________________________________

'hwut.report.features --html=<file>' writes the report as one
self-contained HTML page; '--ods=<file>' as an OpenDocument spreadsheet.
Both hold four tabs:

    Matrix     a row per leaf: external id, brief (its title), state, and
               the test runs that implement it, with their verdicts
    Tree       the aggregates and their leaves, as the central file has
               them; each aggregate with its title, state and counts
    Features   a row per leaf: external id, name, title, doc, aggregate,
               state, internal id, effective keys, documents
    Tests      a row per test application: file, title, doc, test runs
               with their verdicts, features

    an external id in 'Matrix'   leads to its row in 'Features'
    a test run in 'Matrix'       leads to its test's row in 'Tests'
    a leaf in 'Tree'             leads to its row in 'Features'
    a document of a feature      opens from its row in 'Features'

The tree is interactive. On the page: 'Expand all', 'Collapse all', a box
per state to show only the IMPLEMENTED ok, IMPLEMENTED fail, IMPLEMENTED
untested or OPEN untested leaves, and a word filter. In the spreadsheet the levels are row groups, folded and
unfolded at the sheet's margin.

    $ hwut.report.features --html=features.html
    'features.html' written -- 4 feature(s), 3 test(s)

The 'Tests' tab shows what a test says of itself: its 'title', and its
'doc' -- a text of as many lines as it takes, written in the test's block
between three double quotes:

    # @hwut {
    #     title    = "Routing"
    #     doc      = """
    #         Sends CAN frames through the router and prints where each
    #         one leaves.
    #
    #         'burst' sends two in a row: their order must hold.
    #         """
    #     features = ["forward"]
    # }

The text is taken as written; the indentation common to its lines is
removed. Only TEST directories that state features are in the document.
The same tree yields the same file, byte for byte.

THE WAY TO THE CODE. After a coverage run the document can say where each
feature's test runs went, and lead there:

    $ hwut.cov.run
    $ hwut.cov.conv.to_html -o covpages
    $ hwut.report.features --html=doc/features.html --cov-html=covpages

The 'Features' tab then carries, per feature, the sources and lines only
its runs executed (section 9); each source is a link to its coverage page,
at the first of those lines:

    calc/calc.py: 5..7    ->    ../covpages/calc/calc.py.html#L5

The link is relative to where the document stands: the document and the
directory of pages travel together. '--code' alone gives the column
without links.


11  WHAT hwut.run DOES WITH ALL THIS
______________________________________________________________________________

Nothing that changes a verdict. A test runs and is judged whether or not
its links resolve and its features are registered. Where features below
the run's directory stand in no line of the central file, its last line
says how many => hwut.features.register; 'hwut.help' says more. The
relation is read by 'hwut.report.features', 'hwut.help', 'hwut.sanitize'
and the 'hwut.features.*' faces.


12  REFERENCE
______________________________________________________________________________

    hwut.features.init                    writes the central file, every
                                          feature unplaced
    hwut.features.register [dir]          adds what is new; names the rest
    hwut.features.tree [<base>] [--list] [-b] [-e]
    hwut.features.retire <id>             a leaf, or an aggregate and all
                                          below it
    hwut.features.move <dir> <new dir>
    hwut.features.key.add <id> <key>
    hwut.features.key.remove <id> <key> | --all <key>
    hwut.report.features [--matrix] [--code] [--cov-dir=<dir>]
                         [--html=<file>] [--ods=<file>] [--cov-html=<dir>]
                         [--directory=<path>]
    hwut.help                             explains 'NONSENSE?' and what is
                                          not registered
    hwut.sanitize.propose --relations [-o <file>]
    hwut.sanitize.apply <file>
    hwut.sanitize register <dir> | redirect <id> <path>
                | repoint <external> <internal> | fold <id> <first id>
    <any face with a wish> [-F|--feature <id-glob>]...
                           [-e|--feature-ext <id>]... [-k|--keys <expr>]

    hwut-root-features.conf   features { directory_map { "<id>" = "<path>" }
                                         tree { <key> { title doc
                                                        documents keys
                                                        childs { ... } }
                                                "<external>" = "<id>:<name>" }
                                         retired { ... } }
    hwut-features.conf        features { keys
                              (TEST)                childs { <name> { title doc
                                                  documents keys } } }
    '@hwut { }' block         features = ["<name>", ...]
                              doc      = """<text>"""

A 'hwut-features.conf' outside a TEST directory, and 'hwut-feature-map.conf',
are the vocabulary of an earlier HWUT: nothing reads them, 'register' names
them. Every face answers '--help' with its full text. The complete
statement, with what is still open, is 'adm/WORK/spec/23-features.txt'.
