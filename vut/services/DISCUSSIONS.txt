todo-1  'hwut.rename' / 'hwut.rename-choice' ACROSS A DIRECTORY BOUNDARY
------------------------------------------------------------------------------
RULED (session 2026-09-04, during the coverage component's database/
readers split): both faces should be able to carry a test's book
entry, register entry, nominals and candidates from ONE directory's
tree into ANOTHER's, not only re-key it within the directory it
already stands in.

THE GAP THAT RAISED IT. Splitting 'coverage/TEST' into
'coverage/TEST', 'coverage/database/TEST' and 'coverage/readers/TEST'
left 'GOOD/result_db.csv' and 'GOOD/test_ids.dat' stale in all three:
each still names -- or is missing -- test files that physically moved.
Hand-editing them was refused (GOOD files, and a directory's book with
them, are recorded on real infrastructure, never fabricated); the
session left the three directories with these books unreconciled.

WHY IT IS NOT AS LARGE AS IT LOOKS. Every primitive a cross-directory
move needs already exists, built for the SAME-directory case:

    a fresh id in the target        'TestIdDb.register()' -- issuing
                                    one for a test new to a directory
                                    is its ordinary path, not a special
                                    case (bookkeeper B-2: issued once,
                                    never reused -- exactly the
                                    guarantee a moved test still wants)
    the source entry retired        'hwut.remove''s book/register
                                    clearing ALREADY retires an id
                                    rather than freeing it for reissue;
                                    the same retirement is what a
                                    cross-directory move wants of the
                                    SOURCE side
    which files move                'rename.move_tuple()' already
                                    computes every (from, to) pair --
                                    nominals, candidates, every sidecar
    a moved coverage record's       'record.seated(record, run)' is
    new run id                     already the one seam that stamps a
                                    record with a run id; re-seating
                                    under the target's fresh id is a
                                    second call, not new machinery

WHAT IS ACTUALLY NEW. The command shape: today '--directory=<path>'
selects ONE 'Store'/'Bookkeeper' for the whole call, because a rename
has only ever meant re-keying within it. A cross-directory move needs
TWO -- a source and a target -- and 'move_tuple()"'s destination paths,
today built from the SAME store as the source, need to come from the
target store instead. Worth a spike measuring the two-'Store' shape
against 'move_tuple()' before ruling further; no disc-N stands yet
because no fork has been found, only labour.

RETIRES WHEN BUILT: the stale 'result_db.csv' / 'test_ids.dat' left
under 'coverage/TEST/', 'coverage/database/TEST/' and
'coverage/readers/TEST/' by the 2026-09-04 split become the first real
exercise of it.
