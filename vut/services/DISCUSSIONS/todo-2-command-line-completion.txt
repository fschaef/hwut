todo-2-command-line-completion.txt                    ** DESIGN, NOT BUILT **
______________________________________________________________________________

RAISED (chat, 2026-08-29). Every face should complete on TAB, in bash,
zsh and PowerShell at least.

==============================================================================
THE CONSTRAINT THAT DECIDES THE DESIGN
==============================================================================
MEASURED, on the machine this was written on:

    import vut.services.run          0.711 s

A COMPLETION RUNS ON EVERY TAB PRESS. Seven hundred milliseconds is a
terminal that feels broken, and a person will stop pressing TAB rather
than wait. So the design is not 'where does the completion logic go' —
it is 'HOW LITTLE CAN BE LOADED BEFORE ANSWERING'.

==============================================================================
THE SHAPE
==============================================================================
ONE ENTRY, on the general face:

    hwut --command-line-complete <shell-name> "<the line so far>"

AND IT IS ANSWERED BEFORE ANYTHING IS IMPORTED. The launcher's module
opens:

    import sys
    if "--command-line-complete" in sys.argv[1:3]:
        from vut.services import _complete
        sys.exit(_complete.main(sys.argv[2:]))
    #  everything else -- the engine, the orchestrator, compare --
    #  is imported BELOW this line and never reached on a TAB.

'_complete' imports 'os', 're' and nothing of this tree. THE FAST PATH
IS THE WHOLE POINT: a completion that loads the engine has already
lost, whatever else it gets right.

THE SHELL NAME IS AN ARGUMENT because the three shells want different
things: bash wants bare lines, zsh wants 'candidate:description'
pairs, PowerShell wants its own object shape. ONE COMPLETER, three
renderings — and adding a shell is a rendering, not a reimplementation.

THE WHOLE LINE IS PASSED, not a word index. The completer parses it
itself, so the shell scripts stay thin enough to be obviously correct,
and a bug is fixed in Python rather than in three dialects of shell.

==============================================================================
THREE TIERS, AND ONLY THE FIRST IS FREE
==============================================================================
    STATIC     the face names, the option names of each face
               NO TREE READ AT ALL. A table in '_complete', or the
               'USAGE_TOKEN_TUPLE' of the wish -- but read as TEXT,
               never by importing the module that holds it.

    CHEAP      test applications here, choices of one, directories
               ONE DIRECTORY LISTING, or one file read. 'hwut.play
               <TAB>' offering the applications of this directory
               costs an 'os.listdir' and a line scan for the marker.

    DEAR       labels that stand, targets that are bound
               THE FILE MUST BE READ AND PARSED. 'hwut-root.labels'
               is small and its format is simple, so a private reader
               in '_complete' is right -- IMPORTING 'labels/_file.py'
               DRAGS THE ENGINE IN, and that is the trade this whole
               design exists to refuse.

    WHERE A TIER CANNOT BE ANSWERED CHEAPLY, IT ANSWERS NOTHING. A
    completion that is sometimes absent is a small disappointment; one
    that is always slow is abandoned.

==============================================================================
THE LAW A COMPLETER MUST NEVER BREAK
==============================================================================
IT NEVER FAILS LOUDLY. A traceback printed into a shell's completion
buffer corrupts what the person was typing. Every path in '_complete'
that could raise ends in 'no candidates', silently -- this is the ONE
place in this framework where swallowing is correct, and it is correct
for the same reason the observer swallows (operations/observer.py): a
watcher must not break what it watches.

IT WRITES NOTHING AND RUNS NOTHING. No lock is taken, no file is
created, no test is executed. A TAB is not a command.

==============================================================================
WHAT WOULD BE COMPLETED
==============================================================================
    hwut.<TAB>                    the face names
    hwut.run --<TAB>              the wish's options, and run's own
    hwut.run --label <TAB>        the labels that stand          DEAR
    hwut.play <TAB>               the applications here          CHEAP
    hwut.play test-a.sh <TAB>     that application's choices     CHEAP
    hwut.target <TAB>             the targets bound here         DEAR
    hwut.labels.remove <TAB>      the labels that stand          DEAR
    --dir <TAB>                   directories below here         CHEAP

==============================================================================
OPEN
==============================================================================
 a  DOES THE GENERAL FACE ANSWER FOR ALL, or does each face answer
    for itself? One entry means one fast path to keep fast; per-face
    means each knows its own options without a table.
    RECOMMENDED: THE GENERAL FACE, with the per-face option lists
    read from a TABLE in '_complete'. A table duplicates what the
    faces declare -- but the alternative imports them, and that is
    the 0.711 s this design exists to avoid. THE TABLE'S DRIFT IS
    CATCHABLE: a suite can compare it against each face's real
    'USAGE_TOKEN_TUPLE' and go red when they part.

 b  IS THERE A COMPLETION FOR '<file-glob>'? The short form takes
    bare words as targets, and a person may want the applications
    offered there too.
    RECOMMENDED: yes, same CHEAP tier as 'hwut.play'.
