================================================================================
VUT Event Component - Discussion Record
================================================================================

This file records the design decisions reached during the design
conversation, with rationale for each. The intent is that someone
reading this later understands WHY the code looks the way it does,
not just WHAT it does.

Decisions are listed roughly in the order they were settled.


--------------------------------------------------------------------------------
DECISION 1 - Event identity is system-wide and unique
--------------------------------------------------------------------------------

DECISION:    Every event has a single identity, drawn from a system-
             wide namespace where names must be unique. Realised today
             via the class-name-as-id mechanism (see Decision 10).

RATIONALE:   One identity space matters for dispatch and for log/wire
             interpretability. Federated id spaces (per-subsystem
             enums, tuple ids) fragment without solving a problem we
             have today. The tuple-composite idea (E_Entity, E_Event)
             remains deferred.


--------------------------------------------------------------------------------
DECISION 2 - Pydantic for payload validation via TypeAdapter
--------------------------------------------------------------------------------

DECISION:    Use Pydantic v2 to validate event data, but via TypeAdapter
             on plain frozen dataclasses, NOT by making every Event a
             BaseModel subclass.

RATIONALE:   The TypeAdapter is created lazily on first use of
             as_dict()/from_dict(). Hand-written validation would
             produce poor error messages. The cost is one Pydantic
             import; the benefit is robust schema enforcement at wire
             boundaries.


--------------------------------------------------------------------------------
DECISION 3 - SUPERSEDED by Decision 11.
--------------------------------------------------------------------------------

The earlier Router-with-subscribe-on-{event,category,predicate}
design was the right first step, but proved to mix two concerns:
predicate matching AND transport-aware dispatching. Decision 11
splits those into separate components.


--------------------------------------------------------------------------------
DECISION 4 - Categories are subsystems, not event shapes
--------------------------------------------------------------------------------

DECISION:    E_EventCategory members are subsystem names: TEST_RESULT,
             WORKFLOW, NETWORK, COMPILATION, DIAGNOSTIC. Flat list.

RATIONALE:   Consumers filter by subsystem interest, not by abstract
             event shape. "All terminal lifecycle events regardless of
             subsystem" is a predicate, not a category. Generic Task
             events default to WORKFLOW; subclasses re-categorise.


--------------------------------------------------------------------------------
DECISION 5 - Marshaller is a class-as-singleton, no instances
--------------------------------------------------------------------------------

DECISION:    The Marshaller is a class with classmethods only and a
             class-level _SPECIALISTS attribute (frozen
             MappingProxyType). No constructor, no instances.

RATIONALE:   For VUT's deployment shape (one matched build per process),
             synchronisation between producer and consumer is free
             because both share the same Marshaller class. The cost
             (editing marshaller.py to add a specialist) is small.


--------------------------------------------------------------------------------
DECISION 6 - serialize/deserialize live on Event AND on Marshaller
--------------------------------------------------------------------------------

DECISION:    Event has a .serialize() instance method and .deserialize()
             classmethod, both of which delegate to Marshaller.
             Marshaller exposes them as classmethods too.

RATIONALE:   Discoverability via 'event.' IDE completion, plus
             consistency: the Marshaller is a class-as-singleton so
             both call paths produce identical output.


--------------------------------------------------------------------------------
DECISION 7 - Routing addresses live in payloads, not on Event
--------------------------------------------------------------------------------

DECISION:    Event has only timestamp plus subclass-declared fields.
             No source_id or target_id on the base. Events with real
             addressing carry it as named fields with specific
             semantics (task_id, artifact_id).

RATIONALE:   Most events are broadcast facts about state changes.
             Always-present routing fields would be overhead for the
             broadcast case AND would flatten distinct routing
             semantics into anonymous pairs.


--------------------------------------------------------------------------------
DECISION 8 - Versioning is deferred but acknowledged
--------------------------------------------------------------------------------

DECISION:    No per-event version number, no schema-evolution
             machinery. The operating contract: events are produced
             and consumed within ONE matched build; cross-build
             replay is UNDEFINED.

RATIONALE:   When schema evolution becomes a real requirement, we
             will have a concrete migration to design against. Until
             then, the discipline is "do not rename event types
             lightly".


--------------------------------------------------------------------------------
DECISION 9 - File consolidation: one file per concept
--------------------------------------------------------------------------------

DECISION:    Files are grouped by what is read together. enums.py,
             event.py, events.py (the catalogue), marshaller.py,
             dispatcher.py, channel.py, channel_parameter.py,
             terminal.py, router.py - each its own concept, each
             editable independently.


--------------------------------------------------------------------------------
DECISION 10 - Event id is derived from the class name; E_EventId removed
--------------------------------------------------------------------------------

DECISION:    E_EventId enum is gone. Event.__init_subclass__ sets
             cls.id = cls.__name__ and registers cls in CLASS_BY_ID.
             Duplicate names raise EventIdCollision at class
             definition time.

RATIONALE:   Adding an event is one step, not two. Identity is
             self-describing. Rename costs are real but acceptable
             because event types are API surface anyway.


--------------------------------------------------------------------------------
DECISION 11 - Split routing into Dispatcher / Channel / Terminal / Router
--------------------------------------------------------------------------------

DECISION:    The earlier monolithic Router is decomposed into four
             components, each with one concern:

                 EventDispatcher    -- predicate-to-sink matching
                 EventChannel       -- bidirectional point-to-point
                                       transport (ABC + 4 subclasses)
                 EventTerminal      -- one end of a Channel; owns a
                                       receive-side Dispatcher
                 EventRouter        -- hub of Terminals; uses an
                                       internal Dispatcher to select
                                       outgoing destinations

             The Dispatcher is the foundational primitive, reused by
             both Terminal (receive-side fan-out) and Router (outgoing
             selection).

             EventChannelParameter is a single class with classmethod
             factories that return PAIRS of ECPs (one per side). The
             ECP is the protocol-agnostic constructor parameter for
             EventTerminal.

HISTORY:     The earlier Router conflated two distinct concerns:
             matching events to subscribers (general) and choosing
             the delivery mechanism (sink-specific). Pulling out the
             Dispatcher made it reusable; introducing the Terminal
             gave us a transport abstraction we knew we needed for
             cross-process work.

             The Router stays as a useful component for hub patterns
             (e.g. the WFM with one Terminal per user order) but is
             now structurally a Dispatcher-plus-Terminals, not a
             monolith.

RATIONALE:   - Clean concern separation: matching vs transport vs
               peer-management.
             - Dispatcher reused in two contexts; one filter API to
               learn.
             - Channel ABC enables transport substitution without
               touching consumer code; ProcessQueue / Remote channels
               can be added without changing the Terminal/Router
               surface.
             - EventTerminal is the SAME class regardless of
               transport - the ECP carries the variation.

ALTERNATIVE: Earlier proposal had EventRouter derived from
             EventTerminal. Rejected: a Terminal is one peer, a Router
             is a hub of peers; the IS-A relationship is wrong.

ENFORCE_ASYNC_CALLBACKS_F:
             A Dispatcher constructed with this flag rejects sync
             callable sinks at subscribe time. The Terminal's receive-
             side Dispatcher uses this mode because slow sync callbacks
             on the receive loop would block further Event delivery.
             Object-with-.send sinks are still accepted (the consumer
             can push to a thread Queue and process there).

SOURCE FILTERING:
             EventRouter.add_terminal accepts an optional
             source_terminal_list. Used to prevent forwarding loops
             ("don't send Network events back out the Network
             Terminal they came from"). publish_from(src, ev) tags
             the event with its origin for the duration of the
             dispatch; publish(ev) is equivalent to publish_from(None,
             ev). None in the source_terminal_list means "matches
             local publish() calls".


--------------------------------------------------------------------------------
DECISION 12 - When a Channel ends, the transport ends
--------------------------------------------------------------------------------

DECISION:    There is no transport-layer notion to maintain past the
             Channel's lifetime. close() on a Channel shuts down its
             underlying transport (closes queues, drops sockets); the
             peer detects this as receive() returning None.

RATIONALE:   End-to-end clarity. Avoids the complexity of a "transport
             that survives Channel close" abstraction that would have
             no clear consumer. If a peer wants to reconnect, it
             constructs a new ECP/Channel/Terminal triple.


--------------------------------------------------------------------------------
DECISION 13 - Event registration is gated by an explicit category context
--------------------------------------------------------------------------------

DECISION:    Event subclasses must be declared inside a
             `with category("NAME"):` block. The block stamps each
             enclosed class with its .category and composite .id
             ("<category>.<__name__>"). Declaring outside any open
             block raises EventDefinitionOutsideCategoryContext.

             E_EventCategory (the closed enum) is gone. Categories
             are user-defined strings. Multiple files may contribute
             to the same category. The dispatch table CLASS_BY_ID is
             a flat dict keyed by composite id.

             Event.lock_registration() seals the registry; after
             lock, opening a category or defining an Event raises
             EventRegistrationLocked. The lock is one-way (no
             unlock).

RATIONALE:   The previous model had .category as a ClassVar declared
             on every subclass. This made categories closed (one
             enum, system-wide) and forced every subsystem's events
             into a central enum file. The category context manager
             flips this: categories are an open vocabulary, and the
             file declaring an event is also the file that says
             which category it belongs to.

             The lock catches a real failure mode: a late import
             registering an event after the event vocabulary should
             be sealed. Without a lock, this is silent and detectable
             only by mysterious "unknown id" errors during
             deserialisation. With the lock, the late import fails
             at the point of definition.

             CLASS_BY_ID is FLAT (not nested by category). The
             Marshaller has the composite id in hand from the wire
             envelope; one dict access is enough. A nested structure
             would need parse-and-walk on every deserialise. The
             per-category enumeration use case is rare and served
             by events_in_category() which walks the flat dict once.

NAMING:      The context manager is plain `category("NAME")`. The
             flag method is `lock_registration()`. The exception is
             `EventDefinitionOutsideCategoryContext` (verbose but
             unambiguous - this exception names a specific
             programmer error).

WIRE IMPACT: The wire id becomes composite ("WORKFLOW.EventTaskDone"
             rather than "EventTaskDone"). Slightly longer; the
             readability is worth it, and string comparison in
             CPython is fast enough that the extra bytes do not
             matter at the speeds we expect.


--------------------------------------------------------------------------------
DECISION 14 - The event package ships no application events
--------------------------------------------------------------------------------

DECISION:    events.py contains only EventTerminalUp and
             EventTerminalDown, both in category EVENT_INFRA. These
             are wire-level lifecycle messages used by the Terminal
             handshake. All application events (workflow, compile,
             network, test, diagnostic) are declared by their owning
             subsystems in their own modules.

             The event package is a TOOLKIT, not a registry of
             application events.

HISTORY:     Earlier iterations of events.py shipped 10 events for
             the WORKFLOW and COMPILATION categories. These were
             placeholders; they belonged to subsystems that did not
             yet exist. Carrying them in the event package coupled
             the package's evolution to subsystems it should not
             know about.

RATIONALE:   The event package owns IDENTITY, DISPATCH, and
             TRANSPORT. It does not own the catalog of what events
             exist in any particular VUT build. Subsystems own their
             event vocabularies; the event package provides the
             mechanism to declare and route them.

             The only exception is EVENT_INFRA - events the event
             package itself produces, ABOUT ITSELF. These cannot
             live anywhere else without making the event package
             depend on something downstream.

TEST IMPACT: Tests that previously imported the shipped application
             events now declare their own under test-local category
             names (TEST_LOCAL_DISPATCHER, TEST_LOCAL_TERM_TASK,
             etc.). Tests are now self-contained: each declares
             the event vocabulary it needs.


--------------------------------------------------------------------------------
DECISION 15 - Terminals exchange a symmetric Up / Down handshake on the wire
--------------------------------------------------------------------------------

DECISION:    Each EventTerminal participates in a wire-level
             lifecycle protocol with its peer using two EVENT_INFRA
             events:

                 EventTerminalUp    sent on receive-loop entry
                 EventTerminalDown  sent on deliberate stop()

             start() blocks in state UP_PENDING until the peer's Up
             arrives, then transitions to UP. The protocol is
             symmetric: each side sends Up on receive-loop entry and
             waits for the other side's Up. No client/server role.
             Both sides must `start()` concurrently (use
             asyncio.gather); sequential `await a.start(); await
             b.start()` deadlocks.

             stop() sends Down to the peer before closing the
             channel. Down receives NO reply; the side that sent it
             is gone. The peer's receive loop sees the Down and
             exits cleanly.

             EVENT_INFRA events received from the peer are handled
             INTERNALLY by the Terminal and are NOT forwarded to the
             user's .dispatcher. To learn about a peer going down,
             register set_peer_down_callback(). The EventRouter
             uses this callback to auto-remove an entry when its
             peer disconnects.

RATIONALE:   A Terminal that connects without confirming the peer
             exists is unsafe; sends may go into a queue with no
             reader. The blocking handshake catches the "peer never
             arrived" case at start time rather than at first send.

             The symmetric protocol is the simplest version that
             actually works. Asymmetric "client connects, server
             accepts" protocols add complexity for no real benefit -
             both sides need each other equally, and both sides
             know to call start().

             Down is best-effort. If the channel is already broken
             when stop() tries to send Down, the failure is logged
             and ignored. The peer detecting "channel.receive()
             returned None" is the fallback signal.

             EVENT_INFRA events not reaching .dispatcher is a
             deliberate choice. Lifecycle is the Terminal's own
             state machine; passing infra events to user handlers
             would invite users to write their own lifecycle logic
             that fights with the Terminal's. The peer-Down callback
             is the one exposed hook, and only because the Router
             needs it.

CONTEXT MANAGER:

             The Terminal supports `async with EventTerminal(ecp)
             as t:`. start() runs on enter; stop() runs on exit,
             whether normal or via exception. Both forms (explicit
             start/stop and context manager) are supported because
             different call sites prefer different shapes.


--------------------------------------------------------------------------------
DECISION 16 - Encryption is a pluggable Cipher inside the Channel
--------------------------------------------------------------------------------

DECISION:    Encryption for serialising channels is a pluggable
             strategy object, the Cipher (cipher.py). The Channel
             delegates the per-message transform to it:

                 async handshake(raw_send, raw_recv)
                 encrypt(blob: bytes) -> bytes
                 decrypt(blob: bytes) -> bytes

             The default IdentityCipher is a pass-through (no
             encryption, no-op handshake). Four implementations ship:
             IdentityCipher, FernetCipher (symmetric,
             cryptography.fernet), NaClBoxCipher (public-key, PyNaCl
             Box), TLSCipher (ssl.SSLObject in memory-BIO mode).

             A Cipher operates on BYTES, between serialisation and
             transport. It is meaningful only for the serialising
             channels - ProcessQueueChannel and RemoteChannel.
             In-process channels (Async, Thread) move live Event
             objects, never serialise, and always use IdentityCipher.

             The crypto handshake runs INSIDE the channel's connect(),
             which make_channel() calls before returning. The channel
             is fully secured before the Terminal ever sees it; the
             Terminal is entirely unaware of the Cipher.

             Cipher is NOT exported from the event package's
             __init__. It is a channel-internal concern. Users
             configure encryption indirectly, by passing a CipherSpec
             to a channel-parameter factory.

WHY THE CHANNEL, NOT THE MARSHALLER:

             The Marshaller's job is Event <-> wire-dict. Encryption
             is a property of the TRANSPORT - it belongs with the
             thing that moves bytes between endpoints. Putting crypto
             in the Marshaller would force every channel, including
             the in-process ones, to carry machinery they cannot use.

WHY A STRATEGY OBJECT, NOT A WRAPPER CHANNEL:

             A wrapper Channel would have to re-implement the full
             EventChannel ABC (send, receive, close) just to insert
             two byte transforms. The Cipher member inserts exactly
             those two transforms (plus a handshake) and nothing
             else - less surface, less to get wrong.

THE ECP CARRIES A RECIPE, NEVER A SECRET:

             A Cipher must reach spawned channels (Process, Remote)
             via the EventChannelParameter. The ECP carries a
             CipherSpec - kind plus a key REFERENCE (env-var name,
             file path), never key bytes. CipherSpec.build() resolves
             the reference LOCALLY, on whichever side constructs the
             channel.

             Rationale: a secret inside a pickled ECP leaks (pipe
             buffers, swap, logs); for for_remote() a key carried in
             the ECP would be transmitted over the very channel it
             secures. The ECP only NAMES the key; deployment
             provisions it. Key distribution to remote machines is
             out of scope for the event component.

SECRECY IS NOT IDENTITY:

             An ephemeral key exchange with no pre-shared anchor
             gives a CONFIDENTIAL channel with an ANONYMOUS peer: an
             attacker in the middle can handshake with each side
             separately and read everything, and both sides still
             see "encrypted". Authentication requires a pre-shared
             anchor - a shared key, a pinned peer public key, or a
             verified certificate.

                 FernetCipher pre-shared key      -> authenticated
                 FernetCipher ephemeral only      -> encrypted, NOT
                                                     authenticated
                 NaClBoxCipher pinned peer key    -> authenticated
                 NaClBoxCipher unpinned           -> encrypted, NOT
                                                     authenticated
                 TLSCipher with cert verification -> authenticated

             For local transports (Process, Thread) identity does
             not matter - there is no wire to sit on. For
             RemoteChannel it does. cipher.py's module header states
             this so a future reader does not pick an unauthenticated
             configuration thinking it is merely the weakest option
             rather than a qualitatively different one.

HANDSHAKE IS BELOW THE EVENT LAYER:

             The Cipher handshake exchanges raw bytes, NOT Events,
             over raw_send / raw_recv primitives the Channel supplies.
             It must be below the Event layer: an Event cannot be
             sent securely until the Cipher is up, so the handshake
             that establishes the Cipher cannot itself be Event-based.

TLS NOTES:

             TLSCipher stores its ssl.SSLContext and runs the TLS
             handshake in memory-BIO mode (ssl.SSLObject), so it fits
             the bytes-in/bytes-out shape like any other Cipher. Two
             caveats, documented in code: (a) the TLS listen end
             needs server_side=True and the connect end
             server_side=False, so a TLS for_remote() pair generally
             needs different specs per end - symmetric ciphers
             (Fernet, NaCl) do not have this asymmetry; (b) TLS
             records do not map one-to-one onto application messages,
             so a production TLSCipher would buffer - the shipped
             implementation targets the common case where a message
             fits the record machinery.

TESTING:     test-cipher.py exercises all four ciphers (round-trips,
             handshakes, the NaCl pinned-key mismatch) and the
             channel-level integration through make_channel().
             TLSCipher is not in the suite - it needs a certificate
             pair on disk, the same reason RemoteChannel is not
             exercised. Add an integration test when a real
             remote+TLS deployment exists.


--------------------------------------------------------------------------------
THINGS LEFT OPEN
--------------------------------------------------------------------------------

1. Tuple-composite event ids (E_Entity, E_Event). Worth revisiting
   if/when federation problems bite.

2. Versioning machinery. Worth revisiting if/when persistent storage
   or cross-build replay becomes required.

3. Workload-id field on Event. Will be added when workloads exist
   and predicates need them.

4. Dynamic startup-phase specialist registration on Marshaller. The
   classmethod structure is ready for it; no machinery built.

5. RemoteChannel has not been exercised in the test suite (its
   transport requires actual TCP sockets and is more complex to
   test in isolation). The wire format is covered indirectly via
   Marshaller tests. When the first real remote consumer exists,
   add an integration test.

6. The Router's source_terminal_list feature is implemented and
   tested but no actual subsystem uses it yet. The mechanism is
   there for when a network-incoming Terminal feeds the Router that
   also feeds network-outgoing Terminals.

7. Construct (https://construct.readthedocs.io) is flagged in the
   Marshaller module header as a natural fit for binary specialist
   serialisation, complementing Pydantic's structured-data
   validation. Not built; revisit when an event type's wire size
   shows up in profiling.

8. Peer authentication during the Terminal handshake. The Up/Down
   handshake currently confirms a peer is THERE, not WHO it is.
   When a Cipher provides authentication (pre-shared key, pinned
   peer key, verified certificate) the peer is authenticated at the
   Cipher layer below. Without such a Cipher, RemoteChannel has no
   peer-identity check. A token exchanged in EventTerminalUp, or a
   challenge-response, would add identity at the Terminal layer -
   not built.

9. TLSCipher record buffering. The shipped implementation assumes
   each application message fits the TLS record machinery in one
   pass. A production version would buffer partial records across
   encrypt/decrypt calls. Revisit if TLSCipher moves past
   integration-test use.

10. String interning / token-substitution for repeated long strings
    (file paths, identifiers) on the wire. Simplest form: a
    build-time-constant shared table, no negotiation. Dynamic
    interning needs a token-assignment protocol and defined
    behaviour for unknown tokens. Deferred until a wire-size
    profile justifies it; grouped with the Construct note as a
    wire-size optimisation.
