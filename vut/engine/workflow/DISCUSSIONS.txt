DISCUSSIONS — workflow component (append-only)
================================================================================

2026-06-12  Rationale displaced from README during topology rewrite
--------------------------------------------------------------------------------

MOTIVATION (formerly README header). Original driver: coordinate and
trace generation plus execution of HWUT unit tests so that the complete
process is part of the test. Errors in construction and code generation
become part of the failure. Result: a unit-test framework stable under
unstable test applications.

BARE USER TERMINAL. Problem: the user needs a report channel and a
cancellation handle. Earlier design: a UserComHandle carrying a report
queue plus a termination signal. Idea: the plain EventTerminal subsumes
both — '.dispatcher' is the report channel, '.stop()' plus the WFM-side
peer-down callback is the cancellation. Cost: cancellation intent is
inferred from channel teardown; a transport failure that drops the
channel is indistinguishable from a deliberate cancel. Mitigation: at the
user boundary the two collapse to the same correct reaction — stop
working for a listener that is gone.

NO ECHO ON CANCEL. No closing Event after '.stop()': the user's own
action needs no confirmation, and the destination terminal is already
gone. Cost: none at the user boundary; a supervisory observer wanting
cancel confirmations must subscribe elsewhere (EventTargetCancelled on
another order's terminal does not exist — open point if ever needed).

SELECTOR / SUPERVISOR SPLIT. Problem: "run the runnable tasks" mixes a
policy decision (which, how many, in what order) with mechanism
(spawning, watching, aborting). Idea: TaskSelector decides, TaskSupervisor
executes; the interface between them is a list of task ids. Cost: one
extra component and hand-off. Mitigation: strategies (FIFO,
most-blocking-first, fail-fast, CRM) become drop-in TaskSelector
subclasses without touching supervision.

KLEENE THREE-VALUED DEPENDENCY LOGIC. Problem: at evaluation time some
artifact states are not yet decided; two-valued logic forces premature
false. Idea: UNKNOWN as first-class value lets 'false and unknown'
short-circuit to false (task NEVER runnable) while 'true and unknown'
stays open (NOT_YET). Cost: every expression node carries three-valued
truth tables. Mitigation: confined to the dependency-expression nodes;
nothing outside the DependencyGraph sees UNKNOWN.

ALTERNATIVES VIA SHARED PRODUCTS (decision recorded during rewrite).
RecipeKnower.get_tasks() returns alternative solutions as list-of-lists;
Workload.tasks flattens them. The alternative structure is not stored on
the Workload: it is equivalent to "several tasks produce the same
artifact", which tasks_by_product_db expresses already. Cost: the
original grouping into named solutions is lost after workload assembly.
Mitigation: none needed so far; revisit if per-solution selection or
reporting is wanted.
