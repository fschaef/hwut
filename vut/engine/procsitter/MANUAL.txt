______________________________________________________________________________

1  PURPOSE: THE SUPERVISED SYSTEM CALL
______________________________________________________________________________

PLACE ON THE MAP:

    .-------------------------------------------------------------.
    |  OUTER BOUNDARY (administrator: container, VM, ...)         |
    |  security, isolation, reproducibility                       |
    |                                                             |
    |    .----------------------------------------------------.   |
    |    |  HWUT session                                      |   |
    |    |                                                    |   |
    |    |   .-------------.  .-------------.  .----------.   |   |
    |    |   | supervised  |  | supervised  |  |supervised|   |   |
    |    |   | call:       |  | call:       |  |call:     |   |   |
    |    |   | test app    |  | pype stage  |  |'make'    |   |   |
    |    |   '-------------'  '-------------'  '----------'   |   |
    |    '----------------------------------------------------'   |
    '-------------------------------------------------------------'

The procsitter is HWUT's replacement for 'subprocess'. EVERY subprocess
goes through it: test applications, build and helper tools ('make',
'scp', maintenance scripts), pype stages. One primitive -- the
SUPERVISED SYSTEM CALL -- is the ground; everything else is built upon
it in a lightweight manner:

    APPLICATIONS      test runs, supervised builds, helper scripts
    (ELSEWHERE)       -- each one an ARRANGEMENT of the two levels
                         below, and none of this component's business
                                       |
                    +------------------+------------------+
    COMPOSITION     |   construction.py                   |
                    |   Link, tee(), chain()              |
                    +------------------+------------------+
                                       |
                    +------------------+------------------+
    THE GROUND      |   procsitter.py                     |
                    |   Procsitter.run() -- containment   |
                    |   + attribution                     |
                    +-------------------------------------+

A supervised call CONTAINS the unintentional misbehavior of the process --
endless loops, hangs, runaway memory, fork bombs, disk flooding -- and
ATTRIBUTES it: the call dies alone, the session survives, and the record names
the exhausted resource.

    without supervision:                with supervision:

    'make' of test #317 hangs           'make' of test #317 hangs
        |                                   |
        v                                   v
    the whole session hangs             call: FAIL_WALL_CLOCK_EXCEEDED
    "job timed out" -- where?           after 60.0 s -- attributed;
                                        session continues

The supervision's limits are defined by the following 'No-s'. It is:

 -- NOT A SECURITY BOUNDARY against malice.

 -- NO ISOLATION (no namespaces, no read-only roots, no private network
    stacks).

 -- NO CHECK OF ENVIRONMENTAL NEEDS (network connection, GPU, etc.).

Those concerns belong to the ADMINISTRATOR, who chooses the outer boundary --
container, VM, dedicated runner -- independently of this level.

The procsitter is PLATFORM-INDEPENDENT: one implementation, python 'stdlib' plus
'psutil', no wrapper binaries, no per-OS backends. A cap the platform cannot
enforce is REPORTED in the result, never silently ignored (section 6).


2  QUICK START
______________________________________________________________________________

EXAMPLE USAGE:

    import asyncio
    from   vut.engine.procsitter.procsitter import Procsitter, ProcsitterConfig

    async def main():
        procsitter = Procsitter(ProcsitterConfig(max_wall_clock_sec=120.0),
                                work_dir="build/")
        result     = await procsitter.run(["make", "-j4", "all"])
        if result.containment is not E_Containment.OK_COMPLETED:
            print("make failed:", result.containment.name,
                  result.exit_code)

    asyncio.run(main())

The same primitive runs 'scp backup.tar host:', a generator script, or a test
application. The result of the call is reported in 'result.containment':

   -- E_Containment.OK_COMPLETED: successfull execution.
   -- E_Containment.FAIL_<name>:  error containment of type '<name>'.


3  MODEL
______________________________________________________________________________

Execution follows the following scheme:

    ProcsitterConfig        "what may this call do?"      CONTRACT
       |
       v
    Procsitter.run(...)     "run it, supervised"          EXECUTION
       |
       v
    ProcsitterResult        "what happened, and why?"     ATTRIBUTION RECORD

There is ONE concrete Procsitter class -- no platform hierarchy, no factory.
What varies per platform is enforcement strength, and that variance is
reported, not classed (section 10).

Consumption of the process's output is NOT the procsitter's concern: 'run()'
hands output chunks to caller-provided handlers. What the handlers do --
discard, log, feed another supervised call, feed the comparison engine -- is
composition ABOVE the ground (sections 7, 8).


4  CONFIGURATION: THE CAPS
______________________________________________________________________________

'ProcsitterConfig' is the per-call contract, and every field in it is a
CAP the procsitter ENFORCES:

    field                meaning
    -------------------  ----------------------------------------------------
    max_wall_clock_sec   total run time--hang-catcher: e.g. a process blocked
                         on a dead socket burns no CPU; only wall clock
                         catches it.
    max_cpu_time_sec     CPU seconds (RLIMIT_CPU).
    max_memory_mb        resident memory, summed over the whole process GROUP
                         (watchdog).
    max_pids             process count of the group.
    max_file_size_mb     size cap PER created file (RLIMIT_FSIZE).
    max_disk_mb          TOTAL allocation under work_dir (watchdog, st_blocks):
                         the many-files loop RLIMIT_FSIZE cannot see.
    min_free_disk_mb     FREE-SPACE FLOOR of work_dir's filesystem. Below it
                         the call is terminated so the OPERATING SYSTEM stays
                         operable.

Any cap hit terminates the supervised process. The result names the cap that
triggered. A cap the running platform cannot enforce is REPORTED in
'.unenforced' -- never silently dropped.

Default values can be examined in dataclass 'ProcsitterConfig'.

5  THE SUPERVISED CALL
______________________________________________________________________________

    async def run(self,
                  command:        Sequence[str],
                  stdout_handler: async callable(bytes) | None = None,
                  stderr_handler: async callable(bytes) | None = None,
                  stdin_reader:   asyncio.StreamReader  | None = None,
                  stop_event:     asyncio.Event         | None = None
                  ) -> ProcsitterResult

'command' is the argv SEQUENCE -- [program, arg, ...] -- executed DIRECTLY (no
shell) in 'work_dir'.

'stdout_handler', 'stderr_handler' receive output chunks as they arrive; a
channel without a handler is DRAINED (a full OS pipe would block the child).

'stdin_reader', if given, is piped into the child's stdin and closed at its EOF.

'stop_event', when set terminates the run from outside (FAIL_STOPPED).


Anatomy of one supervised call:

    launch      preexec hook (child, POSIX): own process group
    |           (setsid) + rlimits: CPU time, file size
    |
    |  +------------------ concurrently ---------------------------+
    |  |  stdout pump ----> stdout_handler (or drain)              |
    |  |  stderr pump ----> stderr_handler (or drain)              |
    |  |  stdin  pump <---- stdin_reader (optional)                |
    |  |  stop watcher ---- kills on stop_event                    |
    |  |  WATCHDOG (every 0.25 s):                                 |
    |  |      wall clock over cap?          -> kill, attribute     |
    |  |      group RSS over cap?           -> kill, attribute     |
    |  |      group member count over cap?  -> kill, attribute     |
    |  |      records peaks; registers every descendant seen       |
    |  |      process exited but children linger > 1 s? -> reap    |
    |  +-----------------------------------------------------------+
    |
    teardown    ALWAYS runs (try/finally): kill ladder if needed,
    |           tasks cancelled, stdin transport closed, post-mortem
    |           sweep of observed descendants (pid + create-time
    |           guarded -- no pid-reuse accidents)
    v
    ProcsitterResult

NOTE:__________________________________________________________________________
Teardown is CANCELLATION-PROOF. If the run is INTERRUPTED mid-flight -- Ctrl-C,
or a logout tearing the harness down -- the child would otherwise survive: it
setsid'd into its own session, so nothing else would reap it, and such orphans
accumulating across runs exhaust the per-user process table (the accident that
eventually LOGS A DEVELOPER OUT). So on an interrupt the group is hard-killed
SYNCHRONOUSLY (group + leader, no await to be stolen) and swept. A module-level
atexit backstop killpg's any group a dying harness leaves registered; only a
SIGKILL of the harness itself can defeat that (no process can catch it) -- that
residue is the outer boundary's concern.
_______________________________________________________________________________


The KILL LADDER, used by every containment and by stop_event:

    SIGTERM to the process GROUP
        |
        |  2 s grace
        v
    SIGKILL to the process GROUP
        |
        v
    sweep: any observed descendant that escaped the group is killed

    (an INTERRUPTED run skips the grace: SIGKILL at once, group AND
     leader, synchronously -- no leak even mid-cancellation.)

The straggler rule deserves emphasis: children INHERIT the output pipes. A
process that exits while its forked child sleeps on would hold the harness's
stdout pump open indefinitely -- the watchdog reaps such stragglers one second
after the main process is gone. No call can leave processes behind, and no
call's leftovers can stall a pipeline.

Misbehavior of the CALLED PROCESS never raises -- it is a RESULT. 'run()'
raises only on HARNESS faults: an exception inside a caller-provided handler
(the process is killed, nothing leaks, then the exception surfaces); an
impossible spawn is reported as FAIL_LAUNCH.


6  THE ATTRIBUTION RECORD
______________________________________________________________________________

The result of an execution is reported in a 'ProcsitterResult':

    .containment      E_Containment  THE VERDICT: OK_* vs FAIL_*
    .exit_code        int | None     process's own exit code;
    .wall_clock_sec   float          measured
    .cpu_time_sec     float | None   measured (getrusage delta, watchdog fallback)
    .peak_memory_mb   float | None   group peak (watchdog)
    .peak_pids        int | None     peak process-group member count (watchdog)
                                     => reason for 'FAIL_PIDS_EXCEEDED'
    .peak_disk_mb     float | None   peak allocation under work_dir
                                     => reason for 'FAIL_DISK_USAGE_EXCEEDED'
    .stderr_last_100_lines str       last 100 LINES of stderr, captured when
                                     no stderr_handler was given.
                                     => reason for nonzero exit.
    .unenforced       tuple[str]     caps this platform could not
                                     enforce -- honest reporting

Containment Overview:

    E_Containment            fired by                  typical accident
    -----------------------  ------------------------  ----------------
    OK_COMPLETED             exited by itself, code 0  (success)
    FAIL_COMPLETED           exited by itself, code    the app's own
                             != 0 (incl. signal death) failure/crash
    FAIL_WALL_CLOCK_EXCEEDED watchdog                  hang, deadlock
    FAIL_CPU_TIME_EXCEEDED   kernel, SIGXCPU           endless loop
    FAIL_MEMORY_EXCEEDED     watchdog (group RSS)      leak, hoard
    FAIL_FILE_SIZE_EXCEEDED  kernel, SIGXFSZ           one huge file
    FAIL_PIDS_EXCEEDED       watchdog (group count)    fork bomb
    FAIL_DISK_USAGE_EXCEEDED watchdog (work-dir walk)  many-files flood
    FAIL_DISK_SPACE_LOW      watchdog (free-space      filesystem near
                             floor)                    full (OS at risk)
    FAIL_STOPPED             external stop_event       (fast-fail)
    FAIL_LAUNCH              spawn impossible          bad command

A 'OK_COMPLETED' means that the run was successful, given that the caps of
'.unenforced' were not considered.

Two subtleties, both deliberate:

  - An application that IGNORES SIGXFSZ, e.g. CPython:
    => receives EFBIG from write() at the file-size cap
    => fails by its own exception.
    => Containment reads FAIL_COMPLETED with a nonzero exit code.
    Cap triggers, but with differing message.

  - Possible race:
    Fork bomb death by the NPROC rlimit (fork fails inside the process)
    against by the watchdog's group count.


7  CONSTRUCTION: LINK, tee(), chain()
______________________________________________________________________________

A 'Link' links channels, such as an 'stdout' as source and 'stdin' as a drain.
It is unaware of processes, procsitting etc..

There are three composition blocks -- 'Link', 'tee()', 'chain()' -- and no
class beyond them. Everything in sections 8 and 9 is built from these.


7.1  THE LINK

    link = Link()
    A.run(argv_a, stdout_handler = link.feed)    # A produces
    B.run(argv_b, stdin_reader   = link.reader)  # B is fed

         .--------. link.feed         link.reader .--------.
         | call A |-------------> o ------------->| call B |
         '--------'             Link              '--------'
          own caps,                                own caps,
          own record                               own record


7.2  tee() -- FAN-OUT

A consumer is a plain async function, and functions ADD. 'tee()' is the sum
of consumers: ANYONE MAY LISTEN to a production port.

    B_in, C_in = Link(), Link()
    A.run(argv_a, stdout_handler = tee(B_in.feed, C_in.feed))

    # A's stdout ---+---> B's stdin
    #               '---> C's stdin

The reverse does not exist: two productions cannot merge into one control
port deterministically -- ONE VOICE COMMANDS.


7.3  chain() -- THE PIPELINE

    c = chain([(a, argv_a), (b, argv_b), (d, argv_d)],
              stdin_reader=None)

    c.tail          Link: the chain's production end
    c.stop_event    stops every stage at once
    c.task_tuple    one task per stage

    records = await asyncio.gather(*c.task_tuple)      # per stage

       .---------. Link .---------. Link .---------.  Link: .tail
       | stage 0 |----->| stage 1 |----->| stage 2 |--------------> consumer
       '---------'      '---------'      '---------'
        own record       own record       own record

The three rules:

(1) EOF ONWARD: a stage that ends closes its outgoing Link.

(2) STOP ON EARLY DEATH: a stage ending while an UPSTREAM stage still
    runs sets the shared stop_event.

    SIGPIPE semantics, supervised; this is also what BOUNDS MEMORY,
    since an in-memory 'feed' never blocks; else, an upstream would
    fill a dead chain's buffer without limit.

(3) EVERY STAGE ACCOUNTED: one task per stage, gathered.

A chain's first stage may itself drink from a Link ('stdin_reader='):
recorded input, or a dialogue's back-edge.


7.4  LISTENING TO A PRODUCTION

A stage's THIRD tuple element carries extra keyword arguments into that
stage's 'run()'. A 'stdout_handler' among them does NOT replace the chain
edge -- it is TEE'd with it. The production reaches the next stage AND the
listener.

    c = chain([(ps_0, argv_0, {"stdout_handler": tap}),
               (ps_1, argv_1)])

       .----------.  tee  .----------.
       | stage 0  |---+-->| stage 1  |------> c.tail   (transformed)
       '----------'   |   '----------'
                      '-> tap                          (raw)

Within the tee the chain edge is fed FIRST, the listener second: a failing
tap never starves the pipeline of a chunk.

EXAMPLE: a log tap -- a listener is a plain async function.

    log_f = open("raw.log", "wb")
    async def tap(data):
        log_f.write(data)

    c       = chain([(ps_0, argv_0, {"stdout_handler": tap}),
                     (ps_1, argv_1)])
    records = await asyncio.gather(*c.task_tuple)
    log_f.close()

EXAMPLE: an eavesdropper -- a listener that is a Link.

    raw = Link()
    c   = chain([(ps_0, argv_0, {"stdout_handler": raw.feed}),
                 (ps_1, argv_1)])

    async def eavesdrop():
        while not raw.reader.at_eof():
            chunk = await raw.reader.read(4096)
            ...

    listener = asyncio.create_task(eavesdrop())
    try:     records = await asyncio.gather(*c.task_tuple)
    finally: raw.close()
    await listener

THE TWO RULES OF A LISTENER:

(1) CONSUME IT. An unread Link buffers without bound.

(2) CLOSE IT. 'chain()' closes ITS OWN edges (rule 1 of 7.3). A listener's
    Link is no edge, so the chain never closes it: 'raw.reader.at_eof()'
    stays False and an eavesdropper waiting for EOF waits forever. Close
    it after the stages are gathered.

Listeners ADD, like any consumer:

    {"stdout_handler": tee(raw.feed, tap)}


7.5  THE EXTRA KEYWORD ARGUMENTS

    key              in a chain stage
    ---------------  ---------------------------------------------------
    stdout_handler   a LISTENER, tee'd with the chain edge (7.4)
    stderr_handler   passed VERBATIM -- stderr is no chain edge. Wiring
                     it REPLACES the ground's default capture: that
                     stage's '.stderr_last_100_lines' stays empty.
    stdin_reader     THE CHAIN'S -- the upstream stage feeds it.
                     For the first stage: chain(..., stdin_reader=...)
    stop_event       THE CHAIN'S -- shared by every stage.
                     Across chains:      chain(..., stop_event=...)

An owned key in a stage's extra kwargs is a wiring mistake; 'chain()'
asserts on it at construction, where it is written.

EXAMPLE: a stage's stderr, read live.

    err = Link()
    c   = chain([(ps_0, argv_0, {"stderr_handler": err.feed}),
                 (ps_1, argv_1)])
    ...
    try:     records = await asyncio.gather(*c.task_tuple)
    finally: err.close()                     # no edge -- 7.4, rule 2


7.6  MAN IN THE MIDDLE (interaction)

A controller C riding a subject A -- answering its prompts on stdin while a
consumer B keeps listening undisturbed -- is no new primitive. It is a CYCLE
in the graph: production is tee'd, control is answered.

    A.stdout --tee--> to_B.reader   (B: any consumer -- a filter, a log)
                 '--> to_C.reader
    C.stdout -------> back.reader --> A.stdin

    A and C are symmetric peers; B is a third listener on the sum.

    to_c, back = Link(), Link()
    async def run_subject():
        try:     return await A.run(argv,
                     stdout_handler=tee(consumer, to_c.feed),   # + B
                     stdin_reader  =back.reader)
        finally: to_c.close()        # A gone -> C sees EOF
    async def run_controller():
        try:     return await C.run(ctrl_argv,
                     stdin_reader  =to_c.reader,
                     stdout_handler=back.feed)
        finally: back.close()        # C gone -> A stdin EOF
    a_record, c_record = await asyncio.gather(run_subject(),
                                              run_controller())

Two supervised calls, two attribution records: contained on BOTH ends. The
controller may equally be a pype script in its own procsitter --

    ctrl_argv = ["python3", "-u", "tools/hwut_pype/hwut_pype.py",
                 "dialogue.pype"]
    # dialogue.pype -- the subject asks, pype answers:
    #     on: "capital-of-france" => {
    #         print("paris")
    #     }
    #     on: <else> => ignore;

-- the SAME wiring, nothing special. Note the '-u': a supervised answerer's
output must be UNBUFFERED; a buffered answer never arrives and the dialogue
stalls until a wall clock strikes. A dialogue deadlock is an accident like
any other; the caps contain it.

stderr is read from EACH call's own record by default (the last-100-lines
capture); to read it live, wire a Link onto 'stderr_handler' -- identical to
stdout, no flag.


8  PLATFORMS AND DEGRADATION
______________________________________________________________________________

    mechanism                Linux  macOS  BSDs   Windows
    -----------------------  -----  -----  -----  -------
    wall clock + RSS + pid
      watchdog (psutil)        +      +      +       +
    rlimits: cpu, fsize
      ('resource')             +      +      +       -
    process-group kill         +      +      +      (single
                                                    process)
    everything reported        +      +      +       +

Dependencies: python stdlib + 'psutil'. Without psutil the RSS and
pid-count caps are off and REPORTED ('.unenforced'); wall clock and
rlimits keep working. Without 'resource' (Windows) the kernel caps are
off and reported; the watchdog carries wall clock and memory.

Deliberate non-choices, so nobody re-litigates them:

  - RLIMIT_AS is NOT used: it breaks interpreters that reserve large
    virtual address spaces. Memory containment is RSS-watchdog-based;
    the ~0.25 s poll is adequate against accidents -- adversaries are
    out of scope by definition.
  - RLIMIT_NPROC is NOT used: it caps processes per REAL USER ID --
    system-wide, not per-call. Set from a point-in-time snapshot it
    STARVES a legitimate build the instant unrelated processes of the
    same user push the global count past the snapshot (on a busy
    desktop: a build fork returns EAGAIN, "Resource temporarily
    unavailable", and the tool dies mid-build). THE process-count cap
    is the watchdog's group-member count -- correctly scoped to the
    call's own group. The one-poll blind spot (a burst between polls)
    is an accident the watchdog then contains; adversaries are out of
    scope.


9  RELATION TO HWUT TESTING
______________________________________________________________________________

The component's own suite (TEST/) follows the standard scheme:
'config.py' bootstraps sys.path (walks up to 'vut/'), test files begin
with 'from config import HwutRunner', choices per accident class,
outputs baselined in GOOD/. Two rules learned there, worth keeping for
every test that uses the procsitter:

  - Assert NORMALIZED outcomes where mechanisms race (section 6): the
    GOOD file must hold on every platform and every run.
  - Silence asyncio's logger warnings in the harness
    ('logging.getLogger("asyncio").setLevel(logging.ERROR)'):
    child-reap races may emit spurious, nondeterministic lines.


10  QUICK REFERENCE
______________________________________________________________________________

THE GROUND -- every subprocess, always:

    Procsitter(config, work_dir)
    await procsitter.run(argv, stdout_handler=..., stderr_handler=...,
                      stdin_reader=..., stop_event=...) -> ProcsitterResult
                      # argv = ["make", "-j4", "all"] -- no escaping

    result.containment           E_Containment: OK_COMPLETED
                                 is success; every FAIL_* a fault
    result.containment           E_Containment (section 6)
    result.unenforced            caps the platform cannot enforce

COMPOSITION -- pipelines of supervised calls:

    link = Link()         upstream stdout_handler = link.feed
                                 downstream stdin_reader = link.reader

    c     = chain([(procsitter_a, argv_a),
                   (procsitter_b, argv_b)],
                  stdin_reader=...)          # optional: stage-0 control
    c.tail.reader            the chain's production end -- a Link is
                                 THE interface toward any consumer
    await asyncio.gather(*c.task_tuple)  # one record PER STAGE

    to_c, back = Link(), Link()              MAN IN THE MIDDLE, pure
    subject.run(argv,                        composition: production
        stdout_handler=tee(consumer,         tee'd (consumer keeps
                           to_c.feed),       listening), control
        stdin_reader  =back.reader)          answered. controller =
    controller.run(ctrl_argv,                any second procsitter,
        stdin_reader  =to_c.reader,          e.g. pype with 'python3
        stdout_handler=back.feed)            -u' (unbuffered).
    # + finally: to_c.close() / back.close() consumers ADD; one voice
    #                                        commands.

Rules of thumb:
  - Route EVERY subprocess through the procsitter -- 'make' and 'scp'
    deserve wall clocks too. Never call 'subprocess' directly.
  - Set 'max_wall_clock_sec' first; it is the one cap that catches
    everything eventually and works on every platform.
  - One Procsitter per call, one work_dir per test: scratch isolation is
    the cheapest hygiene there is.
  - Each pipeline stage gets its OWN procsitter: attribution stays sharp.
  - Read '.unenforced' in reports: a pass without memory enforcement
    is a pass -- but say so.
  - Security, isolation, reproducibility: outer boundary. Always.
