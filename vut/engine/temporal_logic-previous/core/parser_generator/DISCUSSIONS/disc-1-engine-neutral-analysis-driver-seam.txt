disc-1  PULLING THE LL(1) ANALYSIS/DRIVER OFF THE NODES; CORE LANGUAGE-NEUTRALITY
===============================================================================
SCOPE     parser/core. A design fork, deliberately deferred.

DECIDED (in RATIONALE):
    first_set is the load-bearing runtime primitive (branch dispatch);
    check_alts is a load-time validator built on it. The lexer's need for the
    specific grammar was resolved by inversion (core/lexer exposes
    register_grammar; the outer __init__ calls it once). The parser->luau Role
    import is gone (E_SpanMode is core-owned).

OPEN -- two coupled questions, both "do not design from one example":
    1. The LL(1) approach lives as an ANALYSIS + DRIVER pair currently FUSED
       onto the node classes (first_set / check_alts / expand are node methods).
       A second approach (PEG, a code-emitter) would need them pulled off into
       an Ll1Analysis + Ll1Driver over the neutral grammar AST. The seam shape
       is undecided -- designing it from the single LL(1) example would very
       likely be wrong for the second approach.
    2. REMAINING CORE->OUTER LEAKS. core/ll1_engine constructs the specific
       outer node types (RuleFile, the opaque-span leaf); core still names the
       embedded-Luau handoff in places. To reuse core for a non-Luau language
       the Luau handoff must become a caller-supplied framing-handler hook and
       the result-container / leaf construction must be injected. Same Tier-2
       concern as (1).

WHY DEFERRED:
    No second approach and no second target language exist yet. Both seams would
    be designed blind. Build each when the second consumer is real.

ENTRY CONDITION:
    A concrete second analysis approach, or a concrete non-Luau target, forces
    the seam. Until then the fusion stands and the leaks are flagged, not fixed.
