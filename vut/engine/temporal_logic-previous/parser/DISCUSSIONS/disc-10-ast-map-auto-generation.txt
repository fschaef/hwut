===============================================================================
disc-10  CAN ast_map BE GENERATED FROM (product=f(rule) x shape x roles)?
===============================================================================

STATUS: open analysis. NOTE (A-13 supersedes the framing): the "one rule,
one product type" language below is retired -- a rule's product is a
BOUNDED SPECTRUM fixed by shape (A-13). 'Blocker 1' relocation (disc-9) and
the lone content-violation (_comparison) below still stand.

ORIGINAL: The question: given the paradigm that a rule's PRODUCT is
        a function of the rule, the diluted-TOP-flavour-with-roles CST, and the
        rule that SEMANTICS ARE NOT PART OF PARSING -- can the whole AST_MAP be
        produced automatically? Verdict: the CORE yes; a bounded remainder no.
        Recorded so the generator scope is known before anyone builds it.

THREE CLASSES OF MAP ENTRY

  CLASS A -- pure constructors (the bulk, ~80%).
      Every "<rule>": Class.from_seq / from_or / from_token / from_span entry.
      The factory body is fully DETERMINED by (product type x CST operator shape
      x role tags): SEQ reads children by stable slot or role key, OR by fired
      branch, OPT/STAR/PLUS off their own shape. No input the grammar lacks.
      GENERATABLE with no hand authoring. "mode": Mode.from_seq carries nothing
      not already in "rule 'mode' produces Mode, shape SEQ".

  CLASS B -- OrMap / role routers (type, algebr/atom, number, code-block, arg).
      The routing TABLE is branch-role -> action. Two sub-cases:
        - arms that PASS (forward child) or forward v.text  -> mechanical from
          shape/role; generatable.
        - arms that build a leaf with a BAKED CONSTANT (the _const(KIND) literal
          arms; OpaqueLeaf.from_span)  -> the constant (STRING vs BOOL vs ...)
          is NOT in the shape. This is "Blocker 1". disc-9 dissolves it by
          carrying the role hint instead of stamping an enum -> after disc-9 the
          literal arms become uniform ConstantLeaf.from_token and JOIN Class A.

  CLASS C -- free functions with logic. Two very different reasons they resist:
      (i)  STRUCTURAL RESHAPING, still pure shape: _name_dotted/_head_and_rest
           (comprehension over STAR segments), _parens (unwrap an OPT), _left_fold
           /_un_fold (fold a STAR into a left-nested tree, COLLAPSE to the bare
           operand when the STAR is empty). These are shape-only -> generatable
           IF the generator is taught the fold/unwrap/segment idioms. Still
           parsing, not semantics.
      (ii) INPUT-DECIDED PRODUCT TYPE -- the deep blocker. _cause_named
           (Cause | CauseRef), _effect_named (EventSpec | EffectRef),
           _clockwork_name_step (EventSpec | Assign | Recip), _comparison
           (Comparison | BoolRef | operand). ONE rule yields DIFFERENT product
           types depending on a slot's contents. This VIOLATES the generator's
           founding premise product=f(rule): here product=f(rule, INPUT).

THE TWO TRUE BLOCKERS TO "PRODUCT = f(rule)"

  B1  Constant-domain tagging (Class B literal arms). A token-meaning table.
      -> RELOCATED OUT OF THE PARSER by disc-9 (hint carried; domain assigned in
         pass 2). After disc-9, not a parser blocker.

  B2  Input-decided product type (Class C-ii). Splits again:
        - "the parens decide" tails (_effect_named, _cause_named,
          _clockwork_name_step) and the fold-collapse: the deciding input is a
          CST FACT (OPT present? STAR empty?). This is legitimately PARSING
          (D-26, parens are syntax), NOT semantics -- so it cannot be excluded as
          "semantic". But it is product=f(rule, SHAPE), not f(rule). GENERATABLE
          ONLY IF the paradigm is WIDENED to let the OPT-presence / STAR-arity
          pattern be a generator input (declared per rule: "product is X when the
          parens slot is present, else Y").
        - _comparison's BoolRef arm fires on isinstance(left, ReferenceLeaf): a
          test on the TYPE of an already-built child -- downstream-product
          knowledge the grammar cannot carry at all. NOT generatable under any
          shape widening. CANDIDATE to move to pass 2 (the same move as A-12 for
          Declaration): parser builds the comparison shell uninterpreted, the
          semantic layer finalizes the bare-reference case to BoolRef. That would
          remove the last non-generatable dispatch from the parser entirely.

BOTTOM LINE
    Not COMPLETELY automatic, but the residue is small and named:
      - generated core: Class A + (post disc-9) the literal arms;
      - generatable shell IF product=f(rule x shape) is accepted: the shape
        idioms (Class C-i) and the parens-decide tails (Class C-ii first half);
      - irreducible under "no semantics in parsing": ONLY _comparison's
        child-type test -- and that one wants to move to pass 2.
    KEY FINDING: what blocks full generation is NOT semantics leaking into the
    parser (that boundary is clean). It is that a few rules genuinely have
    INPUT-DEPENDENT product types, and "the parens decide" is a deliberate,
    correct parser-side decision that simply does not fit a one-rule-one-product
    generator. Levers to close the gap: (1) widen to product=f(rule x shape) for
    the parens-decide tails; (2) adopt disc-9 for the literals; (3) move
    _comparison's BoolRef finalization to pass 2.

DEPENDS ON / RELATES TO
    disc-9 (removes B1).  disc-11 (the pass-2 visitor that would receive the
    _comparison BoolRef finalization and the Declaration fan-out).  A-12 (the
    precedent: carry uninterpreted, finalize in pass 2).
