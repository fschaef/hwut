R-50.  Authoring vocabulary: tuple = sequence, list = optional, OR = sentinel
-------------------------------------------------------------------------------
Decision: a GRAMMAR rule body is built from plain Python literals plus three
named operators, chosen so the dict reads like a grammar table.
  (a, b, ...)        SEQUENCE      -- a bare tuple
  [a, b, ...]        OPTIONAL      -- a bare list (one element [x] = x optional;
                                     more = optional sequence)
  (a, OR, b, ...)   ALTERNATION   -- the OR sentinel placed BETWEEN branches
  PLUS(x) STAR(x)    one/zero-or-more
  "<name>"           a reference to GRAMMAR rule 'name'
  "literal"          a silent bare-string keyword
Rejected: OPT(x) as a wrapping call (retired). A wrapping call doubles the
visual nesting on the common case ([in: ... [as: ...]] vs OPT((..OPT((..))))),
and the bracket already means 'optional' everywhere in SYNTAX_DOC prose.
Rejected: OR(a, b, ...) as a variadic call. The between-branches sentinel
reads as BNF's 'a | b | c' with no wrapping parens; an overloaded '|' operator
was rejected because it needs real combinator objects on both sides, which
reintroduces the visual noise the change was meant to remove.
Mechanism: _compile_child lowers a tuple to SeqNode unless it holds the OR
sentinel (then split into an Alt); a list to OptNode (one-element list lowers
to Opt(elem) directly, identical to the old OPT(x); multi to Opt(Seq(...))).
Invariant: a single-element optional produces NO list wrapper in the AST -- see
R-52.

-------------------------------------------------------------------------------
R-51.  Rule references written as "<name>", not R("name")
-------------------------------------------------------------------------------
Decision: a rule reference is a bare string in angle brackets, "<cause>", so
the GRAMMAR source is character-for-character aligned with the <name> spelling
SYNTAX_DOC already uses for every nonterminal. compile_leaf resolves a bare
string that starts '<', ends '>', length > 2 to the interned NonTerminalNode.
Rejected alternative spelling '~name': its only advantage is that no keyword
could ever collide with the sigil, but the collision it guards against is
hypothetical (no '<...>'-spelled keyword exists or is planned; all keywords are
colon-suffixed words or punctuation), and '~name' reintroduces a translation
step between code and prose -- the opposite of the goal.
Escape hatch (for the hypothetical future keyword literally spelled '<...>'):
write it explicitly as T.string("<...>"). A string-shape Terminal is now
accepted as a leaf (silent keyword), so the '<...>'-means-reference convention
applies ONLY to bare strings; an explicit T.string bypasses it. The single-char
keywords '<' and '>' (container brackets in <fwd-kind>) are unaffected: too
short to be read as references.

R-52.  A list (optional) leaves no 'list-ness' in the value stream
-------------------------------------------------------------------------------
Question asked: does a single-element optional ['<decl-parens>'] produce a list
in the AST, or the bare element?
Answer: NEITHER a list nor a synthesized wrapper. OptNode.expand pushes its body
directly into the current frame when the lookahead starts it, and pushes nothing
when absent. So optionality is expressed only by PRESENCE or ABSENCE of the
element among frame.values; whatever the inner element builds to flows up
unwrapped. ['<decl-parens>'] present => the decl-parens value (itself a list of
ArgDecls, from _build_decl_parens) appended as one frame value; absent => no
value, and the rule's builder defaults the field (e.g. _build_mode sets
params=[]).
Consequence (load-bearing): builders that type-spot frame.values rely on this
flattening. _build_spawn distinguishes its optional modifiers by Python type
(a str = the 'in:' container, an ast.Luau = the 'as:' handle); were a
single-element optional to wrap its value in a [value] container, that
type-spotting would break. The design is internally consistent on this point.

R-53.  When a rule collapses to a bare role-bearing terminal (and when not)
-------------------------------------------------------------------------------
Question asked: <mutation> and <report-string> are one-terminal rules -- could
they be terminals with a role instead? And: does the terminal's 'role' member
give the builder a sufficient hint?
Finding: the role identifies a span's CONTENT KIND (how the oracle parses and
validates it), but NOT its AST type, because role is not unique per node. The
opaque terminal t_opq_stmts (Role.STATEMENT_BLOCK) is used in three rules --
<mutation> (-> Mutation), <init> (-> InitBlock), <deinit> (-> DeinitBlock).
Same terminal, same role, three AST node types, separated only by grammatical
position (a bare span in effect position; a span after 'init:'; a span after
'deinit:'). The role cannot carry that distinction; the rule (or its keyword
prefix) does.
Rule of thumb: a rule collapses to a bare role-bearing terminal ONLY when the
role is unique to one grammatical position AND the action merely forwards (no
distinct AST type). <guard> already IS this: a bare t_opq_cond (Role.CONDITION,
used nowhere else), and _build_guard returns frame.values[0] unwrapped -- a raw
Luau node, no wrapper. <report-string> does NOT qualify: its terminal is the
plain, role-less t_re_string, shared with <rvalue> and <include>; the rule
exists precisely to assign meaning by position (a quoted string in effect
position is a ReportString, not an Arg). <mutation> does NOT qualify either:
STATEMENT_BLOCK is shared three ways and Mutation is a distinct node the
effect-walker expects.
Decision: leave <mutation> and <report-string> as rules. They are load-bearing,
not degenerate. AST type is a function of grammatical position, not of a
terminal's intrinsic properties -- the same principle that keeps <dotted-name>
a rule.

R-54.  'as:' on a spawn is reachable only inside 'in:'
-------------------------------------------------------------------------------
Decision: <spawn> nests the optional 'as:' handle INSIDE the optional 'in:'
clause -- ("+!", <dotted-name>, <arg-parens>, ["in:", <dotted-name>,
["as:", t_opq_lvalue]]) -- so 'as:' without a preceding 'in:' is a syntax error.
Rationale: the 'as: { lvalue }' handle is the name by which the named container
holds the spawned instance; a handle with no container to hold it is meaningless.
Earlier the two optionals were siblings (in: and as: independently optional),
which admitted the nonsensical 'as:' without 'in:'.
Build impact: none. _build_spawn type-spots frame.values (see R-52), so the
structural move of 'as:' under 'in:' leaves both the container str and the Luau
handle reachable in the flattened frame; the action is unchanged.
Rationale, costs, and rejected alternatives for the parser layer. README =
settled mechanics; SYNTAX_DOC (parser/syntax.py) = the concrete syntax; this =
why. Entries newest-first, 'R-N'.

R-4  TOKEN IDENTITY IS THE TERMINAL OBJECT (SINGLE SOURCE)
-------------------------------------------------------------------------------

The hand-maintained E_TokenId enum and the spelling->id tables (_NAME_OF,
_REGEX_CLASS_NAME) are gone. A token's identity is now the Terminal object that
produced it (terminals.py); the lexer attaches that object as Token.kind, and
the engine compares tokens by object identity ('is'), never by a name. There is
one source -- the parser engine's terminal database -- and no second copy of
"what tokens exist" to drift.

  - Every token is a Terminal: T.regex / T.string / T.captured / T.opaque, plus
    T.framing for lexer/engine machinery (luau-open, luau-block, comment,
    whitespace, mismatch, end-of-file). Framing tokens are tokens like any other
    -- referenced by identity, named by the same scheme -- and are special only
    in carrying a friendly tag and in being declared in terminals.py rather than
    minted from a rule (they have no GRAMMAR spelling).

  - A bare string in GRAMMAR is sugar: the engine routes a plain-string leaf
    through T.string, which mints (or reuses) the Terminal. Several rules using
    the same spelling share one Terminal -- reuse keyed by _name() -- so '(' is
    one token however many rules write it.

  - Terminal._name() (engine-internal, hence the underscore) is the identity:
    factory plus every distinguishing field (regex:<pattern>, string:<spelling>,
    captured:<spelling>, opaque:luau:<role>, framing:<tag>). _register keys on
    _name(): the first terminal of a name is recorded in declaration order, a
    repeat returns the existing one. Two terminals that are NOT identical can
    never share a _name(), so a clash is by construction the same terminal --
    duplicate definition is reuse, never silent divergence.

  - Token ids are not a communication surface. They surface only in parser
    debug tracing, for which token_debug_names() renders {Terminal: _name()}.
    The lexer-spec generator and the FIRST/LL(1) machinery work on Terminal
    objects directly.

  REJECTED: positional/minted id NAMES with no readable form. The names are
  derived by _name() from the factory and fields, so they stay legible in debug
  traces and the test inventory without any authored table. Builders that once
  compared kind.name == "KW_VOID" / "KW_CONTAINER" / "ID" now compare against the
  terminal objects (t_kw_void, t_kw_container, t_re_id) by identity.

R-3  TERMINAL DATABASE + GENERATED LEXER SPEC
-------------------------------------------------------------------------------

The grammar's terminal and authoring vocabulary was regularized:

  - Angle-bracket spellings retired. A rule reference is R("name"); GRAMMAR dict
    keys lost their brackets ("spawn", not "<spawn>"). With '<'/'>' now only the
    literal container brackets, a bare string in GRAMMAR is unambiguously a
    silent keyword, so the engine's leaf dispatch simplified to a type switch
    (Terminal / Ref / bare string) with no string-prefix parsing.

  - Terminals are named objects in a preamble (terminals.py defines the T
    factory and the terminal database; parser/syntax.py makes the T.* calls).
    Three shapes, grouped by name: t_re_... (regex classes id/number/string/
    name_colon), t_opq_... (opaque Luau spans carrying their Role), t_kw_...
    (captured keywords kept in the parse frame). The role lives on the opaque
    terminal object, so a position's role is fixed by which t_opq_ it names,
    checkable at authoring time. Plain silent keywords (on:, =>, :end, ... )
    stay bare strings -- a deliberate slight inconsistency for visual sweetness;
    they get no terminal definition and are extracted from the grammar.

  - Combinators are the classes Alt/Opt/Plus/Star, exposed to GRAMMAR under the
    capitalized aliases OR/OPT/PLUS/STAR so a rule body reads as grammar
    operators. The alias IS the class (no wrapper functions). No SEQ alias: a
    sequence is a bare tuple.

  - The lexer's _TOKEN_SPEC is GENERATED from the terminal database plus the
    bare keywords walked out of GRAMMAR, ordered by a deterministic seven-tier
    shape sort (skip groups; leading-colon; trailing-colon longest-first;
    bare/captured; symbols longest-first; regex classes in declaration order;
    MISMATCH). The author supplies no token id and no precedence number; the
    only lever is the declaration order of the regex-class lines (t_re_name_colon
    before t_re_id, or 'name:' would lex as a bare id and a stray ':'). Token
    ids (E_TokenId) stay a fixed naming convention keyed by spelling/shape --
    the names the engine and builders are written against -- generated, not
    authored. Generation is lazy (imports syntax/terminals inside the builder)
    so the import graph stays acyclic: parser_nodes -> lexer -> diagnostic only.

  REJECTED: an equivalence assert of the generated spec against the old
  hand-written spec. SYNTAX_DOC is now the only reference; the deterministic
  tier sort IS the spec. A TEST instead freezes the generated spec as a GOOD
  file, comparing as a (name, pattern) SET modulo re.escape normalization and
  asserting the overlap-ordering constraints -- not list-identity, since tier 3
  is now strict longest-first by design.

R-2  'until switched' REMOVED
-------------------------------------------------------------------------------

The 'until switched' state-closer is gone, and 'switched' is no longer a
keyword. A <state> block now ends structurally -- at the next state-machine
element or 'end' -- and its trailing 'until' causes are optional (STAR, not
PLUS). The <state-untils> rule (a parser-only left-factoring artifact) and its
builder were deleted; _build_state now mirrors _build_mode (members, then the
trailing run of Cause nodes). This stays LL(1): 'until:' is not in FOLLOW(state),
so the optional until-run is unambiguous against the next element.

The sibling-armed transition that 'switched' used to spell is now implicit in
the state machine's mutual-exclusion semantics; it was never a runtime event.

  MIGRATION CAVEAT (not special-cased): with 'switched' no longer a keyword, an
  old 'until: switched' lexes 'switched' as an ordinary identifier and parses as
  "until an event named switched" -- silently, not an error. There is no
  rejection for this; authors updating old rule files must remove the clause.

Parser package: file/directory restructure, the two-layer split, and the
sprites example                                            (session 2026-06-08)
-------------------------------------------------------------------------------

WHAT WE DID

  Renamed two misleading files (pure, parity-proven): grammar.py -> actions.py
  (it held the _build_* ACTIONS, not the grammar); syntax.py -> grammar.py (it
  holds the GRAMMAR dict + terminal defs).

  Split the package into two layers:
    OUTER  parser/  grammar.py (GRAMMAR + terminals), actions.py (_build_*),
                    ast_nodes.py (AST shapes), rule_parser.py (facade)
    core/  grammar-agnostic: ll1_engine.py (was parser_engine.py; Grammar +
                    EngineParser + FIRST/check_alts/driver), grammar_ast.py (was
                    parser_nodes.py), combinators.py (was syntax_support.py),
                    lexer.py, terminals.py, diagnostic.py
  Dependency direction is now enforced OUTER -> core.

WHAT THE SPLIT TAUGHT US (kept, because it was not obvious going in)

  - first_set is the LOAD-BEARING primitive (used at runtime for branch
    dispatch); check_alts is BUILT ON first_set (a load-time validator only).
    The removable one is check_alts, not first_set. An earlier momentary
    conclusion that we "only need check_alts" was BACKWARDS.

  - The approach (LL(1)) lives in an ANALYSIS + DRIVER pair, currently FUSED
    onto the node classes (first_set/check_alts/expand are node methods). To
    make a second approach (PEG, code-emitter, ...) possible they must be pulled
    OFF the nodes into an Ll1Analysis + Ll1Driver over the neutral grammar AST.
    Deferred: designing that seam from one example would very likely be wrong
    for the second; build it when a second approach is real.

  - The split exposed TWO core->outer leaks that had been invisible while
    everything sat in one directory:
      1. lexer needed the specific GRAMMAR to harvest string keywords. RESOLVED
         by inversion: core/lexer exposes register_grammar(GRAMMAR); the outer
         parser/__init__.py calls it once on import, so every entry path (facade
         or a direct core.lexer import in a test) finds it wired. The lexer
         reads no grammar by import.
      2. ll1_engine constructs ast_nodes.RuleFile and ast_nodes.Luau -- two
         specific OUTER node types. Repointed to 'from .. import ast_nodes' so
         it works, but core is therefore NOT yet fully engine-neutral.

  - KNOWN REMAINING LEAKS (core is not yet language-agnostic; deferred, flagged
    honestly rather than claimed done): core/lexer, core/ll1_engine,
    core/terminals import ...luau (the embedded-Luau handoff + Role); ll1_engine
    constructs RuleFile/Luau. Both are the SAME Tier-2 concern: to reuse core
    for a non-Luau language, the Luau handoff becomes a caller-supplied
    framing-handler hook and the result-container/leaf construction is injected.

  - Tooling lesson: each move was verified by re-running every test choice
    against the blessed GOOD files (byte-for-byte), NOT by a compile check.
    Parity caught four breakages a compile check would have missed: a stale
    terminal import in aux_walker, bundled facade/core imports needing splitting,
    the register-on-import requirement, and the ast_nodes core->outer edge.

  - A still-uploaded copy of grammar.py crashed with
    "No module named ...parser.syntax_support": it predated BOTH the rename and
    the restructure. The fix is the two repaths on lines 76-77:
    from .core.combinators import OR, PLUS, STAR  and
    from .core.terminals import T.

THE sprites EXAMPLE (parse-only)

  One file, monkey_data/sprites.rule (5223 lines), exercising the full grammar
  surface: include statements (recorded as AST nodes, NOT resolved -- resolution
  is a semantic concern), event/clock definitions, forward declarations, 72
  state machines (exclusive behaviour), 10 mode groups (concurrent behaviour --
  villain psychologies, etc.), 30 top-level causality rules. Parses to 172
  top-level items, 0 diagnostics. The 'sprites' test choice prints an AST CENSUS
  (node-type counts, 16393 nodes across 20 types) rather than the full dump, so
  its GOOD file is compact and diffable.

  Construction note: only legal constructs were used -- rvalues are positional
  (number | string | bare-identifier | { luau }), NO name=value, and a dotted
  arg such as event.name must be wrapped as { event.name }. That last point is
  the seed of the next discussion (see below).

OPEN FOR NEXT TIME

  Positional arguments vs. the ability to refer to event members. Today an
  effect that wants a member of the triggering event must wrap it opaquely --
  ! Chase({ event.target }) -- so the static layer cannot see the event-member
  dataflow. Question: is "refer to a member of the triggering event" a
  rule-file-plane RELATION (deserving first-class, non-opaque syntax) or an
  EXPRESSION (correctly behind the braces, per the colon principle)? A separate
  prompt drives that discussion; the load-bearing check is whether a dotted-name
  rvalue stays LL(1) against the existing bare-identifier branch.
