LANGUAGES, TOOLS, FORMATS -- the coverage roads, and what is witnessed
==============================================================================

THE THREE AXES, AND WHO OWNS WHICH. A LANGUAGE names a registry entry;
the entry lists TOOLS in preference order; 'elect' takes the first the
machine has; the tool's FORMAT names the reader. Twenty-one tool names,
eleven formats, one record. The record is the unifier -- everything
below dies at harvest.

THE COUNTS ABOVE ARE THE ONLY NUMBERS THIS FILE STATES. The table of
which tool speaks which format is printed by 'hwut.cov formats' from
the registry itself, and is not copied here (RATIONALE D-13). What
follows is the SHAPE of the roads and the HISTORY of how each was
witnessed -- which is what this file is for and what the registry
cannot hold.

ON A 'UNIFYING BINARY FORMAT'. The unifying FORMAT exists and is not
binary: the VUT-COVERAGE record -- text, delta-coded, versioned,
measure-tagged, one writer per key space. Its being TEXT is load-
bearing: the GOOD files read as specifications, a record diff is a
legible fact, and 'grep' is a query tool. At these sizes binary buys
nothing and costs inspection. What 'hwutcov' SHOULD name, if anything,
is the unifying EXECUTABLE: one entry point with verbs --

    hwutcov elect <language>          name the tool this machine serves
    hwutcov instrument <build-argv>   amend a build line (the build-
                                      node provision)
    hwutcov probe <executable>        can it REGISTER coverage? refuse
                                      by name before the run spends
    hwutcov run <argv>                wrap where the road wraps
    hwutcov report <work-dir>         the named second call
    hwutcov harvest <work-dir>        artifact -> record
    hwutcov merge <record>...         where the measures admit it

-- so the orchestration's build and run nodes consume the component
without importing it, and records remain the only interchange.

    2. THE PROVISION CHAIN -- the run side of the reader role. Today
       'wrap' is the IDENTITY in nine of eleven readers and
       'report_argv' is None in nine: the component READS eleven
       formats and can ARRANGE two. For the other nine the readers
       say in PROSE what the build line must carry -- gcov's
       '--coverage', verilator's '--coverage', jacoco's '-javaagent:',
       ghdl's '-fpsl', luacov's 'require' -- and a forgotten flag is
       discovered at HARVEST, as an honest ABSENT, after the run has
       already been spent. So:
           instrument(build_argv, config)  the build node asks what
                                           the build line must carry
           probe(executable, config)       can this executable REGISTER
                                           coverage? ('.gcno' present,
                                           '__gcov_' symbols, coverage
                                           points in a verilated model)
                                           -- refuse BY NAME before the
                                           run spends anything
       plus 'report_argv' on the 'verilator_coverage' alias naming
       'verilator_coverage --write-info' where a 'coverage.dat' stands
       -- which is also the first alias that must OVERRIDE rather than
       forward, since two tools sharing a format do not share a drive.
    3. 'hwut.cov', the unifying EXECUTABLE. Its verbs and the reader
       role's calls are ONE LIST, or one of them is lying:

           elect       (registry)
           instrument  instrument(build_argv, config)
           probe       probe(executable, config)
           run         wrap(argv, ...)
           report      report_argv(...)
           harvest     harvest(dir, root, config)
           merge       (record.merge)
