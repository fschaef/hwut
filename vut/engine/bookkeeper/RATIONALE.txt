THE BOOKKEEPER -- settled decisions
==============================================================================

Entries are PROBLEM / DECISION / COST / GRAVEYARD, appended, never
rewritten. Decisions made while the component was a sub-package of the
orchestrator stand in that component's RATIONALE (D-4, D-6, D-7, D-8)
and are not copied here.


B-1  THE BOOKKEEPER IS A COMPONENT, NOT PART OF THE ORCHESTRATOR
                                                              (2026-08-25)
------------------------------------------------------------------------------
PROBLEM   The bookkeeper stood in 'orchestrator/bookkeeper/'. It was
          not the orchestrator's alone: 'operations' imported it at
          nine places, and the coverage work then needed the shape of
          a test run as well. Two components below the orchestrator
          were reaching UPWARD into it to name a run.
          The pressure surfaced as a mutual reference. Coverage needed
          'TestRunId'; putting it in the bookkeeper made coverage
          depend on the orchestrator, and 'hwut.cov' will live in the
          orchestrator's services -- so the two packages would point
          at each other. Placing the shape in COVERAGE instead removed
          the cycle and stated something false: that a test run is a
          coverage concept.
DECISION  'engine/bookkeeper/', a sibling of 'operations', 'coverage'
          and 'orchestrator'. It refers to none of them; they refer
          DOWNWARD to it.
          A TEST RUN IS A GENERALITY -- the runner performs one, the
          base records one, a report names one, a coverage record
          attributes work to one -- so its shape stands with the runs'
          ADMINISTRATOR. 'test_run_id.py' holds it, and holds nothing
          else, so the file cannot become a drawer.
          WHAT STAYED WITH COVERAGE: 'Gathered' and the group
          interning. How an aggregator qualifies run ids across
          directories, and how it interns SETS of them, are questions
          only an aggregator asks.
COST      34 import lines across 18 files. One depth correction
          inside the package ('....auxiliary' became '...auxiliary').
          Two GOODs moved, both naming the layer that refuses a bad
          run id: it is the bookkeeper's fault type now, and
          coverage's 'IdentityFault' is a KIND of it, so a caller
          catching the general one still catches the particular.
GRAVEYARD 'TestRunId' in coverage: it says a test run is a coverage
          concept, and the next consumer that is not coverage would
          have to import coverage to name a run.
          'TestRunId' in a general 'engine/' file beside the register:
          the shape and its administrator separated for no reason, and
          a file at engine level with one type in it invites a second.
          Leaving the bookkeeper where it was: two components already
          paid for that placement before coverage ever asked.


B-2  AN ID IS ISSUED ONCE; EACH SCOPE COUNTS FROM 0 TO 2**32   (2026-08-25)
------------------------------------------------------------------------------
SUPERSEDES orchestrator D-7's allocation law (lowest-unused,
          delete-frees) and the guard that law rested on: 'an id
          never leaves the directory's book'.
PROBLEM   Re-use was safe only as long as nothing persisted carried an
          id -- which is exactly what the coverage record was about to
          do (orchestrator todo-4 t-9). A record naming run 47, kept
          across a removal and a later accept, would attribute its
          lines to a test that never ran them, and 'hwut.affected'
          would answer with confidence and be wrong. Purging every
          record at removal defends the store but not a record that
          travelled: exported, copied, in a gathered tree. Records
          carrying NAMES instead makes every rename rewrite them.
          Many of the discussions that led to lowest-unused are lost;
          under that uncertainty the safe law is the simplest one.
DECISION  AN ID IS ISSUED ONCE AND NEVER AGAIN. Every scope counts
          from 0; its next id is one above the highest it ever issued;
          the register file carries that mark ('N:' lines, format 4)
          so a removal cannot lower it. Removal deletes the NAME; the
          number is retired without tombstone or flag -- only the mark
          remembers. An id may therefore leave the book: it decodes
          later to the same test or to 'no longer registered', never
          to another test.
          THE SCOPES ARE ORTHOGONAL and count on their own: the
          applications of a directory, the choices of one application,
          the groups of a directory (B-3).
          THE CEILING IS 2**32 ('ID_LIMIT', one home, 'test_run_id.py'):
          a scope that would issue it refuses by name. More than 2**32
          tests, choices or groups in one directory is not a thing that
          happens; the ceiling states it rather than relying on it.
          Version 3 registers, which kept no mark, are refused by name.
COST      The register's 'reuse' choice became 'retire'; six GOODs
          moved from 1-based to 0-based ids, audited line by line.
          Coverage's index and affected tests followed (eleven GOODs,
          every movement an id). A register file grows by one 'N:' line
          per application.
GRAVEYARD Lowest-unused with records purged at removal: silent
          misattribution for any record outside the store.
          Tombstones ('A:47 -' kept after removal): a second way to say
          what the mark says, and a file that grows with every removal.
          A 64-bit ceiling: unreachable by construction, which is not
          a limit but the absence of one; 2**32 is a stated bound.


B-3  A SET OF RUNS IS A NUMBER, AND THE NUMBER IS THE BOOKKEEPER'S
                                                              (2026-08-25)
------------------------------------------------------------------------------
CORRECTS  B-1, which left 'the group interning' with coverage.
PROBLEM   B-1 argued that a SET of runs is a question only an
          aggregator asks. That is false in the same way D-16's
          leaf-purity argument was false about the run itself: a
          coverage index attributes a stretch to a set of runs, but so
          may a report, a flaky-test hunt, the compare engine's
          tolerance grouping. The next consumer would have imported
          coverage to name a set of runs.
DECISION  'group_table.py' stands here: 'GroupTable' in memory over any
          hashable run key, 'GroupDb' bound to 'GOOD/group_ids.dat'
          beside the register and written like it. Group ids are a
          THIRD id scope under B-2's law: 0 is the empty set by
          construction, the rest issued once, mark persisted, ceiling
          2**32. Nothing removes a group; a set of runs that once
          existed is a fact a record may name.
          ONLY 'TestRunId' KEYS ARE STORED. A key an aggregator
          qualified across directories belongs to that one aggregation
          (coverage D-14) and 'format' refuses it by name.
          WHAT STAYS WITH COVERAGE: 'Gathered', the qualification of a
          run id by its found-directory, and the fold over it. The
          cross-directory 'group of groups' a gather may need is noted
          in coverage todo-10 and is ephemeral to hwut.
COST      'coverage/identity.py' dissolved: the table moved here, the
          value type moved to 'coverage/index.py', 'IdentityFault'
          became 'GroupFault' (still a kind of 'RunIdFault'). Four
          choices moved from 'coverage/TEST/test-identity.py' to
          'TEST/test-group_table.py', re-recorded; one ('keys') to
          'coverage/TEST/test-index.py'.
GRAVEYARD The group table as a third table INSIDE 'test_id_db.py': one
          file for two lifetimes -- a register entry is removed, a
          group never is -- and a name/number table beside a
          set/number table.


B-4  AN ABORTED ACCEPT HANDS ITS ID BACK                       (2026-08-25)
------------------------------------------------------------------------------
PROBLEM   A coverage record is seated with a run id at HARVEST, which is
          during the run 'hwut.accept' performs -- before the acceptance
          is known to stand. So accept must name a run it may not keep.
          A run OUTSIDE accept presupposes a registered choice and asks
          nothing new; only accept's own run does.
DECISION  ACCEPT ALLOCATES AS USUAL and, if it aborts, calls
          'give_back(run_id)'. The entry is removed, and the scope's
          mark STEPS BACK where that id was the last one issued; where
          something was issued after it, the mark STANDS and the number
          is simply retired.
          Both outcomes keep B-2: an id whose mark stepped back reached
          no file that survives (the register is rewritten in the same
          call), and a retired one is never issued again by definition.
          NO MACHINERY: no reservation, no transaction, no pending
          state, nothing to recover after a crash. A crashed accept
          leaves a registered name whose test never blessed, which
          'vanished()' and 'hwut.sanitize --unregistered' already
          describe.
COST      One method and one printing section in the register's 'retire'
          choice.
GRAVEYARD 'reserve' / 'commit' / 'discard' as a transaction over the
          register: a second lifetime for an entry, a file that must be
          understood in two states, and a recovery question for every
          crash between the two calls.


B-5  THE SHAPE OF A RUN IS THE BOOK'S TO READ                (2026-08-31)
______________________________________________________________________________
PROBLEM   'display' wanted GREW/SHRANK/DIVERGED (E-29) live, in its
          HINTS block. E-31 forbids the RUN taking a shape -- its
          compare aborts on the first mismatch and has read neither
          text whole; only a post-hoc reader of both WHOLE files may
          say GREW from SHRANK. 'hwut.report' owned that reader
          ('services/report.py.difference_shape'). Could 'display'
          reach the same answer without 'engine/*' importing
          'services/*' -- the one edge 'adm/LAYERING.txt' forbids?
DECISION  'difference_shape' MOVES onto 'Bookkeeper' as
          'shape_of(test, choice, subject="stdout")'. It took only a
          candidate path and a nominal path, and 'Bookkeeper' is
          already the one place that knows both (E-34: "the record of
          the process that produced a result is part of that
          result"). It is a THIRD thing beside the book and the
          observations (E-36) -- a READING of what those two already
          point at, computed on demand, never stored.
          'services/report.py' calls 'bookkeeper.shape_of(...)' in
          place of its own copy of the same two-file read. ONE LAW,
          ONE PLACE: the shape of a difference was becoming two
          functions in two layers that would drift the day one of
          them learned a new shape.
NOT DONE  No new 'engine/display -> engine/bookkeeper' edge opens.
          'display's HINTS block excludes a plain 'differs from GOOD'
          outright (E- pending in 'engine/display/RATIONALE.txt') and
          so never needs a shape; nothing currently asks 'display' to
          reach the bookkeeper. If that changes, the edge is a
          one-line addition to 'adm/LAYERING.txt' and the door
          already carries the answer.
COST      One method moved (not rewritten) from 'services/report.py'
          to 'engine/bookkeeper/bookkeeper.py'; one call site in
          'services/report.py' updated. 'test-report.py' touches the
          boundary and wants a verdict-count check on real
          infrastructure, not fabricated here.



B-6  THE BOOK IS A TABLE, AND HOLDS NO CONFIGURATION            (2026-09-01)
______________________________________________________________________________
PROBLEM   The book carried a copy of the configuration beside every
          verdict: per test the source, its kind, the caps WITH THE
          FRAMEWORK'S DEFAULTS FOLDED IN; per choice the canonicalisers
          and the compare-setup delta. E-36 ruled it in ("a reader
          asking what this test was configured to do must be told
          it") and, two lines later, ruled the same kind of copy OUT
          for acceptance history ("a second, poorer copy in the book
          is a copy that can disagree") -- one entry, two standards.
          Measured: NOTHING READS THE COPY BACK. It is write-only
          data in an oracle file, it is a second source beside the
          header and 'hwut.conf' that git already versions with the
          book, and it CHURNS: a moved default rewrites every book in
          the tree with no verdict having changed.
DECISION  THE CONFIGURATION LEAVES THE BOOK, all of it -- test facts,
          choice facts, canonicalisers, compare delta. What held is
          recoverable from the same commit's header and 'hwut.conf',
          exactly as E-36 already argued for history. What remains is
          a DECISION about a (test, choice), and nothing else:

              test  choice  operation  verdict  report  coverage
                                       last_accept  stderr  stain

          THAT IS A TABLE, AND THE BOOK IS WRITTEN AS ONE:
          'GOOD/result_db.csv', one row per (test, choice, operation)
          and one row per choice with 'operation' empty carrying the
          choice's own facts ('stderr' note, 'stain'). A git diff of
          GOOD/ then reads as "this verdict changed", one line, and
          nothing else. JSON earned its keep only for the nesting
          that has just left.
          THE SHAPE STAYS BEHIND THE DOOR. Every face reads through
          the accessors ('result', 'choices', 'tests', 'stain',
          'stderr_note', ...; E-37, and the leak closed the day
          before); the model those answer from is the bookkeeper's
          private business and did not change. Only 'record()', the
          serialisation and the file name changed.
          A BOOK WRITTEN BEFORE THIS ENTRY IS READ, ONCE. Where
          'result_db.json' stands and no '.csv', it is loaded, its
          configuration dropped, and the first write lays down the
          '.csv' and removes the '.json' -- ONE base, never two.
          'hwut.sanitize' knows both names for that one transition.
COST      'record()', '_write_book()', 'book()' and the file name;
          '_test_facts', '_choice_facts', '_stated_caps' and the two
          unused configuration accessors removed; one suite that
          printed the raw dict ('operations/TEST/test-session.py')
          re-recorded.
GRAVEYARD The framework VERSION in the book, as the one fact git of
          the test tree does not hold: rejected for now -- it would
          be the same number on every row of every book in the tree,
          and belongs, if anywhere, in one place at the root.
          Choice facts REPEATED on every operation row: one schema,
          but a stain change would then touch every row of the
          choice, and the diff would lie about what changed.


B-7  ONE ROW PER CHOICE; ';' AND ':'; NO NESTED SYNTAX            (2026-09-01)
______________________________________________________________________________
AMENDS    B-6, the same day, before any tree carried its table.
PROBLEM   B-6 carried the MODEL'S shape onto disk -- an 'operation'
          column -- without asking whether the shape was right. It is
          not: 'Accept' never records (the face promotes through
          'Store.accept()' and the book never hears of it), and
          'Display' recorded a VIEWING as a verdict of record. The
          column held one value everywhere, and forced a second row
          per choice to carry facts that have no operation. B-6 also
          hid a mini-language in one cell ('3@<when>|ok;fail;ok') and
          leaned on CSV quoting for a name carrying the separator --
          a quoted name in a diff is the noise a table exists to
          remove.
DECISION  ONE ROW PER (TEST, CHOICE). The columns are the decision
          about that choice, flat:
              test;choice;verdict;report;last_accept;coverage;
              stderr;stain_repeat_n;stain_when
          THE SEPARATOR IS ';', AND IT IS NEVER QUOTED: a test or
          choice name containing ';' or ':' is REFUSED at the
          specification's door ('validator'), once, and the codec
          assumes what the door enforced. Refuse rather than quote.
          ':' IN THE 'test' COLUMN MEANS "THE SAME AS THE ROW ABOVE"
          -- the mark the display already speaks for a repeated
          application. Key columns only: a ':' under 'verdict' would
          make "did this verdict change" a two-row question. COST OF
          THE MARK, accepted: removing a test's first row turns the
          next row's ':' into a name, so that deletion shows as two
          lines -- the display makes the same trade.
          THE STAIN IS TWO PLAIN COLUMNS. 'repeat_n' and 'when' are
          the decision (disqualified until re-proved that often). The
          'verdict_list' that convicted it is what THIS machine SAW
          (E-36) and leaves the book; nothing read it.
          A DISPLAY DOES NOT RECORD. 'session.py' enters the book for
          VERDICT and NOMINAL goals only; a viewing writes nothing.
          'last_accept' lands on the choice's row when the acceptance
          face is made to enter the book -- a separate, named gap.
INDEX     The rulings that shape the book, wherever they stand:
              E-20, E-22  (services)  the run's base; observations
              E-34, E-36  (services)  the local database; time-and-
                                      place as the membership law
              E-37        (services)  the door
              B-1..B-7    (here)
          See 'adm/DISCUSSIONS/disc-1-document-consistency.txt'.
COST      The codec and the model ('record', 'result', 'stain'), the
          validator's name law, 'session.py's goal gate, 'report.py's
          one call; the bookkeeper's suites re-recorded ONCE.
GRAVEYARD Quoting instead of refusing: correct, and unreadable.
          The verdict list in the observation database: right home,
          and no reader -- deferred until one asks.


B-8  THE EMPTY NAME SAYS "AS ABOVE"                              (2026-09-01)
______________________________________________________________________________
AMENDS    B-7, the same day.
PROBLEM   B-7 borrowed the display's ':' for "the same as the row
          above" in the 'test' column, and so had to forbid ':' in
          every name. But the mark carried no information the CELL
          did not already carry: an empty test name means nothing in
          itself, so an empty cell can mean "as above" with nothing
          added and nothing forbidden.
DECISION  AN EMPTY 'test' CELL IS THE ROW ABOVE'S. No mark; ':' is
          an ordinary character in a name again; only ';' -- the
          separator itself -- stays refused at the validator. A table
          of B-7's one day with ':' cells is read the same way.
COST      Three lines in the codec, one tuple in the validator.
