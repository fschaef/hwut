todo-2  RE-ASSOCIATION: WHAT IS STILL OPEN  (compare)
----------------------------------------------------------------------------

The SHAPE is settled and stands in README 11.7: a realignment re-folds the
BLOCK the edit fell into, the block is a chunk, compare names it, the IDE
quotes the name back. What is left is not a choice of algorithm but two
gaps between that shape and the code.

(a) THE OUTER TEXT HAS NO BLOCKS.  'AssociationChunkPipe' flushes an outer
    chunk only at '##!', '####' or EOF, so a nominal without regions is
    ONE block and "re-fold the block" is "re-fold everything".

        with regions:   [outer][##!pot][outer][##!tbl]   4 blocks
        without:        [ .......................... ]   1 block

    Whether to cut the outer text -- and on what boundary, a blank-line
    run being the obvious candidate -- is OPEN. Note it is INTERNAL: the
    interface speaks block ids either way, so the clients do not care.
    It is also CHECKABLE rather than arguable: split the outer text, run
    compare's own suite, and see whether any GOOD file moves. If none
    does, the boundary is free; if one does, the split changed what the
    edit search may match across, and that is the real cost, named.

(b) STARTING THE FOLD AT A BLOCK NEEDS THE STATE BEFORE IT, AND TWO
    PIECES OF THAT STATE CANNOT BE CARRIED YET.

        the analogy db     ALREADY carried -- 'ChunkPair' holds the
                           snapshot that holds after it
        the flyweight      created and destroyed PER 'associate()' call,
        registry           so a snapshot from one round is meaningless in
                           the next: its interned ids belong to a dead
                           registry. Either the merge SESSION is one
                           long-lived run across every round, or the
                           snapshot is made registry-independent.
        the constraint     no history at all, and its liveness is a
        space              one-way latch. Until it can be carried, a
                           re-folded block can produce a different cell
                           than the full fold would.

    The registry question is SHARED WITH todo-16 -- the loop's own shape
    decides it -- so it is ruled there, not here.

CORRECTNESS NEEDS NO JUDGEMENT and no measurement: re-folding from block B
must equal 'feed(subject, working nominal)'. An exact oracle.

todo-16  THE MERGE LOOP: PHASE 2, AND THE ROUND RULING
----------------------------------------------------------------------------

WHAT A MERGE IS. The author is shown the comparison and edits the nominal
until it says what the test should from now on accept. Editing changes the
ALIGNMENT -- which line stands beside which -- and the alignment is
COMPARE's, never the editor's. So after an edit the author is shown the
comparison AGAIN, computed afresh, until commit or cancel: the loop.

THE LOOP IS BUILT: 'open' and 'close' once, outside; each round one fresh
'compare_feeder.feed(subject, working nominal)'; the no-progress guard and
'MERGE_ROUND_MAX' end a looping driver as CANCEL; 'RemoteDisplay.resolve'
keeps the pipe open; 'mock/mock_ide.py' answers per round. Pinned by
'TEST/test-merge.py' 'loop', 'loop_realigns', 'loop_pipe' with their GOODs
(20/20 green, audit r10). The keyed session (services E-61) realigns on
'r' through the same road.

STILL OWED (phase 2, protocol):

    'block_id' on 'SectionBeginInst' and on 'Resolution' (README 11.7),
    the regenerated 'SIGNATURE_UI_PROTOCOL.txt' that follows from it,
    and the field carried by whatever client comes ('protocol.lua' is
    gone, E-62). The hub records the id
    and still re-feeds in full: nothing behaves differently yet, and
    after it no client ever changes again.

THE ONE RULING OWED HERE. Compare offers alignment through 'feed()', and
one call to it is one RUN: it sets up its own internal state at the start
and tears it down at the end. The question is how a session of N rounds
maps onto runs:

    ONE RUN PER ROUND        round 1: [ run ]   round 2: [ run ]   ...
                             Simple. Each round is independent and exact.
                             Nothing carries over, and nothing needs to.

    ONE RUN PER SESSION      round 1: [ run ................... ] round N
                             Only needed if a later round wants to REUSE
                             what an earlier one computed.

Per round is the obvious default and is all a full re-feed needs. It is
recorded as a ruling only because of what it forecloses: compare's
flyweight registry is created and destroyed WITH the call, so a state
snapshot taken in round 1 means nothing in round 2 -- its interned
identities belong to a registry that no longer exists. Block-scoped
re-folding (todo-2) is exactly a later round reusing an earlier one's
state, so if per-round is ruled, todo-2's remaining work becomes "make the
snapshot registry-independent" rather than "keep one run alive".

Neither answer blocks this entry: A FULL RE-FEED PER ROUND IS ALREADY A
CORRECT REALIGNMENT, exact by construction. The loop therefore does not
wait for block scoping. Block scoping waits for the loop -- and the full
re-feed is the oracle it must equal.

todo-17  A SECOND IDE  (VS Code, Notepad++, whatever comes)
----------------------------------------------------------------------------

What the nvim work left for the next editor, measured THEN -- the Lua
client and 'down_fixture.json' are GONE since E-62 (audit r10, 2026-10-05);
the numbers are of files that no longer stand:

    feed.py               494 lines   REUSED WHOLE. The Python side is
                                      editor-neutral: JSON lines out, one
                                      UP envelope back.
    down_fixture.json       --        REUSED WHOLE. The same oracle in a
                                      neutral form, so a client in any
                                      language is held against exactly
                                      what the Lua client is held against.
    protocol.lua          154 lines   RE-IMPLEMENTED. The protocol is
                                      language-neutral; this file is not.
                                      Fold DOWN, read cells, build UP.
    view.lua              125 lines   REPLACED ENTIRELY. Editor API.

So a second RICH client costs roughly 150 lines of protocol plus whatever
its editor's own view needs -- and none of the Python side moves.

THE CHEAP PATH FIRST. Any editor that can be launched on files already
works through 'MergeToolDisplay', with no client at all:

    code --wait --diff <subject> <nominal>
    notepad++ -multiInst -nosession <subject> <nominal>

That is tier 1, and it is what a new editor should get before anyone
writes a plugin for it. A RICH client earns its cost only where the
editor can render compare's OWN alignment -- which is the whole reason
the tier exists, since an editor's own diff is a SECOND opinion beside
the one the verdict came from.

OWED, when a second client is wanted:
    a conformance suite driven from 'down_fixture.json', so every client
      answers the same questions
    the four the Lua client answers already: fold, foreign signature,
      unknown kind, truncated stream

todo-18  A BROWSER CLIENT  (the most universal RICH tier)
----------------------------------------------------------------------------

IT NEEDS NO LIBRARY, and that was measured rather than assumed: DOWN is
already JSON, so a stdlib 'http.server' streaming Server-Sent Events
delivers it, and two columns are plain DOM.

    server   python stdlib, SSE          zero dependencies
    render   two scroll-bound columns    plain DOM
    edit     a textarea                  enough for a first client

WHY IT IS THE BEST DISPLAY CLIENT, better than any editor: every cell
already carries WHY it differs --

    { "subject": "WRONG", "relation_id": "BAD_NOMINAL_DIFFERS",
      "tolerance_id": "STRING", "nominal_ref_i": 0 }

-- so a browser can colour per cell: this DIFFERED, this was tolerated
as a number, this was matched by analogy. An editor's buffer API makes
that awkward; a stylesheet makes it trivial. And the alignment shown is
still COMPARE's, which is the whole point of the tier.

WHERE IT IS WEAKER: editing. An author merging a large nominal wants an
editor. So the natural split is

    DifferenceDisplay (read-only)  -> the browser is the best client
    Accept / merge    (editing)    -> an editor, or a browser with a
                                      real editing component

EDIT THE ROWS, NOT A TEXT BUFFER. The obvious move is to embed an editor
(CodeMirror, Monaco, Ace all exist and are embeddable). It is the wrong
one: a free-form editor owns its own wrapping, breaking and scrolling,
and the nominal pane must stay ROW-ALIGNED with the subject, because the
alignment is COMPARE's. The effort would go into fighting the editor
back into alignment.

Compare hands over ROWS, so the natural model is one editable element
per row:

    row 1   [ alpha  ]  [ alpha ]      read-only | contenteditable
    row 2   [ WRONG  ]  [ beta  ]      alignment is STRUCTURAL: a cell
    row 3   [ gamma  ]  [ gamma ]      IS its row and cannot drift

No library, no wrapping problem, no scroll-binding to maintain, and
per-cell colouring from 'relation_id' comes free -- which a text editor
actively prevents.

WHAT IS LOST: multi-line edits that split or join rows. That is real, and
the loop already answers it: splitting a row CHANGES THE ALIGNMENT, which
is compare's to decide. Edit the cells, send REALIGN (todo-16), let
compare produce the new rows.

A LIBRARY EARNS ITS PLACE only if the nominal is large, or wants syntax
highlighting, or undo across rows -- none of which is true of a typical
expected-output file. Build the row-cell version first.

IF ONE IS EVER USED, one law carries over unchanged: its OWN diff view
must stay off. Monaco ships one, and using it would put a SECOND
alignment beside the one the verdict came from -- the same reason
'test-view.lua' asserts neovim's diff is not engaged. Check what those
libraries currently offer before choosing; this note should not be
trusted for their present state.

NOTEPAD++ specifically: plugins are C++ and there is no scripting host in
the box, so tier 1 ('MergeToolDisplay' launching it on two files) is
likely the permanent answer there rather than a RICH client.

OWED, when wanted:
    reuse 'down_fixture.json' as the conformance oracle (todo-17)
    the UP envelope over the same channel -- a POST, or a websocket if
      the merge loop (todo-16) wants full duplex

todo-21  THE EXPLAIN SEAM -- every silent failure names itself
----------------------------------------------------------------------------
Earned by a real evening: HWUT 1.0 answered a broken nvim interview with
'[NO INFO]' and an empty string. The empty string collapsed five distinct
events -- never spawned / died / wrong interpreter / said nothing / said
it ON THE OTHER CHANNEL -- and the decisive evidence (stderr, which held
the entire answer; nvim -l routes print() there) was collected and
thrown away. Debugging meant editing the framework to add prints.

2.0 already HOLDS every missing fact by construction: ProcsitterResult
(argv, containment, exit, stderr tail, timings) rides in
Supply.record_list and ProvisionRecord.records even in failure; stderr
is a SUBJECT, so the wrong-channel bug is visible in the data. What is
missing is PRESENTATION: the records mostly die unread.

DELIVERED (diagnosis.py + TEST/test-diagnosis.py): explain() renders
REQUEST (argv from the one source), the resolution chain, every
record's containment/exit/stderr-tail, the report token, the channels
with the wrong-channel hint; DiagnosisObserver hangs it on the seam
(12). STILL OWED beyond the list below: the resolution chain CARRIED
IN THE RECORD (today it is recomputed at render time -- honest for a
live diagnosis, not for an archived one), and session-level wiring (a
request flag that installs the observer).

OWED:

    the EXPLAIN observer   one switch that renders, per supervised
                           call: argv; the RESOLUTION CHAIN (shutil
                           .which + symlink chase -- 'nvim ->
                           /usr/local/bin/nvim -> /opt/...'); cwd;
                           exit; containment token; duration; per
                           channel the byte count and first line.
                           An OBSERVER on the existing seam (12) --
                           no operation changes.
    resolution reporting   resolve interpreters at argv construction
                           via shutil.which (the shell's semantics --
                           NEVER whereis), and carry the resolved
                           chain into the record so EXPLAIN can show
                           it. INTERPRETER_NOT_FOUND already exists;
                           now it can say what was searched.
    the wrong-channel hint 'stdout 0 bytes, stderr N>0' is a nameable
                           pattern: one display-side note in the
                           explain rendering ('output on the wrong
                           channel?'). A HINT, never a verdict --
                           provision judges nothing.

THREE LAWS, distilled from the archaeology, for any runner code here:
    (1) an empty answer is never reported empty -- it is reported WITH
        exit code, containment, and the other channel's tail;
    (2) a diagnostic path uses THE SAME call convention as the path it
        diagnoses (1.0's whereis fallback broke this: string vs list,
        and manufactured the red herring);
    (3) children inherit the environment; resolution follows PATH.
