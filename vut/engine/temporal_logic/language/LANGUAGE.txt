==============================================================================
LANGUAGE
==============================================================================

The rule-file language describes the behaviour of an entity as reactions to
events. This document states each language element and shows it in an example.
Rationale for every decision lives in RATIONALE.txt (entries R-1..R-40); this
document carries mechanics only.

Spine (reactor ruling):

              reactor                        reactor++
          (state machine)                   (mode group)
                |                                |
         .------+------.                 .-------+-------.
      behavior      behavior          behavior        behavior
     (ONE active      |              (several may be active)
      at a time)      |                  |                |
         |            |                  |                |
     causality    causality          causality        causality

Real change happens at the causality level. A behavior aggregates
causalities and nothing else; the REACTOR -- a class with behavior
content -- owns the state and receives the events: a 'reactor' governs
which ONE behavior is active, a 'reactor++' lets several run at once.


(0) Foundations: two natures, four relations, one law
======================================================
Everything the language speaks of has one of TWO NATURES, and every
construct in this document is an instance of the relations below. This
section is the design's spine; where mechanics await the type document
they are marked, but the model here governs regardless.

(0.1) The two natures
---------------------
PERSISTENT OBJECTS exist over time and occupy resources; their existence
is a RESPONSIBILITY. They come into being by construction and leave it by
destruction -- both are WORKS (12): construction hands a new debt to the
caller through an out: custody entry; destruction receives a debt
through an in: custody entry and ends it. Composing already-answered-for parts into a
record is AGGREGATION, not work: it creates no new debt beyond its parts.

EPHEMERALS -- events, and the signals built on them -- are defined on the
fly and VAPORATE UPON CONSUMPTION. They may be known or taken, never had;
consumption is their end -- no destruction, no giving onward, no ledger.
Ephemerals are the language's channel of COMMUNICATION, including the
communication of MISBEHAVIOUR: a signal is an ephemeral reporting
malfunction (12.2), consumed by the handler arm that matches it.

The two natures obey different laws throughout; a rule stated for one
never silently applies to the other.

(0.2) The four relations
------------------------
One noun, one relation, everywhere (R-41) -- member declarations, panel
entries, and binding sites all speak the same STATE NOUNS:

    is:      IDENTITY.  What a thing is; inheritance. Creates no
             possession and no debt.
    (unmarked) HAVING -- the ground state, implicit. To have is to owe:
             the haver answers for the end of what it has. 'had:' is the
             optional visibility marker -- having spelled out loud.
    known:   ACQUAINTANCE.  Access without responsibility -- a view.
             Knowing creates no debt and confers no destruction rights;
             the known must outlive the knower's use. Only ephemerals
             and knowledge are ever merely known.
    give     TRANSFER.  Custody moves WHOLE: the giver's name dies --
             it holds Nothing in the given thing's place. Giving is
             moving, never copying -- one object, one debt; and NOTHING
             CAN NEVER BE GIVEN: only a had thing gives, a known never
             (it was never had).

DIRECTION is a different question and has its own words: the panel's
in:/out: sections (12.2) say WHERE an entry moves; the marker on the
entry says WHAT the relation is. '=' at a binding site is
relation-neutral -- the site marker and the panel carry the relation
(R-41.2).

(0.3) The law of ownership tracing
----------------------------------
    GIVE OR DESTRUCT WHAT YOU HAVE.

On every path, every persistent object that is had is either GIVEN onward
or DESTRUCTED by its haver before that haver's own end. Abandonment is
the one crime. The trace of responsibility runs unbroken from the
construction site to the destruction site, through every give between --
statically checkable, because every step is one of the four relations
written in the source. (The ledger's mechanics -- the checker, containers
as collective debt, disposal policies -- bind the future type document;
the law binds now.)

THE GIVE LEAVES NOTHING BEHIND: upon give, the giver's have-relationship
becomes HAVE NOTHING -- the name is dead, and an immediate 'know that'
(keeping acquaintance with the given-away object through the dead name)
is rejected on the path (SEMANTICS 30; likewise after destruct). The
lifecycle entire -- including the KNOWING MODEL of hubs that the emitter
owes -- is the subject document HAVE_KNOW_BE.txt.

DIE UPON END OF THE HAVE-RELATIONSHIP. An object's life is bounded by its
being had: when the having ends -- the haver's own end, or the object
being given away -- the object must already be given or destructed. A
LOCAL VARIABLE IS HAD BY THE WORK THAT HAS IT: the work's terminal
(give or signal) ends the having, so a had obligation local is given
before it -- an out: custody entry is the lawful end of having -- or
destructed;
plain value locals end under the memory exemption (11.1). One law, every
scale: member, local, aggregate part.

(0.4) The line of thought
-------------------------
The language builds outward from this section, in this order:

    natures and relations        (this section)
    the class concept            reactors and types: identity, having,
                                 knowing among the members
    the work                     the act: panels speak the same state
                                 nouns; construction and destruction are
                                 works (12)
    the clockwork                the temporal work (13)
    connections                  pull, signals, pipelines (13.1)

Persistent objects and ephemerals remain of different nature at every
stage; whenever a construct touches both, its law says which nature each
part addresses.


(0.5) Nothing
-------------
ONE noun for non-existence: "Nothing" (Null, None, Nihil: graveyarded).
Two laws kill the null-check plague at the root (R-38):

NOTHING IS NEVER HAD. Having is a relation that requires existence; a
had holder (an unmarked member, an unmarked in: entry, a body local, a
have-container element) can never be or become Nothing -- checked at
every assignment.
The had world is Nothing-free BY CONSTRUCTION: no check is ever needed
on anything had in the frame of a current operation.

NOTHING IS ASSIGNABLE TO KNOWN HOLDERS ONLY. A known holder (a
'known:'-marked entry or binding site, a know-container element) is
therefore potentially Nothing, and
every OPERATION on a known demands a dominating Nothing-gate; the
compiler rejects the ungated use -- the potentiality of an inappropriate
operation is caught immediately (SEMANTICS 28). The gates:

    if: k == Nothing { signal unknown; }   # initial gate: a diverging
    ...k narrowed for the rest...           # Nothing-branch narrows all
                                            # that follows
    if: k != Nothing { target = k; }        # branch gate: k narrowed in
    else: { target = fallback; }            # the not-Nothing branch only

GATE EQUIVALENCE (ruled): 'k != Nothing', 'k != 0', and bare 'k' are
ONE gate -- Nothing is the absent value, zero its numeric face; at
runtime Nothing compares as 0 and reads false in a condition. The
'=='-forms narrow the else-side likewise:

    if: k { target = k; }                   # the same gate, spoken bare
    if: k != 0 { target = k; }              # the same gate, numerically

Work that relies on known things is naturally prone to an 'unknown'
signal -- the initial gate names that idiom. Once a gated known is
assigned to a had holder, everything downstream operates on the had
name, check-free.

(1) Lexical laws
================

(1.1) Keywords end with a colon
-------------------------------
Every keyword is colon-terminated; the colon is part of the keyword.

    is:  when:  known:  had:  in:  out:  signals:
    if:  elif:  else:  match:  case:  for:  int:  float:  step:  from:  start:
    break:  continue:  dropto  as:  in:  with:
    (R-49: 'every:' left the language; 'as:' survives on import: only)
    open:  import:

Exception -- operator, type, and definition-kind words are BARE:

    and  or  not  in  true  false  struct  list  dict
    reactor  reactor++  behavior  cause  work  clockwork  class
    give  tick  signal  destruct  dropto

"in" is therefore a taken word: no identifier may be named "in"; the
definition-kind words and the command words are likewise taken.

RESERVED -- specified in (11)-(14), implementation pending (R-24..
R-27): the keywords "groove:", "elsewhile:", "elseto:", the bare words "finished" (the
built-in exhaustion variant), "Nothing" (0.5), "have" and "know" (the
container prefixes, 10), "give", and the bare kind words "work", "clockwork", "class", "event",
"obligation".

(1.2) Definitions are name-first
--------------------------------
Every definition follows ONE form -- the name leads, the kind follows the
colon, the parameter list rides the kind word:

    <name> : <kind>[(<parameters>)] <kind sections>

    Polling : reactor { ... }
    hot : cause(threshold) temp_high when: e.value > threshold;

Read: "<name> is a <kind> about ...". The form is shared with the member
declaration "name: type;" -- one head, and the word after the colon
decides: a definition-kind word opens a definition, a type ends a
top-level declaration. ('~' abstractness died with the kinds that bore
it; whether reactors want an abstract form is OPEN.)

THE ONE ENTRY SHAPE (homogeneity, R-41 follow-up). Every parens speaks
the same entry -- "[known:|had:] <name> [: <type>] [= <default>]" --
kind parameters, panel sections (12.2), and member declarations (11.1)
alike; unmarked is had, the ground state:

    hot : cause(known: threshold, boost = 1) ...

The one exception is the SIGNAL PAYLOAD (12.2): a signal is neither had
nor known, so its payload fields stay plain.

(1.3) Docstrings
-----------------------------------------------------------------------------
A DOCSTRING is a triple-quoted string -- three double-quotes on each side --
and may span lines. It PRECEDES what it documents:

    """Watches the motor temperature and shuts down on overheat."""
    guard : reactor {
        threshold: float;
        watch : behavior { hot(90.0) => shutdown; }
    }

A docstring may document a reactor or a named cause. A docstring that precedes no definition is the MODULE docstring and
stands as the very first item of the file -- anywhere else it is an error.
Docstrings carry documentation only: they take no part in execution and do
not enter the export surface.

(1.4) Blocks are brace-delimited
--------------------------------
Every block is "{ … }"; braces are mandatory at every depth. A colon-keyword
introduces; a brace-pair delimits.

    if: <condition> { … }

(1.5) Comments
--------------
A comment runs from "#" to end of line. "#" is the sole comment delimiter.
"#{" (optional whitespace before the brace) opens a BLOCK comment, closed
by the balancing "}", nesting by brace count -- usable inline:

    c.count += 1;   # advance the counter
    make #{skin -> a fresh sprite} : work


(2) Causality (atomic behaviour)
================================

A causality links a cause to one or more effects: cause --> effects. It is
anchored in an event — an ephemeral entity of receivable change.

    button_pressed => light_on;

GRAMMAR
    "<causality>": ("<cause>", "<effects>")

(2.1) Cause
-----------
A cause is an event with an optional guard. The guard is a CONDITION (see 4)
introduced by "when:". The cause is the SOLE place a guard attaches.

    MOTOR_ON when: c.fuel == 0 => lighten_fuel_missing;

GRAMMAR
    "<cause-explicit>": ("<event>", ["when:", "<condition>"])

A cause may be named, parameterised, and referenced. The default parameter type
is float. A parameter may carry a VALUE DEFAULT (Python behaviour):

    <name> [: <type>] [= <algebraic>]

A use supplies every parameter WITHOUT a default, each at most once,
positionals before named arguments; a named argument binds a declared
parameter by name: "name = value" (D-28; the same "=" marks a declaration
DEFAULT -- position tells them apart: panel entry vs argument list). A BARE name is a reference, not a call -- no argument judgement
attaches. A named cause CONTAINS its guard; a use site supplies arguments,
not a second guard.

    OPERATION_IMPOSSIBLE : cause(fuel_limit, battery_limit)
        MOTOR_ON when: c.fuel <= fuel_limit or c.battery < battery_limit;

    OPERATION_IMPOSSIBLE(0.1, 2) => SIGNAL_REFUSE_OPERATION;

GRAMMAR
    "<cause-tail>": (["<parens-decl>"], "<cause-explicit>", ";")
    "<cause>":      ("<cause-explicit>", OR, "<call>")

(A named cause is defined through the one name-first form of 1.4:
"<name> : cause(<parameters>) <cause-explicit> ;".)

(2.2) Effects
-------------
An effect is a marker followed by a target, a command-block, or the
shrug. THREE ARROWS, three meanings (R-46 -- the spawning of a
behavior is semantically different from the spawning of an event):

    "=>"    spawns an EVENT / runs work code   (the happening arrow)
    "=!=>"  ACTIVATES a behavior               (standing up)
    "=x=>"  DEACTIVATES a behavior             (standing down;
            R-48: idempotent -- a second '=x=>' is
            a lawful no-op, no second ~EXIT)

THE SHRUG: '<cause> => ;' is a lawful effect -- pure documentation: we
do nothing upon that event; we know it may happen, we ignore it. Under
first-match it CONSUMES the event for this behavior (causalities below,
~ANY included, stay silent). Chain-final by shape.

GRAMMAR
    "<effects>":       ("<effect-marker>",
                        (("<code(causality)>", ["<effects>"]),
                         OR,
                         ("<shrug>",),
                         OR,
                         ("<spawn>", (";", OR, "<effects>"))))
    "<effect-marker>": ("=>", OR, "=x=>", OR, "=!=>")
    "<shrug>":         (";",)

'=!=>' and '=x=>' take a BARE target -- no 'to'; a behavior target
under '=>' REJECTS (activation spells '=!=>').

TERMINATOR LAW: ";" terminates a statement or effect; "}" terminates itself
-- never "};". The chain is right-recursive: the FINAL effect decides -- a
block-final causality ends at its "}", a spawn-final causality takes ";".

    E => go => stop;            spawn-final: ";"
    E => { c.n += 1; }          block-final: ends at "}"
    E => { c.n += 1; } => go;   block mid-chain, spawn-final: ";"

"=x=> X" is well-formed iff X is deactivable (R-46; the reactor row
DIED with the pipe build -- construction is standing, destruct the end):

    entity kind          deactivable
    -------------------  -----------
    event                no
    command-block        no
    behavior             yes -- in a reactor++ only; in a 'reactor'
                                (state machine) a SEMANTIC ERROR: the
                                machine may never stand stateless;
                                transitions spell '=!=>'
    reactor / reactor++  no   (died with the pipe build)
    recurring-emission   --   (R-49: the machinery died; the timer
                              concern is a plant-side feeder's)

"<call>" and "<code>" are disjoint: a command-block contains statements only; an
entity target is a "<call>". An effect needing both a mutation and an entity
target is written as two effects on one cause.

(2.3) Reference and definition
------------------------------
The declaration side is the name-first head of 1.4: the defined name, then
":", then the kind word carrying the formal parameters -- one shared form
across cause and reactor (the AST reunites head name and parameters into
one signature product). "<call>" is the use side (name +
arguments). A "(role)" suffix on a reference — e.g.
"<call(behavior)>" — is an advisory role hint walked by position; it is
non-identity and resolved in the semantic pass.

(2.4) Recurring emission                                 [RETIRED, R-49]
------------------------
The 'every:'/'as:' spawn tail, the handle namespace, and '=x=> <handle>'
LEFT THE LANGUAGE -- the recurrence bolted a lifecycle onto the spawn
(a named, cancellable thing with no panel, no definition, no
~ENTRY/~EXIT): lack of orthogonality. The timer concern moves to a
PLANT-SIDE FEEDER (the feeder-family discussion) ticking events into a
channel as script(...) feeds them.


(3) The reactor and its behaviors
=================================

THE REACTOR (reactor ruling) is the language's one reactive kind -- a
CLASS with behavior content, and an event recipient. The old character,
aspect, and free-standing behaviour DISSOLVED into it:

    'reactor'    a STATE MACHINE  -- one behavior active at a time;
                 '=!=>' deactivates the current and activates the
                 target: the TRANSITION, an atomic leave/enter pair
    'reactor++'  a MODE GROUP     -- several behaviors active at once

    MotorActivity : reactor {
        rpm: float;                       # state lives on the REACTOR
        ON : behavior {
            gas_pedal_push     => open_throttle;
            on_off_button_push =!=> OFF;  # '=!=>' the TRANSITION (R-46)
        }
        OFF : behavior {
            gas_pedal_push     => tone_notify_engine_off;
            on_off_button_push =!=> ON;
        }
    }

GRAMMAR
    "<reactor-tail>":   (["<reactor-panel>"],
                         ["is:", "<call>", STAR((",", "<call>"))],
                         "{", PLUS("<reactor-item>"), "}")
    "<reactor-panel>":  ("(", ["in:",  name, STAR((",", name))],
                              ["out:", name, STAR((",", name))], ")")
    "<reactor-item>":   ("<marked-member>", OR, "<reactor-member>")
    "<reactor-member>": (name, ":", (("behavior", "{", PLUS("<behavior-item>"), "}")
                                     OR ("work", "<work-tail>")
                                     OR ("<type>", ";")))
    "<behavior-item>":  ("<channel-group>", OR, "<causality>")
    "<channel-group>":  ((name, OR, "."), ":", "{", PLUS("<causality>"), "}")

A BEHAVIOR is ONLY causalities: no members, no works, no parameters, no
instances -- it exists nowhere but inside a reactor body, and its code's
SELF is the reactor: the bare-dot binding '.x' reaches the reactor's
member x (4.1). 'A =!=> <behavior-name>' as an effect activates that
behavior IN THIS REACTOR (R-46); '=x=>' deactivates it (reactor++
only). Causalities appear
ONLY inside behaviors inside reactors (ruled) -- the top-level causality
died with the free-standing behaviour. Within a behavior body the
causalities GROUP by in-channel (15.4); the reactor's channel panel and
the whole flow model are chapter (15).

A REACTOR HAS NO ON/OFF SWITCH (pipe ruling): construction builds it
STANDING -- 'a = TrafficLight(...);' in a work body is already a
mutation and a call, and the semantics recognises the construction. A
'reactor' stands in its FIRST declared behavior, a 'reactor++' with ALL
behaviors armed. "Active" means events REACH it: constructed, wired,
and fed is reacting -- synchronously in the deliverer's thread (no
extra thread by default; threading is a future PIPE property). The end
is 'destruct'; there is nothing in between.

"~ENTRY" and "~EXIT" are reserved, non-externally-triggered events that run on
a behavior's activation and deactivation. They take no external trigger and no
guard, and their effect is any causality effect (a spawn or a command-block,
see 2/5).


(4) Values: three sorts, two operator worlds
============================================

Values come in three sorts: a number, a truth, and a collection. The number and
truth sorts are operator worlds connected by exactly two bridges. The collection
sort has no operators -- it is constructed and consumed only. Mutation (see 5) is
a separate thing that yields no value.

ALGEBRAIC — produces a number.
    operators  + - * /        grouping ( )
    primary    numeric literal | data-access | ternary

CONDITION — produces a truth.
    operators  and or not      grouping ( )
    primary    bare condition-valued data-access | comparison | true | false

COLLECTION — a value sort with no arithmetic operators; constructed by a
    comprehension (see 4.3) and consumed by for:, an index base, a
    comprehension from:, an argument, or a mutation right-hand side.
    Compared for equality (STRUCTURAL) and searched with "in".

STRING — a quoted literal ("…") or a string member; no operator world of its
    own. Compared with == / != and searched with "in" (substring). A string
    literal is an expression atom.

BRIDGES (the only crossings into truth)
    comparison   algebraic {== != < <= > >=} algebraic -> condition
                 chaining allowed:  a < b < c  ==  a < b and b < c
    equality     two like values {== !=} -> condition; collections and
                 strings compare STRUCTURALLY (element-wise, character-wise)
    membership   <value> {in | not in} <collection or string> -> condition
                 element of a list, KEY of a dict, substring of a string
    ternary      condition ? algebraic : algebraic -> algebraic

A guard ("when:"), an "if:"/"elif:" test, and a "match:" scrutinee comparison
consume a CONDITION. Arguments and loop bounds consume an ALGEBRAIC value. A
mutation right-hand side is any sort.

(4.1) Bindings
--------------
Two bindings exist (reactor ruling; b/a/c/s died with the kinds they
named):

    e.<name>   member of the event that triggered the causality
    .<name>    THE BARE-DOT SELF: this instance's member -- the reactor
               inside behavior code and reactor member works, the class
               inside class member works. Bare names are locals and
               ports ONLY; a member is always reached through its dot.

(4.2) Data-access
-----------------
Data-access reaches a value out of a structure: a binding-qualified name or a
call, followed by zero or more index steps. It is the place layer the value
worlds, the mutation lvalue, the for: source, and the comprehension from:
all draw on. An lvalue is a data-access, so an indexed place is assignable.

    c.fuel              base only
    c.buf[i]            one index step
    grid[i][j]          chained steps (multi-dimension)
    f(x)[0]             call result, indexed
    c.buf[i] = v ;      data-access as an assignment target

Single index only; the index is an algebraic value; multi-dimension is chaining.

(4.3) Comprehension
-------------------
A comprehension constructs a collection from one or more generators with optional
filters. Generators chain left-to-right; each may carry an "if:" filter. Loop
variables are bare locals scoped to the comprehension, and may destructure.

    [ x*y   with: x, y from: pairs ]
    [ x     with: x from: xs if: x > 0 ]
    [ x + y with: x from: xs if: x > 0
            with: y from: ys ]
    [ [ a*b with: b from: row ] with: row from: matrix ]   nested

The element and each source may be any sort; a collection element nests.


(5) Command-block (imperative body)
===================================

A command-block is the "<code>" effect: it runs imperative statements and
mutates hidden variables. It runs immediately and uninterrupted when its cause
fires, is one atomic terminal leaf (no fan-out, no interleaving), and emits no
events at any depth.

    TRAVELLED_100KM => {
        c.fuel -= 8.31;
        if: c.fuel < 5.0   { c.warn = true; }
        elif: c.fuel < 20.0 { c.warn = false; }
        else:               { c.reserve = false; }
        int: i = 1 .. c.cylinders { c.checks += i; }
    }

Statements:

    mutation        <lvalue> {= += -= *= /=} <algebraic> ;
                    lvalue is a binding-qualified member, head in {e. b. a. c.};
                    "s." is the read-only inbound argument, never a target.

    if:/elif:/else: if: <condition> { … } [elif: <condition> { … }]* [else: { … }]
                    a statement brancher (NOT the value-world ternary).

    match:/case:    match: <scrutinee> { case: <pattern> { … } ... [case: _ { … }] }
                    scrutinee is an algebraic value; patterns are literal, range,
                    or glob (string-wildcard); optional default "case: _".
                    Unmatched with no default is a no-op.

    for:            for: <var> in: <collection> { … }
                    binds <var> to each element (element only, no index).

    count loop      <count-type>: <var> = <algebraic> .. <algebraic> [step: <algebraic>] { … }
                    declares a typed counter <var> inline; <count-type> is
                    int: or float: (extensible). Inclusive bounds; ".." is the
                    range operator; default step +1; "step:" sets it (negative
                    counts down). The counter is a bare local.

    enumeration     <count-type>: <i> with: <x> from: <iterable> [start: <i0>] { … }
                    the count loop's enumeration arm: <i> counts in the
                    counter's type from <i0> (default 0) while <x> walks the
                    iterable -- index and element, paired. Both are bare
                    locals.

A loop variable (for:'s var, the count loop's typed counter, the
enumeration's index and element) is a bare local name, scoped to its loop
body, never escaping it.

(5.1) Loop control
------------------
    break:      exits the nearest enclosing loop (unlabelled).
    continue:   next iteration of the nearest enclosing loop.

(5.2) Exit regions
------------------
LABELS OPERATE ON TWO ACCOUNTS (B-1, R-39), and each account has its own
face at the definition site:

  THE DEAD ADDRESS -- ":<label>:" bare. No body; C-label drop-through:
  control reaching it falls through to what follows, exactly like the
  goto labels of kernel drivers. Self-terminating: the second colon
  delimits it, as "}" delimits a block -- no ";" follows (R-24).
  "dropto <label>" is the forward-only JUMP to such an address -- the
  kernel "goto out:" cleanup idiom made safe: "goto considered harmful"
  (Dijkstra) answered by allowing only forward drops to a declared
  address. dropto targets THIS account only. Lawful in reactive bodies
  and work bodies alike.

  THE CATCH REGION -- ":<label>: => { ... }". The elseto: target: signals
  ROUTED to the label enter the block; NORMAL FLOW SKIPS IT ENTIRELY --
  nobody falls into a handler, and dropto cannot address it. The arm-
  arrow at the definition site is the reader's cue for which account a
  label is on. (elseto: routing itself is on the build list; the target
  form is settled law, and a region's signal statements already count toward
  the work's 12.4 obligations.)

    SOMETHING => {
        c.h = acquire_a();
        if: not c.h.ok  { dropto fail; }
        c.g = acquire_b();
        if: not c.g.ok  { dropto free_a; }
        dropto done;

      :free_a:   c.released_a = release_a(c.h);
      :fail:     c.status = FAILED;
      :done:
    }

"dropto" requires a target and may jump only to an exit-label defined LATER in
the body (forward-only, so it forms no loop). Exit-labels may be defined only at
the outermost body -- never inside a loop, if/elif/else, match, or any nested
block. Loops use the unlabelled "break:"/"continue:"; exit-regions use "dropto"
(jump) and ":<label>:" (define); the two never overlap. The word "exit"
is no keyword of this language (R-24 reserved it; R-43 retired it -- the
fault egress speaks "signal"). The noun EXIT-LABEL survives as the
internal name of the ':<label>:' form only.


(6) Aspect -- DISSOLVED into the reactor
========================================

The aspect died with the reactor ruling: its role -- governing the one

state machine of (3). Where an aspect was written, write a reactor.

(7) Character -- DISSOLVED into the reactor
===========================================

The character died with the reactor ruling: its role -- concurrent,

(8) Namespaces and imports
==========================

A namespace is a named scope holding nested declarations. It is re-openable and
nests to any depth; names declared within are scoped to it.

    open: graphics.sprites {
        sprite : reactor { position: 2dvector;
            idle : behavior { poke => wake; } }
        ...
    }

An import mounts a file or url under a namespace. The path is a quoted string.

    import: "lib/physics.vut" as: physics
    import: "https://example.org/shapes.vut" as: shapes

A namespace path (graphics.sprites, physics) is a plain dotted name --
distinct from a binding-qualified member access (4.1), which has an 'e.'
or bare-dot head. The parser records an import; the semantic pass mounts it
and resolves names scope-aware, walking outward from the current scope.


(9) Relation to other terminology
=================================

This section is the single place that relates the native spine to traditional
statechart vocabulary. These terms are NOT used elsewhere in the language.

    native       statechart
    -----------  ------------------------------------------------
    causality    transition / reaction
    behavior     simple state
    reactor      state machine (XOR: one state active)
    reactor++    orthogonal region set (AND: independent activation)

AND-composition is a 'reactor++' whose behaviors activate independently;
exclusivity is the plain 'reactor', where activating one behavior
deactivates the previously active.


(10) Aggregation types
======================

THE RELATION WORDS PREFIX A CONTAINER (R-38, ruled "for the moment"):
"have list" / "have dict" HAS its elements -- insertion is a give,
removal gives out or destructs, the container carries collective debt
(a container of obligations is an obligation; its destruction
discharges the remainder -- explicitly for explicit classes, SEMANTICS
27(ii)). "know list" / "know dict" KNOWS its elements -- views, no debt,
the known must outlive the container's use; destruction trivial. The
bare words stay the VALUE containers below -- the degenerate case where
the memory exemption makes the relations coincide. Custody checks bind
the type document (SEMANTICS 28, deferred).

Declarations admit three plain VARIABLE-TYPED containers (no type parameters,
no member functions):

    buffer:  list;                 a sequence of anything
    scores:  dict;                 a map of anything to anything
    point:   struct { x; y; };     named slots

A type is a built-in (int float string bool), one of these containers, or a
named type. The containers are untyped for now; type constraints (a typed list,
dict, or struct field) are a later addition. A "struct" is an anonymous slot
bundle of VALUES; a named composite kind under the relations of (0.2) is a
CLASS (11) -- the struct carries no custody vocabulary and no debt.


(11) Class                  [SETTLED -- implementation lands in the F-9 passes]
===============================================================================
A CLASS defines a KIND of persistent object (0.1): a named composite whose
members are declared under the relations of (0.2). One noun -- CLASS -- for
the composite kind; "type" remains the general word spanning primitives,
classes, and specs. (The REACTOR (3) completes the integration the old
character deferred: a reactor IS a class with behavior content.)

(11.1) Members: one brace, marked relations
-------------------------------------------
    <name> : class [is: <target>, ...]
                   [{ <class-item>+ }]
    <class-item>: [known:|had:] <name> : <type>;    a member declaration
                | <name> : work ...                 a member work (11.3)

The is:-list names AT MOST ONE concrete class, ANY NUMBER of abstract
kinds (11.5), and optionally the debt marker 'obligation' (11.2).
Concrete bases chain; the concrete spine is a path. In the RESOLVED
ancestry of any kind no '~' kind is reachable twice -- the diamond
shape REJECTS. Names are DISJOINT across the entire resolved ancestry:
a name declared twice anywhere in it REJECTS -- member, work, or
signature alike, identical panels included. A child only ever ADDS
(pure extension); there is no override and no merge; every name has
exactly one declaration and at most one body in the whole ancestry.

ONE body brace (R-41.3): member declarations and member works interleave
freely; the marker on a declaration is the relation, having implicit.

    is:        inheritance -- identity, no possession.
    (unmarked) CUSTODY members -- the instance's own; 'had:' spells the
               same out loud. Two grades:
              - VALUE members (numbers, strings, aggregates of values):
                had under the MEMORY EXEMPTION -- their end is automatic
                with the instance's end; no ceremony.
              - OBLIGATION members (11.2): had for real -- the instance
                owes their end.
    known:     VIEW members -- acquaintance, no debt, no destruction
               rights; the known must outlive the knower's use.

    sprite : class {
        pos: vec2;
        tex: gpu_texture;
        known: atlas: texture_atlas;
    }

(11.2) Obligation classes
-------------------------
"is: obligation" marks a class whose instances are TRACKED DEBTS under
the (0.3) law:

    file_handle : class is: obligation

Debt is TRANSITIVE through custody: a class with an obligation among its
custody members is itself an obligation -- aggregation carries the debts of
its parts. Debt rides the spine the same way (R-60): the base slice's
custody members are the instance's custody members -- a class whose
concrete base is an obligation is itself an obligation. '~' kinds
carry no state and never classify. Complete law: a class is an
obligation iff marked 'is: obligation', or an obligation stands among
its own custody members, or its concrete base is an obligation. Value-only classes are debt-free and live entirely under the
memory exemption. (The ledger's mechanics bind the future type document;
the classification binds now.)

(11.3) Construction and disposal are member works -- role by panel
-------------------------------------------------------------------
There is NO constructor keyword and no special form. A class body holds
MEMBER WORKS; their ROLE is read off the panel:

    a member work whose out: names the class   is a CONSTRUCTION WORK
    a member work whose in: names the class    is a DISPOSAL WORK

(the naming entry a CUSTODY entry -- a 'known:' view is never the
constructed product nor the received debt, R-41.1)

"A work that gives and signals" -- construction can fail, and its panel
says so; disposal receives the debt and discharges it.

CONSTRUCTION WORKS OPERATE ON SELF. The machinery allocates self; the
body initialises it through the bare-dot binding ('.member') and ends
with 'give:'. The body never allocates and never names the out-port
object; the out: entry is the panel's custody declaration. Position
splits the call:

    VALUE POSITION      c = car.from(...) else: { ... }
        a fresh self is allocated, the from initialises it, custody
        arrives at the target.

    LONESTANDING        engine.from(p = give p) else: { ... };
        the from runs on the CURRENT self. Lawful only inside a
        construction body, and only naming the DIRECT base's from --
        the base slice initialises one level per body, the chain
        recurses. Any other lonestanding use REJECTS.

THE TWO-BLOCK FORM (R-65): a from may carry two blocks --
'{ <provider> } { <initialiser> }'. The PROVIDER is invoked when self
must be provided; it always gives (implicitly -- it gives the self);
an empty provider is the default operation, ALLOCATION. The
INITIALISER is the body above: works on self, bare-dot. Circumstance
applies them: value position runs provider then initialiser;
lonestanding skips the provider and runs the initialiser on the
current self. The one-block form means default provider + that block
as initialiser. A pool-consulting provider makes the flyweight
sayable.

The aggregate literal (10) binds a class's OWN members only; inherited
members enter through the direct base's from.

SEMI-DECLARATION (for clean and brief class definitions). A class body may
list a member work by name alone -- '<name> : work', no panel, no body,
optionally a block comment where the panel will be -- and the COMPLETE
definition must follow at top level, spelled with the role marker:

    +<class>.<ext> : work( <panel> ) { <body> }     a CONSTRUCTION WORK
    -<class>       : work( <panel> ) { <body> }     THE disposal work

The marker asserts what the panel must show (role by panel): a '+'
completion carries the class on an out: custody entry, the '-'
completion on an in: custody entry; '+' works are
many (hence the extension), the disposal work is one (declare's duplicate
law holds it) and needs no semi-declaration. Both directions are checked:
every semi-declaration is completed, every '+' completion completes a
semi-declared member.

    pair : class {
        lo: float; hi: float;
        make #{a, b -> the ordered pair} : work
    }
    +pair.make : work(in: a, b
                      out: p : pair
                      signals: disorder) { ... give p; }
    -pair : work(in: p : pair) { ... give; }

THE CANONICAL CONSTRUCTOR is 'Class.from' -- an ordinary extension name
by convention ('from' bare is a name; only 'from:' with the glued colon
is the keyword -- name-first spacing '+pair.from : work' never meets it).
CONSTRUCTOR OVERLOADS identify BY ARGUMENT NAME: several '+class.ext'
completions may share one extension (one semi-declaration lists it once);
their FIRST input entries carry pairwise DISTINCT names, and a call of an
overloaded extension LEADS WITH A NAMED ARGUMENT -- the SELECTOR -- whose
name picks the overload. The remaining arguments bind against the
selected panel: named claim theirs, positionals fill the unclaimed inputs
in declaration order. A non-overloaded extension calls as any work
(12.5); an overload without inputs cannot be identified and is rejected.

    pair : class {
        lo: float; hi: float;
        from #{bounds, upper -> the pair; center -> around it} : work
    }
    +pair.from : work(in: bounds, upper
                      out: p : pair signals: disorder) { ... }
    +pair.from : work(in: center
                      out: p : pair signals: disorder) { ... }

    b.t = pair.from(bounds = 1, 2)  else: { disorder => ; }
    b.u = pair.from(center = 4)     else: { disorder => ; }

A full member work written inline in the class body remains lawful.
Member works are called through the class's dotted name:

    sprite : class {
        pos: vec2; tex: gpu_texture;
        make : work(in: skin
                    out: s : sprite
                    signals: no_texture(path)) { ... give s; }
        free : work(in: s : sprite
                    signals: free_failed(code)) { ... give; }
    }

    s = sprite.make("ghost") else: { no_texture(p) => signal build_failed(p); }

Composing already-answered-for parts remains AGGREGATION, written as a
literal with member bindings:

    s = sprite{pos: vec2(0, 0), tex: give t};        (form RESERVED)

The colon binds MEMBERS (a relation being established); "=>" binds PORTS
at a call (an act being wired, 12.5) -- the two never mix. An obligation
part enters the aggregate only by GIVING: the literal takes custody, the
giver's name dies -- and the giver holds Nothing in the given thing's
place (SEMANTICS 30, ruled). The marker's SPELLING is in question since
bare 'give' became the terminal statement (command-spelling ruling) --
flagged with disc-9. Aggregation is not work; ACQUISITION is (0.1).

(11.4) Destruction
------------------
An instance ends only by being GIVEN onward or DESTRUCTED (0.3).
Destruction is a WORK: a disposer receives the instance through an
unmarked in: entry -- custody arrives -- and, in its body, discharges
every obligation member --
giving it onward or destructing it in turn; value members end under the
memory exemption. A disposer for a debt-free class is legal and empty of
duty.

THE SPINE TEARS DOWN IN REVERSE (R-59): a spined class's disposal work
discharges its OWN obligation members, then lonestanding '-<base>'
runs on the current self as the LAST act -- direct base only, one
level per body, the chain recursing to the root. A spined disposal
lacking the call REJECTS; the call outside a direct child's disposal
body REJECTS. Each level discharges exactly the members it declared.

AUTOMATIC DESTRUCTION CANNOT FAIL (R-36; end mode by panel, R-61): a
disposal is an ordinary work; any class may define one. Its PANEL
decides the end mode. A disposal that declares NO signals discharges
silently; automatic ends are lawful. A disposal that DECLARES SIGNALS
makes the class EXPLICIT: destruction is never automatic -- every end
is WRITTEN with the 'destruct' statement, so every signal is answered
at its site, normal work-call discipline:

    destruct t else: { busy(when) => ; }

For explicit classes -- signalling disposals -- the compiler owes THREE PATH CHECKS (SEMANTICS 27;
staged for the type-flow phase): (i) every had local of the class is
given or destructed on ALL paths; (ii) a container holding such objects
explicitly destructs its remaining elements upon its own destruction;
(iii) an aggregate having such a member explicitly destructs it in its
disposal work. Non-explicit objects discharge automatically. The give-or-destruct
duty must be dischargeable on every path, fault paths included: a
refusable last resort would demand handlers inside handlers without
ground, and failure-during-cleanup would shadow the original fault.
Trouble during release is an occurrence to report (an EVENT on the bus),
never a refusal that re-obligates the caller: the having has ended the
moment custody arrived. The asymmetry is deliberate -- acquisition may
be refused, handing back cannot. (The philosophy in full:
EXPLANATION/explain-destruction-cannot-fail.vut.) (Containers as collective debt, disposal policies bound at
construction, and the dispose primitive bind the future type document.)


(11.5) The tilde law: ideal kinds
---------------------------------
A '~' prefix on the DEFINED NAME declares an IDEAL kind (name-first,
1.2 -- the kind word is never prefixed), for every kind word: class,
reactor, reactor++, clockwork, work. The ideal is shape without
flesh -- semantic level only, never in the objective world. The
concrete provides the flesh: classes and reactors by is:-composition,
works by conformance (12.8). For the class:

    ~drivable : class {
        steer : work(in: angle : float
                     signals: bad_angle);        a SIGNATURE -- panel
                                                 entire, no body
        honk  : work() { ... give: }             a DEFAULT BODY
    }

An abstract kind carries WORK SIGNATURES and optionally DEFAULT
BODIES. It carries NO state members. It never instantiates; it stands
only as an is:-target. A default body may call the kind's other works
and emit its declared signals; SEM-24 testimony holds over it as over
any body. A composing class answers every bodiless signature with a
work in its OWN brace; the R-56 disjointness law (11.1) governs every
name it brings.

'~x : reactor' is the abstract form of the reactor (3); its
contribution law binds a later section.

(12) Work                   [SETTLED -- implementation lands in the F-9 passes]
===============================================================================
A WORK replaces the function/exception pair: a subroutine with named input
and output PORTS (as an entity in VHDL) and a mandatory, non-reifiable
FAULT CHANNEL. Everything that can leave a work -- outputs and malfunction
signals alike -- stands on its face; the call site is statically obligated
to handle every declared signal. Invoking a work is a CALL.

(12.1) Definition forms
-----------------------
The one form of 1.2 conquers all three:

    <name> : work( <panel> ) { <body> }     a defined work
    ~<name> : work( <panel> );              a WORK TYPE (12.8): the
                                            ideal -- panel without
                                            machine, tilde law 11.5

(12.2) The panel
----------------
The panel is FLAT and DIRECTION-SECTIONED (R-41.1): the sections say
WHERE an entry moves, the per-entry marker says WHAT the relation is --
the state nouns of (0.2), having implicit. Entries are comma-separated
within a section; sections are keyword-led and juxtaposed; each entry is
"[known:|had:] <name> [: <type>] [= <default>]"; "=" is the declaration
DEFAULT marker -- the call-site binder is "=>" (12.5) -- and is
relation-neutral: the marker and the section carry the relation.

    in:       entries that ARRIVE with the call. Unmarked: custody in --
              the giver's name dies, this work now has (never defaulted
              for obligations -- a default would conjure custody from
              nowhere; custody law binds the future type document).
              'known:' marks a VIEW -- told, not owned; a defaulted
              known entry may be omitted at the call site; defaulted
              entries follow non-defaulted ones.
    out:      entries that LEAVE at give -- ordinary local variables of
              the body, delivered as the named bundle (12.4); a default
              initializer counts as assigned from the start. Unmarked:
              custody out -- the caller will have. 'known:' hands a view.
    signals:  the closed fault set, flat and top-level (a signal is
              neither had nor known): each signal an on-the-fly
              enumeration variant, optionally carrying named typed
              payload fields -- "no_convergence(residual: float)". A work
              without signals: cannot signal; its call sites carry no
              handling obligation.

    bundle_adjustment : work(in: pc_a : cloud, pc_b : cloud,
                                 known: eps : float = 1e-6
                             out: center : point2d, rotation : mat2
                             signals: no_convergence(residual: float),
                                      singular_matrix(rank: int)) { ... }

SCOPE OF SIGNALS. A work's variants exist in exactly four places: its
declaration, its body (at signal statements), the else:-handlers at its call
sites, and work types (12.8). They are not types in the surrounding
program. Two works may both declare "no_convergence"; these are unrelated
and can never meet -- except measured against one work type, whose
vocabulary then governs.

(12.3) Result semantics
-----------------------
The result of a call is a SUM: either the complete bundle of all declared
outputs, or exactly one signal. Never both, never neither, never a partial
output set. After a successfully handled call, all bound outputs are
unconditionally valid.

(12.4) Body terminals
---------------------
COMMAND SPELLING (ruled): commands are BARE words -- the ':' died on
give/tick/signal/destruct/dropto -- and EVERY simple statement ends with
';'.

    give <port>, ...;         the UNIQUE success terminal (R-37 -- the
                               keyword names the act), exactly once, and
                               ALWAYS THE LAST STATEMENT ON ITS PATH
                               (ruled): code after it is unreachable and
                               unreachable code is an ERROR. The list
                               NAMES the leaving out: ports (R-41.4) --
                               each exactly once, none foreign, none
                               missing, and IN DECLARATION ORDER (order
                               ruling: one order everywhere, the list
                               mirrors the panel; checked); the bundle
                               leaves in that same order (12.5). Bare "give;"
                               stands where no out: is declared. Every
                               path reaching the terminal must have every
                               out: entry definitely assigned
                               (SEMANTICS 23). (With bare 'give' now the
                               statement itself, the call-site custody
                               marker of disc-9 awaits a DIFFERENT
                               spelling -- flagged.)
    signal <variant>(<payload>); the fault egress (R-43: 'exit'
                               renamed) -- anywhere, any number of times;
                               leaves the work immediately with that one
                               own signal; no outputs; the same
                               unreachability law follows it. Payload
                               expressions evaluate at the signal. A BARE
                               "signal;" is the nothing-more egress of a
                               clockwork (13.3, R-41.7). In NORMAL work
                               code the statement takes NO routing
                               suffix -- a work's signal travels the
                               fault channel to the caller; the routed
                               form belongs to behavior work code
                               (15.3, R-43).

Both directions are checked: every variant-carrying signal names a
declared variant; every self-declared variant is emitted by at least one
reachable signal statement. UNREACHABLE CODE IS AN ERROR (ruled): after
give, signal, or dropto, flow only resumes at an exit-label (the jump
target).

(12.5) Call-site binding
------------------------
INPUTS follow the Python argument pattern: positionals bind in declaration
order; named arguments "port = value" bind by name (D-28); positionals
precede named (an overloaded extension's SELECTOR leads, 11.3); no port
bound twice; every non-defaulted input supplied.

OUTPUTS bind in the assignment form: targets left of "=" bind
out: entries in declaration order; known and had are PART OF THE TYPE
(agreement ruling): a known out: entry is received at a 'known:'-marked
site, a custody entry at an unmarked one -- both directions checked --
"c, r = bundle_adjustment(pc1, pc2) else: ...". The PORT-MAP form (inputs
and outputs associated by name in one parenthesis, the call read as a
wiring diagram) is RESERVED: its output-association spelling is an open
question (disc-9 C-1 residual) since "=" cannot say "flows out to".

SAME-TYPE RULE (outputs only): positional output binding is refused when
two out: entries share a type; the port-map form is demanded.

VISIBLE DISCARD: every out: entry is bound or visibly discarded -- "_"
positionally ("c, _ = ..."), or a trailing "_" in the port-map form for
"the rest is deliberately dropped". A call binding neither all ports nor
a discard does not compile.

(12.6) The aware assignment and the handler
-------------------------------------------
    c, r = bundle_adjustment(pc1, pc2) else: {
        no_convergence when: e.residual > 0.5
                        => { log(e.residual);
                             signal adjustment_failed(e.residual); }
        no_convergence  => { c = last_c; r = last_r; }
        singular_matrix => signal bad_input;
    }

A call of a signalling work MUST carry an else: block (a work without
signals takes none). No signal object is bound -- "else: {", never
"else: e {": the fault channel selects an arm; it is not a value.

THE ARM IS A CAUSALITY (R-44), and what it names is an EVENT (R-45,
14.1: a signal IS an event on the fault channel):

    (<event> | ~ANY) [when: <condition>] => <action>

  - the pattern names one event of the callee's declared fault set;
    payload reads 'e.<field>' -- the field names of the event's
    declaration (a signals: entry IS an event definition, R-45); no
    destructure rides the pattern;
  - 'when:' guards the arm exactly as it guards a cause;
  - FIRST-MATCH down the list -- uniform with dispatch everywhere
    (R-44); an arm after an unguarded ~ANY is DEAD (hard error);
  - '~ANY' matches any event of the set; under it 'e' IS NOTHING --
    an author wanting details names the event;
  - <action> is a block, a signal, or ';' (the arm-level shrug);
  - the minimal legal handler is the EMPTY BLOCK "else: {}" -- the
    written shrug; silence does not compile, deliberate omission
    leaves a searchable trace (legality constrained by the flow rule
    below).

COVERAGE IS TESTIMONY (R-44, the design point; see
explain-no-exceptions): the author testifies awareness of every
possible outcome by writing a reaction to each -- every declared
event met by an unguarded arm, or ~ANY present as the signed blanket
clause. A guard-hole (an event met only by guarded arms, no ~ANY) is
a FAILURE TO TESTIFY -- a compile error. This is why the language has
no exceptions: no outcome can travel an invisible path past an author
who never named it.

WHAT AN ARM MUST DO -- each arm independently:
  1. DIVERGE ("give", "signal <event>", or a provably non-falling path);
  2. PRODUCE SUBSTITUTES (assign the targets; ordinary definite
     assignment); or
  3. FALL THROUGH -- legal only where no invalid binding remains:
     statement-form call, or every target pre-initialized (keeps its
     prior value). Fresh bindings with a falling-through arm do not
     compile.
Code after an aware assignment sees fully valid outputs, unconditionally.

(12.7) The handler family: elseto: and elsewhile:, and the common ground
------------------------------------------------------------------------
First morpheme names the channel, second the control flow: "else:" handle
once; "elsewhile:" handle while it faults; "elseto:" handle over there.

ROUTED HANDLING. "elseto: <label> with: <carrier>;" routes this site's
fault wire to a label region further DOWN in the same body -- the honest
form of the kernel unwind cascade:

    f   = open_file(path)    else: { no_access(p) => signal unreadable(p); }
    buf = alloc(65536)       elseto: close_f with: otto;
    n   = read_into(f, buf)  elseto: free_b  with: karl;
    ...
    give;

    :free_b: {
        karl.short_read(got) => log(got);
        karl.=>              => ;
    }
        free(buf);
    :close_f:
        close(f);
    signal unreadable("io");

  - labels are spelled ":name:" (5.2); a LABEL REGION is the label, an
    OPTIONAL match block, and statements; regions stack into the FAULT
    SECTION;
  - CARRIERS are labels, not values: "with: otto" names the arrival
    channel; legal only as a pattern qualifier "otto.<variant>(...)" in
    the label's match block; carriers are inferred from routes;
  - match blocks are ARRIVAL-SPECIFIC, statements are SHARED: control
    cascading down from above skips the block; a label with no match
    block is the routed omission marker;
  - exhaustiveness PER CARRIER when a block is present; "otto.=>" the
    per-carrier default, a final bare "=>" the label-wide default;
  - every path through the fault section ends deliberately: an
    "signal <own variant>" or a jump to the give-terminal (legal only with all
    out: entries assigned -- a recovered fault); no fall-off, no fall-IN
    from the normal path;
  - DOWNWARD ONLY, SAME BODY ONLY; definite assignment holds on every
    route and cascade path.

COMMON GROUND. An inline block may end in a ground opened by the divider
"==": every non-diverging arm drops in; the flow obligation of 12.6 moves
to the ground's end; payloads are dead below "=="; at most one "==",
after all arms:

    x, y = some_work(a, b) elsewhile: {
        no_convergence(r) => { eps = eps * 10; }
        hard_error(m)     => signal broken(m);
        ==
        attempts = attempts + 1;
        if: attempts >= 5 { signal gave_up(attempts); }
    }

LOOPING CALL. "elsewhile:" re-executes the aware assignment at the
block's end (arguments re-evaluated afresh); on success, outputs bind and
control continues after the block. "break:" leaves without success,
legal under the fall-through conditions of 12.6. "elsewhile: {}" is the
visible retry-until-success loop. Inline form only: routed regions stay
loop-free.

(12.8) Work types and work references (R-64; 'spec' retired)
-------------------------------------------------------------
A WORK TYPE is an ideal work -- the panel without the machine:

    ~event_handler : work(in: event_id : int, content : str,
                          time : float);

The tilde law (11.5) governs: shape without flesh, semantic level
only, never in the objective world; work types declare no input
defaults. A work CONFORMS by structural fit: ports match by
direction, position, type; its own signals a SUBSET of the type's.
A work type stands wherever types stand -- members, ports,
containers:

    dict<int, ~event_handler>            a dispatch table
    known: p : ~event_handler;           a typed acquaintance

A WORK REFERENCE is a VALUE of a work type, assigned to a real work
at some time; from binding onward it stands in the objective world.
It is held as acquaintance (known:) -- no custody, no debt; the
known must outlive the use. An indirect call is checked against the
work type: handler mandatory and exhaustive over the type's signals
set; the type's names govern. A work-type-typed member need not emit
every variant of the type's set (the type is a promise for a
family); the every-variant-emittable check of 12.4 applies to
self-declared sets only.

(12.9) Fallible primitives
--------------------------
Division and modulo may emit the built-in variant "div_by_zero"; a
statement containing a fallible division carries a handler -- the same
three forms. One handler per statement, over the UNION of the statement's
fault sources; evaluation is left-to-right. Provably nonzero divisors are
exempt (SEMANTICS 21 holds this check today). "div_by_zero" obeys every
ordinary signal rule. The principle generalizes to any fallible primitive
the language later defines.

(12.10) Signals never travel
----------------------------
A variant is not nameable outside the four places of 12.2, so re-raising
a foreign signal is INEXPRESSIBLE: a work reporting trouble upward
signals with one of its OWN variants -- every level speaks of malfunction in its
own vocabulary. Payloads may travel; tags may not. A signal can never be
stored, collected, or re-raised at a distance: a branch taken, not a
value.


(13) Clockwork              [SETTLED -- implementation lands with the work construct]
===============================================================================
A CLOCKWORK is the work family's temporal member: a pull-driven producer,
the single linearization of a state machine (kin to the aspect, whose
behaviours are free states; the kinship is noted, the constructs are
separate, R-25).

(13.1) Topology
---------------
A clockwork may PULL MANY (its inputs are themselves clockworks, consumed
via next()), may KNOW things, and is PULLED BY EXACTLY ONE consumer through
its single outward port, next(). Its signals are received by the puller's
"else:" handler. The winding relation admits no cycle. Pipelines are chains
of clockworks in which only the final consumer pulls; each stage's
exhaustion and faults translate upward through ordinary handlers -- forced
translation, flowing through time.

(13.2) Panel
------------
The definition follows the one form (1.2) with the flat panel of 12.2:

    in:       entries arriving at winding -- unmarked into custody,
              'known:' a view for the run
    out:      the PER-TICK outputs (panel and terminal correspond:
              out: declares, tick delivers, signal ends the stream)
    signals:  the closed fault set

    line_reader : clockwork(in: f : file_handle
                            out: line : string
                            signals: io_error(code: int)) { ... }

What a clockwork takes at winding it holds across ticks. (The custody
ledger across ticks and the written early-disposal path "winddown:" bind
the future type document.)

(13.3) Egresses and waits
-------------------------
Three egresses close a body stretch:

    tick             deliver the declared out: bundle implicitly and
                      SUSPEND until the next pull; no operands -- the
                      panel already named everything (a per-tick delivery
                      names nothing anew, so tick stays bare, R-41.4)
    signal;          orderly exhaustion -- the BARE, nothing-more egress
                      (R-41.7, R-43): the puller receives the built-in
                      variant "finished". A clockwork never speaks give --
                      it has nothing to give, only ticks to deliver and an
                      end to announce (checked, R-41.4); bare signal is
                      catcher-mandatory at the pull site (13.4).
    signal <variant> fault mid-stream, one of the own declared signals

Three waits suspend a running clockwork, one law for all -- progress is
guaranteed because each is crossed only when the outside world acts:

    tick             awaits the next pull from below
    groove: { arms }  awaits causes (the clockwork's WAIT construct,
                      R-25(3)): the script parks; a firing arm cause runs
                      its arm and the script continues -- an arm may
                      deliver (tick) or fault (signal) from within
    next() on input   awaits delivery from above; EVERY next() is a
                      suspension point of the caller

(13.4) The pull
---------------
next() is the event that runs the clockwork: the puller is the clock.
There is ONE spelling -- next() is intrinsically potentially-suspending;
no wait-variant exists. Its match domain is the declared signals: set
UNION the built-in variant "finished" (exhaustion is an event -- no
option types, no sentinels):

    v = cd.next() else: {
        finished => break:;
    }

Winding is an ordinary call -- no constructor: instantiation is calling
the clockwork's name with construction arguments, an aware assignment
with handled faults.

(13.5) Consumption loop
-----------------------
    for: v from: cd { ... } else: { ... }

"from:" announces the pulled source plainly -- a wound generator, by
name or wound at the loop ("generator = cw(args); ... for: v from:
generator"); the 'from: give' custody flavour was RETIRED by ruling.
"finished" IS the loop's own end. The trailing else: must cover the
remaining signal set and is omitted exactly when that set is empty.
Disposal of the consumed run binds the future type document.

(13.6) A complete small clockwork
---------------------------------
    countdown : clockwork(in: n : int
                          out: value : int) {
        int: i = 1 .. n {
            value = n - i + 1;
            tick;
        }
        signal;
    }

    for: v from: countdown(10) { print(v); }



(14) Ephemerals             [SETTLED -- implementation lands in the F-9 passes]
===============================================================================
Ephemerals are the second nature (0.1): defined on the fly, VAPORATING
UPON CONSUMPTION -- known or taken, never had; no construction ceremony,
no destruction, no ledger. They are the language's channel of
communication, including the communication of MISBEHAVIOUR.

(14.1) One concept
------------------
The EVENT of section 2 (the causality's anchor) and the mechanism behind
a work's signals (12.2) are ONE concept -- an ephemeral value carrying a
variant and its payload. Section 2 is the event on the reactive bus;
this section is the event as data; a SIGNAL is the same creature on the
FAULT channel -- one mechanism, two channels.

THE EVENT DEFINITION (R-45) is the freestanding form:

    blink : event(v, kind);
    heartbeat : event();

and a signals: entry of a work/clockwork panel IS this same definition
in panel position -- 'signals: too_small(gap)' declares the event
'too_small(gap)', scoped as the work's fault set (the 12.2 scoping).

THE NAME-ONLY ENTRY (R-47): a signals: entry may RELATE to a defined
event -- and naturally SHADOWS it:

    blink : event(v, kind);
    meter : work(... signals: blink) { ... }    # name-only

ADOPTION: the entry takes the definition's field structure -- the
catch reads e.v, e.kind; no respelling. THE SHADOW: within the work's
fault places (12.2) the name means THIS WORK'S FAULT; the outer event
is hidden there. 12.2 and 12.10 stand entire -- the fault stays
ephemeral and work-local, never channel cargo; two works adopting
'blink' own two separate faults; a behavior's routed 'signal blink to
note' (outside the fault scope) still emits the GLOBAL event.
Structure adopted, identity local. A name-only entry resolving to no
definition is the bare signal of old.

One noun -- EVENT, the ephemeral; 'signal' names the VERB (the emitting
statement, R-43) and the fault-channel ROLE. ARITY is checked (the F-9
slice): a signal statement carries exactly its entry's fields --
respelled or ADOPTED (R-47) -- and an emission of a defined event
carries only declared field names. The RESPELLED entry mismatching its
definition stays a flagged fork.

(14.2) Event-typed entries and the matcher
------------------------------------------
An event-typed in: entry declares the variants that travel with the
call; the bare variant names are in scope exactly within that argument
list:

    set_level : work(in: known: level : event(GRADE_5, FULL(v: int))) { ... }
    set_level(FULL(v = 3));

The EVENT MATCHER applies the handler-block anatomy (12.6) to an event
variable -- first-match, dead-arm error, exhaustiveness over the declared
set, payload scoping per arm -- all rules unchanged. Consumption by a
matching arm is the ephemeral's END.

(14.3) Signals: the misbehaviour ephemerals
-------------------------------------------
A signal IS an event (R-45) and adds the fault-channel laws of (12):
non-reifiable (12.10), scoped to exactly four places (12.2), consumed
first-match by the else:-arm -- itself a causality in form (R-44) --
that matches it. Payloads may travel; tags may
not. That misbehaviour is spoken in ephemerals is by design: trouble is
an occurrence to react to, never an object to own.


(15) The pipe model           [RULED AND BUILT -- the pipe pass]
===============================================================================
ALL FLOW IS ROUTED. An event travels a CHANNEL from a sender to its
subscribers; a bus is simply a shared input channel; global broadcast
dispatch is no more. Wiring is written in WORK bodies -- the plant is a
programme, not a configuration.

(15.1) Channels and the panel
-----------------------------
A CHANNEL is a PUBLISH/SUBSCRIBE OBJECT -- the routing map is NOT inside
the reactor. The reactor HAS its channel objects: created with it,
destructed with it, named in its panel. The channel KNOWS its
subscribers (known-hub semantics, HAVE_KNOW_BE (3): a destructed
subscriber reads Nothing and delivery skips it).

The reactor panel names channels PLAINLY -- no types, no markers; a
channel is not a data port:

    lamp : reactor(in: cmd out: status) { ... }

    in:    channels the reactor RECEIVES on
    out:   channels the reactor PUBLISHES on

Beside the named channels every reactor has its SELF channel, spelled
'.': the one place it hears its own emissions (15.3, 15.4).

(15.2) Wiring is work
---------------------
'a = TrafficLight(...);' instantiates -- a mutation and a call, no new
grammar; construction builds the reactor STANDING (3). The WIRE is a
work statement creating a PIPE:

    a ----> b;                  the plain arrow
    a --[ statusx ]--> b;       the channel-named arrow

Dash sections carry TWO OR MORE dashes ('a --> b' is a wire, 'a-> b' is
not one). Wiring registers the destination as a SUBSCRIBER of the
source's out channel. The wire's channel must stand in the source's
out: AND the destination's in: -- both ends checked (SEMANTICS 31). The
plain arrow rides the source's SINGLE out: channel; both ends are bare
body locals holding constructed instances.

GRAMMAR
    "<wire>": (name, (("--+[", name, "]", "--+>"), OR, "--+>"), name, ";")

(15.3) Emit routing
-------------------
An emission takes an optional 'to' suffix -- a bare word naming one of
the emitter's out: channels:

    <cause> => <event-spec> to <channel>;

Suffix-less send FANS: the event publishes on EVERY out channel PLUS the
self channel. Fan-out at a channel is deliver-to-all subscribers.

THE STATEMENT FORM (R-43): inside BEHAVIOR WORK CODE (an effect's
command block) the signal statement is the same emission --

    <cause> => { ...; signal <event-spec> [to <channel>]; ... }

-- equivalent to the arrow '=> <event-spec> [to <channel>]': 'to' names
an out: channel, suffix-less FANS, flow CONTINUES (an emission, not an
egress). The arrow form and the statement form coexist. In NORMAL work
code the same word is the fault egress and takes no routing suffix
(12.4); the position is never ambiguous.

GRAMMAR
    "<spawn>":       ("<call>", ["to", name],
                      ["every:", "<numeric>", ["as:", name]])
    "<signal-stmt>": ("signal", [(name, ["<parens-arg>"],
                                  ["to", name])], ";")

(15.4) Receive routing: channel groups
--------------------------------------
Within a behavior body, causalities GROUP by in-channel; the group head
is the channel name, or the bare dot for the SELF channel:

    RED : behavior {
        cmd: {                       # events arriving on 'cmd'
            go =!=> GREEN;
        }
        .: {                         # the reactor's own emissions
            self_check => { .n += 1; }
        }
    }

THE GROUP LAW: a group's channel stands in the panel's in: ('.' is
always lawful). With ONE in-channel the grouping may be omitted -- bare
causalities belong to that channel; with none declared they belong to
the self channel. Ungrouped causalities beside SEVERAL in-channels are
UNLAWFUL -- messy interfering namespaces (SEMANTICS 31).

'~ANY' AS A CAUSE (R-44): any event that comes -- in a group, any event
arriving on that group's channel. Under ~ANY, 'e' IS NOTHING; behaviors
stay NON-exhaustive -- ~ANY here is convenience, never obligation (the
testimony law belongs to the else: block, 12.6).

TWO LEVELS, NEVER MIXED (R-44, scope ruling): a reactor++ ROUTES an
incoming channel event to ALL live behaviors, in the order of their
textual position (a dead behavior is skipped); INSIDE one behavior the
arm-list is a first-match switch -- one causality fires, the rest of
that list stands suppressed (so an unguarded ~ANY reads as "everything
the causalities above did not take"). Routing between behaviors,
switching within one.

(15.5) Delivery
---------------
The publisher delivers to ALL live subscribers, synchronously in the
deliverer's thread (no extra thread by default; threading is a future
PIPE property). A destructed subscriber reads Nothing and is skipped --
no dangling delivery can exist by construction. Zero live subscribers
leaves the trace line

    drop <channel> <event>

The synchronous-instant law of dispatch is unchanged: one delivery is
processed to completion -- every matching causality of the receiver's
armed behaviors, guards fixed at arrival -- before the next; emitted
events append (breadth, no re-entrant dispatch).

(15.6) Feeders and drains
-------------------------
A FEEDER is a PROVIDED class-type-like kind: an event source with out
channels and no in channels (keyboard, file, socket, joystick, timer,
...); it is constructed and wired like anything else. The harness
feeder replays a WRITTEN event sequence for golden masters -- one event
per drain step; an entry is an event name with an optional D-28
named-argument payload (R-42):

    f = script("dial_turned(delta = 2.5); temp_high(value = 95); go");
    f ----> c;

The mirror kind -- the DRAIN (in channels only; file writer, display,
sink) -- follows; the TRACE is conceptually the built-in drain.

(15.7) A complete small plant
-----------------------------
    lamp : reactor(in: cmd out: note) {
        RED   : behavior { cmd: { go => blink to note =!=> GREEN; } }
        GREEN : behavior { cmd: { go =!=> RED; } }
    }
    (One causality, a CHAIN of two effects -- emit, then transition:
    under first-match (R-44) two separate 'go' causalities would fire
    only the first; the chain is the idiom for "both".)
    horn : reactor(in: note) {
        count: float;
        LOUD : behavior { blink => { .count += 1; } }
    }
    plant : work() {
        f = script("go; go");
        a = lamp();
        h = horn();
        f ----> a;
        a --[ note ]--> h;
        give;
    }

(16) The physical unit type                       [RULED AND BUILT -- R-50]
===========================================================================

(16.1) The literal and the type
-------------------------------
    <number> "[" <unit> "]"          the unit-carrying literal
    <name> : physical[<unit>];       the declared type

    .dist  = 6.0 [m];
    speed : physical[m/s];

A bare number is DIMENSIONLESS (the zero vector); the dimensionless
case costs nothing -- a plain number stays a plain number.

(16.2) The unit grammar
-----------------------
A <unit> is a PRODUCT/QUOTIENT of unit names:

    <unit>    : <uprod> ("/" <uprod>)*        left-assoc: J/kg/K == J/(kg*K)
    <uprod>   : <ufactor> (("*" | WS) <ufactor>)*   asterisk AND
                                                    whitespace multiply
    <ufactor> : <uname> [<upower>]
    <upower>  : "^" <signed-int>              m^2, s^-2
              | "^(" <int> "/" <int> ")"      m^(1/2) -- rationals
                                              parenthesise ('m^1/2'
                                              would collide with the bar)
              | <unicode-superscript>         m², s⁻² -- lifted signed
                                              integers

Names are the seven SI bases or the derived units of UNITS.txt
(N, J, W, Hz, ...); an unknown name REJECTS [UNIT].

(16.3) The representation -- surface, canonical, display
--------------------------------------------------------
    SURFACE    the author's spelling -- any of them;
    CANONICAL  the RATIONAL EXPONENT VECTOR over (kg, m, s, A, K,
               mol, cd): product = vector ADD, quotient = SUBTRACT,
               power = SCALE, equality = vector EQUALITY -- one
               normal form, no cancellation algorithm;
    DISPLAY    the QUOTIENT of nominator to denominator: positive
               powers left of the bar, negative right, sorted; '1'
               the dimensionless nominator; a multi-term denominator
               parenthesises.

    [N] and [kg m/s^2] are ONE unit and PRINT identically: kg*m/s^2.
    [J/kg/K] displays m^2/(s^2*K).    [s⁻²] displays 1/s^2.

(16.4) The algebra -- the unit is part of the TYPE (R-51)
----------------------------------------------------------
The unit is part of the value's TYPE, and the algebra below is that
law's observable meaning in every expression:

    + -           same vector required -- unit_mismatch else;
    * /           vectors add / subtract: units DERIVE
                  (.dist / 2.0 [s] IS an m/s);
    comparison    same vector required;
    scalar        a bare number scales: 3.0 * .speed stays m/s;
    collapse      a derived ZERO vector is a plain number again
                  (.dist / .dist is 1.0, no unit);
    zero value    a physical member's P-5 zero is the UNITED zero
                  (0.0 [m/s]) -- the declaration's unit rides it.

THE SEAM: a write into a declared-physical place checks the value's
vector against the declaration -- statically where both are known
(F-9 carries the full static flow), and at RUN TIME as the built-in
fault 'unit_mismatch' beside div_by_zero (SEMANTICS 21): catchable at
an aware statement, payload e.left / e.right the two canonical
displays.

    .speed = .dist else: {
        unit_mismatch => { log(e.left); }     # 'm/s', 'm'
    }

(16.5) Representation freedom (R-51)
------------------------------------
HOW an implementation represents the unit is a codegen concern, not a
semantic one. Two conforming strategies:

    the REFERENCE INTERPRETER (Python) carries the rational-exponent
    vector on values -- validation is its job, thoroughness is free
    there, and the trace oracle ('set .speed = 3.0 [m/s]') is its
    voice;

    the LUAU EMITTER erases units on statically-proven paths (a typed
    member's arithmetic compiles to bare numbers) and tags only
    VARIANTS -- values whose type travels at run time (untyped locals,
    event payload fields, heterogeneous containers) -- checking at the
    boundary where a variant meets a typed place.

The reach of erasure equals the reach of the static typing net: what
F-9 proves, the emitter may drop.
