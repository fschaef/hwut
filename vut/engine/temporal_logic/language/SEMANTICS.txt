==============================================================================
SEMANTICS
==============================================================================

Semantic constraints -- the pass-2 checks the grammar does NOT enforce. The
parser accepts a wider language; this document lists what the semantic unit must
verify and reject. Authority: this file for the checks; RATIONALE.txt (R-n) for
why; LANGUAGE.txt for mechanics; grammar.py for the accepted surface.

Each entry: the CHECK, its SOURCE rule(s), and the rationale reference. Every
entry carries an explicit SEVERITY in its title line:

    [REJECT]  elaboration fails: the module cannot become a SemanticModule.
    [WARN]    elaboration proceeds: the semantic unit emits a remark naming
              the site and the reason; the produced SemanticModule is
              unaffected.

A WARN entry is a DELIBERATE non-fatal check -- not an unenforced rule and not
an oversight. A missing severity marker is a format error, never an implicit
default.


(1) Deactivation admissibility                            [REJECT, R-1/R-46]
-----------------------------------------------------------------------------
"=x=> X" is well-formed iff deactivable(X). The parser accepts "=x=>" before any
target; the semantic unit rejects it where the target is not deactivable.
    deactivable:  behavior yes -- in a reactor++ ONLY; in a 'reactor'
                  (state machine) REJECT [REACTOR]: the machine may never
                  stand stateless, transitions spell '=!=>' (R-46);
                  reactor / reactor++ NO (died with the pipe build);
                  recurring-emission handle -- DIED with R-49;
                  event no, command-block no.
    THE THREE-ARROW LAWS (R-46, checked): a behavior target under '=>'
    REJECTS (activation spells '=!=>'); '=!=>' demands a behavior of
    this reactor; '=!=>'/'=x=>' take a bare target (no 'to', no
    'every:' -- R-49 then retired 'every:' from the language).


(2) Guard placement                                             [REJECT, R-5]
-----------------------------------------------------------------------------
A guard ("when:") attaches only to a cause. A named cause carries its own guard;
a use site supplies arguments, not a second guard. (Grammar already restricts
"when:" to <cause-explicit>; the no-second-guard rule on a cause-ref use is the
pass-2 part.)


(3) Command-block emission ban                                  [REJECT, R-6]
-----------------------------------------------------------------------------
A command-block (and every nested branch/loop body) emits no events: it contains
no <call>-to-entity and no effect marker. (Structural in the grammar -- the
statement world has no effect production -- so this is a confirming check, not a
primary one.)


(4) Scope of member bindings                              [REJECT, R-9, §4.1]
-----------------------------------------------------------------------------
Every member access names its binding (reactor ruling; b/a/c/s died):
    e.       inside a causality (the fired event's member)
    . (bare) THE SELF -- the reactor's member inside behavior code and
             reactor member works; the class's member inside class
             member works
The semantic unit rejects a binding used outside its available scope;
the refinement of self-availability (a bare-dot in a free work, say)
is PARTIAL -- the head is admitted structurally, deeper placement law
lands with the type document.


(5) Lifecycle events                                           [REJECT, R-10]
-----------------------------------------------------------------------------
~ENTRY and ~EXIT are reserved, non-externally-triggered. They take no external
trigger and no guard. They may appear only as the cause of a causality in an
entity body. (Grammar admits them as events; the no-guard / reserved-use checks
are pass-2.)


(6) Loop-variable locality                                     [REJECT, R-13]
-----------------------------------------------------------------------------
A for: loop variable, a count-loop typed counter (int:/float: v = a .. b), or the enumeration arm's index-and-element pair (D-17) is a bare local, scoped to its loop body; it
does not escape and does not shadow a binding-qualified name (no e. or bare-dot
head). A comprehension's destructuring variables are likewise local to the
comprehension.


(7) Exit-region discipline                               [REJECT, R-14, R-24]
-----------------------------------------------------------------------------
The exit-region is the kernel goto-label idiom made safe ("goto considered
harmful" -- Dijkstra -- answered by forward-only drop-through). Checks:
  (a) ":<label>:" DEFINES a bare drop-through label (no body, C-label
      semantics: control falls through it to what follows; self-terminating,
      R-24 -- the second colon delimits, no ";").
  (b) An exit-label may be defined ONLY at the OUTERMOST function/command-block
      body -- never inside a loop, if/elif/else, match, or any nested block.
  (c) "dropto <label>" is the forward-only JUMP: it may target only an
      exit-label defined LATER than the dropto in the same outermost body. A backward or
      self target is an error.
  (d) "dropto <label>" requires a target: the label must be defined by some
      ":<label>:" in the body; an undefined label is an error.
  (e) break:/continue: are unlabelled and bind to the nearest enclosing loop.


(8) Match patterns                                             [REJECT, R-13]
-----------------------------------------------------------------------------
Match scrutinee is an algebraic value; patterns are literal, range, or glob
(string-wildcard), with an optional default "case: _". Exhaustiveness is NOT
checked (no closed member set); an unmatched scrutinee with no default is a
no-op.


(9) Data-access and lvalues                                    [REJECT, R-16]
-----------------------------------------------------------------------------
A data-access is a binding-qualified name or call, then chained "[<algebr>]"
index steps. An lvalue is a data-access (indexed assignment is well-formed).
Single index only (no slices, no comma-tuples). Index is an algebraic value.
PASS-4 HALF (the lvalue law): a mutation lvalue is a binding-qualified
member, head in {e, b, a, c}; "s." is read-only (arguments are never
written); a non-binding lvalue head is rejected. Every binding level has a
DEFAULT INSTANCE in the currently open scope, so a binding never rejects on
POSITION -- the recipe records binding and member; which concrete instance
is link's business.


(10) Collections                                               [REJECT, R-17]
-----------------------------------------------------------------------------
A collection is a value sort with no operators: constructed by a comprehension
(or literal), consumed by for:, an index base, a comprehension from:, an
argument, or a mutation RHS. The semantic unit rejects any attempt to operate on
a collection (there is no collection algebra yet). A comprehension's generators
chain left-to-right; each may carry an "if:" filter.

"[" disambiguation: "[<algebr>]" glued after a base is a data-access index step;
a standalone "[<element> with: ...]" is a comprehension. The parser separates
them by content (LL(2)); confirm on real input.


(11) Recurring emission                                      [RETIRED, R-49]
-----------------------------------------------------------------------------
The recurring spawn and its handle LEFT THE LANGUAGE (R-49 -- lack of
orthogonality); the timer concern is a plant-side feeder's (held
discussion).


(12) Namespaces and imports                                [REJECT, R-18, §8]
-----------------------------------------------------------------------------
"open: <dotted> { ... }" opens a named scope; it is re-openable and nests
unrestricted; names declared within are scoped to it. A <name-dotted> is a plain
dotted path, NOT a binding-qualified member access (no e. or bare-dot head); the
two dotted-name notions must not be conflated.

"import: \"<path>\" as: <dotted>" mounts the quoted file/url under the given
namespace. The parser records the import; the semantic pass mounts it: it reads
the imported unit's exported names (name -> kind, scope) into the export table
WITHOUT touching references; later resolution reads from there. Names resolve
scope-aware: a bare reference resolves within the current scope, then walks
outward.


(13) Route-by-role                                              [REJECT, R-8]
-----------------------------------------------------------------------------
Every grammar OR-alternation whose branches build different AST types tags each
branch with a role; the semantic unit routes by that role to the matching AST
factory. A role is advisory and non-identity (it never affects lexing/interning/
FIRST_2) and is checked only for spelling against the ROLES vocabulary at load.
A missing role on a same-node-kind alternation (operator-token choices) is not an
error -- those build one node.


(14) Aggregation types                                         [REJECT, R-19]
-----------------------------------------------------------------------------
list, dict, and struct { x; y; ... } are plain VARIABLE-TYPED containers: no
type parameters, no member functions. Element/key/value/field types are dynamic
-- the semantic unit performs no element-type check (there is no declared
element type yet). Type constraints are a deliberate future addition. A struct
field is a bare named slot.


(15) Count loop                                                [REJECT, R-13]
-----------------------------------------------------------------------------
"<count-type>: <var> = <begin> .. <end> [step: <step>]" declares a typed bare-
local counter. ".." is the range operator -- two dots, lexed by maximal munch
distinct from the single member-access "." (so "1..10" and "c.x" do not
collide); confirm on real input. <count-type> (int:/float:) is role-bearing and
extensible. Bounds and step are algebraic; bounds inclusive; default step +1.
The semantic unit gives the counter the declared numeric type and scopes it to
the loop body.


(16) Clockwork                                             [RETIRED, R-25]
-----------------------------------------------------------------------------
The tick-paced clockwork left the language (R-25); the successor -- the
pull-driven clockwork -- landed with the work construct. The aspect that
once hosted this section DIED with the reactor ruling (the reactor of
LANGUAGE 3 unifies aspect and character); reactors take NO panel --
they are classes, constructed by works. The number is kept as a
tombstone.
(17) Abstract-target remark                                [WARN, R-10, F-3]
-----------------------------------------------------------------------------
An effect targeting an ABSTRACT entity -- "=> X" or "=x=> X" where X is
defined with the "~" marker (R-10) -- is WELL-FORMED and elaboration proceeds.
The semantic unit emits a remark naming the site and the abstract target. It
is not yet known whether a variable may someday reference an abstract
behaviour, so the language does not hard-block the construct structurally --
but every occurrence must be visible: "even if it is to make ourselves aware
when making design decisions related to abstract behaviors" (FR ruling on
fork F-3, REACTIVE-ENGINE-REBUILD). This is the first WARN-severity entry;
its non-fatality is deliberate, not an omission. NOTE (reactor ruling):
'~' abstractness left the surface with the old kinds, so this warning
currently has NO TRIGGER -- it stands dormant until the abstract-reactor
question is ruled.

(18) Duplicate declaration                              [REJECT, pass-3, F-6]
-----------------------------------------------------------------------------
The same name declared TWICE in the SAME scope is rejected: two definitions,
a definition and a member declaration, an import alias shadowing either, or
an "open:" whose path segment names something already declared as a
non-namespace. The FIRST declaration stays authoritative -- the declare walk
continues past the rejection (collect and continue), so every further
duplicate in the file is reported in the same run, and later diagnostics keep
their anchor. Re-opening a NAMESPACE path is NOT a duplicate: each link is
published once and a re-open EXTENDS the scope (renewal decision, R-18).
Severity is REJECT (fatal at the next phase boundary): an ambiguous export
surface must never reach elaborate. Detected by the declare unit, which runs
only behind the strict F-6 gate -- any parser diagnostic blocks declare, so
this entry is judged over clean trees only.

(19) Reference resolution                                   [REJECT, pass-4]
-----------------------------------------------------------------------------
EVERY reference resolves or rejects (the spine contract: access KNOWN,
always). The resolution surface is the module's own declared surface plus
every mounted peer's, scope-aware outward (12); declaration-first ordering
guarantees the full surface exists before any module elaborates. The ONE
place a name may resolve to nothing without rejection is a CAUSE TARGET or
an EMISSION TARGET (an effect's spawn, a clockwork emit): there it IS a raw
event (R-1) and the recipe records kind 'event' -- a known access, not an
unresolved one. Bindings (e/b/a/c/s) are always known: each level has a
default instance in the open scope (see 9). RESIDUE -- written segments
beyond the matched name -- is verified as far as the declared surface
reaches: its FIRST segment into a definition-kind or named-cause target must
name a declared member (a parameter or a declared member name), local
and mounted
alike; deeper residue (struct fields) and residue under a binding travel to
link, recorded on the recipe.


(20) Arguments -- the Python law                       [REJECT, pass-5, D-11]
-----------------------------------------------------------------------------
A parameter may carry a VALUE DEFAULT: "name [: type] [= <algebr>]" (D-11).
A BARE use of a name is a REFERENCE, not a call -- no argument judgement
attaches. A PARENTHESISED use of a resolved parameterised target (a
definition or a named cause) is judged: positional arguments come first (a
positional after a named argument is rejected); every parameter WITHOUT a
default is supplied exactly once; no parameter is supplied twice
(positional-plus-named double cover included); a named argument naming no
declared parameter is rejected; more positionals than parameters is
rejected. Targets without a declared surface -- raw events, bindings,
locals, residue-navigated members -- are never judged here. Argument TYPES
(the sort layer) are deliberately not this entry's.

(21) Division requires a fault handler                     [REJECT, pass-10]
-----------------------------------------------------------------------------
A division ("/" or "/=") whose denominator is not PROVABLY NONZERO -- a
nonzero numeric constant, optionally negated -- may divide by zero at run
time and therefore requires the "else:" fault handler (the let-else form,
without the let). The handler SURFACE IS PENDING: until it lands in the
grammar, such a division is rejected outright. A constant nonzero
denominator ("x / 2", "x /= -4.0") needs no handler and passes silently.
The check is elaborate's, over every algebraic expression and mutation.

(22) Docstring placement                                   [REJECT, pass-11]
-----------------------------------------------------------------------------
A docstring (three-double-quote boundaries, multi-line) PRECEDES the
definition it documents: a reactor or a named cause; it rides that definition's product. A docstring that precedes no
definition is the MODULE docstring and is lawful only as the file's very
first item. Anywhere else a bare docstring documents nothing and is
rejected. A docstring before a top-level DECLARATION is parseable (grammar
D-20, a consequence of the name-first factored head) but documents nothing
this law admits: it is rejected; the declaration itself remains published.
Docstrings are inert to execution and to the export surface.

egress) names no

(24) The aware statement                                  [REJECT, PARTIAL]
-----------------------------------------------------------------------------
A statement carrying an "else:" handler covers the UNION of its fault
sources (LANGUAGE 12.9): within such a statement the SEMANTICS-21
division rejection is suppressed -- the runtime raises div_by_zero into
the handler instead.

THE ARM (R-44/R-45): '(<event> | ~ANY) [when: <cond>] => <action>' --
the arm IS a causality in form; the pattern names an EVENT of the
callee's fault set; payload reads 'e.<field>' (names from the event's
declaration, carried to the catch by the raise); first-match; under
~ANY, 'e' is Nothing. CHECKED TODAY: guard expressions walk; an arm
after an UNGUARDED ~ANY is dead -- REJECT [STRUCTURE]; at most that one
blanket ends the list.

COVERAGE IS TESTIMONY (R-44, the law) -- CHECKED over RESOLVED
callees (the F-9 slice): for a call of a resolved top-level signalling
work, every event of its declared fault set must be met by an
UNGUARDED arm naming it or ~ANY present -- a guard-hole REJECTS; an
arm naming a NON-fault of the callee REJECTS; the MANDATORY-HANDLER
direction REJECTS (a signalling work called without else:, and a
signalling work buried in EXPRESSION POSITION -- its faults have no
arm there, 12.6); a PRIMITIVE statement's arms may name only the
built-ins (div_by_zero, unit_mismatch). DEFERRED with the remaining
PARTIAL: unresolved/namespaced callees, and the flow obligations of
12.6 (diverge / produce substitutes / guarded fall-through).


(25) Semi-declaration and completion                      [REJECT, PARTIAL]
-----------------------------------------------------------------------------
D-27. A class body's semi-declared member work ('name : work', empty
panel, no body) MUST be completed by a top-level '+class.ext : work(...)'
definition; a '+' completion MUST complete a semi-declared member of an
EXISTING class; the marker/panel agreement of LANGUAGE 11.3 is checked
over TYPED CUSTODY entries -- a '+' completion's out:, a '-'
completion's in: (a 'known:' view is never the product nor the debt,
R-41.1), must name the class (untyped sections defer, PARTIAL). At most
one '-class' per class -- held by declare's duplicate law (the qualified
name (class, '-') collides), not re-checked here. A '-' completion with a
signals: section is REJECTED unless it carries the EXPLICIT flag '()'
(R-37): AUTOMATIC DESTRUCTION CANNOT FAIL (LANGUAGE 11.4). DEFERRED: namespaced
completion resolution beyond the top scope; the disposal CALL surface
(rides the dispose primitive, type document).


(26) Constructor overloads identify by argument name      [REJECT, PARTIAL]
-----------------------------------------------------------------------------
R-33 (supersedes R-32's arity law). Several '+class.ext' completions may
share one extension (declare's duplicate law stands aside for exactly
this shape; the first publication carries the export entry). DEFINITION
SITE: overloads of one extension (two or more) carry pairwise DISTINCT
first-input names; an overload without inputs cannot be identified and
is rejected. CALL SITE: a call of an overloaded extension leads with a
NAMED argument -- the selector -- whose name is one overload's first
input; an unnamed lead or an unknown selector is rejected (checked at
aware-mutation walks). A single completion is not an overload and needs
no identification. DEFERRED: call sites outside aware mutations
(statement-form calls, for:-from: windings); overloads across module
boundaries.


(27) Explicit destruction -- the give-or-destruct checker      [DEFERRED]
-----------------------------------------------------------------------------
R-37. THE LAW, ratified now; the CHECKER awaits type flow. A class whose
disposal carries the explicit flag ('-class() : work(...)') is EXPLICIT:
its destruction is never automatic -- every end is written with
'destruct <object>() (; | else: { arms })', a normal work call whose
signals the site answers. The compiler owes three path checks over
explicit classes:
  (i)   every had local of the class is either given or destructed
        explicitly on ALL paths through its haver;
  (ii)  a container holding such objects explicitly destructs its
        remaining elements upon its own destruction;
  (iii) an aggregate having such a member explicitly destructs it in its
        disposal work.
Non-explicit objects discharge automatically (and their disposal cannot
signal, SEMANTICS 25). CHECKED NOW: 'destruct' is lawful only inside
work/clockwork bodies (an automatic context cannot answer a disposal);
the statement parses with its handler; the explicit flag lifts the
no-signals rejection. DEFERRED: the three path checks entire (type
flow); the disposal DISPATCH at run time (the interpreter traces the
statement and ends the local's having in its frame); 'elsewhile:' and
the wait construct at destruct sites (the register's D-2 family).


(28) Nothing and knownness                                [REJECT, PARTIAL]
-----------------------------------------------------------------------------
R-38, surface per R-41. Inside work bodies: the 'known:'-marked in:
names are the KNOWN set (potentially Nothing), and a 'known:'-marked
binding SITE (R-41.2) joins it -- knownness propagates without gating,
the gates keep firing at the OPERATION; everything else in frame is HAD
(never Nothing, by 0.5's construction). The law is ALWAYS ACTIVE and
FLOW-SENSITIVE (ruled): the checker complains ONLY about UNGATED access
-- where the flow makes Nothing impossible (a dominating gate narrowed
the name), the access is fine; no mention-gating, no activation switch.
GATE EQUIVALENCE (ruled): 'm != Nothing', 'm != 0', and bare 'm' are
ONE gate (Nothing is the absent value, zero its numeric face; at
runtime Nothing compares as 0 and reads false); the '=='-forms narrow
the else-side likewise.
The site-vs-panel AGREEMENT law is
RULED: known and had are part of the TYPE -- each binding target's site
marker must match the corresponding out: entry's marker, both
directions, targets against outs in declaration order (12.5); checked
where the callee resolves here (top-level works, selector-resolved
overloads; the rest defers to the type document). Corollary (ruled):
NOTHING CAN NEVER BE GIVEN -- giving moves custody, a known is never
had, so 'give' on a known rejects. CHECKED NOW, three rejections: (a) an operation (any
BinOp operand other than a Nothing-compare) on an un-narrowed known;
(b) a had holder receiving an un-narrowed known; (c) the Nothing literal
assigned to a had holder. Nothing-compares ('k == Nothing' / '!=', either
operand order) are always lawful -- they ARE the gates. NARROWING, two
recognized shapes over exact bare-name gates: a '!= Nothing' condition
narrows its then-block ('== Nothing' its else-block); an '== Nothing'
then-block that DIVERGES (last statement signal or give, no else:)
narrows the rest of the body -- the initial-gate idiom. ACTIVATION BY MENTION
(PARTIAL, flagged fork): the checks run in bodies that speak of Nothing
anywhere (a gate, a compare, the literal); silent bodies keep pre-R-38
discipline -- the bridge until type flow scopes the law exactly (value-
typed knowns exempt; Nothing-admitting types bound everywhere, mention
or not). Mentioning is not gating: a compare activates the law without
narrowing anything. PARTIAL/DEFERRED: joins and compound conditions
('a != Nothing and b != Nothing'); deeper divergence shapes; knownness
of class members and reactive contexts; the have/know CONTAINER custody
checks (insertion-is-give, collective debt, 27(ii) linkage) -- the type
document's chapter.

(30) Have nothing after give or destruct                  [REJECT, PARTIAL]
-----------------------------------------------------------------------------
R-40. Upon give, the giver's have-relationship becomes HAVE NOTHING; the
same upon destruct. Any later use of the dead name on that path --
operand, copy, acquaintance -- REJECTS: the name knows nothing of
existence (HAVE_KNOW_BE (2)). CHECKED NOW: the destruct-half over work
bodies, path-sensitively (branch-local deaths do not leak out of their
arm; joins are conservative toward NOT-dead and defer). RULED, awaiting

checks land with the written give sites (the call-site give marker and

contexts. The KNOWING MODEL (one hub
per known object: pointer + knower count; destruction zeroes the
pointer, all knowers read Nothing; the hub re-usable at zero knowers)
binds the EMITTER and is recorded in HAVE_KNOW_BE (3) -- SEMANTICS 28's

(31) The pipe laws                            [REJECT, PARTIAL, pipe ruling]
-----------------------------------------------------------------------------

  (i)   GROUP LAW: a channel group's head stands in the reactor's in:
        panel; '.' (the self channel) is always lawful. Ungrouped
        causalities are lawful with at most ONE in-channel (they belong
        to it; with none declared, to the self channel); ungrouped
        beside SEVERAL in-channels REJECTS.
  (ii)  ROUTED EMISSION: a spawn's 'to <channel>' names an out: channel

        FORM (R-43) joins the law: 'signal <event> [to <channel>];' in
        behavior work code is the same emission -- its 'to' checks here,

  (iii) WIRE PLACEMENT: a wire is a WORK statement (WIRING IS WORK);
        in a reactive command-block it REJECTS. Both ends resolve as

  (iv)  WIRE ENDS (PARTIAL): where an end's construction is visible in

The provided FEEDER kind 'script' resolves without declaration (an

(32) The physical unit algebra                            [REJECT, PARTIAL, R-50]
-----------------------------------------------------------------------------
CHECKED TODAY: an unknown unit name in a physical type or literal
REJECTS [UNIT] (UNITS.txt is the glossary); a division's SEM-21 gate
sees through a physical literal (the unit changes nothing about
zeroness). AT RUN TIME the unit is CARRIED (algebra B): '+'/'-'/
comparison demand equal vectors, '*'/'/' derive, a bare number scales,
the zero vector collapses to a plain number, and a mismatched write
into a declared-physical member raises the built-in fault
'unit_mismatch' (payload: the two canonical displays) -- catchable at
an aware statement exactly as div_by_zero (SEMANTICS 21). THE STATIC
NET (F-9 slice, built): unit vectors INFER through literals,
declared-physical members and ports, negation, and every operator;
a provable mismatch under '+'/'-' and a provable WRITE-SEAM mismatch
into a declared-physical place REJECT [UNIT] -- unless the statement
carries a handler (the SEMANTICS-21 suppression mirrored: the runtime
unit_mismatch path then answers). DEFERRED: argument and give seams,
inference through calls and event fields. REPRESENTATION (R-51): the unit is part
of the value's TYPE; vector carriage is the REFERENCE interpreter's
strategy, not a semantic obligation -- the Luau emitter erases
statically-proven paths and tags variants; erasure's reach equals the
static net's reach.
