===============================================================================
NOTE  --  THE INDEPENDENT PARSER GENERATOR
===============================================================================

This directory is, today, the grammar-agnostic engine the VUT rule-file parser
runs on. It is named parser_generator because it is meant to become one: a
standalone, MIT-licensed project, extractable from VUT, that takes a grammar and
a node description and produces a parser.

This NOTE records WHY that is worth doing -- the one idea that would let it
stand beside ANTLR and Lark rather than behind them. It is potential, not a
plan; nothing here is built beyond what the README describes. It is kept so the
idea is not lost while the reactive engine (the actual product) is built.

-------------------------------------------------------------------------------
THE SEAM EVERYONE LEAVES IMPLICIT
-------------------------------------------------------------------------------

A parser generator has two jobs: recognise the input (the parse), and let you
turn the parse into your own structure (the build). The incumbents do the first
well and leave the second as the user's problem, handed off across an IMPLICIT,
POSITIONAL seam:

  ANTLR  hands you a parse tree + a visitor/listener; you read children by
         position and rule name.
  Lark   hands you a Tree + a Transformer; you read tree.children[i].

In both, the shape you receive is dictated by the grammar's INCIDENTAL
structure, and your build code pattern-matches against that incidental shape by
INDEX. The coupling is unnamed and brittle: insert a token, wrap an alternation,
reorder a branch -- and every index downstream shifts out from under the
transformer. Anyone who has maintained an ANTLR visitor has felt this. The build
code is the part that breaks when the grammar moves, because the seam between
"what the grammar happened to produce" and "what the builder reads" was never
made into a contract.

-------------------------------------------------------------------------------
WHAT THIS ENGINE DOES INSTEAD
-------------------------------------------------------------------------------

The CST this engine produces is a DESIGNED INTERFACE, not a byproduct. The seam
between parse and build is explicit, shape-typed, and addressed by ROLE rather
than by position:

  SHAPE CARRIES INTENT.   OPT_Node, OR_Node, SEQ_Node, STAR_Node are distinct
     types. An optional cannot masquerade as an alternation; the node's type is
     a statement of what the grammar operator MEANT, checkable, not inferred.

  FACTORIES BIND BY ROLE.   A node is read as node["key"], by the advisory role
     a position carries, not as children[2]. Captured-terminal index drift --
     the thing that breaks positional transformers -- cannot reach a role-keyed
     read. Move the grammar; the factory still binds.

  ONE FACT STATED ONCE.   The factory names (from_seq, from_or, from_span,
     from_token) make the grammar operator, the CST node type, and the factory
     signature the SAME fact, visible at the call site. The AST-map family
     (OrMap, OptMap, StarMap) routes a CST shape to the constructor that
     consumes it. The contract is named on both sides; a mismatch is a visible
     error, not a silent mis-index.

The result: the build code is DECOUPLED FROM GRAMMAR CHURN. That is the thing
the incumbents do not give, because their CST is an accident and this one is an
artifact.

-------------------------------------------------------------------------------
THE COMPETITIVE THESIS (ONE SENTENCE)
-------------------------------------------------------------------------------

  A parser generator whose parse tree is a TYPED, ROLE-ADDRESSED INTERFACE, so
  that AST construction survives grammar changes.

Not "faster than Lark." Speed is table stakes and a latecomer loses on it. This
competes on the oldest unsolved annoyance in the field -- the brittle, positional
parse-to-AST seam -- and is unbeatable on exactly that one axis.

-------------------------------------------------------------------------------
WHAT WOULD MAKE THE CHALLENGE REAL
-------------------------------------------------------------------------------

1. LEGIBILITY.  The idea must be tellable in a README's first paragraph. Today
   it lives in terse conventions (from_or, the OPT-not-OR law, role hints). For
   it to challenge anyone, the seam-contract story has to be on the tin.

2. THE GRAMMAR-CHURN DEMO.  The proof is a ~30-line example: write a grammar +
   factories, then CHANGE the grammar (insert a token, reorder an alternation),
   and show the factories still bind because they read by role -- where the
   equivalent Lark Transformer silently mis-indexes. That demo is the pitch.

3. STAY ON THE ONE BLADE.  The pull, once "challenging ANTLR," is to chase their
   checklist: more target languages, error recovery, IDE plugins. That dilutes.
   The LL(2) bound and the absence of error recovery are fine to cede. Be
   unbeatable on the seam contract; do not be mediocre on twelve other axes.

4. THE ORACLE IS PART OF THE MOAT.  Because the parse output is a faithful,
   named CST and VUT records byte-exact GOOD files over it, the CORRECTNESS of
   the parse/build contract is testable in a way visitor pipelines are not.
   "Change the grammar; the GOOD files tell you exactly which factory contracts
   moved." That development experience compounds with the architectural claim.

-------------------------------------------------------------------------------
EXTRACTION
-------------------------------------------------------------------------------

The engine extracts as this directory plus core/diagnostic and the abstract
world/span_oracle contract. ONE seam blocks a clean lift today: ll2_engine
constructs parser.ast_nodes (RuleFile/Luau) directly -- see DISCUSSIONS/seam-1.
Until the result-container and leaf construction are injected (a caller-supplied
framing handler, as the SpanOracle inversion already did for the embedded
language), the engine is not yet language-agnostic in fact, only in name. That
injection is the precondition for the standalone project; nothing else stands in
the way.

-------------------------------------------------------------------------------
PRIORITY
-------------------------------------------------------------------------------

Not now. The reactive engine is the product; this is a parser that got good
along the way. The note exists so the potential is recorded, not pursued. The
parser will keep.
