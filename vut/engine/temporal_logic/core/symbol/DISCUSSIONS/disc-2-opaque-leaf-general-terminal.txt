WHAT IS ALREADY GENERAL (do not rebuild)
-------------------------------------------------------------------------------
T.opaque(mode) is ALREADY a first-class terminal kind in the generator:
shape=="opaque", is_opaque, its own FIRST set {(t_fr_span_open,)}, its own
consume path (frames[-1].add(parser.consume_span(self))). 'mode' already rides
on the terminal so a rule says "this position takes an opaque span of THIS
kind". The terminal is general; only its RESULT is not.

The one leak: consume_span constructs world.span_oracle.SpanResult (ll2_engine
L567) and the engine imports SpanResult (L11). That is the sole core->world
edge for SpanResult, and the engine's own docstrings call the prior shape "a
layering leak".

-------------------------------------------------------------------------------
DECIDED -- opaque absorption yields a general Leaf, parameterized by REFERENCE
-------------------------------------------------------------------------------
An opaque terminal in the tree is a DESCRIPTION of how to access opaque
content -- the same leaf-nature as every terminal (disc-1). Its access kind is
"opaque content, reached by <reference>". So it is a fourth Leaf derivation:

    core/symbol/ast.py
      Leaf
       |- ConstantLeaf      inline value
       |- ReferenceLeaf     by key / navigation    (resolution slot)
       |- AnonymousLeaf     built in place
       +- OpaqueLeaf        opaque content + mode; reference kind PARAMETERIZED

OpaqueLeaf PARAMETERIZED BY how the content is referenced -- the generalization
asked for: inline TEXT today; OFFSET+EXTENT, URL, ... derivable later WITHOUT
touching the engine (Leaf is a base; add a reference kind when a terminal needs
one). 'mode' rides as a carried parameter value (an oracle concept from world),
NOT a constructed world type the engine names.

PRODUCTION SITES (CRUCIAL -- the engine builds NO ast type):
    ENGINE (ll2_engine.consume_span)    consumes the T.opaque terminal and
                                        yields a NEUTRAL span result
                                        (text, mode, begin). Names no ast type.
                                        Does NOT build OpaqueLeaf.
    APPLICATION (parser/ reduce action) lifts that neutral result into
                                        ast.OpaqueLeaf. The parser is allowed to
                                        import core/symbol; this is where it
                                        happens.

Consequence: the engine has NO edge into core/symbol. It keeps yielding a
neutral triple, exactly as today. The ONLY engine-side question left is whether
that triple stays the world.SpanResult type or becomes a barer neutral value
(disc-2 does NOT force this; see fork note). world keeps SpanMode/SpanOracle
(its own measurement vocabulary). OpaqueLeaf lives in core/symbol and is built
application-side.

This UNIFIES three things into one:
    engine SpanResult-leak  +  parser OpaqueCode  ==>  OpaqueLeaf
OpaqueLeaf.get_references(oracle) yields tuple[ReferenceLeaf] (disc-1): names
found in opaque text are the SAME resolvable leaf the bracket grammar
produces, lazily born. SpanReference (world) is the raw pre-tree finding,
LIFTED to ReferenceLeaf at OpaqueLeaf.get_references -- the parser boundary,
which is allowed to touch both world and core/symbol.

-------------------------------------------------------------------------------
DECIDED BY PRECEDENT -- the lazy reference cache
-------------------------------------------------------------------------------
OpaqueLeaf.get_references is a memoised accessor over one compare=False,
repr=False slot, written once via object.__setattr__ -- exactly today's
OpaqueCode.get_references. The oracle is an ARGUMENT per call; the leaf never
holds a live oracle handle.

-------------------------------------------------------------------------------
DECIDED -- OpaqueLeaf takes the TEXT for now; OPEN to other reference kinds
-------------------------------------------------------------------------------
ast.OpaqueLeaf carries the span TEXT for now (inline content + mode + begin).
This is the only reference kind that exists today.

It is DELIBERATELY OPEN to other ways of referencing the content -- offset +
extent into the source, a url, an external handle, ... -- added when a second
kind actually appears. Leaf is a base; a new reference kind is a new field or
derivation then, with no engine change (the engine yields the neutral triple
regardless). The README records this openness so the inline-text shape is not
mistaken for a closed decision.

No tagged-union / discriminator machinery is built now: only TEXT exists, and
building the union before a second kind exists is speculative apparatus.
