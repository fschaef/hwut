
EVENT STRUCTURE (STREAM → RULE SPACE)
====================================

An EVENT is an immutable record emitted by the system under test and observed
by the RULE SPACE. Events are the *only* input channel through which the STREAM
affects the RULE SPACE.

Each EVENT consists of a fixed set of mandatory members and an extensible set
of user-defined attributes.


1. Mandatory Members
--------------------

Every EVENT instance has the following mandatory members:

  name : string
    - The symbolic name of the event.
    - Must match the grammar of an identifier:
        [A-Z][A-Z0-9_]*    (recommended, not enforced by engine)
    - Examples:
        INIT
        PLAYER_DIED
        NETWORK_CONNECT

  time : float (seconds)
    - Logical time of occurrence.
    - Must satisfy:
        time >= 0
        time >= time(previous_event)
    - Provided either explicitly by the stream (@TIME:) or implicitly by the
      engine (system time).
    - Time is monotonically non-decreasing across the stream.

  seq : integer
    - Global occurrence index (0-based or 1-based, engine-defined).
    - Strictly increasing by 1 for each incoming primitive event.
    - Used for deterministic ordering and provenance tracking.


2. Attribute Members
--------------------

In addition to the mandatory members, an EVENT may carry zero or more
*attributes*. Attributes are user-defined and domain-specific.

Each attribute is a key–value pair:

  attribute_name : attribute_value

### Attribute Names

- Type: string
- Grammar:
    [a-zA-Z_][a-zA-Z0-9_]*
- Must not shadow reserved names:
    name, time, seq
- Attribute names are case-sensitive.

### Attribute Values

Allowed attribute value types are intentionally restricted:

  - boolean
      true | false

  - integer
      64-bit signed integer
      (no enforced bounds, but test designers should define domain limits)

  - float
      IEEE 754 double
      (NaN and ±inf are strongly discouraged)

  - string
      UTF-8 string
      Recommended to use enumerations where possible

  - enum (convention)
      A string chosen from a finite, domain-defined set
      Example:
        state ∈ { "IDLE", "RUNNING", "PAUSED" }

No other types are permitted:
  - no tables
  - no functions
  - no userdata


3. Attribute Semantics
----------------------

- Attributes are immutable once the EVENT is created.
- Attributes belong to the *event instance*, not to the event name.
- Two occurrences of the same event name may have different attribute sets.

Example:

  @1.25: COLLISION(actor="PLAYER", target="WALL", force=3.2)
  @1.30: COLLISION(actor="PLAYER", target="ENEMY", force=7.8)


4. Event Identity
-----------------

An EVENT occurrence is uniquely identified by:

  (name, seq)

Attributes do NOT participate in identity; they are descriptive metadata.


5. Visibility in the RULE SPACE
-------------------------------

When an EVENT occurs:

- It is inserted into the NOW set for the current step.
- It is appended to OCCURRENCE_DB[name] with its full instance data.

In the Lua RULE SPACE:

- The event instance is accessible as a read-only table:
      EVENT_NAME.attribute

  Example:
      if COLLISION.force > 5 then ...

- Attribute access is read-only; attempts to modify attributes result in error.


6. Event Specification (for rules and predicates)
-------------------------------------------------

In rule expressions, an EVENT may be referenced in two forms:

  (a) By name only:
        EVENT_NAME
      Meaning:
        “An event with this name occurred (NOW or SEEN, depending on context).”

  (b) By name with attribute constraints:
        EVENT_NAME(attr == value, ...)
      Meaning:
        “An event with this name and matching attributes occurred.”

Attribute comparisons are restricted to equality (==) in event specifications.
All other comparisons must be expressed in Lua predicates.


7. Special Events
-----------------

The engine provides the following implicit events:

  END
    - Emitted exactly once, after the last stream event.
    - Has no attributes.
    - Used to express end-of-test conditions.


8. Error Handling and Validation
--------------------------------

The engine must reject an EVENT if:

- Mandatory members are missing.
- Attribute names collide with reserved names.
- Attribute values are of unsupported type.
- Time violates monotonicity.

Rejected events are fatal stream errors.


9. Design Rationale (Non-Normative)
-----------------------------------

- The restricted attribute type set ensures:
    - deterministic behavior
    - easy serialization
    - clear rule semantics
- Complex structures belong in the host (Python), not in events.
- Events describe *what happened*, not *how it should be processed*.

This strictness is intentional and supports auditability, safety, and clarity.
