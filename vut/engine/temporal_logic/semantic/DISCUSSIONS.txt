Rationale, costs, and rejected alternatives for the semantic layer. README =
settled mechanics; this = why. Entries newest-first, 'L-N'. Parser ledger

-------------------------------------------------------------------------------
LIVE QUESTIONS (open; resolve before the resolver is built)
-------------------------------------------------------------------------------

  S-Q1  ENCLOSING-OPEN-SCOPE VISIBILITY. When an inner scope references a name
        in a still-OPEN enclosing scope (e.g. Traffic uses SIREN declared in the
        still-open 'outer' that contains it): is the enclosing scope visible by
        virtue of lexical nesting, or must it be mounted too?
          (1) nesting IS the explicit dependency -- visible, no mount. (leaning)
          (2) even the encloser must be explicit.
        Lean (1): the author wrote the inner scope INSIDE the outer; that is on
        the page, structural, not implicit. Requiring a mount to one's own
        enclosing scope is redundant with visible nesting.

  S-Q2  SPAWN-TARGET TOLERANCE -- the lone open item after S-6. A '+! Type'
        references an aggregate TYPE. Under the S-6 general rule it is (B): the
        type must be declared by name and kind above the spawn (B.1), body may
        follow (B.2). Open ruling: keep (B), or hold spawn targets to (A) (type
        FULLY defined before any spawn of it, the event-like strict treatment)?
        Flagged "functional / a problem to think about". Singleton references
        ('+! THE_ONLY') follow whatever spawn targets get. Everything else in
        S-6 is settled. Note: the declaration syntax (S-Q3 / parser R-40) admits
        'is: mode_group' and 'is: state_machine' regardless of how S-Q2
        resolves, so settling S-Q2 needs no syntax change -- only a resolver
        ruling on whether a forward-declared aggregate type may back a forward
        '+!' spawn.

  S-Q3  DECLARATION SYNTAX -- (B.1) needs a way to DECLARE a name+kind without
        (yet) defining it. RESOLVED in the parser layer (R-40): 'has:' is
        already a declaration inside an aggregate (kind implied by the frame);
        'is:' ('<name> is: <kind>') is its scope-level sibling (kind stated). No
        new resolver work beyond matching each declaration to a same-scope
        definition (the (B.2) check). -> parser R-40; SYNTAX <forward-decl>. 'has: HUNGER' already does this for aggregate
        members; but for the general (B) case (a mode declared by name+type
        above, body later; a type declared before a forward spawn) the grammar
        may need explicit DECLARATION elements distinct from DEFINITION. To be
        designed against the parser/SYNTAX in a separate pass (see the prompt
        accompanying this work). Until then the resolver assumes (B.1) is
        satisfiable by whatever declares-and-types a name (membership, has:,
        and any future forward-declaration form).

RESOLVED  --  resolution discipline (S-series)
-------------------------------------------------------------------------------

  S-6   THE (A)/(B) REFERENCE RULE -- declared-and-typed is the gate; the scope
        is the deadline. Supersedes the definitional/operational framing tried
        in the first draft of S-5 (kept below as REJECTED). One general rule,
        then per-entity application.

        GENERAL RULE. A reference target:
          (A) must either be defined before the reference location; or
          (B) if it profits from or requires loose referencing, it
              (B.1) must be declared by name and type -- present in the same
                    scope above the reference; and
              (B.2) its full definition (body, members' bodies, transitions)
                    must follow later in the same scope (the nesting scope of an
                    aggregate).
        === border: general rule above / per-use-case application below ===
        Events / clocks: (A). Degenerate case: being LEAVES, they have no later-
            definition need -- an event references nothing (not another event,
            not a mode), so it carries no relationship of explanation that could
            be painful or circular to order. Nothing about it profits from loose
            referencing, so (B) never applies. Strict; one place to declare,
            one place to find.
        Modes: (B). A mode's effect block may transit into another mode
            ('=> ! OTHER'). Restricting transit to already-defined modes would
            make DAG state machines impossible -- no forward or cyclic edge.
            Target declared by name+type above (B.1); body and transitions
            follow (B.2).
        Aggregate members under 'has:': (B). 'has: HUNGER' declares HUNGER by
            name and links it to type HOMEOSTASIS (B.1); HUNGER's definition may
            follow later in the scope where HOMEOSTASIS lives (B.2). Profits from
            loose referencing -- naming the parts of a whole before detailing
            each is how one describes the whole; the (B.2) scope may be the
            aggregate's nesting scope, not strictly the aggregate body.
        Arming targets ('! MODE', '=> ! MODE'): (B). An arming target IS a mode
            target, inheriting the mode rule -- the DAG-transition need seen from
            the effect side.
        Spawn targets ('+! Type'): (B) by default -- type declared by name+kind
            above (B.1), body may follow (B.2) -- but UNDER REVIEW (S-Q2): may be
            held to (A) instead. Singleton refs follow the spawn-target ruling.

        Two scope facts this rule rides on:
          - (B.2) is BOUNDED: a (B.1)-declared name with no (B.2) definition by
            the scope's close is an error reported AT the close. The closing-
            scope principle (S-2) survives as the DEADLINE on (B.2); it is no
            longer the rule by itself -- declared-and-typed (B.1) is the gate.
          - (A)/(B) is the INTRA-scope discipline. Reaching ANOTHER scope still
            requires an explicit mount (S-4); a closed-sibling or nonexistent
            target is still a hard error (S-3). Inter-scope discipline sits above
            (A)/(B), unchanged.

        REJECTED (first-draft framing): "DEFINITIONAL (forgiving) vs OPERATIONAL
        (strict)" as the governing cut. Replaced because the real gate is
        "declared and linked to a type at the reference site," with events as
        the leaf-degenerate case where declared-and-typed coincides with fully-
        defined. The definitional/operational labels described the symptom
        (members forgiving, events strict) but not the cause (declared-and-typed
        vs not), and mis-predicted modes (operational yet forgiving, because
        DAGs demand it).
        -> README (C), rewritten around (A)/(B); declaration syntax -> S-Q3.

  S-4   DEPENDENCIES MUST BE EXPLICIT -- MOUNT TO USE ANOTHER SCOPE. A scope
        cannot reach another scope's names by lexical proximity or ambient
        global visibility. It must DECLARE reliance ('include ... as ...') and
        only then name what it mounted. Reading a scope's mounts then tells you
        the COMPLETE, finite, auditable set of other scopes it can depend on.
        REJECTED: ambient innermost-out lexical search ACROSS scope boundaries
        (the README's original (C)) -- that is implicit dependency, the
        "definitions elsewhere" chaos the completeness principle (S-3) exists to
        prevent. Implicit cross-scope edges end in chaos; explicit mounts keep
        the dependency surface on the page. (Open: whether a still-OPEN encloser
        counts as already-explicit via nesting -- S-Q1.)
        -> README (C), (D); supersedes the cross-scope part of the old (C).

  S-3   A CLOSED SCOPE IS COMPLETE AND FINAL -- NEVER REOPENED. Once 'close' is
        seen the scope is sealed: its name set is fixed forever, never extended.
        Payoff: to comprehend a scope the reader looks in EXACTLY ONE place
        (open..close); having read it, they have everything -- no "might also be
        defined elsewhere" residue. The seal holds BOTH ways: outsiders may not
        forward-reference INTO a closed scope either, or reading the scope would
        no longer reveal all uses of its names. Deep reason behind balanced
        open/close (R-37): the brackets bound the total KNOWABLE extent of the
        entity, not just its syntax.
        Consequences, hard errors at the reference site:
          - reference into an ALREADY-CLOSED sibling scope -> error (sealed).
          - reference into a NONEXISTENT scope -> error (reader has nowhere to
            look; no deferral, no "maybe later").
        -> README (C); cf. R-37.

  S-2   THE BOUND IS A CLOSING SCOPE, NOT TEXTUAL ORDER. A forward reference is
        coherent IFF a closing delimiter caps the wait -- a marked endpoint in
        the input stream by which the referent MUST be resolved. 'default RED'
        before RED appears is fine: RED must be a member of this machine, whose
        scope closes; the reader holds the unresolved name only to 'close', and
        the close guarantees the wait terminates. The decisive property is not
        "defined before used" but "is the question mark guaranteed to expire."
        Serves a real authoring need: sometimes A must be explained via B before
        B is fully given, because giving B first would be exhaustive or backwards
        (the default is part of HOW you describe the machine). Strict define-
        before-use WITHIN a scope is the hostile over-correction; the scope
        boundary makes the bounded-forward safe.
        Mechanics: two regimes joined at the closing delimiter -- bounded-forward
        WITHIN an open scope (obligation drained at 'close'; a name still
        dangling at close is an error reported AT the close, where the reader
        also expected resolution), and resolve-against-already-established ACROSS
        scope boundaries. No whole-file second pass: the "second pass" is just
        draining each scope's pending list at its matching close -- close to a
        single descent carrying a small bounded per-open-scope obligation.
        -> README (C).

  S-1   FORWARD REFERENCE != CIRCULARITY; FEEDBACK LOOPS NEED NO FORWARD REF.
        (a) Two-pass resolution does not risk name cycles: pass one records
            names, consulting no other name, so it cannot loop. The only genuine
            cycle risk is in INCLUDES (A mounts B mounts A), which exists
            regardless of one-pass/two-pass and is handled by the ordered-chain
            cycle diagnostic (L-10).
        (b) REJECTED (a wrong claim made mid-discussion): "reactive feedback
            loops require use-before-definition." False. A loop A->B->C->A lives
            in the CAUSAL WIRING, not in text order. Declare every entity first,
            then write the causal rules wiring them; the cycle is in the wiring,
            which references only already-declared names. Allowing use-before-
            definition buys NO expressiveness that declare-then-wire lacks; its
            only effect is to PERMIT documents that do not make sense read
            linearly and then quietly repair them. The objection that settled
            it: "if I reference something before I define it, I do not know what
            I am talking about" -- correct and decisive, EXCEPT where a closing
            scope bounds the wait (S-2).
        -> motivates S-2..S-5.

  L-14  EVENT DELIVERY IS IMPLICIT -- DERIVED FROM 'on:', NO SUBSCRIBE CONSTRUCT.
        An event reaches a reactor exactly when the reactor names it in an 'on:'
        cause; the cause's guard ('& { ... }') is the filter. The engine derives
        the publisher/subscriber wiring from the event types named across the
        live 'on:' causes. The author writes reaction; routing follows.

        REJECTED -- an explicit 'subscribe: <event> [filter: { <cond> }]' element
        on aggregates. It carries no information the causality does not already
        hold: 'subscribe: E filter: { p }' and 'on: E & { p } => ...' name the
        same event and the same predicate. 'filter:' and a cause guard are the
        same predicate; offering both is two surface forms for one meaning -- the
        redundancy the colon work exists to remove. Worse, it leaks plumbing
        (who-routes-what) into the rule-file plane, which speaks intent, not
        transport.

        NO SUBSCRIBE-WITHOUT-REACT CASE. "See an event only to observe/filter,
        without reacting" is not a real exception: observing-to-maintain-state
        IS a reaction ('on: E & { p } => { sm.seen = sm.seen + 1 }'); and with no
        effect there is nothing to deliver. So delivery-derived-from-'on:' loses
        no expressible behaviour.

        CONSEQUENCE: this feature needs NO syntax -- no grammar, lexer, or
        recording change. It is a model note only: delivery is a consequence of
        reaction being declared. (-> README EVENTS; SYNTAX A.2.2 cause+guard.
        The prefix on a qualified event name may still inform default routing as
        a convenience, but explicit naming in 'on:' is the contract.)


        thing produced -- resolved FQN, scope tree, diagnostic text -- and the
        GOOD recording judges it. Printing 'SUCCESS:'/'FAIL:' self-reports
        REJECTED: a test that grades its own homework hides the actual output
        behind a verdict the author asserted; the reader can no longer see what
        the resolver did, only that the author claims it passed. HWUT's contract
        is output vs. recording; the verdict is the diff, not a printed line.
        (A 'SUCCESS:.*' happy-pattern convention from a sibling project does NOT
        apply here.)
        -> README (F).

  L-12  UNSPAWN VALIDITY = STATIC RESOLVE + KIND CHECK; LIVENESS = RUNTIME.
        '-! north' checks that 'north' resolves to an instance symbol from a
        reachable Spawn 'as'. Whether the instance is live on the path reaching
        the unspawn is NOT checked. Cost: a file can pass the static check yet
        unspawn a not-yet-spawned instance at run time. Mitigation: that is a
        data-plane fact -- it depends on guards and event order (R-6, R-2:
        substance lives in Luau), which this layer cannot evaluate without
        becoming an interpreter. Flow-aware unspawn checking REJECTED for this
        layer: wrong plane. The static check still catches the real authoring
        error -- a name that was never an instance anywhere.
        -> README (E.3); SYNTAX A.2 ('-!'); cf. R-31 (target validity = here).

  L-11  INSTANCES RESOLVE BY THE ORDINARY RULE -- NO SPECIAL CASE. An 'as'
        instance is a name in its defining scope (R-37); '-! north' and
        '-! world.europe.north' resolve by the same innermost-out search and
        descent as any other reference. A separate instance lookup path was
        considered and dropped: one resolution algorithm, parameterized only by
        the expected KIND at the site. Cost: none beyond the kind tag already
        carried.
        -> README (C), (E.3).

  L-10  INCLUDE CYCLE = ORDERED CHAIN DIAGNOSTIC. A re-entered file is not a
        bare 'cycle detected'. The mount stack -- the explicit set tracking
        in-progress files -- is printed in order: first file, what it mounted,
        onward to the mount that re-enters. Cost: the detector must retain mount
        sites, not just a visited flag. Mitigation: the flag alone names the
        closing edge only; the author then hunts the route by hand. The set is
        cheap; the route is the diagnostic's whole value.
        -> README (D).

  L-9   INCLUDE = PARSE-ONCE CACHED, BUILD A FRESH TREE PER MOUNT. 'Parse once'
        (R-38) honored by caching the lex+parse, keyed by resolved file path.
        The cheap table-build runs PER MOUNT. REJECTED: grafting one shared
        Scope object at two mount points -- a node would then have two parents,
        two paths, two FQNs, breaking FQN = path + name as a single-valued
        identity. Cost of per-mount build: the same file mounted twice builds
        its tree twice. Mitigation: building is a linear walk over an
        already-parsed AST; the expensive stage (lex+parse) is the cached one.
        Shared-identity aliasing REJECTED on the identity ground, not the cost
        ground.
        -> README (D).

  L-8   INCLUDE VISIBILITY = ASYMMETRIC BY STRUCTURE. The mounted unit's root
        carries no parent across the graft, so outward lexical search physically
        stops at it -- the mounted unit cannot see the mounting scope -- while
        descent from the mounter still walks in. The Python-style direction
        (R-36, R-38) is thus enforced by the tree shape, not by a runtime guard
        the resolver must remember to apply. Cost: the graft is a special edge
        (crossed one way, not the other). Mitigation: it is the ONLY such edge;
        every other parent link is symmetric, and the asymmetry is exactly the
        module-boundary semantics wanted.
        -> README (A), (D).

  L-7b  RESOLUTION = INNERMOST-OUT LEXICAL, HEAD-SEARCHED-THEN-DESCEND. A bare
        name searches the site scope, then outward to the unit root. A dotted
        ref searches only its HEAD outward, then descends strictly for the tail.
        REJECTED: searching every dotted segment outward -- 'Traffic.RED' would
        let 'RED' escape 'Traffic' and match some outer RED, defeating the
        qualification the author wrote. Fully-qualified-from-root accepted as the
        FQN identity (L-7d) but not required at a reference site; bare/partial
        cover the natural cases.
        -> README (A), (C).

  L-7c  SEPARATOR STAYS THE DOT. Matches Luau's qualification operator
        ('Colors.RED', 'player.name', 'Color.New()' all dot). REJECTED: a colon
        'colonned-name'. In Luau a colon is method-call-with-self sugar
        ('o:m(x)' == 'o.m(o, x)') AND the type-annotation separator; a third,
        namespace meaning collides with both the moment the reader crosses into
        a guard or body. Dotted 'Traffic.RED' reads identically in a VUT
        reference and in the emitted Luau field access. The colon's one
        legitimate VUT use -- ArgDecl 'member : type' -- already mirrors Luau's
        annotation colon; no second meaning loaded onto it.
        -> README (A); SYNTAX (dotted-name).

  L-7d  ONE UNDIVIDED NAME SHELL PER SCOPE -- NOT PER-KIND SUB-MAPS. Modes, mode
        groups, state machines, instances, AND events compete in one map; any
        in-scope name clash is an error. REJECTED: three sub-spaces (types /
        events / instances) keyed so a type and an instance could share a
        spelling. Ground: a name meaning 'the event RED' in one breath and 'the
        mode RED' in another is the confusion to forbid; an event is action --
        reacted to, reasoned about -- not configuration, and must not alias a
        configuration name. Creative freedom from shared spellings is not worth
        the interference. Cost: an author cannot reuse a spelling across kinds in
        one scope. Mitigation: distinct scopes (or qualified names) still let the
        same spelling recur where it cannot be confused. The KIND tag survives
        for the REFERENCE side only (L-12, README C), never to partition
        definitions.
        -> README (A); cf. R-37 (mode (+) state-machine share one namespace --
        generalized here to all kinds).

  L-7a  AGGREGATES OPEN SCOPES; MEMBERS ARE DOTTED NAMES. A mode group and a
        state machine each open a child scope; their inline members are symbols
        there, reached as 'Agg.member' by ordinary tree descent (A.2: a
        member-ref resolves against its enclosing aggregate; the qualified form
        is the same referent). REJECTED: a per-aggregate 'members' dict hung off
        the type symbol -- a second, parallel lookup mechanism beside the scope
        tree. One mechanism: membership IS scope containment, so 'Traffic.RED'
        and 'world.europe.berlin' resolve by the identical descent. A global
        'mode RED' and a member 'Traffic.RED' cannot collide -- different scopes.
        -> README (A), (C); cf. R-37.

  L-7   SCOPE TREE + STACKLESS BUILD. The table is a TREE of scopes mirroring
        the nesting (open, mode group, state machine), each scope a single
        name->symbol map; not a flat FQN map (loses lexical search) and not a
        tree-without-maps (forces a walk per lookup). FQN falls out as the
        root-to-symbol path. The builder walks the AST on an explicit
        (scope, item) stack, NOT Python recursion -- the same motivation that
        made the parser stackless (R-34): namespace nesting is unbounded, a
        recursive build would overflow where the parser does not. Cost: an
        explicit stack is more code than a recursive descent. Mitigation: the
        parser already paid and proved this (depth_bomb FAIL->PASS); the build
        reuses the discipline.
        -> README (A), (B); cf. R-34, R-37, R-38.
