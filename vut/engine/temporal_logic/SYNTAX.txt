===============================================================================
REACTIVE RULE ENGINE  --  HWUT 2.0
SYNTAX  --  concrete syntax of rule files
===============================================================================

ARCHITECTURE:

    Python code parses the 'setup file'. The setup file defines

      - Event and their member structure
      - Rules that match from <cause> to <effect>
      - Lurker and their member structure
      - Setup of the object space

    The object space lives entirely in Luau, python code acts as a transpiler
    of the setup file into Luau code. Luau code to be embedded in the generated
    code is consistently bracketed by '{' ... '}'.

-------------------------------------------------------------------------------
(1) GRAMMAR: RULE DEFINITION
-------------------------------------------------------------------------------

    <rule>:        <causality> | <lurker>

    <causality>:   'on' <cause> ( '=>' <consequence> )+ 'off'

    <cause>:       <trigger> [ '&' <guard> ]

    <lurker>:      'lurk' <lurker-name> [ '(' <arg-decl-list> ')' ] ':'
                       <causality>+
                       ( 'until' <cause> )+

    <trigger>:     <event-name>     [ 'as' <bind-name> ]
                   <event-cond>     [ 'as' <bind-name> ]
                   'ANY'            [ 'as' <bind-name> ]
                   'TERMINATION'    [ 'as' <bind-name> ]

    <event-cond>:  <event-name> '(' <field-cond> (',' <field-cond>)* ')'

    <field-cond>:  <member> <comp-op> <rvalue>
                   <member> 'GLOBS' <istring>

    <comp-op>:     '<' | '>' | '>=' | '<=' | '==' | '!=' | '~='

    <guard>:       '{' <luau-condition> '}'

    <consequence>: <event-spec>             # emit an event
                   '+' <lurker-arming>      # arm a lurker instance
                   <report-string>          # report a formatted line of text
                   '{' <luau-code> '}'      # mutate the object space

    <event-spec>:    <event-name> '(' [ <arg-list> ] ')'

    <lurker-arming>: <lurker-name> '(' [ <arg-list> ] ')'

    <arg-list>:      <arg> (',' <arg>)*

    <arg>:           [<member> '='] <rvalue>

    <rvalue>:        <number>
                     <istring>
                     '{' <luau-expr> '}'

    <arg-decl-list>: <arg-decl> (';' <arg-decl>)*
    <arg-decl>:      <member> ':' <type>

    <report-string>: <istring>

    <istring>:       '"' <luau-string-expr> '"'   # interpolated Luau string


EXPLANATION:

<rule> defines a relation between something that happens and what happens as
       a consequence.

<lurker> is a 'conditional' rule, that can be armed as a consequence of
         something that happened. While armed, it behaves like an ordinary
         <causality>. An 'until' clause defines when it stops being armed.

<trigger> is an event, or an event with particular properties. The event's
          instance can be passed by a given name (specified after 'as').

   examples:

      on TICK as t & { t.time > 0 } => LOG(time = t.time) off
      on ANY  as e & { car.gas == 0 } => FRUSTRATION(time = e.time) off

   'ANY' matches every event, including cascade-emitted events and the
   terminating event. 'TERMINATION' matches only the terminating event of
   the trace; inside a lurker it fires per still-live instance, which is the
   natural way to express the truncation backstop.

      lurk WAITING_FOR_ACK(req : number) :
          on ACK & { ACK.req == self.req }
          => "ack received for {self.req}"
          off
          on TERMINATION
          => "no ack received for {self.req}"
          off
      until ACK & { ACK.req == self.req }

<event-cond> is a filtering trigger: it matches only events whose member
             values satisfy the listed conditions. Conditions are joined
             implicitly by 'and'. The comparison operators are the usual
             ones; '!=' and '~=' both mean not-equal (the latter is Luau's
             spelling, both are accepted).

      on STOP_SIGN_PASSED(lane == 2) as s
      => "stop sign in left lane at t={s.time}"
      off

             A trigger may also be paired with a '&' guard. The event-cond
             narrows which events match; the guard narrows further based on
             arbitrary object state.

      on PING(port == 80) as p & { vehicle.alarmed }
      => "ping while alarmed: {p.ip}"
      off

<field-cond> compares an event member against an rvalue. Two forms: an
             ordinary comparison via <comp-op>, or a glob match via
             'GLOBS'. The latter is asymmetric: the member is on the left,
             the glob pattern is on the right, written as an interpolated
             string with Unix-style globs ('*', '?', '[...]'):

      on LOGIN(user GLOBS "[fF]red") as l
      => "fred logged in at t={l.time}"
      off

             Glob patterns are translated to Luau patterns at transpile time;
             no glob library at run time. Interpolation in the pattern works
             as in any <istring>: 'name GLOBS "{config.prefix}_*"'.

<guard> is an arbitrary Luau boolean expression in '{ }'. The braces are
        mandatory and exist for unambiguous span termination: a Luau
        expression may contain ':' or other tokens the rule-file parser
        does not parse, so the parser cannot otherwise find where the guard
        ends. The rule-file parser does not parse inside '{ }'; it asks the
        Luau helper to find the matching brace. Guards are compiled at
        transpile time, so a malformed guard is reported before any event
        is processed. Guards read state, they do not mutate it.

<consequence> is what happens as a result of a cause. Every consequence is
              prefixed by '=>', which is the marker of causality. There are
              four kinds:

                 emit an event:      => EVENT(arg = ...)
                 arm a lurker:       => + LURKER(arg = ...)
                 report a line:      => "text {with} interpolation"
                 mutate state:       => { vehicle.speed = 0 }

              The state-mutation form is opaque Luau, the same as a guard:
              the parser does not parse inside '{ }'. Each consequence is on
              its own line, and the consequence list ends with 'off'. The
              event-type name in an emit, and the lurker name in an arm, are
              always literal -- never computed by Luau. The arguments may be
              computed (see <rvalue>); only the names are fixed.

              The four kinds may be interleaved freely in any order within
              one rule, each starting with its own '=>'.

      on COLLISION as c
      => { vehicle.damaged = true }
      => WRECK(severity = c.severity)
      => "wreck at t={c.time} severity={c.severity}"
      off

<event-spec> constructs an event. The event-name is literal; arguments
             are <member> '=' <rvalue> pairs, or positional <rvalue>s. The
             'time' field is intrinsic and not written in the emit; the
             engine sets it to the current instant.

<lurker-arming> constructs and arms a lurker instance. Its argument syntax
                is the same as for event-spec. Every '=> +' creates a fresh,
                distinct instance -- two armings cannot share an arm time
                (the same rule cannot fire twice at one instant), so there
                is no re-arm case to consider.

<arg> binds an argument by name or by position. Named arguments may follow
      positional ones; the parser allows both forms in the same call.

<rvalue> is one of three things: a literal number, an interpolated string,
         or a Luau expression in '{ }'. The Luau form is for everything that
         needs computation -- arithmetic, member access, function calls,
         conditional values. The literal forms exist so that simple cases
         (a constant lane number, a fixed message) need no '{ }' noise.

<arg-decl-list> declares a lurker's parameters. Each parameter has a name
                and a type. Parameter order matters: positional arguments
                bind in declaration order.

<report-string> is an interpolated string emitted as a report line. Report
                lines are the test's output. They are not printed during the
                run -- they are collected, and after the trace completes
                they are sorted alphabetically and uniqueness-filtered into
                a deterministic block. HWUT compares that block against a
                nominal recording. The engine does not judge; it reports.
                Sort+dedup discards order and multiplicity; the author
                recovers what the test needs by putting it INTO the string
                (a zero-padded timestamp prefix for order, a state-held
                counter for multiplicity).

<istring> is an interpolated Luau string in double quotes. Holes use
          braces, as in Luau's backtick-string form, but adapted to the
          rule-file delimiters: '"hello, {user.name}"'.

'off' closes every 'on' block, both at top level and inside a lurker. The
      keyword is uniform: a rule is the same shape wherever it appears. A
      reader knows from the keywords alone where a rule starts and ends; no
      indentation rules, no lookahead, no context-dependent termination.

'until' closes a lurker. A lurker may have several 'until' clauses; the
        instance stops being armed the moment any one of them fires. This
        serves the unless-cancelled pattern naturally: end on a deadline or
        end on a success event, whichever comes first.

      lurk AWAIT_ACK(req : number) :
          on TERMINATION
          => "timeout on request {self.req}"
          off
      until TICK & { TICK.time >= self.armed_at + 5 }
      until ACK  & { ACK.req == self.req }


-------------------------------------------------------------------------------
(2) LURKERS  --  LIFECYCLE AND SEMANTICS
-------------------------------------------------------------------------------

A <lurker> is a class. '=> +' is its constructor: it arms one instance into
existence. An 'until' clause is a condition under which an instance ceases
to be armed.

PARAMETERS

A lurker may declare a parameter list. Parameters are plain data, bound onto
the instance as members of 'self'. A primitive parameter is bound by value;
an object-typed parameter is bound as a reference into the one object space,
never a copy. The instance carries no member functions and no constructor
body -- arming binds data to 'self' and nothing else runs at creation.

INSTANCE IDENTITY

The engine stamps every instance with two readable members:

    self.armed_at        the 'time' at which the instance was armed
    self.armed_index     the sequence index of the arming event

Identity is the declared parameters plus the arm time. Because the arm time
of two armings can only coincide if they happen at the same instant T, and
the same arming rule cannot fire twice at one T (no event type twice at T),
every '=> +' produces a fresh, distinct instance. There is no re-arm case.

LIFECYCLE

An instance is armed (lives) from its arming until one of the lurker's
'until' clauses becomes true for that instance. 'until' is a condition, not
a destructor: nothing executes when an instance stops being armed; it simply
is no longer live. While armed, the lurker's <causality> blocks fire for
that instance with 'self' bound to it. The engine maintains a live-instance
population per lurker class and evaluates each live instance against each
event.

THE 'armed' QUERY

'armed(LURKER, ...)' is an engine-provided builtin available inside guards.
It is an existence test over the live population: "does a live instance of
LURKER exist whose parameters match the supplied arguments?" Positional
arguments first (binding in declaration order), then named arguments;
unsupplied parameters are wildcards (partial match); only declared parameters
are matchable. The natural pattern is conditional arming:

    on NW_EVENT as nw & { not armed(NETWORK_WATCHER, nw.ip, nw.port) }
    => + NETWORK_WATCHER(ip = nw.ip, port = nw.port, firewall = global_fw)
    off

TERMINATION AND TEARDOWN

'on TERMINATION' inside a lurker fires once per still-live instance at the
terminating event of the trace. This is the truncation backstop: an
obligation whose deadline never arrived is caught here, per instance. There
is no teardown pass and no destructor -- at end of the trace the entire Luau
object space is discarded and all lurker instances are released with it.

WORKED EXAMPLE  --  vehicle must stop within 10 s of a stop sign

    on STOP_SIGN_PASSED as s
    => + LOOK_FOR_CAR_SPEED(at = s.time)
    off

    lurk LOOK_FOR_CAR_SPEED(at : number) :
        on TICK & { vehicle.speed > 0 }
        => "t={format(TICK.time)} vehicle moving at stop sign"
        off
    until TICK & { TICK.time >= self.at + 10 }

WORKED EXAMPLE  --  parameterized, with conditional arming

    on NW_EVENT as nw & { not armed(NETWORK_WATCHER, nw.ip, nw.port) }
    => + NETWORK_WATCHER(ip = nw.ip, port = nw.port, firewall = global_fw)
    off

    lurk NETWORK_WATCHER(ip : string; port : number; firewall : Firewall) :
        on PING & { PING.ip == self.ip and PING.port == self.port }
        => INTRUSION(ip = self.ip)
        off
        on TERMINATION
        => "watcher for {self.ip} expired unresolved"
        off
    until TICK & { TICK.time >= self.armed_at + 30 }
    until ACK  & { ACK.ip == self.ip }


-------------------------------------------------------------------------------
(3) STRUCT DECLARATIONS  --  EVENT AND OBJECT
-------------------------------------------------------------------------------

Event and object structures are declared in the rule-file language, not in
Luau. 'time' and 'dt' are intrinsic to every event, are not declared, and
are of type 'number'.

    event STOP_SIGN_PASSED {
        lane : number
    }

    object vehicle {
        speed : number
        kinetic_energy : fn() { return 0.5 * self.mass * self.speed^2 }
    }

A field is 'name : type'. Fields are separated by any whitespace -- newline
or otherwise. The types are Luau's: 'number', 'string', 'boolean', plus the
name of any declared event or object type (a reference-typed field). There
is no int/float split; the engine presents a Luau facade to the user.

A member function is 'name : fn(<params>) { <luau> }'. The '{ }' span is
opaque Luau; 'self' is the instance. Member functions are pure data-plane
computation, used as derived properties of an event or object instance.

Object initial values are not given in the declaration. The declaration is
purely structural; initial state is set by the SETUP section.

A '#' starts a comment to the end of the line.


-------------------------------------------------------------------------------
(4) SETUP  --  OBJECT-SPACE INITIALISATION
-------------------------------------------------------------------------------

A rule file contains a SETUP section: plain Luau code, run once at engine
start, before any event is processed. It constructs the singleton objects
and sets their initial state, and declares historian coverage for the events
that need it.

    SETUP {
        vehicle    = object.vehicle()
        vehicle.speed = 0
        global_fw  = object.Firewall()

        historian.track(PING, by=ip)
        historian.track(LOGIN, by=user, last=5)
    }

SETUP runs in the privileged SETUP environment -- the only environment with
an object-construction capability. Rule-body '{ }' blocks (the RULE
environment) may mutate existing objects but cannot construct new ones.
Before SETUP runs, the generated bootstrap injects the object constructors
generated from the declarations and whatever capabilities the sandbox
configuration permits. SETUP cannot widen its own environment. SETUP runs
under the instruction-budget watchdog like all Luau.


-------------------------------------------------------------------------------
(5) EVENT TRACE
-------------------------------------------------------------------------------

A trace is the input time line: a sequence of event occurrences fed to the
engine at run time. It is data, not code -- member values are literals,
never Luau expressions.

    <trace>:            <node>+ <termination-node>
    <node>:             [ <timestamp> ] <trace-event>
    <termination-node>: [ <timestamp> ] 'TERMINATION' '(' ')'
    <trace-event>:      <event-name> '(' [ <member-spec> (',' <member-spec>)* ] ')'
    <member-spec>:      <member-name> '=' <literal>
    <timestamp>:        <number>
    <literal>:          <number> | <string> | <boolean>

Tokens are separated by any whitespace. A trace MUST end with a TERMINATION
event; the engine rejects a trace that does not. 'dt' is never written --
the engine derives it as the delta to the previous event's 'time'.

TIMING -- TWO MODES, NEVER MIXED WITHIN ONE TRACE

A trace is either EXPLICITLY-TIMED (every node carries its timestamp) or
CLOCK-TIMED (timestamp omitted; the live-capture path supplies 'time' from
the system clock). The two are never mixed within one trace. Clock timing
is a live-capture mode only: a SAVED trace file is always explicitly-timed,
because saving freezes the clock-derived values into real timestamps. The
engine itself never consults a clock.

EXAMPLE (explicitly-timed)

    0.0    STOP_SIGN_PASSED( lane = 2 )
    0.1    TICK( )
    0.2    TICK( )
    10.5   TICK( )
    10.5   TERMINATION( )


-------------------------------------------------------------------------------
(6) HISTORIAN AND HISTORY QUERIES
-------------------------------------------------------------------------------

The historian is a Luau object configured in SETUP that records past events
of declared types. Guards and bodies query it via three builtins:

    last(EVENT [, attrs])    -- the most recent matching EVENT, or nil
    since(EVENT [, attrs])   -- time delta since last(EVENT, attrs), or nil
    EVENT(attrs)             -- shorthand for last(EVENT, attrs)

History is paid for only when declared. An event type for which no
'historian.track' is written is not recorded; querying it is a transpile-
time error, not a silent nil.

    SETUP {
        historian.track(PING, by=ip)
        historian.track(HEARTBEAT)
        historian.track(LOGIN, by=user, last=5)
    }

'by=<attr>' (or 'by=<attr1>,<attr2>') keys the per-instance history.
'last=N' bounds entries retained per key; default 1. The first argument is
always a literal event-type name -- the static-name line, extended to
history builtins.

The transpiler statically checks history queries through the Luau helper.
A query against an unhistorised type is fatal: "last(PING) used but PING is
not historised -- add historian.track(PING) in SETUP." A query whose match
attributes are not covered by the historian's 'by=' keying is fatal: "PING
is historised, but not keyed by ip -- the historian's by=... must include
the attributes you query against." Both prevent the silent-nil class of
error.

EXAMPLE

    SETUP {
        historian.track(LOGIN, by=ip)
    }

    on PING as p & { LOGIN(ip=p.ip) ~= nil }
    => "ping from logged-in ip {p.ip}"
    off

    S-6  Armable-unit keyword -> 'lurk' (paired with 'until').
    S-7  '.armed_at' / '.armed_index' -> engine-stamped instance members.
    S-8  Multiple disarm conditions -> 'until' may repeat.
    S-9  Triggering-event reference -> 'as <bind-name>', any trigger
         including ANY and TERMINATION.
    --   armed() wildcard '*' -> rejected; omission is the only wildcard.
    --   Causality marker -> '=>' before every consequence, no exception.
    --   On-block terminator -> 'off', uniform at top level and inside
         lurkers.
    --   Truncation backstop keyword -> TERMINATION (collapsed with the
         trace-terminating event; same instant, two audiences).
    --   Glob matching -> 'GLOBS' keyword in <field-cond>, asymmetric
         (member left, pattern right, interpolated string), Unix glob
         syntax, translated to Luau patterns at transpile time.
