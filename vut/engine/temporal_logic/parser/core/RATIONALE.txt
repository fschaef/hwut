PARSER CORE  --  RATIONALE
===============================================================================
WHY the core parser machinery is shaped as it is. Topology lives in README.txt;
this file owns the settled decisions (what was decided and why). Open items and
decided-but-unbuilt work live as files under DISCUSSIONS/ (disc-N / todo-N).
Core entries are C-numbered, distinct from the language ledger one level up
(parser RATIONALE, whose D-/A-/G- entries own the rule-file decisions).

-------------------------------------------------------------------------------
C-1  ADVISORY ROLE HINTS: TRANSPARENT TAGGING + A CHECKED VOCABULARY
-------------------------------------------------------------------------------
The core MECHANISM behind the language-level role-hint decision (parser A/G
ledger); the language decision -- which positions are tagged, the kind
vocabulary -- lives there.

DECISION
    A grammar position may be tagged with the KIND a reference or terminal is
    expected to denote (a namespace at 'open:', an aggregate at 'spawn:', a mode
    at 'arm:'), to aid the reader and hand pass-2 a per-position expectation,
    WITHOUT changing what the parser lexes, interns, analyses, or builds. Two
    pieces, both in core:
      1. Tagged_Spec -- a TRANSPARENT Operator_Spec wrapper holding one body
         element plus a role string. FIRST_2, the conflict scan, nullable, and
         expand all delegate to the body, so it contributes nothing to the value
         stream. The two authoring forms (a terminal call t("role"), a reference
         suffix '<name(role)>') lower to it.
      2. ROLES -- a checked vocabulary passed to Grammar(roles=...): a dict from
         each role-bearing pattern to the roles it may carry. _validate_roles
         walks the compiled grammar at load and raises RoleVocabularyError on an
         undeclared pattern or unlisted role, beside the LL(2) gate -- so a typo
         ('evnet') fails at COMPILE, not as a far-off pass-2 misresolution.

INVARIANTS (future changes must not violate)
    - NON-IDENTITY. A role never enters a terminal's _name(). If it did,
      t_re_id("event") and t_re_id("clock") would intern as different terminals
      and fracture the one-keyword-one-token guarantee; '<name-dotted(event)>'
      and '<name-dotted(clock)>' would become different references.
    - ADVISORY for pass-2. A declared role is a resolution expectation, never a
      substitute for a kind check; a missing hint is never an error there. The
      LOAD check is the only enforcement, and it checks SPELLING against the
      vocabulary, not semantics.
    - OPT-IN. roles=None skips the check, so the core's toy grammars and any
      consumer not using hints are untouched.

COST (load-bearing, kept)
    Terminals must be dict KEYS for ROLES, so Terminal_Spec gained content
    __hash__/__eq__ on _name(). Because interning yields exactly one object per
    _name(), content equality and identity coincide -- the engine's pervasive
    'is' comparisons are unaffected (a byte-identical suite confirms it). The
    full decoration pass (29 hints, 19 kinds) left the entire suite
    byte-identical; that regression is what proves the wrapper transparent.
    Not chosen: carrying the role as a VALUE wrapper through the CST (would force
    every positional factory to unwrap); folding the role into terminal identity
    (breaks NON-IDENTITY above).
