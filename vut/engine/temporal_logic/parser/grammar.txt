===============================================================================
REACTIVE RULE ENGINE  --  HWUT 2.0
SYNTAX  --  concrete syntax of rule files
===============================================================================

ARCHITECTURE:

    Python code parses the 'setup file'. The setup file defines

      - Events and their member structure
      - Rules that match from <cause> to <effect>
      - Modes and their member structure
      - Mode groups and state machines, aggregating their member reactors
      - Setup of the object space

    The object space lives entirely in Luau, python code acts as a transpiler
    of the setup file into Luau code. Luau code to be embedded in the generated
    code is consistently bracketed by '{' ... '}'.

    The setup file is parsed beforehand and transpiled into Luau code. The Luau
    code is supported by a bootstrap defining 'Class' definition and other
    helpers.

NOTE:

    '##' starts a comment at any point in the setup file and the event sequence.

    '--', '--[[', ']]--' are the usual comment delimiters inside Lua code sections.

    'print' commands inside the Luau code appear on stdout as '##' prefixed.


-------------------------------------------------------------------------------
(A) TRANSPILATION -- generating the reactive engine
-------------------------------------------------------------------------------

(A.1) GRAMMAR:

    ## THE COLON PRINCIPLE. On the rule-file plane we are concerned with being,
    ## having, triggering, and relating -- never with algorithms, algebra, or
    ## container internals (those live in Luau, behind '{ ... }'). The colon is
    ## the mark of a rule-file connective, and it ABUTS ITS FILLER: to the
    ## keyword's right when an operand follows ('on: T', 'mode: X', 'has: X', 'is: K',
    ## 'in: C', 'via: K', 'by: {lv}', 'for: E', 'into: NS', 'until: C',
    ## 'default: R'), and to a
    ## terminator's left when it closes a block (':end', ':close'). A leading
    ## colon finishes something; a trailing colon starts something whose filler
    ## is next. ':' is always a connective and never stands alone; '{ ... }' is
    ## always Luau. These two marks carry every rule-file relation.

    (A.1) GRAMMAR

    The concrete grammar -- every production -- is the GRAMMAR dict above in
    this file (grammar.py). It is the executable form of what was formerly the
    EBNF listing here; read it there. The element vocabulary is documented in
    this file's header. The explanations below (A.2 onward) describe what the
    productions mean.

(A.2) EXPLANATION

(A.2.1) General

BINDINGS: Names that bind nesting entities:

    'e'       event of the current rule firing. Available inside any '{ }'
              span attached to a fired trigger -- guards, '=> { ... }'
              mutation blocks, the Luau expression in any rvalue -- and, with
              the SAME spelling, in bracket conditions and as an rvalue
              ('e.target').

    'm'       mode instance in which the referencing code fragment resides.
              Not bound inside top-level rules; referring to it there is a
              semantic-layer error.

    'sm'      state machine where the code fragment resides. This may be the
              'init' and 'deinit' handlers of the state machine or any code
              fragment in a member state of the state machine.

    'mg'      mode group where the code fragment resides. The mode-group
              counterpart of 'sm': bound inside the 'init'/'deinit' handlers of
              the mode group and any code fragment in a member mode. 'sm' and
              'mg' are the two aggregate self-bindings; exactly one is in
              scope, decided by the enclosing aggregate kind.

    The binding names are NOT reserved words. On the rule-file plane they are
    ordinary leading segments of a <name-dotted>, resolved by the semantic
    layer as self-binding pseudo-symbols; in the opaque plane they are Luau
    locals bound by the generated code. One spelling, both planes: the guard
    '[ e.temp > limit ]' and the guard '{ e.temp > limit }' read identically.


IMPLICIT EVENTS:

    'ANY'    at the same time at any event that occurs.

    'BEGIN'  immediately (zero-time ahead) before first event of the event
             sequence.

    'END'    immediately (zero-time ahead) after last event of the event
             sequence. END carries the system members 'run_time_sec' and
             'event_n', readable as 'e.run_time_sec' / 'e.event_n' inside an
             'on: END' rule.

    'CHANGE' delivered at the STEP BOUNDARY after a no-time cascade in which
             opaque code raised it. CHANGE is a system citizen beside
             BEGIN/END: it is a legal trigger ('on: CHANGE'), it is NOT an
             authorable emission, and it is raised only by opaque code through
             the engine API. Sitting on the time axis, it contributes no
             inbound edges to the cascade graph.

    ANY, BEGIN, and CHANGE are memberless; only END carries the system
    members above.


(A.2.2) Grammar Productions

<rule-file>
         is the top-level container of all setup-file constructs: causalities,
         modes, mode groups, state machines, event definitions, and clock
         definitions.

<reactor> is the umbrella term for a <mode> and a <state>: a named,
         parameterized block of rules with optional 'init'/'deinit' hooks and
         closing 'until' causes. A <mode> overlaps freely with sibling reactors;
         a <state> is mutually exclusive with its siblings (A.2.5). Both share
         the <reactor-elm> body.

<mode> defines a block of rules that operate conditionally. The block
         operates only when it is 'armed', i.e. there is a mode
         instantiated as an effect of some <cause>. A mode is closed by its
         'until' causes ( one or more ).

<state> is a <mode> living inside a <state-machine>. Its body and its trailing
         'until' causes are both optional ( zero or more ); an empty state --
         'state NAME:' with neither -- is legal, a pure transition target. The
         block is terminated structurally by the next state-machine element or
         'end' (A.2.5).

<trigger> is an event named by a <name-dotted> (a definition reached through
          a namespace or an import is a legal trigger), optionally narrowed by
          a guard. The triggering event is always accessible as 'e' inside the
          rule's guards, Luau spans, and rvalues -- no per-rule binding form
          is needed.

   Examples:

      on: TICK & { e.time > 0 } => LOG(time = e.time)

      on: ANY  & { car.gas == 0 } => FRUSTRATION(gravity = 0.1)

      on: PING & { Glob("tester_?_intruder"):match(e.user) and e.ip ~= "127.0.0.1" }
      => INTRUSION(intruder=e.user)

   'ANY' matches every event, including cascade-emitted events and the
   terminating event.

   Example:

      mode: WAITING_FOR_ACK(req: number)
          on: ACK & { e.req == m.req }
          => "ack received for {m.req}"
          on: END
          => "no ack received for {m.req}"
      until: ACK & { e.req == m.req }

<guard>

    is the condition gating a trigger, in one of TWO forms.

    (1) A Luau boolean expression in '{ }'. The rule-file parser does not parse
    inside '{ }'; it asks the Luau helper to find the matching brace. Guards are
    compiled at transpile time, so a malformed guard is reported before any event
    is processed.

        Luau guards must read state, not mutate it. The Luau helper performs a
        sound *syntactic* read-only check on every guard: any assignment, and any
        call to a recognised mutating builtin ('table.insert', 'table.remove',
        'table.sort', and similar) is reported as a fatal transpile error. The
        check is sound but not complete: a guard calling a user-defined function
        that itself mutates state cannot be detected statically.

    (2) A bracket condition in '[ ]': a boolean algebra over comparisons and
    boolean references. The parser builds the condition tree directly (it is
    not opaque), so names and comparisons are validated by the static layer.

        condition   :=  '[' <cond> ']'
        <cond>      :=  <cond-and> ( 'or'  <cond-and> )*
        <cond-and>  :=  <cond-not> ( 'and' <cond-not> )*
        <cond-not>  :=  [ 'not' ] <cond-atom>
        <cond-atom> :=  '(' <cond> ')'  |  <cond-term>
        <cond-term> :=  <name-dotted> [ <op-cmp> <operand> ]
        <op-cmp>    :=  '>=' | '<=' | '==' | '!=' | '>' | '<'
        <operand>   :=  <name-dotted> | number | string | 'true' | 'false'

        The ladder encodes precedence -- 'not' over 'and' over 'or' -- with
        parentheses to override. A <cond-term> WITHOUT a comparison tail is a
        bare boolean reference: '[ GHOSTS_AT_HOME ]' and '[ not e.armed ]'
        are legal, equivalent to '== true' comparisons. Both comparison sides
        admit a <name-dotted> -- an event member through the 'e' binding
        ('e.port'), a variable ('TIMEOUT'), or a struct member
        ('tracker.number') -- symmetrically: '[ e.elapsed > TIMEOUT ]' and
        '[ TIMEOUT < e.elapsed ]' alike. Literals stand only on the right.
        Comparison only: there is no arithmetic and no function call (use a
        Luau guard for those). 'and' / 'or' / 'not' are reserved words; name
        resolution and operand kinds are semantic-layer checks.

        Example:
            on: NetworkUp & [ e.ip_adr == "10.0.0.1" and e.port > 1024 ] => ...
            on: Collision & [ (e.severity > 3 or e.fatal == 1) and not e.handled ]

<effect>
    is what happens as a result of a cause. Every effect is prefixed by '=>',
    which is the marker of causality. There are five kinds:

         emit an event:        => EVENT(arg = ...)
         arm a mode:           => !  MODE(arg = ...)
         spawn (default):      => +! STATE_MACHINE(arg = ...)
         spawn into container: => +! STATE_MACHINE(arg = ...) in: C via: e.name
         end existence:        => -! STATE_MACHINE
         report a line:        => "text {with} interpolation"
         mutate state:         => { vehicle.speed = 0 }
         run an effect bundle: => BUNDLE_NAME

     The state-mutation form is opaque Luau, the same as a guard, but without
     the read-only restriction: a '=> { ... }' span is the place to write
     changes to the object space. Each effect is on its own line, and the
     effect list ends at the first line that is not an '=>' effect (no closing
     keyword). The event-type name in an emit, the mode name
     in a '!' arm, and the aggregate-type name in a '+!' spawn are always
     literal -- never computed by Luau. The arguments may be computed (see
     <rvalue>); only the names are fixed.

     '!' arms a single mode (<mode-arming>). '+!' spawns a named aggregate
     instance -- a <mode-group> or a <state-machine> (<spawn>) -- and '-!'
     unspawns one (<unspawn>). The verbs are distinct: '!' targets a reactor,
     '+!'/'-!' target an aggregate. Only a named (spawned) entity may be
     unspawned, so '-!' takes a reference by name, not a fresh invocation. A
     spawn may name a target container with 'in: C'; the 'via: <rvalue>' key
     is reachable only inside that 'in:' clause, since the key is the name by
     which the container holds the instance -- 'via:' without 'in:' is a
     syntax error.

     The six kinds may be interleaved freely in any order within one rule,
     each starting with its own '=>'.

     Example:
         on: COLLISION
         => { vehicle.damaged = true }
         => WRECK(severity = e.severity)
         => "wreck at t={e.time} severity={e.severity}"

<def-cause>, <def-effect>, <cause-named>, <effect-named>
    A cause or an effect-list may be NAMED ONCE and REUSED, so a recurring
    trigger+guard or a recurring bundle of effects is written in a single place.

    A cause definition gives a cause a name, a parameter signature, a 'for:'
    EVENT BINDING, and a MANDATORY guard introduced by '&', so the definition
    reads exactly like a use site:

         event: TEMPERATURE_MEASUREMENT(temp: float)
         cause: TOO_HOT(limit: int) for: TEMPERATURE_MEASUREMENT
                                    & [ e.temp > limit ]

    'for:' names the event as a <name-dotted>; the event is defined before the
    cause definition, and the cause definition itself is fully defined before
    any rule references it. The guard is mandatory -- a guard-less definition
    would be a bare alias of its event -- and its body is a CONCRETE guard
    only (a Luau span or a bracket condition), never another cause reference:
    no alias chains. 'e.member' references inside the definition's guard are
    checked against the 'for:' event's members once, at the definition. A
    guard referencing only variables is legitimate; the binding makes member
    references checkable when present, it does not demand them.

    An effect definition names an ordered bundle of effects and may carry a
    parameter signature, parallel to a cause definition; each '=>' is the same
    effect signal as in a causality rule:

         effect: SUPER_POWER => PACMAN_RUN(speed = 12)
                             => PELLET_BLINK
                             => GHOSTS_FLEE

         effect: Boost(level : int) => SPEED_UP(by = level)
                                    => FLASH

    A causality rule may then fire a defined cause BY REFERENCE, passing actual
    arguments, and name a defined effect bundle BY REFERENCE as a bare name:

         on: TOO_HOT(75) => SUPER_POWER

    On the cause side and on the effect side alike, the named form is ONE
    grammatical shape -- a <name-dotted> with an optional argument list -- and
    the PARENS DECIDE: 'NAME(args)' is a cause reference / an <event-spec>
    emission; a bare 'NAME' is an inline trigger / an effect-bundle reference.
    The decision is made on the token after the name (which is why the grammar
    is LL(2) rather than LL(1)). Names may be DOTTED, so definitions reached
    through namespaces and imports are referenceable: 'on: Sprites.GHOST_EATEN',
    '=> NS.Effects.cleanup'. Resolving a reference to its definition (and
    checking a cause reference's arguments against the signature) is a pass-2
    concern; the parser records definitions and references, it does not expand
    or bind them. A cause reference followed by '& <guard>' parses; whether it
    is legal is a semantic-layer decision.

    A bare effect reference and a parenthesised event-spec may sit side by side
    in one effect list:

         on: TOO_HOT(20) => SUPER_POWER => Beep(3)

    fires the cause TOO_HOT with argument 20, then runs the SUPER_POWER bundle,
    then emits Beep(3).


<event-spec>
    constructs an event. The event-name is literal; arguments are member '='
    <rvalue> pairs, or positional <rvalue>s. The 'time' field is intrinsic and
    not written in the emit; the engine sets it to the current instant.

<mode-arming>
    constructs and arms a mode instance. Its argument syntax is the same as
    for event-spec -- 'NAME(arg = value, ...)'.

    An arming with identical parameters to a currently live instance is a
    silent no-op: 'init' is not re-run, 'begin_time' is not updated, the
    first instance remains. 'init' runs exactly once per instance, at
    the moment it comes into existence. 'deinit' runs exactly once per
    instance, at the moment it ceases -- whether that is the firing of an
    'until' clause or the trace's END event finding the instance still live.
    When one 'until' clause fires for an instance, no further 'until' clauses
    for that instance are checked: this guarantees 'deinit' runs at a
    single well-defined moment, and lets an 'until' clause safely reference
    the still-existing instance.

<spawn>
    constructs an aggregate instance -- a <mode-group> or a <state-machine> --
    with the verb '+!'. The aggregate-type name is literal. One shape, with one
    optional modifier chain:

         => +! SM_TRAFFIC(lane = 2) [ in: <container> [ via: <rvalue> ] ]

    THE ARGUMENT LIST IS MANDATORY -- it is how the instance is instantiated.
    The parentheses are required; the list inside may be empty for a type that
    takes no arguments ('+! SM_TRAFFIC()'). A bare type name with no parentheses
    is a SYNTAX ERROR -- there is no parameterless spawn form.

    'in:' -- WHICH CONTAINER catches the instance. Absent, the instance is
       offered to the per-kind DEFAULT container, which accepts it unless one of
       identical type and identical parameterisation is already present, in
       which case the spawn is the same silent no-op as a duplicate
       <mode-arming> (identity = parameters, as for modes). Present, the
       instance is offered to the named container instead.

    'via:' -- THE KEY the container holds the instance under. For a dict
       container this is the key. The operand is an <rvalue>: a literal, a
       <name-dotted> (an event member 'e.name', a variable, a struct member),
       or an opaque '{ luau }' expression. 'via:' is legal only inside an 'in:'
       clause -- a key without a container is meaningless.

         => +! SM_TRAFFIC(lane = 2) in: sprite_bin via: e.lead_id

    Whether an offered instance is admitted is the CONTAINER's decision, taken
    under a mutex; a rejected offer leaves no instance and runs no 'init'. The
    type name and any parenthesised argument names are literal; only argument
    values and the 'via:' key may be computed.

    SINGLE-INSTANCE there is no dedicated construct. Spawn the type once,
    at BEGIN; it lands in the per-kind default container and is addressed by
    its type name ('-! SM_TRAFFIC' ends it). Script-side access goes through
    the holding container.

         on: BEGIN => +! SM_TRAFFIC(lane = 2)


<unspawn>
    ends the existence of an instance with the verb '-!'. The operand is a
    reference by name (bare or dotted), not an invocation: no arguments. Ending
    existence runs the instance's 'deinit' once, exactly as a firing 'until' or
    the trace END would, and releases the instance from whatever container
    holds it.

      => +! SM_TRAFFIC(lane = 2) in: bin       # spawn into a container
      => -! SM_TRAFFIC                          # end existence
      => -! LIGHTS.GLOW                          # dotted reference

    Resolving the operand to an existing instance is a semantic-pass concern;
    an operand resolving to no instance is a validation error (pass 2), not a
    parse error. Whether the instance is live at that moment is a run-time fact
    the static pass does not decide.


<declaration>
      introduces a scope-level name with 'is:' and a KIND. One head -- a bare
      name, an optional ROUND-bracket '(' <list-decl-arg> ')' signature, 'is:'
      -- followed by one of FOUR kind shapes, distinguished by their leading
      keyword:

        north(lane: int) is: state_machine                   -- reactor kinds
        Idle             is: state
        Watcher          is: mode
        Patrol           is: mode_group

        ghost_state_tracker(                                 -- struct
            number : int;
            chasing: bool;
        ) is: struct

        Sprites is: container<dict>                          -- container
        Ghosts  is: container<fifo, 64> by: { db.ghosts }

        TIMEOUT is: int(5)                                   -- variable
        RETRIES is: int(3) by: { cfg.retries }
        tracker is: ghost_state_tracker(number = 3, chasing = false)

      REACTOR KINDS ('mode', 'state', 'mode_group', 'state_machine') forward-
      declare a name before its definition -- the (B.1) gate of the (A)/(B)
      forward-reference rule, the scope-level counterpart of an aggregate's
      'has:' ('is:' states the kind outright; 'has:' lets the frame imply it).
      The matching definition follows later in the same scope. The signature
      says HOW a later '+!' instantiates the type, which the engine needs even
      when only the declaration is in scope; since a '+!' is the begin-of-life
      of an instance and we cannot tell at declaration time whether one will
      target the name, the signature is MANDATORY on the spawnable kinds --
      'mode_group' and 'state_machine'. 'mode' and 'state' take NO signature
      (armed, not instantiated).

      STRUCT declares an aggregate VALUE type. The signature IS the member
      list -- the same '(member: type ; ...)' form an aggregate definition
      declares -- and it is MANDATORY: the declaration is the complete
      definition, there is no struct forward declaration. Members may be
      built-in-typed or struct-typed, so structs nest. Structs are (A)-strict
      -- fully defined before any use -- which makes member cycles impossible
      by construction.

      CONTAINER is the kind that reaches into Luau: its ANGLE brackets carry
      TYPE PARAMETERS -- ordinary <arg>s (a shape word 'dict' / 'list' /
      'fifo', an optional size, access flags), opaque to the rule-file plane
      and read by the resolver. The angle brackets are OPTIONAL ('X is:
      container' takes the per-kind defaults). Angle, not round: a container
      is parameterised by type, never instantiated by a constructor signature.
      Round = HOW TO INSTANTIATE; angle = WHAT KIND. A container is never
      spawned: it exists as soon as the scope that declares it exists. It
      takes no round-bracket signature.

      VARIABLE declares a name of a built-in type ('int', 'float', 'string',
      'bool') or of a previously declared struct type, with a MANDATORY
      round-bracket initialiser. The initialiser is an argument list: for a
      built-in type, exactly one positional value; for a struct type, values
      binding positionally or by name against the struct's member signature,
      exactly as mode parameters bind. NAME and TYPE are static -- a scope
      symbol like any other, legal in bracket conditions and as an <rvalue> --
      while the VALUE lives in the opaque world: engine-owned storage,
      materialised in the generated bootstrap, readable and writable from
      opaque code. The rule-file plane has no assignment construct, so write
      access is opaque-only by construction. Initialisers evaluate in
      DECLARATION ORDER at bootstrap; a name referenced in an initialiser
      resolves under the (A) define-before-use rule. A variable takes no
      round-bracket signature before 'is:'.

      'by: { lvalue }' OPTIONALLY binds a container or a variable to an
      EXISTING opaque-code reference, for script-side access under a script-
      chosen name. The kind-vs-shape legality -- which kinds require, accept,
      or forbid the head signature, the initialiser, the angle brackets, and
      'by:' -- is a pass-2 check; the grammar accepts the shared head on any
      kind.


<arg> binds an argument by name or by position. Named arguments may follow
      positional ones; the parser allows both forms in the same call.

<rvalue>
      is something that can be assigned to an event member or a mode
      parameter in the <list-arg>. It is one of: a NUMBER or STRING literal;
      'true' / 'false'; a <name-dotted>; or an opaque '{ luau }' EXPRESSION.
      A <name-dotted> covers a bare word whose meaning the static layer does
      not fix (a container type-parameter such as 'dict' / 'fifo'), a
      variable, a struct member ('tracker.number'), and a self-binding member
      ('e.target' -- the legible, non-opaque way to forward a triggering
      event's member as an argument, e.g. '=> ! Chase(e.target)'). The parser
      admits an rvalue everywhere an <arg> is admitted; whether a given site
      accepts a given name is a pass-2 concern, not a parse error.


<name-dotted>
      is a dot-separated chain of identifiers -- 'TIMEOUT', 'e.target',
      'NS.Sprites.GHOST_EATEN', 'tracker.pos.x' -- and the ONE member-access
      and reference shape of the rule-file plane. The parser fixes no meaning:
      the semantic layer resolves the leading segment (a namespace, an
      aggregate, a variable, a struct, or one of the self-binding pseudo-
      symbols 'e' / 'sm' / 'mg' / 'm') and descends the remaining segments.
      Expressions and computation still belong behind '{ }'.


<list-decl-arg>
      declares an aggregate's parameters -- or a struct's members -- by name
      and type, ';'-separated. Parameter order matters: positional arguments
      bind in declaration order. A type is a built-in ('int', 'float',
      'string', 'bool'), the name of a declared struct, or the name of a
      class created in 'on: BEGIN'.

      Class-typed parameters are bound by reference into the one object space.


<report-string>
      is an interpolated string emitted as a report line. Report lines are the
      test's output. They are not printed during the run -- they are collected,
      and after the trace completes they are sorted alphabetically and
      uniqueness-filtered into a single text block.

      HWUT compares that block against a nominal recording. The engine does not
      judge; it reports. Sort+dedup discards order and multiplicity; the author
      recovers what the test needs by putting it INTO the string (a zero-padded
      timestamp prefix for order, a state-held counter for multiplicity).

<istring>
      is an interpolated Luau string in double quotes. Holes use braces, as in
      Luau's backtick-string form, but adapted to the rule-file delimiters:
      '"hello, {user.name}"'.

DELIMITERS:

(no terminator)    closes an 'on' block. Each effect is introduced by '=>',
                   so the effect list ends at the first line that is not an
                   '=>' effect. An 'on' block needs no closing keyword.
'end'              closes a mode group and a state machine.
('until' <cause>)+ closes a mode.
( 'until' <cause> )* on a state are optional; the state block is closed
                   structurally by the next state-machine element or 'end'.

A mode may have several 'until' clauses; the instance stops being armed the
moment any one of them fires. This serves the unless-cancelled pattern
naturally: end on a deadline or end on a success event, whichever comes first.
A state stops being armed when a sibling state is armed (the state machine's
mutual exclusion), or on any of its own 'until' causes, whichever fires first. A
mode group and a state machine have no closing 'until' causes of their own; they
are aggregates and are closed by 'end'.

      mode: AWAIT_ACK(req: number)
          on: END
          => "timeout on request {m.req}"
      until: TICK & { e.time >= m.begin_time + 5 }
      until: ACK  & { e.req == m.req }


(A.2.3) Details on Modes

LIFECYCLE

  '=>' '!' <mode-arming> instantiates a mode and activates a mode block.

  'until' <cause>          removes the mode from existence.

  A mode block is only executed, if an according mode exists.

PARAMETERS

Parameters specified in a mode's definition and passed during instantiation
are bound to the instance of the mode, referred to by the binding 'mode'.
Primitive parameters are bound by value, class-type parameters are passed
by reference -- as enforced by the Luau engine.

The engine stamps every instance with two readable members in addition
to the parameters defined in the mode's declaration:

    m.begin_time        'time' at which it was instantiated.
    m.begin_event_index index of the event that caused the instantiation.

The engine-stamped members may not be specified by the user. The parameter
list provides identity: no two modes exist with identical parameter lists.

QUERY:

Live instances of a reactor class -- a mode or a state -- are queried in the
Luau world using the reactor's type name as the access point. There is one
primary call form and four boolean reduction methods.

   <reactor-name>:list(<member-condition>*)
       Provides a list of modes of the given name where the member
       conditions are fulfilled. If no condition is provided all modes
       of the given kind are returned.

   <reactor-name>:has(<member-condition>+)
       True if a mode with the given conditions exists.

   <reactor-name>:any(<member-condition>*)
       True if at least one live instance matches the conditions.
       With no conditions, true if any live instance exists at all.

   <reactor-name>:all(<member-condition>+)
       True if every live instance matches the conditions.
       Conditions are required (a conditionless 'all' is vacuous).

   <reactor-name>:none(<member-condition>+)
       True if no live instance matches the conditions.
       Conditions are required (use ':empty' for the conditionless case).

   <reactor-name>:empty()
       True if no live instance of <reactor-name> exists at all.
       Takes no conditions.

    <reactor-name>:last(<member-condition>+)
        last mode that triggered with condition.

    <reactor-name>:since(<member-condition>+)
        time since last mode with condition occurred.

Member conditions accept either a literal value (matched by equality) or
a comparator object: Glob, Approx, Less, LessEq, Greater, GreaterEq,
Eq, UnEq, Pattern (see section C). The engine's generated _match()
dispatcher routes each condition through the comparator's :match method
or falls back to '==' for literals; the author writes the comparator,
the engine does the dispatch.

Examples:

    if STOP_SIGN_MODE:any() then
        -- at least one stop-sign watcher is live
    :end

    if #PING_WATCHER:list(port = 80) > 5 then
        -- more than five live port-80 watchers
    :end

    for m in PING_WATCHER:list(ip = Glob("192.168.162.*"), port = 80) do
        -- iterate over matching live instances
    :end

    on: ANY & { vehicle.speed < 50 and not SPEED_LIMIT_WATCHER:any(limit = Greater(50)) }
    => { driver.mode = "relax" }

The last example reads: "for any event, if the vehicle is going under 50
and no live speed-limit watcher is monitoring a limit greater than 50,
set the driver to relax mode." ':any' is the natural choice here because
Luau does not coerce tables to boolean (an empty list is truthy); ':any'
gives an honest yes/no without surprises.

Based on the mode block definitions, the transpiler generates a specific
class for each mode kind, carrying the query methods (':list', ':has',
':any', ':all', ':none', ':empty', ':last', ':since') and the polymorphic
_match dispatch.

'init' and 'deinit' define Luau code to be executed upon construction
and destruction of a mode. It is called 'init' since the members
of a mode are already paired as members to the 'mode' binding. No
constructor arguments are passed.

Example: vehicle must stop within 10 s of a stop sign

    on: STOP_SIGN_PASSED
    => ! LOOK_FOR_CAR_SPEED(at = e.time)

    mode: LOOK_FOR_CAR_SPEED(at: number)
        on: TICK & { vehicle.speed > 0 }
        => "t={format(e.time)} vehicle moving at stop sign"
    until: TICK & { e.time >= m.at + 10 }

Example: parameterized, with conditional arming

    ## arm one watcher per (ip, port); the ':has' guard is illustrative --
    ## under idempotent re-arm a duplicate arming would be a silent no-op
    on: NW_EVENT & { not NETWORK_WATCHER:has(ip = e.ip, port = e.port) }
    => ! NETWORK_WATCHER(ip = e.ip, port = e.port, firewall = global_fw)

    mode: NETWORK_WATCHER(ip: string; port: number; firewall: Firewall)
        on: PING & { e.ip == m.ip and e.port == m.port }
        => INTRUSION(ip = m.ip)
        on: END
        => "watcher for {m.ip} expired unresolved"
    until: TICK & { e.time >= m.begin_time + 30 }
    until: ACK  & { e.ip == m.ip }

There is one special mode, the GROUND_MODE, which is active all the time.
All causalities which are not bound to an explicit mode belong to the
GROUND_MODE.

(A.2.4) Details on Event Definitions

Event structures are declared in the rule-file language. 'time' and 'dt'
are intrinsic to every event, are not declared, and are of type 'number'.

    event: STOP_SIGN_PASSED(
        lane: number;
    )

    event: NETWORK_PINGED(
        n: number;
        incoming_ip: string;
    )

A field is 'name: type'. Fields are separated by any whitespace -- newline
or otherwise. The types are Luau's: 'number', 'string', 'boolean', plus
the name of any declared event type or any class created in 'on: BEGIN' (a
reference-typed field). There is no int/float split; the engine presents
a Luau facade to the user.

Event signatures correspond 1:1 to mode signatures in the way that they
specify the argument list.

(A.2.5) Details on State-Machine Definitions

A state machine is an aggregate of states in which at most one member-state is
active at a time. Arming one member-state deactivates whichever member-state
was active before. Each member-state is a state, arming a new one is a
transition, and the mutual-exclusion is automatic.

A member-state is declared inline in the state-machine body with the 'state'
keyword and an unqualified name:

    state <reactor-name> [ '(' <list-decl-arg> ')' ] ':'
        <reactor-elm>*
        ( 'until' <cause> )*

A state defined elsewhere is pulled in with 'has:':

    has: <ref-member>

A name may also be DECLARED at scope level before its definition, with its kind
stated, using 'is:' (the <declaration> production, A.2.2).

'is:' is the scope-level counterpart of the aggregate-body 'has:'. Both declare
a name together with its kind -- the (B.1) gate of the forward-reference rule.
'has:' lets the enclosing aggregate imply the kind (a mode group / state machine
holds only member modes / states, so 'has: NAME' already says "NAME is a
mode/state"); 'is:' states the kind outright, because a scope holds names of
several kinds and the frame fixes nothing. The name is bare: declaration and
definition share one scope, so nothing is qualified across a boundary. Beyond
its signature a reactor-kind forward declaration opens no Luau and carries no
body -- the definition site carries the body. Having and being: 'has:' / 'is:'.

The 'container' kind is the one that reaches into the script world. A container
is a place spawned instances are caught into; 'X is: container<...>' declares
that X may be used wherever a container is expected (the kind shapes, the
optional angle-bracket type parameters, and the 'by:' script binding are
specified at <declaration>, A.2.2). A container is never spawned; it exists as
soon as its declaring scope exists. A spawn reaches a declared container by
name with 'in:' and may name the key its caught instance is held under with
'via:':

    on: Hatch => +! ghost(seed) in: Ghosts via: e.id

Here 'in: Ghosts' is an ordinary (B.1) forward reference to a container
declared with 'is: container<...>'; the container declaration is exactly what
lets the spawn name it before the container's full setup appears in scope.

Inside the Luau code sections of the state machine itself and its member
states, the nesting state machine is referred to by the binding 'sm', and all
members declared in the state-machine signature are read-available.

<state-machine> declares the aggregate. After its signature it may carry zero
or more 'is: <base>' statements, each naming one base aggregate it inherits
from; multiple bases are written as multiple 'is:' statements. Beyond its member
states it has:

   'is:'   names a base aggregate (one base per 'is:' statement, repeatable).
           The parser records the base names in source order; how a base's
           members combine with the derived aggregate -- additive, override,
           collision handling -- is resolved by a later layer, not at parse time.

   'default' specifies the active state when no state otherwise remains
             active -- before any state is armed, or after a state terminates
             via its own 'until' with no successor armed. The target is a
             <ref-member>. If 'default' is not specified, an empty VOID state
             is activated.

   'init'  runs once when the state machine comes into being. Arguments to
           the state machine are already bound to the 'sm' binding -- same as
           'e' in <causality>, 'm' in <mode>, and the mode-group
           counterpart 'mg'.

           The typical body arms the first state.

   'deinit'  runs once when the state machine ceases. Takes no arguments.

A <ref-member> is resolved against the enclosing aggregate, so a member is
named by its bare <reactor-name>. The qualified form
'<aggregate-name>.<reactor-name>' is also accepted and is GOOD PRACTICE where
it aids the reader; the bare form and the qualified form denote the same
member. 'VOID' names the implicit empty state.

A state ceases when a sibling member-state of the same state machine is armed
(automatic mutual exclusion), or when one of its own 'until' causes fires,
whichever happens first. The sibling-armed transition is implicit in the
state-machine semantics, not spelled at a closing line. A state's 'until' causes
are optional ( zero or more ); the block is closed structurally by the next
state-machine element or 'end'.

When a member-state ceases -- whether by a sibling being armed or by one of its
own 'until' causes -- its 'deinit' (if any) runs. The "first until wins, no
further untils checked" rule (section 2) applies among its own 'until' causes.

Example: a task state machine

    state_machine: SM_TASK
        default: VOID
        init: {
            ...
        }
        deinit: {
        }

        state: SLEEP
            on: WAKE => ! RUN
        until: EVENT_TASK_TERMINATED

        state: RUN
            on: TICK & { e.time >= m.begin_time + quantum }
            => ! SLEEP
        until: EVENT_TASK_TERMINATED
    end   # a state machine is closed by 'end'; it has no 'until' of its own

Arming 'RUN' from within 'SLEEP' deactivates SLEEP (the state machine's mutual
exclusion) and activates RUN. The two states alternate; 'until
EVENT_TASK_TERMINATED' lets either state leave the cycle on a
EVENT_TASK_TERMINATED event.

(A.2.6) Details on Mode-Group Definitions

A mode group is an aggregate of modes WITHOUT single-active semantics: its
member modes overlap freely, any number live at once, and arming one does not
deactivate another. It is the non-exclusive counterpart of the state machine.

A member mode is declared inline in the mode-group body with the 'mode'
keyword, or pulled in with 'has:':

    mode <reactor-name> [ '(' <list-decl-arg> ')' ] ':'
        <reactor-elm>+
        ( 'until' <cause> )+

    has: <ref-member>

Inside the Luau code sections of the mode group itself and its member modes,
the nesting mode group is referred to by the binding 'mg' -- the counterpart of
'sm' for a state machine. A mode group has 'init' and 'deinit', exactly as a
state machine does, and is closed by 'end'. Like a state machine, it may carry
zero or more 'is: <base>' statements after its signature (one base per 'is:',
repeatable); the parser records the bases and a later layer resolves how they
combine. It has NO closing 'until' causes of
its own, and NO 'default':
with overlapping members there is no single active member to fall back to, so
no fallback exists. A <ref-member> inside a mode group resolves against the
group by bare <reactor-name>, with the qualified form accepted as good
practice.

The 'end' terminator is what makes an inline member mode unambiguous: a member
mode carries its own ( 'until' <cause> )+, and 'end' (not another 'until')
marks where the last member -- and the group -- closes.

    mode_group: MG_ALERTS
        init: { sm.count = 0 }

        mode: BLINK
            on: TICK => { sm.count = sm.count + 1 }
        until: ANY

        mode: BEEP
            on: TICK => SOUND()
        until: EVENT_SILENCED

        has: GLOW
    :end

Both aggregates are spawned as an effect with '+!' (see <spawn>): the type name
with its mandatory argument list, optionally directed to a named container with
'in:' and keyed with 'via:'. An instance's existence is ended with '-!' (see
<unspawn>).


(A.2.7) Details on Namespaces

A namespace brackets a group of declarations into a named scope:

    open <name-dotted>
        <top-level>+
    :close

The body is any run of top-level constructs -- causalities, modes, aggregates,
event and clock definitions, and further namespaces. Nesting is unrestricted in
depth. There are several independent namespaces (no single global flat space);
names declared inside a namespace are restricted to the scope in which they are
defined.

The dotted name opens several levels at once, so a deep scope needs one 'open',
not one per level. This:

    open: world.europe.germany.berlin
        ...
    :close

opens the single nested scope 'world.europe.germany.berlin' directly, rather
than:

    open: world  open europe  open germany  open berlin
        ...
    close close close close

A 'close' takes no name; the matching 'open' is unambiguous from the nesting.
A namespace may contain a nested 'open'/'close':

    open: world.europe
        on: TICK => ! WATCH()
        open: germany.berlin
            mode: GUARD
                on: ALERT => SIREN()
            until: ANY
        :close
    :close

(The binding rules -- how a reference resolves across namespaces, and how
instance-name visibility works -- are a semantic-pass concern, not a parsing
one.)


(A.2.8) Importing Other Files

Another file's namespace is mounted into this one with:

    import: "<file>" into: <name-dotted>

The IMPORTING file decides the mount point (the 'into' path); the imported
file is placement-agnostic and does not name its own location -- the same file
may be mounted at different paths in different files, and there is no
self-naming collision. This mirrors how a module system separates a unit's
internal, self-relative names from its external, caller-chosen placement.

    import: "city_rules" into: earth.europe.berlin
    import: "sensor_pack" into: sensors

    open: world.zone
        import: "diagnostics" into: diag      # mount inside a scope
        on: TICK => HEARTBEAT()
    :close

An import may appear at the top level or inside an 'open' scope; the mount
path is relative to where the import sits. The imported file is parsed once on
its own and is lexically self-contained: its internal references resolve within
itself, not against the mounting file's surrounding scope.

The parser only RECORDS each import (the file name and the mount path).
Resolving the file, parsing it, and mounting its symbol table -- and the
visibility and caching rules that govern that -- are semantic-pass concerns,
not parsing ones.



(A.3) OBJECT SPACE INIT and DEINIT

The object space of the Luau engine is initialized and de-initialized with the
'on: BEGIN' and 'on: END' handlers. The 'on: BEGIN' causality is handled before
any event in the event trace. The 'on: END' causality is handled after the last
event in the event trace.

'on: BEGIN' and 'on: END' handlers are special in that they:

  -- do not allow for a <guard>
  -- cannot EMIT events (no <event-spec> effect): they sit before the first and
     after the last trace event, so emitting one would inject an event outside
     the trace's own timeline. Other effects are fine -- spawn ('+!'), unspawn
     ('-!'), mode-arming, mutation, and Luau setup/teardown.

The 'on: BEGIN' handler defines the classes whose instances populate the object
space, brings up the single-instance aggregates, sets their initial state, and
declares tracer coverage for the events that need it.

    on: BEGIN => {
        -- Define a class
        local Vehicle = Class.create("Vehicle", {}, function(self)
            self.speed = 0
            self.damaged = false
        end)

        -- Construct a one-off Luau object
        vehicle = Vehicle()

        -- Declare tracer coverage
        tracer.watch(PING)
        tracer.watch(LOGIN, 5)
    }

The counterpart is the 'on: END' handler, that is executed after the last event
of the event trace.

    on: END => {
        release.file_handle()
        disconnect_uart()
        ...
    }


The initialization procedure can rely on the bootstrap environment being
set up. Also, it is restricted to the permissions defined by the Luau
environment about network access, file access and the like. It runs
under the instruction-budget watchdog.

No code fragment can access objects of the engine itself, except through
dedicated read-only functions.

No Luau code fragment can emit events.

(A.4) CLOCKS

A clock: operates on synthetic time and emits periodic events of a user-defined
name. A clock: is defined by the name of the event it emits and the time
interval in which it emits that event. The definition syntax is

   'clock' <event-name> <number>

where <number> is a floating point number giving the extent of the time
interval between two clock events. The clock: stores internally the last time it
has sent an event. Every clock: is activated upon the first event in the event
sequence, where it sends its first event and sets the 'last sent time'.

Whenever an event arrives, it considers the timestamp of that event. It
determines the difference

    delta_t = e.time - clock.last_time_event_sent

It then sends events based on 'synthetic time'

    for t = clock.last_time_event_sent; t <= e.time ;  t += delta_t:
        emit <event-name>(time=t)

This allows for integration of differential equations, or other simulation
processes that require some linear timeline.

(A.5) NOTES

(A.5.1) IDENTITY AND CONSTRUCTION

EVENTS, MODES, and STATE MACHINES USE REAL METATABLES, NOT 'Class.create'

The transpiler generates a metatable per declared event type. Each
metatable carries the type identity, queryable by Luau's standard
introspection ('typeof', 'getmetatable'). This is *deliberately
different* from how objects are constructed: events are transpiler-
generated structures the static checks need to identify at compile time;
objects are user-defined classes constructed in 'on: BEGIN' via the
'Class.create' factory. Two mechanisms, two jobs.

Each event class is produced by the runtime 'Space' and bound to it. The
class carries the eight query methods (':list', ':has', ':any', ...) over the
flat history its Space's tracer retains for that type; an untraced type has an
empty history and answers every query accordingly.

EVENTS HAVE NO 'init' / 'deinit'

Only modes and state machines have 'init' / 'deinit' hooks. Events are
primitive: ephemeral, non-reactive, carrying no state across time. They come
into being at their instant and vanish; there is nothing for a construction or
destruction hook to do. The hooks belong to the stateful, lifecycle-bearing
constructs (modes, state machines), not to events.


-------------------------------------------------------------------------------
(B) EVENT TRACE
-------------------------------------------------------------------------------

A trace is the input time line: a sequence of event occurrences fed to
the engine at run time. It is data, not code -- member values are
literals, never Luau expressions.

    <trace>:            <node>+ <termination-node>
    <node>:             [ <timestamp> ] <trace-event>
    <termination-node>: [ <timestamp> ] 'END' [ '(' ')' ]
    <trace-event>:      <event-name> [ '(' [ <member-spec> (',' <member-spec>)* ] ')' ]
    <member-spec>:      <member-name> '=' <literal>
    <timestamp>:        <number>
    <literal>:          <number> | <string> | <boolean>

Tokens are separated by any whitespace. A trace MUST end with a
END event; the engine rejects a trace that does not. 'dt' is
never written -- the engine derives it as the delta to the previous
event's 'time'.

TIMING -- TWO MODES, NEVER MIXED WITHIN ONE TRACE

A trace is either EXPLICITLY-TIMED (every node carries its timestamp) or
CLOCK-TIMED (timestamp omitted; the live-capture path supplies 'time'
from the system clock). The two are never mixed within one trace. Clock
timing is a live-capture mode only: a SAVED trace file is always
explicitly-timed, because saving freezes the clock-derived values into
real timestamps. The engine itself never consults a clock.

EXAMPLE (explicitly-timed)

    0.0    STOP_SIGN_PASSED( lane = 2 )
    0.1    PING(ip="8.8.8.8", port = 80)
    10.5   END

-------------------------------------------------------------------------------
(B.1) EVENT QUERIES
-------------------------------------------------------------------------------

Event queries follow the syntax and semantics of mode queries.

An EVENT that is not traced by the tracer cannot respond to these queries.
The tracer may restrict the number of events held in time backwards.

    on: BEGIN => {
        tracer.watch(PING)
        tracer.watch(HEARTBEAT)
        tracer.watch(LOGIN, 5)
    }

A watched type holds one flat history stream -- every occurrence of the type
lands in a single ring. 'last=N' bounds the entries retained for the type;
default 1. The first argument is always a literal event-type name -- the
static-name line, extended to history builtins. Match attributes are applied
at query time against the stream; the tracer is not keyed by attribute.

The transpiler statically checks history queries through the Luau
helper. A query against an untraced type is fatal: "PING:last() used but
PING is not traced -- add tracer.watch(PING) in 'on: BEGIN'." This prevents
the silent-nil class of error.

EXAMPLE

    on: BEGIN => {
        tracer.watch(LOGIN)
    }

    on: PING & { LOGIN:has(ip = e.ip) }
    => "ping from logged-in ip {e.ip}"

-------------------------------------------------------------------------------
(C) BOOTSTRAP HELPERS  --  available inside guards and Luau spans
-------------------------------------------------------------------------------

The bootstrap injects a small fixed set of helpers into the Luau
environments. They cover patterns the rule-file language does not have
syntax for, sparing the author from rewriting the same Luau scaffolding
in every test.

COMPARATOR CLASSES

Comparator objects are value classes whose only purpose is to participate
in a query's '<member-condition>'. Each carries a '__className' on its
metatable and a ':match(actual)' method. The engine's generated
'_match(actual, expected)' dispatcher (emitted into every mode class
and every event-query method by the transpiler) reads the '__className',
routes to the comparator's ':match', and falls back to '==' for literals.

   Glob(<pattern>)       Unix glob: '*', '?', '[...]'.
   Approx(v, eps)        |actual - v| < eps.
   Less(v)               actual <  v.
   LessEq(v)             actual <= v.
   Greater(v)            actual >  v.
   GreaterEq(v)          actual >= v.
   Eq(v)                 actual == v   (mostly redundant with bare literals).
   UnEq(v)               actual ~= v.
   Pattern(<pattern>)    Luau native string pattern ('%w', '%d', '^', '$', ...).

A new comparator plugs in by setting '__className' and providing
':match(actual)'. The engine dispatcher recognises it automatically;
authors do not write the dispatch.

   Example:
       on: TICK & { not SPEED_LIMIT_WATCHER:any(limit = Greater(50)) }
       => { driver.mode = "relax" }

In a free Luau guard (one not routed through a query method), the author
calls the comparator's ':match' directly:

       on: PING & { Glob("tester_?_intruder"):match(e.user) }
       => INTRUSION(intruder = e.user)

THE BAR FOR ADDING A HELPER

The set of bootstrap helpers is small, fixed, engine-provided -- no
third-party Luau libraries. The bar for adding one is "would every
nontrivial test reinvent this?"
