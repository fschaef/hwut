===============================================================================
DISCUSSIONS  --  guards, effect-def signatures, aggregate inheritance
===============================================================================
(Append-only. This block records the rationale and costs of the constructs
added this round. Topology lives in README.txt / SYNTAX_DOC; this file owns the
"why" and the "what it costs".)

-------------------------------------------------------------------------------
D-1  Bracket-condition guard as an alternative to a Luau guard
-------------------------------------------------------------------------------
PROBLEM
    A guard written as a Luau span '& { ... }' is opaque to the engine: the
    parser holds it as black-box text, the static layer cannot see which members
    it reads, and a behavioural trace cannot attribute a fired guard to a
    subcondition. Opacity works against the reviewer-attention principle.

IDEA
    Admit a second guard form, a bracket condition '& [ ... ]': a boolean
    algebra ('and' / 'or' / 'not', parenthesisable) of comparisons over the
    triggering event's members. The parser builds an explicit Condition tree, so
    the static layer can validate member references and comparisons.

    Members are LEADING-DOT, SINGLE-LEVEL: '.ip_adr' is the 'ip_adr' member of
    the event the trigger named. The event is implicit -- a guard gates exactly
    the trigger it follows -- so no event name is written. Comparison only:
    operators are '>= <= == != > <', operands are a member, a number, or a
    string. No arithmetic, no function calls.

COST
    1. Expressiveness ceiling. The algebra deliberately cannot express computed
       terms. A guard needing 'distance(a,b) < t' has no bracket form.
    2. Reserved words. 'and', 'or', 'not' become keywords; they can no longer be
       identifiers. The six operators and '[' ']' are new tokens.
    3. A second guard shape on Cause.guard (Luau | Condition) -- two node kinds
       a consumer must handle.

MITIGATION
    1. The Luau guard is RETAINED, not replaced. The bracket form is the
       transparent fast-path for the common member-comparison case; Luau remains
       the escape hatch for anything computed. The two coexist on Cause.guard.
    2. Reservation is the standard keyword cost; 'not'/'and'/'or' are matched on
       word boundaries so identifiers like 'notice' are unaffected.
    3. Condition is a distinct named root, so the two guard forms are
       type-distinguishable, not order- or shape-spotted.

DECISION DEFERRED TO PASS-2
    Binding a '.member' to a declared event member, and type-checking a
    comparison against that member's type, are static-layer concerns. The parser
    only builds the tree.

NOTE (bare-member truthiness)
    'comparison only' means a bare member is NOT an atom: '[ .secure ]' is
    rejected; write '[ .secure == 1 ]'. Admitting bare-member truthiness would
    widen the rule (cond-atom would gain an evt-member branch); left out by the
    'comparison only' decision.

D-2  Effect-definition signature
-------------------------------------------------------------------------------
PROBLEM
    A cause definition carried a parameter signature ('cause: N(p:T) on: ...'),
    but an effect definition carried only a bare name ('effect: N => ...'),
    so an effect bundle could not be parameterised the way a cause could.

IDEA
    Give effect-def the same '<signature>' a cause-def uses:
    'effect: Boost(level: int) => ... '. EffectDef gains name/params, parallel to
    CauseDef.

COST
    EffectDef.name changes from a single identifier to a dotted-name list, and
    the node gains a params field -- a consumer reading EffectDef must adjust.

MITIGATION
    The change makes EffectDef and CauseDef structurally parallel, removing a
    special case rather than adding one. Effect-ref is unchanged this round; the
    'effect-ref carries args' question (and its collision with event-spec) is NOT
    reopened here.

-------------------------------------------------------------------------------
D-3  Aggregate inheritance via repeated 'is:' statements
-------------------------------------------------------------------------------
PROBLEM
    State machines and mode groups could reuse single members via 'has:', but
    could not be expressed as "like that aggregate, plus these changes".

IDEA
    Admit zero-or-more 'is: <base>' statements after an aggregate's signature:
    'state_machine: Derived(r:int) is: Base1 is: Base2 <body> :end'. Each
    inheritance is one 'is:' statement; bases are collected, in source order,
    into a 'bases' field on StateMachine / ModeGroup.

COST
    Inheritance is non-local: understanding Derived requires holding its bases in
    mind. This is the property 'has:' composition avoids (every member visible at
    its point of use), and it is the reviewer-attention cost flagged when the
    feature was first reflected on.

MITIGATION
    The PARSER only records the base names; ALL inheritance semantics --
    additive vs. override, name-collision handling, single vs. multiple bases,
    any linearization -- are deferred to a later layer. The grammar admits the
    form; it does not assign it meaning. Whether the resolved semantics keep the
    non-locality cost acceptable is a pass-2 design decision, recorded when that
    layer is built.

-------------------------------------------------------------------------------
D-4  Comparison operators and container type-params share one '<' / '>' terminal
-------------------------------------------------------------------------------
PROBLEM
    The comparison operators must be CAPTURED (the comparison builder reads the
    exact operator from the token). But '<' and '>' were already written as bare
    strings in <fwd-kind> for container type-parameters ('container < ... >').
    A bare string '<' mints a 'string:<' terminal; T.captured('<') mints a
    'captured:<' terminal -- two different terminal objects for one lexeme, which
    the lexer would emit as two competing patterns.

IDEA
    Use ONE captured terminal per lexeme. The comparison rule and the container
    type-param rule both reference the same t_op_lt / t_op_gt.

COST
    <fwd-kind> now carries the '<' / '>' tokens in its frame (they were silent
    before); its builder ignores them. A cosmetic frame change.

MITIGATION
    A single terminal per lexeme is the correct invariant regardless -- two
    terminals for one lexeme is the latent bug, not the fix. The fwd-kind builder
    already slices positionally, so the extra carried tokens are inert.

D-5  CST baseline, transformer overlay -- replacing the _build_* / ACTIONS model
-------------------------------------------------------------------------------
PROBLEM
    Reduction is hand-written _build_* functions in an ACTIONS dict, one per
    rule, registered by name on the PassThroughNode. Each unpacks frame.values
    positionally and builds a frozen AST node. The model is fragile in three
    ways. (1) Every grammar change demands synchronised edits in three files --
    GRAMMAR (grammar.py), the AST node shape (ast_nodes.py), the builder
    (actions.py) -- and their consistency is the author's manual burden. (2)
    Positional unpacking is silent-failure-prone: silent terminals are already
    dropped from frame.values and absent optionals leave no gap, so frame index
    i is NOT grammar position i, and inserting an optional shifts every index
    after it. (3) A forgotten ACTIONS entry is a None pass-through, not an error.

IDEA
    The engine ALWAYS builds a canonical CST. Every rule reduces, bottom-up, to
    a frozen CST node whose shape mirrors its top-level operator:

        OR-rule    -> OrNode  { name, triggered_index, child }
        SEQ-rule   -> SeqNode { name, children[] }
        PLUS-rule  -> PlusNode{ name, items[] }   (items non-empty)
        STAR-rule  -> StarNode{ name, items[] }   (items may be empty)

    Leaves are Tokens (captured terminals), SpanResults (opaque spans), or the
    already-reduced CST/AST nodes of child rules. Silent terminals contribute
    nothing -- this is a PRUNED CST: syntax discarded, structure kept.

    An optional, PARTIAL transformer dict overlays this:

        Grammar(GRAMMAR, transformers=AST_MAP, start="top-level")  # overlay
        Grammar(GRAMMAR, start="top-level")                        # pure CST

    A rule WITH a transformer: the transformer receives the rule's finished CST
    node and returns whatever it wants (a typed AST node, or an adjusted CST
    node). A rule WITHOUT one: its CST node passes through untouched. AST_MAP is
    keyed by rule name; absence of a key means "no transform".

    Transformer signature follows the rule's operator, matching the natural
    frame shape (PART-2 framing, NOT a per-grammar-position factory list):
        SEQ-rule   -> one transformer, receives the SeqNode (children list).
                      The rule owns the meaning of its whole sequence; it does
                      not interpret element-by-element.
        OR-rule    -> one transformer, receives the OrNode; it reads
                      triggered_index off the node to dispatch by branch. (An
                      indexed list of per-branch transformers is sugar over this
                      and may be added later; the node-carries-index form is the
                      primitive. Keyword/captured dispatch is rejected as messy
                      and off-engine -- choose_alt already knows the index.)
        PLUS/STAR  -> one transformer, receives the items list.

CHILDREN ARE TRANSFORMED FIRST (a consequence, not a feature)
    Reduction is eager and bottom-up: a node is finished the moment its frame
    reduces, before its parent's frame reduces. So by the time a parent's
    transformer runs, each child slot already holds the child rule's finished
    output -- a transformed AST node where the child had a transformer, a CST
    node where it did not. The comparison transformer receives an EventMember in
    its left slot, never a SeqNode wrapping one. This is what bottom-up already
    produces; obtaining it costs nothing, and PREVENTING it (re-wrapping finished
    children back into CST for the parent) would cost machinery. There is no
    laziness and no deferral -- "lazy transformation" was considered and
    discarded as a miscategorisation: both orderings are eager, they differ only
    in the child TYPE the parent sees, and the transformed-child type is the
    cheap one and the useful one.

    The case that would justify children-as-CST -- a parent wanting to inspect
    syntactic structure its children erased -- does not arise: the grammar
    already encodes such distinctions as SEPARATE rules with distinct output
    types (paren-cond vs comparison), so a parent reads a child's TYPE, never its
    pre-transform shape.

COST
    1. PASS_THROUGH and DEFAULT sentinels are RETIRED. "Forward the child
       unchanged" is just "no transformer" plus reading OrNode.child /
       SeqNode.children[0]. "Build the generic node" IS the default (the CST
       node itself). Both special cases vanish; so does the dict that named them.

    2. The completeness guarantee is GIVEN UP. The PART-1 design required
       set(AST_MAP) == set(GRAMMAR.rules), enforced at load like an LL(2)
       conflict, so a forgotten transformer was a loud load-time error naming the
       rule. Under a partial overlay, a forgotten transformer is SILENT at load:
       the consumer receives a CST node where it expected an AST node. The
       failure moves from load-time-named-rule to runtime-at-the-consumer. This
       is a deliberate trade of a guarantee for a far simpler structure, recorded
       as a choice, not an oversight.

    3. The CST node is built even for rules whose transformer immediately
       discards it -- one frozen-wrapper allocation per transformed reduction.

MITIGATION
    1. The retired sentinels removed real validation surface (PASS_THROUGH was
       valid only on a single-surviving-value production and had to be checked);
       deleting the concept deletes the check. Net machinery falls.

    2. The silent-forgotten-transformer failure is bounded by typing: CST nodes
       are frozen dataclasses, so a consumer that isinstance-checks its inputs
       fails visibly (and early) on an unexpected OrNode/SeqNode rather than
       corrupting silently. The guarantee is weaker than load-time, but the CST
       node is well-typed, not a raw frame -- the failure is diagnosable.

    3. Allocation cost is bounded and small. CST nodes hold REFERENCES to
       already-reduced children (bottom-up: children finished first), not copies,
       so a node is one allocation over a child list that already exists. Only
       TRANSFORMED rules pay the build-then-discard wrapper; untransformed rules
       pay nothing, because their CST node IS the output. The order is N
       allocations for N reductions -- the same order the old _build_* path paid,
       which also built one node per reduction.

ENGINE CHANGE (minimal)
    SEQ / PLUS / STAR need NO engine change: the dense frame is already exactly
    what their single transformer wants. OR needs the triggered branch index AT
    NODE-CONSTRUCTION TIME -- but choose_alt already returns the chosen branch,
    so the reducer has the index when it builds the OrNode; it is written onto
    the node, NOT threaded through Frame as a sidecar. The earlier sidecar-field-
    on-Frame idea is dropped: the node carries the index, and the transformer (if
    any) reads it there. No Frame change.

CORE LAYERING (close the acknowledged leak)
    The CST nodes (OrNode/SeqNode/PlusNode/StarNode) and the reducer that builds
    them live in core/ -- grammar-agnostic, Luau-free. The transformers and the
    AST node shapes live in the outer layer. A pure-CST parse must NOT reach into
    the outer ast_nodes; this is the chance to remove ll2_engine.parse()'s
    'from .. import ast_nodes' (the RuleFile construction) -- the top level
    becomes a STAR/PLUS CST node like any other, and the outer layer transforms
    it into RuleFile if it wants.

NOT DECIDED HERE (deferred, to be opened when the work lands)
    - Whether an indexed per-branch transformer list is added as sugar over the
      OrNode-carries-index primitive.
    - The migration of the count-sniffing SEQ rules (not-cond, or-cond/and-cond,
      cause) -- they stay SEQ-rules whose single transformer still counts the
      frame values exactly as the _build_* did; outputs (GOODs) identical, the
      logic mechanically lifted. Confirmed left as-is under PART-2; the PART-1
      sparse frame would have forced their rewrite, and that frame is not built.

D-6  Naming the two layers: *_Spec (grammar) vs *_Node (result); SpecNode base
-------------------------------------------------------------------------------
PROBLEM
    The compiled-grammar node classes were named AlternativeNode / SequenceNode /
    OptionalNode / StarNode / PlusNode / TerminalNode / PassThroughNode, in a file
    called ll2_grammar_AST.py. Two confusions followed. (1) "AlternativeNode" and
    the new CST "OR_Node" are the same word twice -- they read as duplicates. (2)
    "ast" in the filename implied a tree of RESULTS, but the file holds the
    compiled GRAMMAR, which is not an AST at all. The names hid a real two-layer
    distinction behind near-identical words.

THE DISTINCTION (the reason both layers exist)
    GRAMMAR layer -- the static description of what the engine MAY match at a
    point. Compiled once, SHARED across every parse, permanent. One object per
    grammar position (one alternation node for <arg>'s "(...|...)", walked by
    every input that reaches it). Carries first2_set / nullable / the conflict
    scan / expand / cst_reduce. It DESCRIBES; it never holds a parse result -- it
    cannot, being shared by all parses at once.

    RESULT layer -- the record of what ACTUALLY matched, this parse, here. A
    FRESH object per occurrence. Carries the outcome: which branch fired, the
    reduced child values. This is the CST (cst_nodes).

    The relation is mould -> casting: one grammar node yields many result nodes,
    one per time that grammar point is reached during a parse. They cannot merge:
    opposite lifetimes and cardinalities (one-shared-permanent vs
    many-per-parse-disposable). Putting triggered_index on the grammar node would
    be a category error -- WHICH branch fired is a property of an input meeting
    the grammar, not of the grammar.

DECISION
    Grammar layer suffixed _Spec, prefixed with the OPERATOR THE AUTHOR WRITES
    (OR / OPT / SEQ / PLUS / STAR), so "the OR_Spec produces an OR_Node" reads as
    cause-and-effect, not as two copies:
        AlternativeNode -> OR_Spec      SequenceNode -> SEQ_Spec
        OptionalNode    -> OPT_Spec     StarNode     -> STAR_Spec
        PlusNode        -> PLUS_Spec
        TerminalNode    -> Terminal_Spec
        PassThroughNode -> Rule_Spec    (it IS one grammar rule; "Rule" is right
                                         here, where it would be wrong for an
                                         inline operator)
    'Spec' chosen over Pattern (regex connotation, nudges toward "Match"), Rule
    (already means a GRAMMAR-dict entry), Op (verb/behaviour connotation, clashes
    with t_op_ terminals), Form/Shape (too vague). 'Match' explicitly rejected:
    these objects do NOT match -- the engine does; they are what it consults.

    Base class Node -> SpecNode. "Node" is the most generic word in the building
    and said nothing; in a file titled GRAMMAR SPEC the base of every inhabitant
    must say spec. The homogeneity then lives in the type tree itself: OR_Spec,
    SEQ_Spec, Terminal_Spec, Rule_Spec are siblings under one SpecNode base
    because they ARE siblings in the walk.

    File ll2_grammar_ast.py -> ll2_grammar_spec.py ("ast" dropped; it was never an
    AST). Retired -- nothing imports it after the rename.

ASYMMETRY (recorded so it is not later read as an oversight)
    OPT_Spec has NO OPT_Node. An optional is the two-branch alternation
    (body | empty); it CASTS to an OR_Node whose triggered_index is 0 (present,
    child=value) or 1 (absent, child=ABSENT). ABSENT is a STATE of OR_Node, not a
    node type (D-5). So the prefix correspondence is OPT_Spec -> OR_Node, not 1:1,
    and that is correct.

    Terminal_Spec likewise has no dedicated result node: a terminal position
    casts to a Token (lexer.py), the leaf-level result. So the leaf has the
    pattern Terminal_Spec (grammar) -> Token (result), same two-layer shape, the
    result object just lives in the lexer rather than cst_nodes.

VERIFICATION
    Pure rename, two passes (classes+file, then Node->SpecNode), each diffed
    BYTE-IDENTICAL against a pre-rename baseline across all 22 recorded test
    outputs (9 core-engine, 5 core-lexer, 6 outer-engine, 2 outer-lexer). Zero
    behaviour change. _Node CST result names deliberately untouched (negative
    lookbehind on the substitution so OR_Node etc. survived).

D-7  Terminal ownership: the parser conducts a dumb lexer; terminals.py retired
-------------------------------------------------------------------------------
PROBLEM
    terminals.py held four jobs: the Terminal spec class, the T factory +
    TERMINAL_DB registry, the framing terminals, and Ref/R. Its stated virtue was
    "depends on nothing in the parser engine and nothing in any embedded
    language", sitting below both grammar.py and grammar_spec.py to avoid a cycle.
    But two things were wrong. (1) Terminal_Spec (grammar leaf) and Terminal
    (lexical spec) were two classes for what is one immutable specification that
    "does not live" -- a redundancy, given Terminal_Spec must remain a SpecNode
    for grammar HOMOGENEITY (every walked position is a SpecNode, no special leaf
    case). (2) The lexer imported Terminal and set Token.kind to a Terminal
    object: the byte-matcher was aware of the grammar-layer identity of the
    pattern it matched -- "a lexer should not be aware of the functionality of the
    pattern it matches against."

WAS THERE A CYCLE? (checked against the code, not the docstring's self-claim)
    No. Current edges: terminals imports nothing; grammar_spec imports terminals +
    cst_nodes; lexer imports terminals (DEFERRED, inside functions) + span_oracle +
    diagnostic, and NOT grammar_spec; combinators imports grammar_spec. Folding
    Terminal into Terminal_Spec moves T/TERMINAL_DB up into the grammar_spec
    layer; the lexer's import target moves terminals -> grammar_spec; grammar_spec
    does NOT import lexer and never would (spec describes structure, lexer consumes
    patterns; the arrow is one-way). lexer -> grammar_spec -> cst_nodes is acyclic.
    The cycle the docstring feared does not exist in this structure; the existing
    deferred-import dodge (lexer.py line ~71) neutralises any load-order wrinkle
    regardless.

DECISION  --  ownership inversion (the "conductor" model)
    Terminal_Spec ABSORBS Terminal: one SpecNode carrying both the grammar-walk
    behaviour (expand / first2_set / nullable / cst_reduce) and the lexical
    specification (shape / pattern / spelling / mode / _name() identity). T mints
    Terminal_Specs; TERMINAL_DB, Ref/R, and the framing terminals relocate into
    the grammar_spec layer. terminals.py is RETIRED.

    The LEXER becomes a pure pattern engine: it receives a LIST OF PATTERNS from
    its conductor, matches bytes, emits tokens tagged with an opaque identity. It
    holds no database, imports no Spec, knows nothing of what a token MEANS to the
    grammar. Its whole interface is "here are patterns, give me the next token."

    The PARSER is the conductor and owns the lexer db: it holds the
    Terminal_Specs, EXTRACTS the pattern table (the tier-ordering logic --
    _generate_token_spec and friends -- is grammar-ordering knowledge the
    conductor owns, not byte-matching), hands the lexer that table, and maps the
    lexer's tagged result back to Terminal_Spec identity for the walk. The parser
    is the only side that knows both vocabularies (spec identity AND pattern) and
    translates between them.

    This is STRONGER than "the lexer reads lexical fields off Terminal_Spec": the
    lexer does not import the spec layer at all. "A lexer should not be aware of
    the functionality of the pattern it matches against" becomes literally true --
    it is aware only of the pattern.

SCOPE  --  STATIC extraction only (this step)
    The conductor extracts the FULL pattern table once at construction and hands
    the lexer all of it; "currently needed" means "the patterns this grammar
    uses", computed once. Same token stream, byte-identical GOODs. This is a pure
    ownership relocation, not a semantics change.

NOTE  --  finer-grained / contextual lexing (FUTURE, not built)
    "What is currently needed" also admits a CONTEXTUAL reading: the conductor
    hands the lexer only the patterns admissible AT THE CURRENT PARSE POSITION
    (the FIRST set where the walk stands), so the candidate set shrinks and grows
    as the parse moves -- scannerless / context-sensitive lexing, letting the same
    bytes lex differently in different grammar contexts (which the opaque-span
    handoff already does ad hoc). That is a real capability shift: it changes
    lexing semantics and could move GOOD files, so it is NOT this step. The static
    seam is its PREREQUISITE (the parser cannot subset patterns by context until
    it owns the db and feeds the lexer), so D-7 is the foundation a contextual
    lexer would build on. CURRENTLY THERE IS ONLY ONE LEXER; the conductor model
    is what would later allow several, or one fed a per-position pattern subset.

D-8  Operator interfaces as signals; actions.py folded into ast_map.py
-------------------------------------------------------------------------------
PROBLEM
    Three outer-layer files carried the rule-to-node machinery: ast_nodes.py (the
    node types), actions.py (the _build_* reduce builders + the dead ACTIONS
    dict), ast_map.py (the transformer overlay wrapping actions). The builders
    still spoke the engine-frame idiom (frame.values) even though the engine now
    produces a CST; the wiring was split across two modules; and AST nodes and CST
    nodes had no shared type, so a semantic walker could not treat them uniformly.

DECISION 1 -- operator interfaces in core, as SIGNALS not behaviour
    core/operator_interface.py defines OR_Interface / SEQ_Interface /
    PLUS_Interface / STAR_Interface over a root Operator_Interface. Every
    operator-shaped node -- generic CST casting AND typed AST node -- derives from
    the one matching its rule's top-level operator.

    The interfaces are SIGNALS, not callable contracts. The investigation that
    forced this: a digested AST node (Trigger, from an OR rule) does not retain a
    raw triggered_index -- the branch choice was translated into typed fields
    (is_keyword, name) at the factory. And nothing ever asks a held child for its
    operator internals: the engine, placing a sub-element in a parent sequence,
    only holds it as a value; the which-branch question is asked once, at the OR's
    own reduce, then baked in (verified -- the engine calls no face accessor
    during a parse). So an accessor contract would force every digested node to
    fabricate an answer (an arbitrary index; an or_child that returns self) that
    no caller reads. That is fakery, and it would break the GENERALITY that
    justifies a separate core: core would define two dialects (CST answers richly,
    AST fakes it) rather than one law.

    The honest, general law is the truthful intersection: every node carries
    'begin', is a placeable tree value, and DECLARES its shape by which interface
    it derives from. The signal is the payload -- it is what error analysis, the
    load-time shape validator, and a category-dispatching semantic pass actually
    consume (they READ THE SHAPE; none call an accessor). The shape-specific
    accessors (triggered_index / seq_children / rep_items) stay CONCRETE on the
    generic CST nodes, where they are honestly answerable, and are NOT hoisted
    into the interfaces as universal obligations.

    Consequence for hierarchy: the 'top-level' rule is an OR rule, so TopLevel
    (the marker for constructs admissible at file scope) IS OR_Interface --
    TopLevel(OR_Interface). A SEQ-rule top-level construct is
    StateMachine(SEQ_Interface, TopLevel): cooperative multiple inheritance of two
    fieldless ABC signals, no diamond hazard. ForwardDecl, whose rule (type-ref)
    is itself OR, is just ForwardDecl(TopLevel) -- OR_Interface + TopLevel would be
    MRO-inconsistent and redundant, since TopLevel already signals OR. Single-
    terminal rules (luau-guard, mutation, report-string -> Luau, Mutation,
    ReportString) derive from NO operator interface: their rule has no operator,
    so there is nothing to signal -- the one principled exemption.

DECISION 2 -- one factory layer: actions.py retired into ast_map.py
    The outer layer is now ast_nodes.py (the node types) and ast_map.py (how each
    rule's CST node becomes one), plus grammar.py and rule_parser.py (grammar
    definition and entry wiring, always separate). actions.py is deleted.

    The _build_* construction LOGIC is preserved verbatim, folded into ast_map.py,
    fed by _node_dense()/_flatten() -- the inverse of the engine's inline-operator
    materialisation -- which recovers from a rule's CST node the dense child list
    the bodies read. "Interpret the CST node directly" is honoured: the factory
    receives the node and interprets it (via the flatten helper, an outer-layer
    mechanism), with no engine frame and no shim crossing the layer boundary. The
    count-sensitive rules keep working unchanged because after flattening an
    absent optional is simply absent again.

    validate_ast_map() runs at compile (alongside the LL(2) check): coverage of
    every grammar rule. The per-class signal-derivation correctness (a SEQ rule's
    node IS SEQ_Interface, etc.) is asserted by ast_nodes deriving from the
    interfaces and is the subject of a dedicated Phase-5 test; the runtime never
    calls a face, so the signal is checked by shape, never by invocation.

VERIFICATION
    Byte-identical across the full suite: 14 core (engine+lexer), 8 outer
    (engine+lexer), 9 monkey-fuzz profiles, 2 cover (positive+negative). The
    migration changed the construction PATH and the node base classes; the AST
    nodes' fields and values are unchanged, so every GOOD holds. The dual-path
    parity harness (TEST/parity-check.py) was a migration scaffold -- with
    actions.py gone there is no second path -- and is removed.

NOT DONE (Phase 5, recorded)
    A dedicated core test asserting per-node signal derivation matches each rule's
    operator, and CST/AST-dict tests with GOODs recorded on real infrastructure.

D-9  Phase 5: standing tests for the CST machinery and signal correspondence
-------------------------------------------------------------------------------
PROBLEM
    The CST/overlay machinery (D-5) and the signal-interface correspondence (D-8)
    were verified during migration by parity diffs against the pre-existing GOODs
    -- evidence of behaviour preservation, but not a STANDING guard. A later edit
    could break the absent-optional-as-OR-state invariant, or change a rule's
    operator without updating its node, and nothing would catch it.

DECISION -- two dedicated tests, printed-output-as-oracle (HWUT discipline)
    core/TEST/test-cst.py (toy grammars, core only):
      cst_shapes / absent_optional / signals / overlay / overlay_partial /
      children_first. Pins the four canonical CST kinds and rule-name stamping;
      the keystone absent-optional invariant (an absent inline optional is an
      OR_Node index=1 child=ABSENT at a STABLE seq slot -- the parent SEQ keeps
      its child count either way, so presence is read off the node, never counted);
      that every CST node IS its operator-interface signal; partial opt-in
      overlay; and children-transformed-first (bottom-up call order proven).

    TEST/test-ast-signals.py (rule-file grammar):
      operator_table / signal_match / exemptions. Classifies each rule's top-
      level operator from the grammar, then asserts every dedicated AST node
      derives from the interface of its rule's operator -- 0 mismatches across
      all 35 built rules. Prints the 11 pass-through and 3 single-terminal
      exemptions explicitly. This is the standing guard: a future grammar edit
      that changes a rule's operator without re-deriving its node prints MISMATCH.

    validate_ast_map() stays the load-time COVERAGE guard (every rule mapped);
    the per-node shape correspondence is the test above, because the produced
    node class is known by parsing, not statically from a wrapped factory.
