===============================================================================
DISCUSSIONS  --  guards, effect-def signatures, aggregate inheritance
===============================================================================
(Append-only. This block records the rationale and costs of the constructs
added this round. Topology lives in README.txt / SYNTAX_DOC; this file owns the
"why" and the "what it costs".)

-------------------------------------------------------------------------------
D-1  Bracket-condition guard as an alternative to a Luau guard
-------------------------------------------------------------------------------
PROBLEM
    A guard written as a Luau span '& { ... }' is opaque to the engine: the
    parser holds it as black-box text, the static layer cannot see which members
    it reads, and a behavioural trace cannot attribute a fired guard to a
    subcondition. Opacity works against the reviewer-attention principle.

IDEA
    Admit a second guard form, a bracket condition '& [ ... ]': a boolean
    algebra ('and' / 'or' / 'not', parenthesisable) of comparisons over the
    triggering event's members. The parser builds an explicit Condition tree, so
    the static layer can validate member references and comparisons.

    Members are LEADING-DOT, SINGLE-LEVEL: '.ip_adr' is the 'ip_adr' member of
    the event the trigger named. The event is implicit -- a guard gates exactly
    the trigger it follows -- so no event name is written. Comparison only:
    operators are '>= <= == != > <', operands are a member, a number, or a
    string. No arithmetic, no function calls.

COST
    1. Expressiveness ceiling. The algebra deliberately cannot express computed
       terms. A guard needing 'distance(a,b) < t' has no bracket form.
    2. Reserved words. 'and', 'or', 'not' become keywords; they can no longer be
       identifiers. The six operators and '[' ']' are new tokens.
    3. A second guard shape on Cause.guard (Luau | Condition) -- two node kinds
       a consumer must handle.

MITIGATION
    1. The Luau guard is RETAINED, not replaced. The bracket form is the
       transparent fast-path for the common member-comparison case; Luau remains
       the escape hatch for anything computed. The two coexist on Cause.guard.
    2. Reservation is the standard keyword cost; 'not'/'and'/'or' are matched on
       word boundaries so identifiers like 'notice' are unaffected.
    3. Condition is a distinct named root, so the two guard forms are
       type-distinguishable, not order- or shape-spotted.

DECISION DEFERRED TO PASS-2
    Binding a '.member' to a declared event member, and type-checking a
    comparison against that member's type, are static-layer concerns. The parser
    only builds the tree.

NOTE (bare-member truthiness)
    'comparison only' means a bare member is NOT an atom: '[ .secure ]' is
    rejected; write '[ .secure == 1 ]'. Admitting bare-member truthiness would
    widen the rule (cond-atom would gain an evt-member branch); left out by the
    'comparison only' decision.

D-2  Effect-definition signature
-------------------------------------------------------------------------------
PROBLEM
    A cause definition carried a parameter signature ('cause: N(p:T) on: ...'),
    but an effect definition carried only a bare name ('effect: N => ...'),
    so an effect bundle could not be parameterised the way a cause could.

IDEA
    Give effect-def the same '<signature>' a cause-def uses:
    'effect: Boost(level: int) => ... '. EffectDef gains name/params, parallel to
    CauseDef.

COST
    EffectDef.name changes from a single identifier to a dotted-name list, and
    the node gains a params field -- a consumer reading EffectDef must adjust.

MITIGATION
    The change makes EffectDef and CauseDef structurally parallel, removing a
    special case rather than adding one. Effect-ref is unchanged this round; the
    'effect-ref carries args' question (and its collision with event-spec) is NOT
    reopened here.

-------------------------------------------------------------------------------
D-3  Aggregate inheritance via repeated 'is:' statements
-------------------------------------------------------------------------------
PROBLEM
    State machines and mode groups could reuse single members via 'has:', but
    could not be expressed as "like that aggregate, plus these changes".

IDEA
    Admit zero-or-more 'is: <base>' statements after an aggregate's signature:
    'state_machine: Derived(r:int) is: Base1 is: Base2 <body> :end'. Each
    inheritance is one 'is:' statement; bases are collected, in source order,
    into a 'bases' field on StateMachine / ModeGroup.

COST
    Inheritance is non-local: understanding Derived requires holding its bases in
    mind. This is the property 'has:' composition avoids (every member visible at
    its point of use), and it is the reviewer-attention cost flagged when the
    feature was first reflected on.

MITIGATION
    The PARSER only records the base names; ALL inheritance semantics --
    additive vs. override, name-collision handling, single vs. multiple bases,
    any linearization -- are deferred to a later layer. The grammar admits the
    form; it does not assign it meaning. Whether the resolved semantics keep the
    non-locality cost acceptable is a pass-2 design decision, recorded when that
    layer is built.

-------------------------------------------------------------------------------
D-4  Comparison operators and container type-params share one '<' / '>' terminal
-------------------------------------------------------------------------------
PROBLEM
    The comparison operators must be CAPTURED (the comparison builder reads the
    exact operator from the token). But '<' and '>' were already written as bare
    strings in <fwd-kind> for container type-parameters ('container < ... >').
    A bare string '<' mints a 'string:<' terminal; T.captured('<') mints a
    'captured:<' terminal -- two different terminal objects for one lexeme, which
    the lexer would emit as two competing patterns.

IDEA
    Use ONE captured terminal per lexeme. The comparison rule and the container
    type-param rule both reference the same t_op_lt / t_op_gt.

COST
    <fwd-kind> now carries the '<' / '>' tokens in its frame (they were silent
    before); its builder ignores them. A cosmetic frame change.

MITIGATION
    A single terminal per lexeme is the correct invariant regardless -- two
    terminals for one lexeme is the latent bug, not the fix. The fwd-kind builder
    already slices positionally, so the extra carried tokens are inert.

D-5  CST baseline, transformer overlay -- replacing the _build_* / ACTIONS model
-------------------------------------------------------------------------------
PROBLEM
    Reduction is hand-written _build_* functions in an ACTIONS dict, one per
    rule, registered by name on the PassThroughNode. Each unpacks frame.values
    positionally and builds a frozen AST node. The model is fragile in three
    ways. (1) Every grammar change demands synchronised edits in three files --
    GRAMMAR (grammar.py), the AST node shape (ast_nodes.py), the builder
    (actions.py) -- and their consistency is the author's manual burden. (2)
    Positional unpacking is silent-failure-prone: silent terminals are already
    dropped from frame.values and absent optionals leave no gap, so frame index
    i is NOT grammar position i, and inserting an optional shifts every index
    after it. (3) A forgotten ACTIONS entry is a None pass-through, not an error.

IDEA
    The engine ALWAYS builds a canonical CST. Every rule reduces, bottom-up, to
    a frozen CST node whose shape mirrors its top-level operator:

        OR-rule    -> OrNode  { name, triggered_index, child }
        SEQ-rule   -> SeqNode { name, children[] }
        PLUS-rule  -> PlusNode{ name, items[] }   (items non-empty)
        STAR-rule  -> StarNode{ name, items[] }   (items may be empty)

    Leaves are Tokens (captured terminals), SpanResults (opaque spans), or the
    already-reduced CST/AST nodes of child rules. Silent terminals contribute
    nothing -- this is a PRUNED CST: syntax discarded, structure kept.

    An optional, PARTIAL transformer dict overlays this:

        Grammar(GRAMMAR, transformers=AST_MAP, start="top-level")  # overlay
        Grammar(GRAMMAR, start="top-level")                        # pure CST

    A rule WITH a transformer: the transformer receives the rule's finished CST
    node and returns whatever it wants (a typed AST node, or an adjusted CST
    node). A rule WITHOUT one: its CST node passes through untouched. AST_MAP is
    keyed by rule name; absence of a key means "no transform".

    Transformer signature follows the rule's operator, matching the natural
    frame shape (PART-2 framing, NOT a per-grammar-position factory list):
        SEQ-rule   -> one transformer, receives the SeqNode (children list).
                      The rule owns the meaning of its whole sequence; it does
                      not interpret element-by-element.
        OR-rule    -> one transformer, receives the OrNode; it reads
                      triggered_index off the node to dispatch by branch. (An
                      indexed list of per-branch transformers is sugar over this
                      and may be added later; the node-carries-index form is the
                      primitive. Keyword/captured dispatch is rejected as messy
                      and off-engine -- choose_alt already knows the index.)
        PLUS/STAR  -> one transformer, receives the items list.

CHILDREN ARE TRANSFORMED FIRST (a consequence, not a feature)
    Reduction is eager and bottom-up: a node is finished the moment its frame
    reduces, before its parent's frame reduces. So by the time a parent's
    transformer runs, each child slot already holds the child rule's finished
    output -- a transformed AST node where the child had a transformer, a CST
    node where it did not. The comparison transformer receives an EventMember in
    its left slot, never a SeqNode wrapping one. This is what bottom-up already
    produces; obtaining it costs nothing, and PREVENTING it (re-wrapping finished
    children back into CST for the parent) would cost machinery. There is no
    laziness and no deferral -- "lazy transformation" was considered and
    discarded as a miscategorisation: both orderings are eager, they differ only
    in the child TYPE the parent sees, and the transformed-child type is the
    cheap one and the useful one.

    The case that would justify children-as-CST -- a parent wanting to inspect
    syntactic structure its children erased -- does not arise: the grammar
    already encodes such distinctions as SEPARATE rules with distinct output
    types (paren-cond vs comparison), so a parent reads a child's TYPE, never its
    pre-transform shape.

COST
    1. PASS_THROUGH and DEFAULT sentinels are RETIRED. "Forward the child
       unchanged" is just "no transformer" plus reading OrNode.child /
       SeqNode.children[0]. "Build the generic node" IS the default (the CST
       node itself). Both special cases vanish; so does the dict that named them.

    2. The completeness guarantee is GIVEN UP. The PART-1 design required
       set(AST_MAP) == set(GRAMMAR.rules), enforced at load like an LL(2)
       conflict, so a forgotten transformer was a loud load-time error naming the
       rule. Under a partial overlay, a forgotten transformer is SILENT at load:
       the consumer receives a CST node where it expected an AST node. The
       failure moves from load-time-named-rule to runtime-at-the-consumer. This
       is a deliberate trade of a guarantee for a far simpler structure, recorded
       as a choice, not an oversight.

    3. The CST node is built even for rules whose transformer immediately
       discards it -- one frozen-wrapper allocation per transformed reduction.

MITIGATION
    1. The retired sentinels removed real validation surface (PASS_THROUGH was
       valid only on a single-surviving-value production and had to be checked);
       deleting the concept deletes the check. Net machinery falls.

    2. The silent-forgotten-transformer failure is bounded by typing: CST nodes
       are frozen dataclasses, so a consumer that isinstance-checks its inputs
       fails visibly (and early) on an unexpected OrNode/SeqNode rather than
       corrupting silently. The guarantee is weaker than load-time, but the CST
       node is well-typed, not a raw frame -- the failure is diagnosable.

    3. Allocation cost is bounded and small. CST nodes hold REFERENCES to
       already-reduced children (bottom-up: children finished first), not copies,
       so a node is one allocation over a child list that already exists. Only
       TRANSFORMED rules pay the build-then-discard wrapper; untransformed rules
       pay nothing, because their CST node IS the output. The order is N
       allocations for N reductions -- the same order the old _build_* path paid,
       which also built one node per reduction.

ENGINE CHANGE (minimal)
    SEQ / PLUS / STAR need NO engine change: the dense frame is already exactly
    what their single transformer wants. OR needs the triggered branch index AT
    NODE-CONSTRUCTION TIME -- but choose_alt already returns the chosen branch,
    so the reducer has the index when it builds the OrNode; it is written onto
    the node, NOT threaded through Frame as a sidecar. The earlier sidecar-field-
    on-Frame idea is dropped: the node carries the index, and the transformer (if
    any) reads it there. No Frame change.

CORE LAYERING (close the acknowledged leak)
    The CST nodes (OrNode/SeqNode/PlusNode/StarNode) and the reducer that builds
    them live in core/ -- grammar-agnostic, Luau-free. The transformers and the
    AST node shapes live in the outer layer. A pure-CST parse must NOT reach into
    the outer ast_nodes; this is the chance to remove ll2_engine.parse()'s
    'from .. import ast_nodes' (the RuleFile construction) -- the top level
    becomes a STAR/PLUS CST node like any other, and the outer layer transforms
    it into RuleFile if it wants.

NOT DECIDED HERE (deferred, to be opened when the work lands)
    - Whether an indexed per-branch transformer list is added as sugar over the
      OrNode-carries-index primitive.
    - The migration of the count-sniffing SEQ rules (not-cond, or-cond/and-cond,
      cause) -- they stay SEQ-rules whose single transformer still counts the
      frame values exactly as the _build_* did; outputs (GOODs) identical, the
      logic mechanically lifted. Confirmed left as-is under PART-2; the PART-1
      sparse frame would have forced their rewrite, and that frame is not built.


D-6 GRAMMAR MIGRATION TO THE 57-RULE LANGUAGE (2026-06-12)

The grammar redesign decided in the semantic-layer log (D-21..D-27 there) is
installed: functionality-prefixed rule names, the five-kind declaration
family, merged named tails ('the parens decide'), the cond ladder with bare
boolean terms and symmetric comparison sides, 'for:'-bound cause definitions,
'import:'/'into:', 'via:' spawn keys, CHANGE.

RESERVED WORDS (lexer-level consequence of the captured kind/type keywords)
    Discriminating the kind-decl slot by CAPTURED keywords makes those words
    reserved EVERYWHERE on the rule-file plane: 'mode', 'state', 'mode_group',
    'state_machine', 'struct', 'container', 'int', 'float', 'string', 'bool',
    'true', 'false' (joining and/or/not, ANY/BEGIN/END/CHANGE, VOID) can no
    longer be identifiers -- not as declared names, not as member segments
    ('e.mode' is a syntax error). Inherent to the keyword-discriminated slot;
    the alternative (bare ids in the kind slot) is not LL-decidable. Recorded
    in SYNTAX_DOC's reserved-words note. The trailing-colon definition
    keywords ('mode:', ...) are unaffected -- longer tokens, earlier tier.

TWIN REF CLASSES OVER ONE <ref-member> VALUE
    <ref-member> reduces to a plain (segments, is_void) pair; 'has:' and
    'default:' wrap it into HasRef / DefaultRef -- same shape, DISTINCT
    classes, so the aggregate assembler dispatches by type, never by
    provenance. StateMachineModeRef is retired with the SM.member split: the
    head stays a segment list, splitting it is resolution's business (F-8).

SPAWN 'via:' NORMALISED THROUGH THE ONE CLASSIFIER
    The 'via:' key rvalue is normalised to a positional Arg via Arg._classify
    -- one classifier for every rvalue position (LITERAL / NAME / LUAU), no
    second normalisation path.

DEFECTS FIXED IN PASSING (both pre-dating the migration)
    - InitBlock/DeinitBlock stored the raw SpanResult despite declaring
      'body: Luau'; now wrapped through Luau.from_span like every other span
      position.
    - monkey-file-creator's AST walkers (_fmt, _collect_node_types) only
      descended lists, but STAR_Node.items is a tuple -- the node-type census
      always reported 0. Walkers now accept tuples.

D-7 OPAQUECODE LANDS (semantic ledger D-1/D-2) (2026-06-12)

ast.Luau is renamed OpaqueCode{text, mode, begin}; 'role' -> 'mode', typed as
core's SpanMode; ast_nodes.py drops its luau import -- the node names no
embedded language. OpaqueCode.get_references(oracle) is the lazy seam to the
span's insides: computed on first call through the abstract
SpanOracle.collect_references (core gains Reference{segments, begin}), begins
rebased onto the node's absolute position, cached in ONE compare=False,
repr=False slot written once via object.__setattr__ -- pure data in identity
and print; the oracle is an argument per call, never held.

OPEN: grammar.py still imports the luau Role to mint its opaque terminals
(T.opaque(Role.CONDITION)) -- a parser -> luau import the D-2 principle
('everything span-related speaks oracle') would also retire. Candidate shape:
a parser-owned SpanMode set (the grammar names rule-language positions --
condition/expression/lvalue/statement-block); the oracle dispatches on
mode.name. NOT done here: it restructures the luau wrapper selection and is
Frank-René's call.

D-8  EFFECT VERBS BECOME TRAILING-COLON KEYWORDS: '+!'/'-!'/'!' ->
     'spawn:'/'unspawn:'/'arm:' (2026-06-13)
-------------------------------------------------------------------------------
PROBLEM
    The three effect verbs were sigils: '+!' (spawn an aggregate), '-!'
    (unspawn), '!' (arm a mode). Sigils carry no self-statement -- a reader
    meets '+!' and must consult a legend -- and they are the only punctuation-
    verbs in a language whose every other connective is a trailing-colon
    keyword abutting its filler ('on:', 'in:', 'via:', 'until:'). The agent
    construct (D-11) makes the cost acute: an agent body carries these verbs as
    BARE commands with no '=>' before them, so a line opening with '+!' is
    cryptic punctuation standing alone.

IDEA
    Replace the three sigils with trailing-colon keywords on the colon
    principle: 'spawn: T(args) [in: C [via: k]]', 'unspawn: T', 'arm: M(args)'.
    One spelling for one concept on BOTH planes -- as a causality effect after
    '=>' and as a bare agent command. The verbs read as commands; the keyword
    states itself.

COST
    1. GOOD churn. Every recording rendering an effect verb changes
       mechanically (cover-syntax-tree, cover-negative, the monkey profiles
       that walk effects, name-dotted-args). Compiled at edit time; never
       fabricated.
    2. The AST node names (Spawn, Unspawn, ModeArming) were already keyword-
       aligned, so no node renames -- only the grammar terminals and the
       SYNTAX_DOC prose move.

MITIGATION
    1. Lexer SHRINKS. Two punctuation tokens ('+!', '-!') leave the symbol
       tier; the '+!'-vs-'+' longest-first concern vanishes. The new keywords
       ride the existing trailing-colon extraction with no new mechanism.

REJECTED
    Keeping '+!' in effects and 'spawn:' in agents: two spellings for one
    concept, the inverse of the one-noun-per-entity rule -- a reader would
    learn the sigil for effects and the keyword for agents and have to know
    they mean the same thing. One spelling, both planes.

D-9  OPAQUE-SPAN MODE BECOMES A CORE-OWNED E_SpanMode ENUM; grammar.py SHEDS
     ITS LAST LUAU IMPORT (closes D-7 OPEN) (2026-06-13)
-------------------------------------------------------------------------------
PROBLEM
    D-7 left ONE parser -> luau import standing: grammar.py minted its opaque
    terminals as 'T.opaque(Role.CONDITION)', importing the Luau layer's Role to
    name rule-language span positions (condition / expression / lvalue /
    statement-block). Those positions are a fact of the RULE LANGUAGE, not of
    Luau -- the rule file says "this guard is a condition span" regardless of
    which embedded language an oracle later measures it in. The import made a
    rule-language fact depend on an embedded-language module.

IDEA
    Core owns the span-mode set as an enum, E_SpanMode (members CONDITION,
    EXPRESSION, LVALUE, STATEMENT_BLOCK), living beside SpanMode in
    core.span_oracle. grammar.py mints 'T.opaque(E_SpanMode.CONDITION)' from
    core, importing no embedded language. The opaque terminal still CARRIES the
    mode and the engine still passes it to the oracle unread; the mode remains
    load-bearing (it tells the oracle how to measure the span) and remains part
    of the terminal's identity ('opaque:' + mode.qualified_name()). Only its
    DEFINING module moves: luau -> core. The Luau layer consumes the core enum
    where it dispatches wrapper selection; its own former 'Role' enum is
    retired or aliased to the core members.

    ENUM NAMING. Every enum in the codebase carries the 'E_' prefix
    (E_ArgKind already; E_SpanMode here; the luau Role enum renamed on the same
    convention). One reading rule for every enum, no exceptions.

COST
    1. The Luau wrapper-selection path keys on E_SpanMode members instead of
       its own Role; a mechanical rename at that seam.
    2. qualified_name() must still distinguish the oracle sub-language so two
       oracles measuring a CONDITION span keep distinct terminal identities;
       the core enum supplies the role half, the oracle supplies the language
       half -- identity composition unchanged from D-7.

MITIGATION
    The change is definitional, not behavioural: the mode object an opaque
    terminal carries is the same shape (qualified_name() / name), so
    consume_span, read_span, and the oracle contract are untouched. The
    interning key is unchanged, so no GOOD rendering an opaque terminal's
    identity moves on this account.

REJECTED
    Leaving Role in luau and importing it (the status quo): keeps a rule-
    language fact owned by an embedded-language module, against the D-2
    principle that everything span-related speaks 'oracle', not 'Luau'.

D-10  ADVISORY ROLE HINTS ON TERMINALS AND RULE REFERENCES (2026-06-13)
-------------------------------------------------------------------------------
PROBLEM
    A <name-dotted> in a rule position carries no statement of what the author
    INTENDS the name to resolve to -- an event, a clock, a mode. The grammar
    admits any name everywhere (resolution is pass 2), so the rule text reads
    flat: 'on: <cause>' does not say its trigger should be a clock, 'for:
    <name-dotted>' does not say its target is an event. The semantic layer
    re-derives intent it could have been told.

IDEA
    An OPTIONAL, ADVISORY role hint, a plain string, attachable two ways:
      - on a terminal, via a CALL operator: 't_re_id("event")' yields a role-
        tagged VIEW of the terminal (role = "event").
      - on a rule reference, via a suffix: '"<name-dotted(clock)>"' parses the
        parenthesised word as the reference's role.
    The hint is recorded on the compiled grammar (a transparent Tagged_Spec
    wrapping the inner element), where the semantic layer reads it as a
    resolution expectation, walked by position. It renders in the wrapper's
    repr for legibility. It is PURELY advisory: the parser core never acts on
    it.

    SURFACING (settled in implementation; refines the original sketch). The
    role rides on the GRAMMAR SPEC, not on a CST value. Tagged_Spec is an
    Operator_Spec whose nullable / first2 / expand delegate straight to its
    body, so it injects NOTHING into the value stream -- the CST is byte-
    identical to writing the body bare, and every AST factory reads its
    children unchanged. The "carried through the CST" of the first sketch would
    have meant a value wrapper every factory must unwrap -- the invasive
    per-position coupling the D-7 collapse removed. Instead the compiled
    grammar carries a position -> role map; pass 2 consults it where it walks a
    reference. Advisory and structural concerns stay orthogonal.

COST
    A transparent wrapper node in the spec tree, and a small extension to the
    reference-string parser ('<name(role)>' alongside '<name>') and a call
    operator on Terminal_Spec. The grammar-walking test support
    (aux_walker.walk) gains one transparent case for Tagged_Spec; the other
    spec walkers already descend via the Operator_Spec '.body' fallback.

MITIGATION (the identity rule that makes the hint safe)
    The role hint is NON-IDENTITY. It does NOT enter _name(), does NOT affect
    lexing, interning, or the LL(2) FIRST_2 analysis. This is the crux: if the
    hint entered identity, 't_re_id("event")' and 't_re_id("clock")' would
    become DIFFERENT terminals and fracture the interning that makes one
    keyword one token -- and '<name-dotted(event)>' and '<name-dotted(clock)>'
    would become different references. The hint rides ALONGSIDE identity, as a
    repr-visible annotation on the spec, never as a distinguishing field. The
    whole parser suite is byte-identical with the two demonstrator hints
    applied ('agent' on: -> clock, def-cause for: -> event), proving
    transparency.

REJECTED
    (B) Folding the functional opaque MODE and the advisory role hint into one
    plain-string 'role'. The mode is load-bearing (it changes what the oracle
    DOES) and MUST be in identity; the hint is advisory and MUST NOT be. One
    field cannot be both in identity and out of it -- conflating them is the
    one-spelling-two-meanings error at the terminal level. They stay two
    distinct fields: 'mode' (functional, in identity, D-9) and the role hint
    (advisory, out of identity, here).

D-11  THE 'agent:' CONSTRUCT -- A TICK-SCRIPTED STIMULUS ACTOR (2026-06-13)
-------------------------------------------------------------------------------
PROBLEM
    A golden-master test needs a deterministic stimulus: a scripted sequence of
    events fed to the system under test. With no in-language construct the
    author writes stimulus by hand in Luau, outside the rule-file plane and
    outside the static checks -- exactly the opacity the transparent plane
    exists to remove.

IDEA
    An 'agent:' construct: a clocked actor defined inside the rule file,
    spawned and unspawned like an aggregate, that emits events on a script.

    SHAPE. 'agent: <id> [(sig)] on: <cause> <elm-agent>+ :end'. The 'on:'
    target reuses the full <cause> syntax (trigger + optional guard, the
    heartbeat shape); the semantic layer resolves the trigger to kind CLOCK.
    The signature parameters ARE the instance members, read through a new self-
    binding 'ag' -- the agent counterpart of 'sm'/'mg'. 'agent' joins the
    declaration kind keywords ('... is: agent'), signature mandatory (a
    spawnable kind). 'init:'/'deinit:' as on a state machine. No inheritance
    (no 'is:' bases). The script is the lifetime: last step done -> deinit ->
    existence ends.

    TICK LAW. Only a PACED event emission consumes a tick. A bare <event-spec>
    'EVENT(args)' is the paced form -- the event fires at the agent's next
    clock beat. Every other step is TICK-FREE: the commands ('spawn:',
    'unspawn:', 'arm:', an opaque '{ }' block, each a BARE step with no '=>'),
    'wait:', 'select:', and the control heads.

    STIMULUS SIDE-CHANNEL. 'instant: EVENT(args)' injects one event into the
    CURRENT queue at the present instant -- tick-free, off the beat. The
    keyword is deliberately weighty: instant injection pours dynamics into a
    running cascade, and the author should think twice.

    WAITING. 'wait: <cause> (=> <effect>)*': suspend until the cause fires; the
    optional effect tail runs CO-TEMPORALLY with the cause, 'e' bound in the
    guard and the tail; a tail-less wait is a pure progression gate. 'select:
    <wait-line>+ :end' groups several waits -- the first cause to fire selects
    its branch, the others are abandoned. After the cause fires the agent
    resumes at the NEXT tick of its own clock (resumption (a)).

    CONTROL. 'if:'/'elif:'/'else:' (one ':end' per chain) and 'while: <cond>'
    (its own ':end') frame step sequences; their conditions reuse the existing
    <guard> (bracket '[ ]' or opaque '{ }'). 'e' is NOT in scope in control
    conditions (no trigger pins it); 'e' from a wait does NOT flow into
    subsequent steps. The constructs compose: any frame body is a step
    sequence, so select/if/while nest without restriction.

    FENCE. The imperative constructs are legal ONLY inside an agent body --
    structurally, the grammar admits them in the agent step rule alone, never
    in a causality effect.

COST
    1. New top-level construct and a fifth declaration kind; new self-binding
       'ag'; a band of new rules (agent, the step alternation, instant, wait,
       select, the if/while frames). LL(2) must hold -- verified on the real
       engine before downstream code.
    2. The bare-emission step opens with the identifier class while every other
       step opens with a trailing-colon keyword or '{'; the step alternation
       is LL(1)-clean by token class, but the claim is checked, not assumed.
    3. GOOD additions for the agent test choices; monkey profile 'agent';
       SYNTAX_DOC examples parsed verbatim.

MITIGATION / DETERMINISM (the ground resumption (a) rests on)
    Resumption (a) -- the agent acts ONLY at ticks of its own clock, the wait
    tail being the sole co-temporal exception -- keeps every scripted emission
    attributable to a clock tick, so a recording is a pure function of the
    trace and the clock periods. The rejected (b) (co-temporal continuation)
    would interleave tick-free commands with the cascade that delivered the
    cause, making their dispatch position a scheduler subtlety the recording
    depends on.

REJECTED
    - A '++' tick sigil marking each tick step: there is no tick sigil; the
      paced emission is the unmarked line and consuming a tick is a property of
      being an emission, not of a marker.
    - 'and:' / a 'flush: ... :end' co-temporal FRAME for several same-instant
      emissions: dropped. Same-instant injection is per-event via 'instant:';
      there is no frame.
    - 'or:' for shared-tail multi-wait: dropped in favour of 'select:' as the
      one multi-wait form (a bare 'wait:' is the one single-wait form).
    - Emission via a marked verb or a retained '=>': '=>' means "it follows
      that" (causality); an agent step is a command, so the bare <event-spec>
      IS the emission and no '=>' precedes a command.

SEMANTIC OBLIGATIONS HANDED ON (recorded in FOR-SEMANTICS, not enforced here)
    on:-trigger resolves to CLOCK; the fence is asserted structurally; 'ag'
    scopes to the agent body; control-condition kinds per F-5; emission names
    resolve per F-11; a PACED agent emission is a stimulus edge entering the
    cascade at a tick boundary, an 'instant:' emission a stimulus edge that may
    land within a running no-time cascade; the agent is never a cascade node.

D-12  RENAME 'agent' -> 'clockwork', 'ag' -> 'cw' (2026-06-13)
-------------------------------------------------------------------------------
DECISION
    The construct introduced in D-11 as 'agent:' is renamed 'clockwork:'
    throughout, and its self-binding 'ag' is renamed 'cw'. The keyword, the rule
    band (clockwork / elm-clockwork / step-clockwork / clockwork-emit /
    -instant / -wait / -select / -if / -while), the reserved word, the AST node
    (Clockwork) and its factory, SYNTAX_DOC, and FOR-SEMANTICS all move together.
    D-11 is left verbatim above as the historical record; read its 'agent' as
    'clockwork' and its 'ag' as 'cw'.

RATIONALE
    'agent' connotes autonomy -- an entity that senses, decides, and reacts. The
    construct has none of that: it runs a fixed script on a fixed clock,
    identical every run. The name advertised a freedom the design forbids, which
    is precisely wrong for a golden-master engine whose value is determinism.
    'clockwork' encodes the constraint instead of fighting it: a pre-wound
    mechanism, executed tick by tick, no choice. The mechanism connotation that
    would weaken an 'actor' name is the point here. 'cw' follows 'sm'/'mg' as the
    two-letter self-binding.

REJECTED
    'monad:' -- collides hard with the FP meaning (bind/return), the opposite of
        an imperative tick-script; actively misleading.
    'machine:' -- collides with 'state_machine:'; the construct is deliberately
        NOT a state machine (linear script, not a transition habitat).
    Keeping 'agent' -- the autonomy it implies is the specific defect above.

TESTS
    New positive coverage lands with the rename: test-engine.py
    'clockwork_shapes' (signature, guarded clock, the step variety, wait tail,
    select, if/elif/else, while, and the FENCE rejection) and the monkey-fuzz
    'clockwork' profile (seed 0xC107).

D-13  ALGEBRAIC + BOOLEAN EXPRESSION BAND, GUARDED MUTATIONS (2026-06-13)
-------------------------------------------------------------------------------
DECISION
    The bracket-condition grammar grows from a comparison-only boolean algebra
    into two LL(2) precedence ladders with an asymmetric, explicit crossing:
      - cond ladder: or/nor < xor/nxor < and/nand < not < comparison;
      - algebr ladder: shl:/shr: < +/- < * < unary-minus < atom;
      - the sole num->bool crossing is <comparison>; the sole bool->num crossing
        is the '?'-bridge ('? <cond> then: <algebr> else: <algebr>').
    '[ ]' groups conditions, '( )' groups algebra -- the bracket names the world.
    <rvalue> is folded into <algebr> (arguments are full expressions). Four
    clockwork-fenced mutation statements are added: '<lvalue> gets: <algebr>'
    (assign), 'incr:'/'decr: <name> [by: <algebr>] [to: <algebr>]' (saturating
    step), and '<lvalue> recip: <algebr> else: <body> :end' (guarded reciprocal).
    Read-only expressions are GLOBAL (every guard); the four mutations are
    clockwork-only.

RATIONALE
    [ ] vs ( ) splits the two worlds so the parser never has to decide at '('
    which ladder it is in -- a real LL(2) conflict otherwise. It is also the
    explicit type boundary the design wants, made syntactic. The crossings are
    deliberately one-way-per-direction and named, so a reader always sees where
    a number becomes a truth value and vice versa.

    Numbers are UNSIGNED ('\d+(\.\d+)?'); negation is the unary-minus operator.
    A signed literal makes binary '-' ambiguous: maximal-munch lexes 'x - 2' as
    'x' '(-2)', two operands. Carving '+'/'-' as their own atoms (the lexer
    operating on units of meaning) and reading '-2' as 'negate 2' removes the
    ambiguity. (F-R: '+/- are separable from the number'.)

    NO division operator. Reciprocal is a STATEMENT ('recip:'), not an rvalue,
    with a MANDATORY 'else:' zero-branch: the spark 'it can be zero' gets a
    prominent position in the code, and division is total by construction (no
    run-time div-by-zero possible). The operand is promoted to float -- the one
    implicit-promotion site.

    Mutations are clockwork-fenced ('operations live in a clockwork frame, not
    floating'): state mutates only on a tick, inside a clockwork body, so every
    write has a time anchor. Reads do not, so the expression ladder stays global
    and the guard grammar stays uniform.

    'by:' introduces the incr/decr amount because a bare optional '[<algebr>]'
    collides with the next (also name-led) statement under LL(2). 'gets:'/'recip:'
    are name-led and left-factored with the paced-emission tail under one shared
    <name-dotted> prefix (dispatch on '(' / 'gets:' / 'recip:'); 'incr:'/'decr:'
    are keyword-led.

    shl:/shr: are spelled as keywords, not '<<'/'>>', so '>>' never collides with
    nested 'container<...>' type closes (the C++ '>>' problem) and the lexer
    stays trivial.

    ONE BinOp / ONE UnOp for both ladders (op read verbatim), 'not' and unary
    '-' unified into UnOp. BoolOp and Not are retired -- a two-operator level
    (or/nor) cannot be an op-by-level n-ary node, so the binary-with-explicit-op
    shape subsumes both. Comparison's operands widen from name-dotted to full
    <algebr>.

REJECTED
    Signed number literals -- ambiguous binary '-' (above).
    A '/' operator -- a silent div-by-zero / int-vs-float liability; 'recip:'
        with a forced zero-branch is the only division.
    'recip:' as a general rvalue -- the zero-branch is control flow and would
        drag a ':end'-terminated block into the expression grammar; statement-
        only keeps the zero spark prominent (F-R).
    '( )' for both worlds -- the LL(2) '(' conflict (above).
    bracketing unary minus '(- x)' -- buys no parsing safety; alg-un already
        disambiguates by position.

TESTS
    test-engine.py 'guards_and_inheritance' exercises the ladders; the monkey
    and the positive/negative coverage walkers reach every new rule. A shared
    walker fix was required: the bridge/paren cycle makes OR rules where EVERY
    branch can re-enter an active rule, so the canonical fallback (and the
    monkey's budget-spent fallback) now choose the shortest-derivation branch
    (min_terminal_distance) instead of branch[0]/fewest-nonterminals, which could
    loop. WalkContext.active became a Counter so a rule re-entered through a
    cycle stays marked until its own frame exits.
