## 1. Normalized lifecycle (authoritative)

A **test run** follows this lifecycle:

RS.initialize()
    ├─ load Lua bootstrap
    ├─ initialize Lua VM
    ├─ load test-specific HEADER
    │     ├─ META-EVENT definitions (non-Lua)
    │     └─ Lua header code (helpers, constants)
    └─ RS becomes ARMED

RS.process(event)   [called repeatedly]
    ├─ update history / occurrence DB
    ├─ derive META-EVENTS (fixpoint)
    ├─ inject TIME / PREV_TIME / NOW into Lua
    ├─ activate / deactivate rule sets
    ├─ execute action blocks
    ├─ evaluate rule expressions
    └─ record violations (or abort)

RS.terminate()
    ├─ inject END event
    ├─ final rule checks
    └─ finalize reports

KEY DECISION:

`process(Event)` is the only feeding function during the test**

It guarantees:
	* determinism
	* replayability
	* testability
	* single causal chain

Everything else (meta-events, rules, statistics) must be *derived* from this.

## 3. Component model (clean and minimal)

### 3.1 Engine (internal core)

	* occurrence database
	* META-EVENT evaluator
	* rule activation logic
	* violation tracking
	* mode handling (compliance / observation)

    **no public API for tests**.

Engine
 ├─ OccurrenceDB
 ├─ MetaEventEvaluator
 ├─ RuleSpace
 ├─ ViolationLog
 └─ Mode (compliance / observation)

### 3.2 RuleSpace (subsystem, internal)

	* embeds the Lua VM
	* loads the bootstrap
	* exposes `exec_header`, `exec_action`, `eval_expr`
	* enforces sandboxing

**not**:

	* manage history
	* decide activation
	* know about test execution

It is a **pure evaluation service**.

	RuleSpace
	 ├─ Lua VM
	 ├─ Lua bootstrap
	 ├─ header_env / action_env / expr_env
	 └─ sandbox enforcement


### 3.3 Event Stream API (public façade)

    This is what **tests and stream drivers** see.
    Minimal and intentional.

    class E_EventStreamAPIMode:
        ABORT_EARLY
        COMPLETE
	class EventStreamAPI:
		def initialize(self, test_spec): ...
		def process(self, event): ...
		def terminate(self): ...
```

Internally, it delegates to `Engine`.

This keeps:

* test authors happy
* engine internals protected
* future refactors painless

---

## 4. Why this separation is optimal

### ✔ No leakage of internals

Tests never touch:

* Lua VM
* rule activation state
* occurrence DB

### ✔ Clear responsibilities

* **EventStreamAPI** → orchestration
* **Engine** → semantics
* **RuleSpace** → evaluation sandbox

### ✔ Multiple façades are easy

You can later add:

* `StreamRunner`
* `ReplayRunner`
* `InteractiveRunner`

All using the **same Engine**.

ARCHITECTURAL CONCLUSION
=======================

The HWUT engine is structured around a strict separation of concerns between
test orchestration, rule evaluation, and sandboxed logic execution.

At the outermost layer, the EventStreamAPI forms the sole public interface for test
execution. A test run follows a fixed lifecycle:

  initialize() → process(event)* → terminate()

After initialization, the engine is considered *armed*: rule activation,
meta-event derivation, and rule checking are enabled. From that point on,
process(event) is the only admissible way to feed information into the system.
This guarantees determinism, replayability, and a single causal chain.

The EventStreamAPI.process(event) method returns a boolean result indicating whether
the current step violated any active rule. The engine operates in one of two
explicit modes:

  - compliance mode:
      The first detected rule violation causes immediate abortion of the test.
      process(event) returns False and no further events are processed.

  - trace-complete mode:
      All events are processed until termination. All rule violations are
      recorded with full provenance. process(event) returns False for steps
      where violations occur, but execution continues.

Internally, the EventStreamAPI delegates all semantics to the Engine, which owns:

  - the occurrence database and time model,
  - meta-event evaluation and fixpoint derivation,
  - rule activation and deactivation,
  - violation tracking and reporting.

The Engine, in turn, relies on a dedicated LuaRuleSpace subsystem to evaluate
user-defined predicates and actions in a sandboxed Lua environment. The Lua
rule space is not autonomous; it is driven exclusively by the Engine and
cannot influence control flow or state outside its declared interfaces.

This architecture intentionally limits mutability, centralizes causality, and
keeps all extension points explicit and reviewable. The result is a system that
is expressive enough for complex temporal and domain-specific tests, while
remaining deterministic, auditable, and robust against accidental misuse.
