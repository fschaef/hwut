VUT-TESTRUN-ADAPTER: SPECIFICATION (draft for review)
============================================================================

Status:   PROPOSED (not yet implemented); this spec is for review.
Layer:    ORCHESTRATION -- one level ABOVE the applications
          (procsitter_test_app, procsitter_build) and the compare
          engine. It ADAPTS heterogeneous test descriptions to ONE
          homogeneous door and ties build + run + compare + an observer
          together.
Decided:  (pending) discussion Frank-Rene / Claude, 2026-07.
          Corrections already folded in:
          (a) 'simulated' is a MISNOMER -> the second provenance is
              REPLAY (relies on stored data of a previous real run).
          (b) ASSOCIATION mode reads the streams out for DISPLAY (fed
              into an IDE / web / db); the FORMAT of that feeding is NOT
              part of this component -- the adapter hands the aligned
              comparison to an OBSERVER and stops there.


----------------------------------------------------------------------------
1  PURPOSE
----------------------------------------------------------------------------

THE TEST RUN ADAPTER: one homogeneous interface for running a test and
reporting what happened -- whatever the test is made of, however it is
produced, and wherever the outcome is shown.

A test is given as a SOURCE FILE. That source may be
  -- an EXECUTABLE already (run it directly),
  -- INTERPRETED by a named interpreter (lua, python, ...), or
  -- COMPILED into a test application first (a supervised build).
The run may PRODUCE its outcome by actually executing (REAL) or by
REPLAYING stored data from a previous real run. And the outcome may be
consumed as a bare VERDICT (equivalence) or as an aligned COMPARISON to
be displayed (association). Every one of these variations goes through
the SAME door:

    run_test(config, observer=None) -> TestRunReport

The adapter owns none of the heavy machinery. Containment is
procsitter's; building is procsitter_build's; judging and aligning is
compare's (via procsitter_test_app). The adapter's job is to ADAPT and
to WIRE -- to turn a test description into the right supervised calls
and route the outcome to an observer.


----------------------------------------------------------------------------
2  THE AXES (orthogonal, as everywhere in this project)
----------------------------------------------------------------------------

The variation space factors into independent axes. A point in the space
is a (provenance, mode, source-kind, observer) tuple; the door accepts
all of them as DATA.

  AXIS 1 -- PROVENANCE: where the subject streams come from.
      REAL     the test is executed: (build if COMPILED) then run under
               a procsitter; the productions are the live streams.
      REPLAY   the test is NOT executed; the subject streams are read
               from the RECORD of a previous real run (stored data).
      The judging/display path downstream is IDENTICAL: a production is
      bytes, indifferent to whether a live stage or a stored file
      produced it. Provenance is the ONLY thing that differs.

  AXIS 2 -- MODE: what is done with the subjects.
      EQUIVALENCE   judge them -> a bare VERDICT (OK / FAIL_*). Fast,
                    fast-fail. This is the JUDGE of procsitter_test_app.
      ASSOCIATION   align them -> a stream of ChunkPairs read out for
                    DISPLAY. This is the LAWYER of procsitter_test_app.
                    The adapter hands the pairs to the observer; how the
                    observer renders them (IDE, web, db) is NOT this
                    component's concern.
      This is EXACTLY the Judge/Lawyer duality that already exists one
      layer down -- reused, not reinvented. 'mode' is a plain field on
      the config, so the ONE door serves both (just as run_test_app
      switches on 'consumer=None' vs a callable). No second entry point
      is needed; that keeps the interface homogeneous.

  AXIS 3 -- OBSERVER: where the events go. A console driver informing a
      user, a web interface, a database of record -- these are
      IMPLEMENTATIONS of one small protocol (section 5), an orthogonal
      SINK, not a behavior. Fanning out to several at once is the tee
      idea again: observers ADD.

  SOURCE KIND (a property of turning a source into a runnable command;
  it matters to REAL only, since REPLAY runs nothing):
      EXECUTABLE    the source IS the program: run [source, args...].
      INTERPRETED   run [*interpreter, source, args...] -- interpreter
                    is an argv prefix (['lua'], ['python3','-u']).
      COMPILED      build the source into an app (procsitter_build),
                    then run the produced application.


----------------------------------------------------------------------------
3  THE HOMOGENEOUS DOOR
----------------------------------------------------------------------------

    async run_test(config: TestRunConfig,
                   observer: Observer|None = None) -> TestRunReport

  input  = configuration (the test AND how to run/judge it)
  output = report (the verdict/alignment AND the attribution records)
  side   = the observer is notified as the run unfolds (default: none).

  @dataclass TestRunConfig:                         # THE COMPLETE INPUT
      # -- identity & place ------------------------------------------
      name:        str                # the test's name (for the report
                                      # and the observer)
      source:      str                # path to the test SOURCE file
      location:    str                # the test app's directory; the
                                      # run's work dir. Outputs land in
                                      # its 'OUT/' subdir (created).
      # -- source -> runnable (REAL only) ----------------------------
      kind:        E_TestSource       # EXECUTABLE | INTERPRETED |
                                      # COMPILED
      interpreter: Sequence[str]|None # argv prefix, INTERPRETED only
      build:       ProcsitterConfigBuild|None
                                      # the supervised build, COMPILED
                                      # only (reused verbatim)
      run_argv:    Sequence[str]      # extra args to the test app
                                      # (after source / after the built
                                      # program); default empty
      # -- subjects (reused from procsitter_test_app) ----------------
      channel:       Comparator|None  # stdout nominal; None: drained
      error_channel: Comparator|None  # stderr nominal; None: tail-kept
      file_db:       dict             # OUT/<name> -> Comparator, post-
                                      # exit (files the test writes)
      # -- the two axes as data --------------------------------------
      provenance:  E_Provenance       # REAL | REPLAY
      mode:        E_TestMode         # EQUIVALENCE | ASSOCIATION
      # -- caps for the run's supervised call ------------------------
      procsitter:  Procsitter|None    # the contained call for the test
                                      # app (REAL); its ProcsitterConfig
                                      # carries the resource caps
      record_store: str|None          # where a REAL run RECORDS its
                                      # streams and where a REPLAY reads
                                      # them; default 'OUT/.rec/' under
                                      # 'location' (section 4)

  @dataclass TestRunReport:                        # THE COMPLETE OUTPUT
      name:        str
      provenance:  E_Provenance
      mode:        E_TestMode
      report:      E_TestRunResult    # THE BRIEF REPORT: OK or the one
                                      # reason token (section 6)
      verdict:     bool               # the reduction (EQUIVALENCE); for
                                      # ASSOCIATION, the same reduction
                                      # computed over the alignment
      subject_verdict_db: dict        # "stdout"/"stderr"/file -> bool
      build_report: ProcsitterResultBuild|None      # COMPILED real only
      run_result:   ProcsitterResultTestRun|None     # REAL only -- the
                                      # underlying judged-run record
      # (ASSOCIATION streams are not stored in the report; they are
      #  delivered to the observer as they are produced -- see 5.)


----------------------------------------------------------------------------
4  REAL vs REPLAY  (and RECORDING = the logging taps)
----------------------------------------------------------------------------

REAL. The adapter:
  1. resolves the source into a command by 'kind' (build first if
     COMPILED; report BUILD_* / TARGET_NOT_BUILT and stop on failure);
  2. runs the judged test via procsitter_test_app.run_test_app, its
     work dir = 'location', its outputs in 'OUT/';
  3. RECORDS the subject streams into 'record_store' AS IT RUNS.

  The recording is NOT a new mechanism. It is the producer-side
  stdout/stderr TAPS added to procsitter_test_app: a log file is a
  consumer on a production port, teed in. A REAL run simply points those
  taps at 'record_store' (stdout.rec, stderr.rec) and copies the OUT/
  file subjects there, plus a small MANIFEST (subject names, nominal
  identities, the verdict, the run's records). Recording is a tee.

REPLAY. The adapter runs NOTHING:
  1. reads the manifest from 'record_store' (RECORDING_MISSING -> a
     FAIL if absent or incomplete);
  2. exposes each recorded stream as a reader and each recorded file as
     a path;
  3. feeds them into the SAME compare calls (is_equivalent for
     EQUIVALENCE, associate for ASSOCIATION) against the SAME nominals.

  REPLAY is deterministic and cheap: re-judging or re-displaying a past
  run without touching the build or the process table. It is the natural
  home for "show me that comparison again" (ASSOCIATION) and for a
  fast regression pass (EQUIVALENCE) over a corpus of recordings.

  OPEN (for review): the record_store layout. Proposed: 'OUT/.rec/' with
  'stdout.rec', 'stderr.rec', 'files/<name>', 'manifest'. Alternatives:
  (b) record only streams and re-read OUT/ files in place (lighter, but
  couples replay to OUT/ surviving); (c) a portable self-describing
  bundle independent of OUT/ (movable across machines). Recommend (a).


----------------------------------------------------------------------------
5  THE OBSERVER  (the display seam; format NOT owned here)
----------------------------------------------------------------------------

The observer is where the outcome LEAVES the component. The adapter
calls it; it does not know or care what happens next. This is the seam
that keeps "display format" out of scope:

    class Observer:                    # duck-typed; all methods optional
        def started(self, name, provenance, mode): ...
        def built(self, build_report): ...          # COMPILED real only
        def verdict(self, subject_name, ok): ...     # EQUIVALENCE
        def association(self, subject_name, chunk_pair): ...  # ASSOCIATION
        def finished(self, report): ...

  EQUIVALENCE feeds 'verdict' (and 'finished' with the report): a
  console driver prints ok/FAIL, a db writes a row. A bare result
  suffices, exactly as you noted.

  ASSOCIATION feeds 'association' with each ChunkPair as it is aligned:
  the streams to be DISPLAYED. An IDE, a web view, a diff pane consume
  them -- but the adapter only HANDS THEM OVER. The rendering/feeding
  format is the observer's business, not the component's.

  Shipped: ConsoleObserver (prints), NullObserver (default, silent).
  Web / db / IDE observers are the caller's, implemented against this
  protocol. Fan-out to several is a CompositeObserver -- observers ADD,
  the same algebra as tee.


----------------------------------------------------------------------------
6  THE BRIEF REPORT  (verdict vocabulary -- reused, lightly extended)
----------------------------------------------------------------------------

E_TestRunResult (vut.auxiliary.test_run_result) already carries the
outcome tokens this layer needs: OK, NOT_EQUIVALENT_WITH_NOMINAL,
TEST_APP_LAUNCH_FAILED, TEST_APP_CONTAINED, TEST_APP_NO_OUTPUT,
OUTPUT_FILE_NOT_FOUND, NOMINAL_FILE_NOT_FOUND, the PYPE_* family, and
the BUILD_* / TARGET_NOT_BUILT family. The adapter REUSES it.

Proposed ADDITIONS (for review): SOURCE_NOT_FOUND (the source file is
absent), INTERPRETER_NOT_FOUND (the named interpreter cannot launch --
distinct from the app itself), RECORDING_MISSING (REPLAY, but the
record_store has no usable recording). Reason precedence: source/build
reasons outrank run reasons outrank subject/nominal reasons, matching
the layering (a test that never built cannot be judged).


----------------------------------------------------------------------------
7  LAYERING / REUSE  (the adapter writes almost no new logic)
----------------------------------------------------------------------------

    ORCHESTRATION   test_run_adapter.py  run_test(config, observer)
                          |              -> TestRunReport
                          |              provenance x mode; source-kind;
                          |              observer seam
        +-----------------+----------------------------------------+
    APPLICATIONS    procsitter_build.run_build (COMPILED) ;
                    procsitter_test_app.run_test_app (REAL judge/assoc,
                    recording via the stdout/stderr taps)
        +-----------------+----------------------------------------+
    COMPOSITION     Link / tee / launch_chain
        +-----------------+----------------------------------------+
    THE GROUND      Procsitter.run  (containment + attribution)

  REAL/EQUIVALENCE  = run_build? -> run_test_app(consumer=None)
  REAL/ASSOCIATION  = run_build? -> run_test_app(consumer=observer-fed)
  REPLAY/EQUIVALENCE= compare.is_equivalent over recorded readers
  REPLAY/ASSOCIATION= compare.associate over recorded readers -> observer

  Everything the adapter adds is: source->command resolution, the
  record/replay store, the observer protocol, and the reason
  precedence. No containment, no compare, no chain logic is
  re-implemented here.


----------------------------------------------------------------------------
8  OPEN QUESTIONS  (to settle before implementation)
----------------------------------------------------------------------------

  - RECORD STORE layout (section 4): (a) OUT/.rec/ + manifest
    [recommended], (b) streams-only re-reading OUT/, (c) portable
    bundle. Which?
  - MANIFEST format: a tiny JSON (portable, human-readable) vs a Python
    literal. Recommend JSON.
  - Does REPLAY re-open the SAME nominal objects from the config, or
    does the recording also store the nominal so a replay is fully
    self-contained? (Self-contained favors (c) above.)
  - NAMING: module 'test_run_adapter.py', door 'run_test', types
    'TestRunConfig' / 'TestRunReport', enums 'E_Provenance' /
    'E_TestMode' / 'E_TestSource'. Confirm or adjust.
  - Should COMPILED's build and the run share ONE work dir ('location')
    or should the build run in 'location' and the app in 'OUT/'?
  - Test corpus discovery (a directory of tests) is a SEPARATE concern
    (a runner over many run_test calls) -- out of scope for the adapter
    itself. Confirm it stays out.
