============================================================================
VUT-ORCHESTRATOR -- RATIONALE
============================================================================

Settled decisions, read-only. Ruled by Frank-Rene, 2026-08-12, closing
test_run's disc-1 (THE RESULT STORE).

----------------------------------------------------------------------------
D-1  ONE BASE REPLACES THE FOOTPRINT
----------------------------------------------------------------------------
PROBLEM   The same fact stood in several places: the footprint, the
          store, the recorded candidates, the configuration's own
          declarations. The attribution record (ProcsitterResult) had
          two transient homes and zero durable ones. The footprint is
          read back for queries and report generation, so a stale copy
          produces a wrong answer.
DECISION  ONE base, 'GOOD/result_db.json', replaces the footprint file
          outright. Six facts collapse to one home each: canonicaliser,
          compare setup, verdict/report, candidate-vs-nominal claim,
          the attribution record (first durable home), the key scheme.
COST      GOOD is written by every Run. Mitigated: the adapter owns
          unprotect/write/re-protect, atomically.
GRAVEYARD Two files (structure in GOOD, volatile footprint outside):
          rejected -- it recreates, inside our own tree, the divergence
          problem the discussion exists to abolish.

----------------------------------------------------------------------------
D-2  PROTECTION IS A GUARD, NOT A BLESSING
----------------------------------------------------------------------------
PROBLEM   GOOD's write-protection marks blessed descriptions of good
          behaviour; a base rewritten on every run is not blessed.
DECISION  The property of immutability is 'misused' for the base: it
          protects a record from unintentional user actions. There is
          nothing to bless about a report db; it just records properly.
COST      Two protection reasons live in one directory. Mitigated: the
          distinction is stated here, once.
GRAVEYARD Placing the base outside GOOD: rejected -- it loses the
          guard, and it is exactly the careless hand the guard is for.

----------------------------------------------------------------------------
D-3  JSON
----------------------------------------------------------------------------
PROBLEM   JSON or HOCON (or JSONC/JSON5/HJSON/YAML) for the base.
DECISION  JSON. Stdlib read and write, lossless byte-stable round
          trips, the existing readers already speak it.
COST      No comments. Mitigated: a comment in any dialect survives
          only until the next machine write; commentary, if wanted, is
          emitted by the adapter as data fields.
GRAVEYARD HOCON: a dependency, a lossy write path, comfort for a file
          nobody may edit by hand. Its includes argument (a base
          referencing another) is speculative -- the directory-list
          layer is parked (test_run disc-8).

----------------------------------------------------------------------------
D-4  DIVERGENCE ON CALL; RENAME IS THE KIND THAT MATTERS
----------------------------------------------------------------------------
PROBLEM   A user edits declarations at will; the base does not follow.
          Entries for renamed or deleted names linger as truth. When is
          the discrepancy detected, and what is the reaction?
DECISION  ON CALL. The caller knows what it asked: 'run all tests'
          makes a missing choice an error; 'run this test with that
          choice' does not. The Bookkeeper provides the verdict as
          data: an unregistered app rename reads DELETED (its tests
          failed), an unregistered choice rename reads NON-RESPONSIVE.
          Healing is a service (hwut.rename, hwut.rename-choice,
          hwut.remove, hwut.remove-choice), never a guess.
COST      'Non-responsive' surfaces later than at write; callers must
          ask. Mitigated: the manager above asks once per task.
GRAVEYARD Detection at write time: a renamed choice's entry is never
          written again, so write-time detection never sees it.
          Detection on every open: greets 'hwut.rename' with the
          complaint it came to resolve.

----------------------------------------------------------------------------
D-5  THE COMPONENT AND ITS SEAM
----------------------------------------------------------------------------
PROBLEM   Where do the base's adapter, the configuration parsing, the
          services and the naming live?
DECISION  One component, vut/engine/orchestrator/: bookkeeper/ (one
          test directory's book), explorer/ (which directories),
          services/, orchestrator.py binding them. The Bookkeeper takes
          THE NAMING -- (test, choice, subject) -> path -- so the key
          scheme has one expression; the report service stops globbing
          and asks. test_run keeps the artifact handling (Nominal
          kinds, promotion on accept) and the directory lock: the
          Bookkeeper answers WHERE, test_run decides WHEN. A rename
          touches declarations and results at once; one component keeps
          that a one-scope transaction.
COST      test_run mounts orchestrator/bookkeeper for every path it
          forms. Mitigated: one import, one face.
GRAVEYARD The adapter inside test_run: four services and a query tool
          that run no test would depend on the component that runs one.
          A Bookkeeper that also handles streams: acceptance is a
          test_run ceremony, not a storage act. 'data_management' as
          the name: names the activity, not the thing. A top-level base
          above the directories: every fact in it a copy, the whole
          problem one level up -- the directory set is the Explorer's
          question, not a second base.

----------------------------------------------------------------------------
D-6  ENTRIES ARE DERIVED (the seam faces the Bookkeeper)
----------------------------------------------------------------------------
PROBLEM   Does test_run flatten an entry and hand a dict, or hand the
          result and configuration for the Bookkeeper to derive?
DECISION  The Bookkeeper DERIVES: record(result, configuration, goal,
          choice_name). compare_setup_delta lives here; when compare
          gains an option, one place learns of it. The attribution
          rides in on result.provision.records without a new argument.
          The Bookkeeper is made ABOVE and handed to every test_run
          mode; a service makes its own inside the service.
COST      The Bookkeeper knows the SHAPE of test_run's result and
          configuration objects. Mitigated: duck-typed attribute
          access; no test_run import at module level, so no cycle.
GRAVEYARD test_run flattening: keeps compare knowledge inside the
          recorder and leaves the dict's shape an unwritten contract
          between two components.


D-7  THE TEST REGISTER: RELATIONAL, LOWEST-UNUSED, DELETE-FREES  (2026-08-25)
------------------------------------------------------------------------------
MOVED    The register described here left this component on 2026-08-25:
         the bookkeeper is a COMPONENT now (bookkeeper RATIONALE B-1).
         The decision below stands as ruled; only its address changed,
         from 'orchestrator/bookkeeper/' to 'bookkeeper/'.
SUPERSEDED IN PART (2026-08-25, bookkeeper B-2): the ALLOCATION law
         below -- lowest-unused, delete-frees, and the guard 'an id
         never leaves the book' -- is replaced by issue-once from 0
         with a persisted mark and a 2**32 ceiling. The relational
         shape, the file's place and the healing services stand.
SUPERSEDES coverage D-9 in whole and coverage D-14 in part: D-14's
          DIR-LOCALITY stands and is load-bearing here; its interned
          pair, monotone allocation, never-reuse law and retirement
          machinery fall.
PROBLEM   Coverage attribution, the healing services and exploration
          all need 'which test is this' as a NUMBER that survives a
          rename. The pair-interning gave one id per (test, choice),
          so renaming an application touched one entry PER CHOICE; and
          its never-reuse law demanded retirement flags and a monotone
          counter -- machinery guarding stored ids that nothing stores.
DECISION  RELATIONAL, in 'bookkeeper/test_id_db.py', one file per
          directory, 'GOOD/test_ids.dat':

              APP      app_id    o--o  application file name
              CHOICE   choice_id o--o  choice name, PER application
              run      TestRunId(app_id, choice_id|None), '47' / '47.66'

          THE ID IS BORN AT FIRST ACCEPT ('hwut.accept' allocates on
          bless, idempotently). ALLOCATION IS LOWEST-UNUSED in each
          table's own scope -- accepting is not time critical, so the
          smallest free number is chosen deliberately: no counter to
          persist, no march to infinity. REMOVAL DELETES the entry and
          frees the id. The guard that makes reuse safe: AN ID NEVER
          LEAVES THE DIRECTORY'S BOOK -- everything persisted carries
          names (coverage D-8; the base's own keys). Should a persisted
          index one day want stored ids, THAT design re-opens this.
          A MISSING register reads empty (a fresh directory); a DAMAGED
          one REFUSES BY NAME -- unlike the result base, because
          exploration restricts itself to the register and an empty
          reading would silently hide every test.
          THE REGISTER GAINS TWO ANSWERS THE PAIR NEVER HAD:
          'vanished()' names every registered application whose file
          left without 'hwut.remove' (the divergence D-4 could not
          see: the base knows results, the register knows EXISTENCE),
          and 'roster()' is what exploration will restrict its
          interviews to.
COST      Accept writes one more file, per allocation, atomically.
          Five service GOODs moved by exactly one line each (the
          register in a directory listing) and one by the new option's
          help text -- audited whole, re-recorded.
GRAVEYARD One id per (test, choice) pair: a fifty-choice rename is
          fifty entries.
          Retirement and never-reuse: protection for stored ids, where
          storing ids is forbidden instead.
          A global register above the directories: needs the lock and
          the coordination dir-locality (coverage D-14) exists to
          remove.

AMENDED (2026-09-04, on retiring 'orchestrator/DISCUSSIONS.txt', whose
         todo-4 carried these two rulings of 2026-08-25 and whose every
         entry is now built):

         WHAT A VANISHMENT COSTS EACH FACE. 'hwut.run' NOTES
         MISSING/FAIL for a registered run whose test or choice is no
         longer there -- a renamed choice among them -- AND THE SUITE
         CONTINUES. A vanished test does not abort a run: the other
         tests still have something to say. Services that need the
         test SOURCE ('hwut.show <file>' among them) REFUSE, because
         there is nothing to read; every other face MENTIONS the
         vanishment and proceeds.

         AN EXPLICIT NAME OUTRANKS THE ROSTER. There is no
         'hwut.register' face: the FIRST 'hwut.accept' creates the
         entry, as above. The roster restricts THE WALK, and nothing
         else -- a file named EXPLICITLY on a command line is
         interviewed regardless of whether it stands in the register.
         That is how a new test runs before it exists in the register,
         and why no registration step is owed to the author.


D-8  IDS IN RECORDS; ONE HOLDING FREES AND DELETES               (2026-08-25)
------------------------------------------------------------------------------
PROBLEM   Three rulings meet. Coverage records carry the test's NAME in
          their header (coverage D-8), so a rename leaves stale names
          inside stored files. Repairing that in 'hwut.rename' adds a
          feature the storage format makes unnecessary: the ruling is
          that VUT-COVERAGE records will REFER TO RUN IDS (or group
          ids), not names. But D-7 frees an id on removal -- and a
          freed id, reissued, would let an OLD record attribute work
          to a NEW test: the false attribution that reports nothing.
DECISION  AN ID MAY BE PERSISTED ONLY IN FILES THE NAMING NAMES.
          'hwut.remove' deletes the run's record files in the SAME
          HOLDING in which it frees the id -- so freeing and deleting
          every persisted reference are one act, and reuse is safe.
          UNOFFICIAL vanishment frees nothing: the register entry
          STANDS (D-7, 'vanished()'), so the id is never reissued
          while stray records could still spell it.
          'hwut.rename' therefore touches NO record content, ever: the
          id inside the record is the identity, the id survives the
          rename, and the name lives in one place -- the register.
          THE RECORD FORMAT REVISION (header names a run id where it
          named test/choice; version bump; the register becomes the
          decode) is coverage work, designed with t-9, not here.
COST      A record without its directory's register decodes to a
          number. Accepted: the register is write-protected, refuses
          damage by name, and travels with GOOD/ -- the same trust the
          result base already carries.
GRAVEYARD Rewriting record headers in 'hwut.rename': a feature against
          a format about to remove its cause.
          Never-reuse and retirement: guards for ids persisted
          ANYWHERE; persisting them only where remove deletes them is
          the cheaper law.

R-73  THE SELECTION IS ONE BRICK -- 'exploration/selection.py'

PROBLEM   Six faces wrote the same four lines apiece: 'explore' or
          'explore_tree', a Bookkeeper where the wish asks the base, a
          'CTestTaskListQuery', and 'get_test_cases'. 'plan',
          'wishlist', 'accept', 'report', 'play' and the label faces
          each assembled them, differing only in whether they walk ONE
          DIRECTORY or A TREE.

          THAT IS NOT SIX FACES USING A COMPONENT. It is ONE ACTION
          IMPLEMENTED SIX TIMES, and the sixth copy is where they
          start to disagree -- 'labels/_faces' had already grown a
          SECOND pass building throwaway queries to re-derive the glob
          reach, because the first pass did not hand it back.

DECISION  Two doors and no more: 'of_directory' and 'of_tree'. Each
          explores, decides the Bookkeeper, builds the query, and
          answers a 'CSelection' -- the cases, the faults, the
          findings, and WHAT IT BUILT ON THE WAY: 'result_db',
          'bookkeeper_db', 'query_db', 'met_set'.

          IT HANDS BACK WHAT IT BUILT because faces need different
          parts of one act: 'hwut.report' reads the book behind the
          selection, 'hwut.plan' needs the QUERY itself ('determine'
          takes a task list, not cases), and a caller asking 'which
          globs met nothing' must not re-derive it -- deriving it
          needs the root and the queries this module built, and a
          caller that tried got it wrong.

          THE HAND-DOWN LAW IS UNCHANGED. The Bookkeeper is still made
          ABOVE the query; only the number of places that make it
          moved from six to one.

COST      A face that wants an unusual combination reaches into
          'CSelection' rather than assembling its own. 'base_f'
          overrides the wish's own answer for the one face that reads
          candidates whatever the wish asked ('hwut.accept').

VERIFIED  352 declared choices unmoved -- five faces refactored and
          not one behaviour changed. Sixteen imports fell out, which
          the static-analysis ratchet counted before I did.

          FACES KNOWING 'Bookkeeper': NINE BEFORE, FOUR AFTER, and the
          four are the ones whose subject IS the record -- 'rename'
          and 'remove' re-key and forget it, 'tell' packs it,
          'stability' reads what it names. The five that lost it knew
          the storage layer existed only because a selection needed
          one handed in.

R-74  THE WISH NAMES DIRECTORIES -- '--dir <glob>'

PROBLEM   The wish selected RUNS. A directory entered only as a filter
          on a run's path, so a vocabulary that could SUBTRACT a
          directory ('--exclude-dir') could not NAME one. That is a
          hole, and it was there before anybody wanted the feature.
          'hwut.execute' exposed it: its subject genuinely IS
          directories, so it parsed its own arguments and shared no
          selection with any other face (disc-9).

DECISION  'Wish.dir_tuple', '--dir <glob>', in the ONE wish parser.
          A UNION among its own globs, NARROWING against the rest of
          the wish -- the law '--label' already taught (disc-8), so
          nobody learns a second rule.
          'selection.directory_tuple' is THE OTHER VIEW of one
          selection: the directories a wish names, whether it named
          them or named runs that stand in them. A face asks for the
          view it needs, and the wish need not know which asked.

COST      Eleven GOODs moved, all of them the usage line: '--dir'
          joined 'USAGE_TOKEN_TUPLE' and nine faces show it.

VERIFIED  352 declared choices green. The matcher is '--exclude-dir's
          own, so a glob with '/' matches the path and a bare name
          matches any component -- one rule wherever a directory is
          named.
