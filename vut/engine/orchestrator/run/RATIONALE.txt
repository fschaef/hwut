============================================================================
VUT-ORCHESTRATOR-RUN -- RATIONALE
============================================================================
Settled. Read-only. O-N handles; plan P-N, scheduler S-N, exploration
R-N cited.

----------------------------------------------------------------------------
O-1  THE OUTER FACE
----------------------------------------------------------------------------
PROBLEM   One call that takes a wish and a root and yields a running,
          observable whole.
DECISION  Two functions. 'orchestrate(root, wish) -> CTreePlan':
          determination, synchronous -- explore the tree (R-69),
          determine per directory (P-17), Bookkeepers made here and
          handed down. 'orchestrator(root, wish, dispatcher_factory)
          -> asyncio.Queue': sets a CTreeScheduler running as an
          asyncio task; the queue carries the report stream and one
          'None' after 'tree-done' closes it. Determination happens
          BEFORE the first event: a refused wish raises at the call.
COST      A running event loop is required; a consumer that wants only
          the end must drain the queue (O-4 pays it back).
GRAVEYARD Returning a report object beside the queue (two carriers of
          one truth, drifting). A thread-backed queue (the house runs
          asyncio; a second concurrency model buys nothing here).

----------------------------------------------------------------------------
O-2  THE STREAM'S SHAPE
----------------------------------------------------------------------------
PROBLEM   TUI, web server and customer application must all read the
          run as it happens, without the scheduler knowing any of
          them.
DECISION  Flat JSON-able dicts, one per event; every event carries
          'format' (integer, starts at 1), 'kind' and 'when'. Kinds
          are PLAIN STRINGS -- no padding, no 64-bit forms; the format
          description notes kinds are ASCII, <= 9 bytes, unique, so a
          consumer MAY pad one into an integer. THE PROMISE: fields
          are only ever added, kinds never removed; unknown kinds and
          fields are ignored; 'format' rises only where the promise
          cannot hold. The table in vocabulary.py IS the format;
          'format_text()' prints it. The emitter asserts every event
          against the table: a wrong event is OUR defect, named at
          emission.
COST      A vocabulary to keep; growth is append-only by promise.
GRAVEYARD 8-byte padded kinds ('dir--beg': paid by every reader,
          earning only in a binary wire we do not speak). Nested
          objects mirroring CRunReport (heavier, and the add-only
          promise breaks at first growth). JSON encoding inside the
          scheduler (serialisation baked into the emitter).

----------------------------------------------------------------------------
O-3  EVERYTHING THAT LEADS TO EXECUTABILITY IS THE TEST
----------------------------------------------------------------------------
PROBLEM   A test that never ran because its build broke must be
          reported as the failed test it is, cause named.
DECISION  'run-ended' carries 'verdict' -- WHY: ok, test-failed,
          build-failed, launch-failed, unsupported, misdep, and the
          list is OPEN under the add-only promise (an unknown verdict
          reads not-ok; 'refused-cap' and 'pype-failed' join with the
          test_run dispatcher). 'cause' names the node whose breaking
          failed this one. A node that never dispatched still gets its
          'run-ended'; a 'run-ended' without 'run-begun' is legal and
          stated in the format.
COST      Two failure carriers per broken supporter: its own event and
          one per supported test -- by design, that IS the premise.
GRAVEYARD A bare good/bad bit (the WHY lost on the wire). Reporting
          only the supporter's failure (the test's own failure
          invisible to a consumer watching tests).

----------------------------------------------------------------------------
O-4  THE SUMMARY IS A FOLD
----------------------------------------------------------------------------
PROBLEM   A final run report is wanted; a second carrier would drift
          from the stream.
DECISION  'summary.fold(events) -> CRunSummary' -- a pure function
          over the stream, shipped beside it; 'drain(queue)' folds to
          the closing 'None'. The queue is the outer face's ONLY
          return; the scheduler's internal CRunReport stays internal.
COST      The whole is only as complete as the stream (which is the
          point).
GRAVEYARD CRunReport returned beside the queue (two truths).

----------------------------------------------------------------------------
O-5  THE RECEIVER
----------------------------------------------------------------------------
PROBLEM   A consumer wants handlers, not a parsing loop; the wire must
          stay ours to change.
DECISION  'CRunReportReceiver', CONCRETE: every 'on_<kind>' a no-op
          with NAMED parameters -- exactly the vocabulary's fields,
          optionals defaulting to 'None', newer fields dropped before
          the call, which is how named parameters survive growth.
          '**fields' on the catch-alls alone: 'on_any' (every event,
          raw, before its handler), 'on_unknown' (a kind the
          vocabulary does not carry), 'on_misfit' (a KNOWN kind whose
          structure does not fit: required field missing or badly
          typed, or no dict at all).
COST      Nothing forces a user to handle anything -- that is the
          point; and the receiver must be regenerated in step with the
          vocabulary (one table feeds both).
GRAVEYARD Abstract methods (every vocabulary growth breaks every
          user). '**fields' on specific handlers (the named surface
          was the stated want).

----------------------------------------------------------------------------
O-6  THE VERDICT WORD LAW
----------------------------------------------------------------------------
PROBLEM   The real dispatcher knows a finer WHY (E_TestRunResult) than
          the six verdict words; the wire had to carry it without
          growing every consumer's switch.
DECISION  'verdict' stays the COARSE six -- a consumer's switch never
          grows -- and 'run-ended' gains the OPTIONAL field 'report':
          the operation's own word, E_TestRunResult verbatim, absent
          where nothing finer is known. Add-only; the promise holds.
          One lift: a TEST whose report is 'test-app-launch-failed'
          carries verdict 'launch-failed' -- the launch is the WHAT,
          whichever node met it.
COST      Two words for one failure where the fine one exists -- by
          design: one for switching, one for reading.
GRAVEYARD Fine words ON the switch (every consumer must know an open
          list to act). Coarse only (the ledger would know what the
          wire withheld).

----------------------------------------------------------------------------
O-7  THE REAL DISPATCHER
----------------------------------------------------------------------------
PROBLEM   The seam (S-1) needed its one binding onto operations.
DECISION  'run/dispatcher.py': the ONE file that knows both sides.
          ONE LOCK, ONE STORE, ONE LIFETIME -- taken at construction
          (DirectoryBusy refused at the door), released at 'close()';
          the per-choice ceremony enters through 'run_test_held', the
          held door, never the standalone one. run_script -> a
          procsitter-supervised 'bash -c' in the directory; run_build
          -> build_action, the finer word kept; open_session -> the
          MultiExecute stands up, the application call LAZY (R-46);
          run_test -> the ceremony, with the session's own
          ChoiceExecute plugged as provision where one stands;
          close_session -> spend and shut down. 'adapter.py' maps
          exploration's CTestApp to operations' TestConfiguration;
          what it does not map is refused, not guessed. The factory
          takes (directory, entry): the entry's app_set names what
          exists; a double may ignore it. 'report_of' hands the wire
          the finer word.
COST      The two-mode ChoiceExecute (held vs one-shot) the dispatcher
          forced into the open; the adapter must grow with the
          exploration vocabulary.
GRAVEYARD Per-choice locks (the mutex is non-recursive; the standalone
          door fights itself). session.run_test per choice (same).
          Scheduler importing operations (the seam was the point).

----------------------------------------------------------------------------
O-8  THE STORE'S OWN GROUND
----------------------------------------------------------------------------
PROBLEM   Found by the end-to-end suite: candidates lived under 'OUT/'
          -- the TEST'S product space, whose every file execution
          reads as a subject -- so each run ingested the previous
          runs' candidates, sidecars of sidecars ('.when.when').
          Storing by default (n-1) surfaced it.
DECISION  The store's records live on THE STORE'S OWN GROUND:
          '<directory>/.hwut-store/' -- candidates, raws, cadences,
          freshness sidecars. 'OUT/' is the test's alone; 'GOOD/'
          stays the author's. The dot-name also keeps the tree walk
          out. Three worlds apart, applied to the disk.
COST      Two blessed suites re-worded to the new ground (audited:
          the rename alone).
GRAVEYARD Filtering store keys out of the subject scan (guessing at
          the door). Snapshot-diff of 'OUT/' (statefulness, races).

----------------------------------------------------------------------------
O-9  THE TRANSLATION: WHAT AN AUTHOR STATES, A COMPONENT RECEIVES
----------------------------------------------------------------------------
PROBLEM   The adapter carried the source kind, the caps, the build and
          the pype -- and DROPPED the rest. A test stating
          'numeric = 0.01' was compared byte-exact; a test stating
          'same' looked for a nominal per choice; a test stating
          'execute' was launched by a derived argv. Each produced a
          CONFIDENT WRONG VERDICT on correct code -- the worst failure
          a validator has, and invisible, because the test simply
          failed and the author saw a diff.
DECISION  Every member of 'TestParameters' reaches the component that
          OWNS it, or is refused BY NAME:
              tolerances (numeric, eq_pattern, nothing, analogy,
              constraints, comment, slash_eqv, whitespace_eqv)
                            -> compare's Configuration, per choice.
                               Nothing stated -> None: an unstated
                               tolerance is compare's own default, and
                               a Configuration built here would only
                               restate it.
              caps          -> procsitter's configuration; an unstated
                               cap keeps procsitter's default, never a
                               zero.
              same          -> the bookkeeper's NamingConfig: one
                               nominal for every choice. Candidates
                               keep their own names, or the choices
                               would overwrite one another.
              execute       -> the CALL itself (R-68): a stated argv
                               stands and the source kind decides
                               nothing.
          A marker pair that is not a pair, and a language no
          interpreter is declared for, are refused at the door.
          THE ORACLE IS A SWEEP: 'run/TEST/test-adapter.py' walks
          'dataclasses.fields(TestParameters)' and names any member
          that reaches nothing -- a parameter exploration gains later
          is swept the day it exists.
COST      The adapter must grow with exploration's vocabulary, and the
          sweep goes red the day it does not. That is the point.
GRAVEYARD Mapping the tolerances "when someone asks" (the byte-exact
          comparison was silent, and looked like the test's fault).
          A per-choice Bookkeeper for 'same' (the naming is the
          APPLICATION's word; the lock is the directory's).

----------------------------------------------------------------------------
O-10 A CONFIGURATION LIVES IN 'configuration.py'
----------------------------------------------------------------------------
PROBLEM   'ProcsitterConfig' lived in 'procsitter.py', 'StoreConfig' in
          'stream_store.py' -- a reader looking for what a component
          can be told had to know which module to open.
DECISION  Every component subject to configuration holds its
          configuration class in 'configuration.py' in its own core
          directory, every member documented there: compare (already),
          operations (already), procsitter (moved), bookkeeper (moved,
          and gained 'NamingConfig'). Each old home RE-EXPORTS its
          class, so existing imports keep standing.
          'specification.py' in exploration is NOT renamed: a
          SPECIFICATION is what an author STATED, before resolution --
          a different animal from a configuration a component consumes.
COST      One import hop for readers of the old modules.
GRAVEYARD One central 'configuration.py' for the tree (a component's
          contract belongs with the component).

----------------------------------------------------------------------------
O-11 DIRECTORIES RUN IN PARALLEL; A DIRECTORY IS A CLOSED ENVIRONMENT
----------------------------------------------------------------------------
PROBLEM   The tree scheduler ran the directories one after another and
          parallelised within one; a tree of many small directories was
          bounded by the slowest chain, not by the host.
DECISION  Every test directory is a CLOSED ENVIRONMENT: no dependency
          stands between two directories, 'on_entry'/'on_exit' stay
          local to their directory (R-69), and the configuration tree
          shapes WHAT a directory runs, never WHEN. The pool is FLAT:
          all directories are started at once under the budget of
          O-12; the ORDER of events across directories is not promised.
          WHEN a directory starts is the STRATEGY's word (O-15). The
          closing blocks keep walk order
          ('tree-begun' carries it); the flow tier is a live surface.
COST      A consumer of the stream may see 'dir-begun' of B before
          'dir-done' of A. The receiver and 'fold()' already keyed by
          (directory, node) and are order-independent.
GRAVEYARD A DAG of directories ordered by frame keys lifted to the tree
          level (lifts R-69; no need demonstrated; stage 2's placement
          does not want it). Parallel as opt-in (the serial run stays
          reachable by one flag; the default is the host's speed).

----------------------------------------------------------------------------
O-12 '--jobs' IS ONE HOST-GLOBAL BUDGET; EVERY DISPATCH TAKES A SLOT
----------------------------------------------------------------------------
PROBLEM   With directories in flight at once, a per-directory bound
          multiplies: 'jobs' times directories standing; a second knob
          for the directory count would have become unavoidable.
DECISION  '--jobs=<n>' is ONE budget of work standing at once on this
          host, across every directory; absent is no bound; '--jobs=1'
          under '--dbd' is the serial run byte for byte. The budget is
          'CBudget' (scheduler/budget.py), made in the tree scheduler
          and handed to every directory's Scheduler in place of the
          bare number -- one mechanism, one meaning; a Scheduler given
          a number still makes a private budget. EVERY dispatched thing
          takes a slot: frame scripts, builds, session launches, tests.
          The word HOST is deliberate: when runs are hosted on several
          machines (stage 2) the budget may re-emerge per host.
COST      No directory is guaranteed a share: a scheduler returning a
          slot may take it back before another's waiter runs, so a
          large directory can run ahead of a small one. Fairness is
          not promised; throughput is bounded, correctly.
GRAVEYARD A per-directory bound (squares the load). Frames running
          free of the budget (a budget of one would then overlap a
          frame with a test somewhere on the host: dishonest).
          Gating inside the work task with a semaphore (the 'started'
          notification would then precede the 'ended' of the slot's
          previous holder, moving every bounded-run GOOD).

----------------------------------------------------------------------------
O-13 THE UNIT OF PLACEABLE WORK IS THE DIRECTORY
----------------------------------------------------------------------------
PROBLEM   Stage 2 places directory runs on other hosts; the seam had
          to exist before it is plugged, and it had to be narrow.
DECISION  'CDirectoryWork(root, entry, dispatcher_factory).run(emit,
          budget) -> CDirDone' is the unit. The dispatcher -- and with
          it bookkeeper, store and the directory lock -- is constructed
          INSIDE the unit, on its own lifetime; the lock is taken where
          the directory is. Nothing crosses the edge but 'emit' and the
          budget; no display, no bookkeeper. A placement backend
          answers a different 'run' for the same unit and streams the
          same events back (DISCUSSIONS/todo-2).
COST      The tree scheduler no longer sees the dispatcher; what it
          knows of a directory is its CDirDone and its events.
GRAVEYARD A unit per node (the lock and the bookkeeper are the
          directory's; a node cannot travel without them).

----------------------------------------------------------------------------
O-14 PARALLEL-RUN SUITES BLESS THE FLOW THROUGH A PYPE FILTER
----------------------------------------------------------------------------
PROBLEM   Interleaved flow lines are nondeterministic; a golden-master
          framework cannot bless nondeterminism, and a flow tier that
          is never blessed has no oracle for its per-scope attribution.
DECISION  A parallel-run choice pipes 'hwut.run' through a '.pype'
          script beside the test application (same file stem, '--
          <choice>' appended where two choices need different
          digests). The filter records the flow lines per directory
          nickname and prints them SORTED, the parallel column dropped;
          the closing blocks pass through verbatim; a machine path in a
          fault's text is masked there. THAT digest is the GOOD. The
          renderer buffers and sorts nothing. '--dbd --jobs=1' is
          blessed RAW. The suite's exit status is PIPESTATUS[0].
COST      A '.pype' file per parallel suite; the dump tool must carry
          the '.pype' extension.
GRAVEYARD Blessing the quiet tier alone (the flow's attribution would
          have stood without an oracle). Sorting flow lines in the
          renderer until 'dir-done' (a live surface turned batch).

----------------------------------------------------------------------------
O-15 THE STRATEGY SAYS WHEN A DIRECTORY STARTS; THE DIGEST IS STRATEGY-FREE
----------------------------------------------------------------------------
PROBLEM   Serial and parallel were two code paths behind a flag. The
          question "what runs next -- and later, where" is a workflow
          question and wants one seat with a contract, filled by
          strategies, the first ones simple enough to test the contract.
DECISION  'run/strategy.py': 'CStrategy.run(guarded_list) -> [CDirDone]'
          is the TEMPLATE -- walk order, start a unit when the hook
          'may_start(index, running)' says so, re-ask on every ending.
          Three strategies, one line each: 'linear' (the run of old,
          THE DEFAULT), 'successor' (the next directory starts while
          the current runs), 'parallel' (all at once). 'hwut.run
          --strategy=<name>'; '--dbd' is 'linear'. The strategy decides
          WHEN only: the budget (O-12) bounds, the unit (O-13) owns.
          HOMOGENEITY: a tree suite's GOOD is the pype digest (O-14)
          recorded under LINEAR; it records WHAT ran, never when; every
          other strategy must reproduce it byte for byte, and the suite
          displays that it does. One GOOD serves all strategies, present
          and to come.
COST      The strategy sees directories, not nodes across directories;
          a node-level strategy (dependencies, standing artifacts, the
          host) is the contract's next step and a ruling of its own.
GRAVEYARD Strategy at the budget (decides whom to wake, not when to
          start -- the wrong seat). One global node scheduler now (too
          much at once; the unit of O-13 would have moved before its
          first two strategies taught anything).

O-16 'E_TestRunResult' STAYS WHERE IT IS -- SHARED IS NOT CROSS-CUTTING

PROBLEM   'adm/import_graph.py --shared' names 'E_TestRunResult' among
          the tree's most-imported names: thirteen modules read it,
          and the lowest common ancestor of those readers is 'engine'.
          Read as a rule, that says the enum belongs in an
          engine-level contract, and 'engine/operations' is where it
          lives.

DECISION  IT STAYS. TWELVE OF THE THIRTEEN READERS ARE 'operations'
          ITSELF; exactly one reaches in from outside -- this
          component's 'dispatcher.py'. That is not a shared
          vocabulary. It is a component's own enum with one external
          reader, and moving it would relocate a name away from the
          twelve modules that live with it in order to serve one.

          THE LESSON, and it corrects how the measurement reads: A
          COUNT OF READERS IS NOT A CLAIM. What matters is whether the
          readers are SPREAD. 'E_ToleranceId' was read by five
          sub-components of 'compare' with no majority anywhere;
          'E_TestRunResult' is read by one component and a visitor.
          The tool answers 'who reads this'; whether they are one
          family is a person's answer.

COST      The lowest-common-ancestor report will keep naming it. That
          is the report doing its job, and this entry is the reason it
          may be passed over.

O-17 THE PROTOCOL LEAVES THE PRODUCER -- 'engine/protocol'

PROBLEM   'engine/display -> engine/orchestrator' was the ONE SIDEWAYS
          ARROW in this tree: every other component pointed downward.
          It existed for two imports -- 'CRunReportReceiver', the
          class a consumer derives from, and 'fold', the pure fold
          over the report stream. Both were written to be consumed
          from OUTSIDE, and their own purposes say so: "any consumer
          may use it: our exit-status logic, a TUI, a customer
          application". Held here, they made a consumer reach into a
          producer for the shape the two agree on, and a TUI or an
          HTML renderer had to drag the orchestrator along to get
          three leaf modules.

DECISION  'engine/protocol' holds 'vocabulary.py', 'receiver.py' and
          'summary.py' -- the kinds of event, the class a consumer
          derives from, and the fold. SEALED: it imports nothing of
          this tree, and the seal is checked (C-2).

          MEASURED, NOT GUESSED. The lowest common ancestor of
          'fold's readers -- 'engine/display', 'services/run',
          'services/stability' -- is THE TREE ROOT; 'receiver's is
          'engine'. The level was read off the readers, not chosen.

          WHAT STAYED: the QUEUE, the scheduler, the dispatcher, and
          every caller of the fold. A protocol is the SHAPE two
          parties agree on; the transport and the machinery stay
          where they run.

COST      Eight modules re-pointed. 'orchestrate.py' now reaches
          three levels up for 'event', which is what it costs to have
          the vocabulary above both parties instead of inside one.

VERIFIED  'engine/display -> engine/orchestrator' is GONE; display
          points down, as everything else does. 224 declared choices
          unmoved. The static-analysis total fell from 284 to 283 --
          the two '__all__' lists, this one and the contract's, are
          sorted now.

O-18 A FAILING CANONICALISER ENDS PROVISION -- IT DOES NOT DELIVER

PROBLEM   'StageCanonicalise' reported a failing pype and DELIVERED
          THE RAW TEXT ANYWAY: "a failing canonicaliser leaves its
          text unchanged and says so; the subject is delivered either
          way". The comparison then ran on a stream the filter never
          touched.

          A CANONICALISER EXISTS BECAUSE THE RAW STREAM IS NOT
          COMPARABLE -- a timestamp, a pid, an address that differs
          every run. Delivering the raw text does not deliver 'almost
          the subject'; it delivers a stream NOBODY EVER MEANT TO
          COMPARE. And where the nominal happens to have been blessed
          from an equally unfiltered run, THE TEST PASSES FOR THE
          WRONG REASON and nothing says so.

          FOUND BY ACCIDENT: a fixture pype written without a shebang
          ran as a shell script, failed, and the comparison proceeded.

DECISION  'product' is None where any canonicaliser fails, so
          provision ENDS with that stage's token -- the one rule this
          shape already had: "a stage whose product is None ends
          provision, and the stages beyond never run".

          THE PYPE IS PART OF THE TEST APPLICATION and may contain
          errors (display/DISCUSSIONS/todo-2). A missing shebang, a
          syntax error, a mode with no '<else>' handler, a file that
          is not there: each is a DEFECT IN THE TEST, and a defect in
          a test is a RESULT -- stated, not swallowed.

COST      A test whose pype is broken now FAILS rather than comparing
          something. That is the point, and it will surface pypes that
          have been silently not running.

VERIFIED  A pype without a shebang: 'pype interpreter missing [FAIL]'.
          A pype whose language is wrong: 'pype failed [FAIL]'. The
          same pype, corrected: '[OK]'.
