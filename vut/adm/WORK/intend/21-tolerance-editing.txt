2  THE RULINGS, VERBATIM, WITH WHAT FOLLOWS FROM EACH

    2.1  "we maintain the configuration in memory and the ETPM works on
         that memory."

         The session holds a WORKING tolerance beside the working
         nominal. The pane renders it as text; leaving the pane parses
         the text back into it. A round (port.py) now carries BOTH: a
         REALIGN is progress when the nominal OR the tolerance changed.
         Nothing reaches a file until the leaving question (2.6).

    2.2  "what about the <F5> for entering and exiting the ETPM?"
         "<F5> closes, remember that you have changed tolerances in
         memory, and realigns shows subject vs. nominal."
         "TRY means simply re-run the compare on subject and nominal
         under changed tolerance parameters."

         F5 opens ETPM from the panes and from the 't' report; F5 in
         ETPM closes it. TRY and CLOSE are ONE act: parse, remember,
         realign. A text that does not parse keeps the pane open with
         the fault in the status bar -- there is nothing to realign
         under. An unchanged text closes without a round.
         The realigned screen marks nothing specially: it is what any
         round shows (GOOD's count, 'w'/'b' intervals, the 't' report
         of the patterns that matched).
         Not in the viewing table ('hwut.run.diff'): a view has no round.

    2.3  "drop <c-c>; no undo all."

         Inside ETPM 'c-c' is bound to nothing.

    2.4  "we need the keystrokes of undo and redo as applied in the main
         mode also. then the main mode undo is not affected by the
         tolerance configuration. each undo stack is separate."
         "add <c-z> and <c-y> as undo and redo alternative keys in both
         modes."

         Main mode: 'u', 'c-z' undo; 'r', 'c-y' redo.
         In an EDITING pane (2.5, 2.6) letters type, so 'c-z'/'c-y' are
         the pane's undo/redo, on the pane's own stack (the text
         buffer's). A tolerance change enters no stack of the main mode.

    2.5  "In normal mode: <e> shall open the nano-like editor mode on
         GOOD. we type normally. <F5> terminates editing and re-runs the
         line association. <c-e> opens $EDITOR and allows to edit the
         file in the given editor. Re-run of line association upon
         exit."

         'e' no longer means $EDITOR; 'c-e' does. While GOOD is edited
         the keymap yields to the buffer as it yields to the search
         line; F5 hands the text to the hub as a REALIGN. An unchanged
         text, or an editor that changed nothing or failed, goes BACK
         TO THE SCREEN -- it does not end the session (defect 5.2).
         The line-based fallback keeps 'e' = $EDITOR: it has no screen
         to edit on.

    2.6  "In ETPM mode [...] default-wise we are in nano-like editing
         mode and leave as said with <F5>. <c-e> opens $EDITOR and
         allows to edit. exit re-runs line association and loads/stores
         config. editing happens on a temporary file."

         The pane opens editable. 'c-e' writes the pane's text to a
         temporary file, runs the editor on it, deletes it, and treats
         the result as F5 treats the pane's text.

    2.7  "upon exit, if changed tolerances are present, ask (1) store
         them in TMP/<source>--<choice>.tolerance.conf (2) try to enter
         it in <source> where the other config is located. (3) omit it."
         "yes ask write or cancel changes upon cancellation."

         On commit ('q'): (1), (2) or (3).
         On cancel ('c-c' in the main mode): (1) or (3); (2) edits the
         page, which a cancelled session does not do.
         (2) TRIES: it writes 'tolerance { }' into the '@hwut { }'
         header, replacing the header's own 'tolerance' where one
         stands, and reads the file back through the exploration's own
         reader. It REFUSES by name, writing (1) instead so the work is
         not lost, where the file has no header (an 'apps' entry), where
         the choice states its own 'tolerance' (the header's would not
         reach it), or where the file read back does not parse (the
         original is restored).
         A commit under a changed tolerance with (3) chosen prints one
         NOTE: the next run judges under the page's own tolerance.

    2.8  "we need a tolerance pattern generator based on the found
         discrepancies. discrepancies in, proposal out. this does not
         have to be perfect, just some idea, that the user might pick
         up."  (Q5, the worked example, answered: "you understood
         properly. yes.")

         THE GENERATOR (slice 1, section 4): the pairs the screen holds
         in, commented 'tolerance' lines out, appended to the pane.

4  THE PROPOSAL GENERATOR

    IN   the delivered line pairs (report.Pair: line numbers, both cell
         lists); the tolerance in force.
    OUT  lines of text, every one a comment, appended to the pane:

         # PROPOSALS -- uncomment what you want, then <F5>
         # numeric_ratio = 0.047       # OUTPUT 2: 12.51 vs 12.00, 4.3% + 10%
         # eq_pattern = ["id=[0-9abz]{3,4};"]
         #     OUTPUT 2: 'id=ab12;' vs 'id=zz7;'

    NUMERIC   every NUMERIC cell pair compare calls different gives
              |s - n| / |n|; the largest, * 1.1, rounded up, is
              proposed where it is below 1 and above the ratio in force.
    WORDS     each differing line pair is split into words; the words a
              line-level diff substitutes are paired. A pair both of
              whose words are numbers the NUMERIC rule covers is left to
              it. Otherwise the shared prefix and suffix stay LITERAL
              (escaped) and the middle becomes:
                a CLASS where both middles are one -- float, integer,
                hex, date, time, path; identifier only where no context
                is shared;
                else BUILT: digits as 0-9, every other character seen
                literal, lengths as seen: '[0-9abz]{3,4}'.
              One 'eq_pattern' line holds the patterns in force plus
              every new one, so uncommenting it keeps what stood.
    BLANKS    a line pair equal but for blanks, under 'whitespace =
              false', proposes 'whitespace = true'.
    NOTHING   a word present on one side only proposes it for 'nothing'.
    CHECKED   a pattern is shown only if it matches both words whole.
    Imperfect by design: a proposal is an idea, applied only when the
    author uncomments it.

     So 'u' cannot take back an edit that F5 has realigned. Carrying the

     replaced; not built, not presumed.
