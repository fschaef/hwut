A FEATURE is one thing a piece of software does, stated by its author in a
sentence. A feature is PROVEN where at least one test run is linked to it
and every linked test run passes. A feature with no linked test run is
UNPROVEN, and an unproven feature counts as not implemented.

A COMPONENT is a directory that is not a TEST directory.

    <component>/hwut-composition.conf     what the component does; its id,
                                          its parent's, its childs'
    <component>/TEST/hwut-features.conf   the features proven in this TEST
                                          directory; its id, its parent's
    a test's '@hwut { }' block            the features this test proves


1  THE FEATURE FILE
______________________________________________________________________________

    features {
        id     = "core-proof"
        parent { core = "What 'core' promises, proven." }
        issued = 2
        1 { name        = "line-pairing"
            title       = "Two streams are aligned line by line."
            explanation = "..." }
        2 { name        = "missing-side"
            title       = "A line present on one side only is shown whole." }
    }

    id            the file's own id (section 4).
    parent        the id of the composition file of the directory above,
                  and how these features serve it (section 4).
    issued        the highest feature number this file ever issued.
    <number>      a feature; the number is its ID inside this file, issued
                  once and never again: the next feature receives
                  'issued + 1'. A feature removed leaves its number unused.
    name          what a test writes to link to the feature. Unique in this
                  file. A name may change; the number stays.
    title         one sentence: what the software does.
    explanation   free text.
    documents     where more is said: a list of paths from this file's
                  directory ('#<anchor>' may follow), or URLs --
                  documents = ["../README.txt#3"]. Printed as 'see' under
                  the feature; links in the feature document.

A feature number means something inside its own file only. Across the tree
a feature is addressed as '<path>#<number> <name>', composed by whoever
reports, at the moment it reports, and stored nowhere (as coverage D-14
rules for test run ids).

An object under a key that is neither a number nor 'parent' is a feature
WITHOUT a number. A number standing twice is refused by the parser; the
first stands.


2  THE LINK
______________________________________________________________________________

    # @hwut {
    #     title    = "Pairing"
    #     features = ["line-pairing"]
    #     choices { gap { features = ["line-pairing", "missing-side"] } }
    # }

'features' is a test parameter like every other: at the root for the whole
test, in a choice for that choice (the choice's list REPLACES the root's,
'[]' links nothing), in 'app_defaults'. A name is looked up in the feature
file of the test's own TEST directory and nowhere else. The link exists in
the test's block only.


3  THE COMPOSITION FILE
______________________________________________________________________________

    component {
        id     = "cmp"
        title  = "Compare"
        does   = "Decides whether an output is equivalent to its nominal."
        parent { eng = "The engine's verdict rests on it." }
        childs {
            core      = "Aligns two streams line by line."
            cmp-proof = "Proves the whole comparison on real pages."
        }
    }

    id            the file's own id (section 4).
    title, does   what the component is and does.
    parent        the id of the composition file of the directory above,
                  and how this component serves it.
    childs        the ids of the statement files directly below -- the
                  components and the TEST directory's feature file -- and
                  what each contributes.


4  IDS, 'parent' AND 'childs'
______________________________________________________________________________

Each statement file gives ITSELF an 'id': a freely chosen string ("cmp"),
unique among the childs of its parent. The files relate to each other by
these ids and by nothing else. No path and no directory name is written.

    parent { <id> = "<how this serves it>" }      or    parent = "<id>"
    childs { <id> = "<what it contributes>" ... } or    childs = ["<id>", ...]

Every relation is stated twice -- the child names its parent, the parent
lists its child -- and the DIRECTORIES state it a third time by where they
stand. The directories are the fact; the two statements are held against
them. The top of a tree (where 'hwut-root.conf' stands) states no parent.


5  THE REPORT
______________________________________________________________________________

'hwut.report.features [--directory=<path>]' walks the tree below the
directory it is called in and prints component -> part -> feature -> test
runs and their verdicts, each component with its id and its counts.

    state of a feature
        PROVEN     one linked test run or more; all of them pass
        FAILING    one linked test run or more; one of them does not pass,
                   or has no verdict in 'GOOD/book.csv'
        UNPROVEN   no linked test run

    'serves'      the directory's own 'parent' sentence
    'as child'    what the 'childs' of the directory above says of its id

OUTSIDE THE RELATION, named below the tree: a test run naming a feature its
TEST directory does not define; 'NONSENSE?' -- a test run linking to no
feature, where the directory states features; a component without a
composition file; a statement that is not read; and every disagreement of
section 6.

'NONSENSE?' IS NO FAILURE (services E-145): the run's verdict stands,
'hwut.run' says nothing of it, 'hwut.help' explains the word. FEATURE FILES
ARE NOT MANDATORY: a TEST directory without one is named nowhere.

FEATURE FILES ALONE ARE COMPLETE (services E-144, ruled): components
without a composition file, and the disagreements of section 6, are named
only where the tree relates by id -- a composition file stands in it or
directly above it, or a feature file states 'id' or 'parent'.

'--matrix' prints, in place of the tree, one table per TEST directory that
carries a feature file:

    engine/compare/core/TEST  #1    #2    #3
    test-pair.sh [plain]      PASS  .     .
    test-pair.sh [gap]        FAIL  FAIL  .
    test-pair.sh [odd]        .     .     .     <- NONSENSE?
    test-stray.sh             .     .     .     <- no feature defined
                                          ^     no test run
      #1 line-pairing  FAILING
      #2 missing-side  FAILING
      #3 untested      UNPROVEN

    ('<- NONSENSE?' behind a run that links to no feature)

    row      a test run; column: a feature; cell: the run's verdict where
             it links
    A link never leaves its TEST directory: the tables are the relation.

'--code' adds under each feature that has a linked run where those runs
went in the code, read from a coverage output ('--cov-dir=<dir>'; else the
nearest 'hwut.coverage/' from the directory upward):

    code only    <source>: <lines>    executed by this feature's runs and
                                      by no other measured run
    code shared  <n> line(s) in <m> file(s)
    code         <n> of <m> linked run(s) not measured

    A hint where to look. What is 'only' depends on what else the coverage
    run measured. Sources standing in a TEST directory are left out.
    No coverage output: a NOTE, and the page without code.

'--html=<file>' and '--ods=<file>' write THE FEATURE DOCUMENT (services
E-146) in place of the page -- one self-contained HTML page, or an
OpenDocument spreadsheet -- with four tabs:

    Matrix     feature id, brief (title), state, implemented by (the linked
               test runs and their verdicts)
    Tree       component -> components below -> TEST directory -> features,
               each component with title and counts
    Features   feature id, name, title, explanation, component, state
    Tests      test file, title, 'doc', test runs and verdicts, features

    feature id in 'Matrix'  ->  its row in 'Features'
    test run in 'Matrix'    ->  its test's row in 'Tests'
    feature in 'Tree'       ->  its row in 'Features'

    THE TREE IS INTERACTIVE (E-148): the page unfolds and folds all
    levels, shows the features of chosen states and those whose line holds
    a word; the spreadsheet carries the levels as row groups.
    A feature's 'documents' stand in 'Features' as links.

    With '--code' or '--cov-dir' the 'Features' tab carries the code only a
    feature's runs reached. With '--cov-html=<dir>' -- where
    'hwut.cov.conv.to_html' wrote its pages -- each source is a RELATIVE
    link '<dir>/<source>.html#L<line>'.

'doc' is a key of the test's block beside 'title' (exploration R-90): what
the test is about, written in triple quotes over as many lines as it takes.


6  THE JUDGEMENT, AND WHAT SANITIZATION PROPOSES
______________________________________________________________________________

'feature_relation.mismatch_list' holds 'parent' and 'childs' against the
directories, for every directory that carries a statement file:

    kind       what disagrees                             healed by
    ---------------------------------------------------------------------
    no-id      the file gives itself no 'id'              relate <dir>
    moved      it stands below one parent; its 'parent',  relate <dir>
               or the 'childs' above, say otherwise --
               and ANOTHER component still lists its id
               while nothing below that one carries it
    parent     'parent' is not the id of the directory    relate <dir>
               above
    unlisted   the directory above does not list the id   relate <dir>
    gone       'childs' lists an id nothing directly      unrelate <dir> <id>
               below carries, and no moved directory
               took with it
    twin       two childs of one parent carry one id      said; the author
                                                          renames one
    unjudged   the directory above gives itself no id     said; its own
                                                          'relate' comes first

'hwut.sanitize.propose --relations' (one of the aspects a bare call asks)
writes one 'relate' per directory -- noted 'moved from <dir>' where the move
was detected -- and one 'unrelate' per dead entry, parents before childs.
'hwut.sanitize.apply' and 'hwut.sanitize relate|unrelate' judge again and
act.

'hwut.run' is not affected by any of it: a test runs and is judged whether
or not its links resolve.


7  THE ONE ADAPTION
______________________________________________________________________________

'engine/orchestrator/exploration/feature_adapt.py' is the one
implementation behind 'relate', 'unrelate', 'hwut.move', 'hwut.rename' and
'hwut.remove'. Text is MOVED, never composed; every edit is text surgery
('amend.py'), so what is not adapted stays byte for byte.

    relate <dir>          1  no 'id': the ONE id the 'childs' above lists
                             that nothing carries, where this is its only
                             child without an id; the directory's name else
                          2  'parent' rewritten to the id above; its
                             sentence stays
                          3  the id entered in the 'childs' above -- CARRIED
                             there with its sentence from the component
                             that still lists it (a detected move), with an
                             empty sentence else
    unrelate <dir> <id>   the entry removed
    hwut.move, across     each feature the test links to that the source's
    TEST directories      feature file defines and the target's does not is
                          written into the target's under the target's next
                          number, and taken out of the source's unless a
                          test that stays still links to it. Defined alike
                          in both: taken out of the source with its last
                          link. Defined differently: both stand, and said.
                          No feature file in the target: it is WRITTEN
                          (R-91).
    hwut.rename, within   nothing to adapt: the link is the block's, and
    a directory           the block is the author's (services E-48)
    hwut.remove           the features left without a linked run are named
    a directory moved     nothing global breaks: below it every id still
    or renamed BY HAND    resolves; what no longer agrees is 'moved', and
                          'relate' carries the entry
    sanitize 'move'       an orphan's records carried after its application
                          go through 'hwut.move' (E-131) and so through the
                          same adaption
