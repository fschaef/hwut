disc-2  THE TARGET SERVICE 'hwut.target'                          ** OPEN **
______________________________________________________________________________

RULED (chat, 2026-08-24):

 1  'hwut.conf' binds USER-DEFINED TARGETS in a SEPARATE dictionary --
    a 'target { }' scope of the directory's own keys:

        hwut {
            target {
                clean = "./clean.sh"
            }
        }

    'on_entry'/'on_exit' are STANDARD targets with fixed semantics and
    their own top-level keys; the separate dictionary exists so the
    open-ended namespace can never collide with them. The validator
    refuses standard names inside 'target { }' by name.

 2  THE FACE:  hwut.target <option-list> <target> <passed-through>
    Everything before the target name is the service's vocabulary;
    everything after it goes to each directory's script, argv-style,
    untouched. One target per invocation.

 3  TWO PHASES. Phase one explores EVERY directory below the root and
    settles the plan; phase two executes. A failure in phase one costs
    ZERO executions -- nothing has run when exploration refuses.

 4  ABSENCE IS A FAILURE BY DEFAULT: a walked test directory that does
    not bind the target fails the run in phase one. Softening options:
        -i, --ignore-absence     skip directories lacking the target
        --default <script-name>  run that script where the target is
                                 absent

OPEN (each a fork, one at a time, before any build):

 a  Inheritance: is 'target { }' LOCAL like the frames (R-69), or may
    a parent bind 'clean' for a subtree? Locality is the standing law;
    inheritance is genuinely useful for 'clean'; this is the hardest
    fork of the cluster.
 b  Walk membership: is a directory with a 'hwut.conf' carrying only
    'target { }' and no test applications walked at all? Today the
    explorer would not call it a test directory.
 c  Machinery: through CDirectoryWork/strategy/budget/lock (a target
    run then never collides with a test run on the same directory), or
    deliberately simpler because it is not a test run?
 d  Exit law and output shape: OK / FAULT on any script failure; wire
    events like a run, or a flatter report?
 e  Script working directory, environment, and what a script's exit
    code means per directory.
