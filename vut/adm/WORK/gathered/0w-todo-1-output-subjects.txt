todo-1  THE 'output' PARAMETER -- SUBJECTS ARE THE TEST'S DESIGN
        decided, unbuilt

DECIDED
    A test states what it produces. New header parameter 'output':

        absent          the subject is '<stdout>', and only that
        a list          the subjects, in order. '<stdout>' is a
                        SPECIAL name marking the standard output
                        channel; every other entry is a FILE NAME,
                        read AFTER the run has ended.

    Example:

        hwut {
            output = ["<stdout>", "result.csv", "diagnostics.log"]
        }

    '<stderr>' IS NOT A VALID ENTRY and is refused by name, with the
    reason (see THE THREE LAWS below).

    WHY CONFIGURATION AND NOT A COMMAND-LINE OPTION: what a test
    produces is its DESIGN, authored once, not something restated at
    every acceptance. The three worlds hold -- configuration says what
    the subjects ARE; the store holds what they WERE; acceptance
    decides which recording is the pole.

    ===================================================================
    THE THREE LAWS -- state these in every manual that touches subjects
    ===================================================================

    (1) STDERR IS NEVER SUBJECT TO TESTING.
        stderr is for ERROR REPORTING, and that is its whole job. It
        is never a nominal, never compared. Where error reporting is
        itself under test, the application FLUSHES IT TO A FILE and
        names that file in 'output'.

        A stream that both carries diagnostics and is held to a
        blessed text can do neither job: every diagnostic an author
        adds while debugging would fail the test, so the author learns
        to stay silent, and the framework has taught them to remove
        the reporting it wanted.

    (2) A FILE IS READ ONLY AFTER THE TEST HAS TERMINATED.
        Therefore file content is NOT subject to race conditions --
        there is no interleaving to observe, no flush to time, no
        FIFO-sink question. This is why a file, and not a stream, is
        the answer to (1).

    (3) PYPE-ING IS ONLY EVER APPLIED TO STDOUT.
        Not to stderr (never read), not to files (not a stream; read
        whole, after the end). 'canonicalisers' is a dict keyed by
        subject and the bookkeeper iterates it generically, but
        'stdout' is the ONLY key that will ever stand in it. The
        generality is harmless; the law is what governs.

    WHAT ACCEPT STILL DECIDES -- one thing, and only for stderr:

        (B) stderr silent          -> FORBIDDEN, silently, the default
        (A) stderr speaks          -> REFUSE. No default: a default
                                      here leaves a user clueless in
                                      front of output that deviates.
                                      Request '--stderr-tol[erated]',
                                      which notes IGNORED.

        There is no second remedy. 'stderr becomes nominal' is dropped.

                    file is explored as a candidate test application
                    by the next walk (seen: the explorer interviewing
                    a CSV), and a STALE file from run N greens run
                    N+1 even where the application stopped producing
                    it -- a false green. The store's record is the
                    product; the file was only the carrier (the sink
                    law of multi_execute._read_sinks). The former
                    'OUT/' DISCOVERY sweep is RETIRED: discovery can
                    never tell 'produced' from 'forgot', so the
                    verdict 'output-file-not-found' could never fire.
    accept          a file subject is promoted like stdout; proven:
                    declare -> run -> bless -> green -> forget the
                    file -> 'output file missing', exit 1.

                    cycle, forgotten -- blessed.
